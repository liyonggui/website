我的做法是三步：**先立一个可证伪的假设 → 去源码里找到定义和调用链 → 写代码把它跑出来验证**。只看不跑，读完记住的还是别人的结论；带着问题读，一个 `object.c` 能顶十篇解读文章。

《Redis 设计与实现》那本书我也读过，但读完做的是另一件事：**把书里那些"embstr 一次 malloc 所以更快"的结论，逐个写压测验证一遍**。大部分成立，有一个反直觉的发现，是书里和所有源码解读文章都不会告诉你的。下面用这个真实案例讲方法。

## 第一步：把"我想学 Redis 源码"换成一个能被证伪的假设

绝大多数人读源码卡在第一步——目标太泛。"读懂 Redis"不是目标，是愿望。真正的目标长这样：

> 假设 A：embstr 只做 1 次 malloc、raw 做 2 次，所以 embstr 的 SET 应该更快。
>
> 假设 B：embstr 是只读编码，那反复 APPEND 应该会明显劣化。

区别在于：**A 和 B 都能被一次实验推翻**。能被推翻的假设才叫问题，不能被推翻的问题读不出结果。带着 A 去翻代码，你会自然翻到 `object.c`；带着 B 去翻，你会撞见 `t_string.c` 里那个关键的转换函数——这两条路径，比你从 `main.c` 往下通读高效一个数量级。

## 第二步：只找三样东西——定义、入口、调用链

不要试图"读完一个文件"。每个假设只需要定位三类代码：

**① 常量定义在哪。** 比如 embstr 那个被背烂的 44 字节：

```c
/* object.c */
#define OBJ_ENCODING_EMBSTR_SIZE_LIMIT 44
```

顺手就明白 44 不是魔法数——它是 `RedisObject + sdshdr8 + 对齐` 之后，还能塞进同一个分配块的余量。所以**换平台、换版本，这个数会变**。这就是"读源码"相对"背八股"的第一个收益：你知道哪些数字是可以不信任的。

**② 命令入口在哪。** `APPEND` 对应 `t_string.c` 里的 `appendCommand`，它在改 value 之前会先调 `dbUnshareStringValue()`，而那个函数里有这么一行判断：

```c
if (o->refcount != 1 || o->encoding == OBJ_ENCODING_EMBSTR) {
    robj *decoded = getDecodedObject(o);
    o = createRawStringObject(decoded->ptr, sdslen(decoded->ptr));  /* 强制转 raw */
    ...
}
```

**embstr 是只读编码，只要想修改它，就必须整体复制成 raw。** 这一行代码，就是"为什么不能对短字符串反复 APPEND"的全部答案——比任何一篇解读文章讲得都清楚。

**③ 分配与扩容逻辑在哪。** `sds.c` 里的 `sdsMakeRoomFor`：1MB 以内近似翻倍扩容，超过 `SDS_MAX_PREALLOC` 改成固定步长线性增长。看到这一行，"预分配后追加是摊销 O(1)"这个结论就不再需要背了。

调试技巧：别硬看，**在 `createStringObject` 下断点**，redis-cli 里敲一次 `SET k hello` 和一次 `SET k <200字节的值>`，两次调用栈的差异 30 秒就能看懂 embstr 和 raw 的分配区别。看十遍代码不如下一次断点。

## 第三步：跑起来验证——这一步大多数人会跳过，但收益最大

读完上面三处代码，理论上你已经"懂"了。但**懂了机制不等于知道值多少钱**。我搭了个小压测（Redis 7 单体、Lettuce Pipeline、c=16、每轮 5s 预热 + 10s 采样，每轮用 `OBJECT ENCODING` 回查编码），结果有两类：

**① 验证成功的假设。** embstr 确实比 raw 快，而且量级值得记：

| 操作 | 编码 | ops/s | avg | p99 |
|------|:--:|------:|------:|------:|
| SET 40B | embstr | **448,159** | 3.58ms | 9.15ms |
| SET 200B | raw | 357,566 | 4.49ms | 12.01ms |
| GET 40B | embstr | **457,400** | 3.52ms | 10.93ms |
| GET 200B | raw | 400,466 | 4.01ms | 10.01ms |
| INCR（int） | int | **532,654** | 3.02ms | 7.85ms |

embstr 比 raw：SET **+25.3%**、GET **+14.2%**。而且 SET 差距比 GET 大一倍——因为写入路径要多付一次 malloc + memcpy，分配器开销只在写入时放大；读取两边都是 O(1) 查 dict 返回指针，差距只剩 cache 命中率。**这个"SET 差 25%、GET 只差 14%"的不对称，只有压过才会讲。**

**② 一个源码读完仍然没告诉我的东西。** 既然 embstr 只读、APPEND 会强制转 raw，那追加延迟会差多少？我测了两组：

| 操作 | 编码 | ops/s | avg | p99 | **max** |
|------|:--:|------:|------:|------:|------:|
| APPEND（raw 预分配） | raw | 410,066 | 3.92ms | 11.22ms | **39.31ms** |
| APPEND（embstr 起步） | embstr→raw | 409,705 | 3.93ms | 9.71ms | **286.79ms** |

**平均吞吐几乎一样，max 差了 7.3 倍。** 只看 avg 和 p99，你会得出"两种写法没区别"的结论——但生产上那 287ms 就是一个查不出原因的毛刺。

这一步为什么重要：源码给你的是**机制**，压测给你的是**代价的量级**。`createRawStringObject` 那行代码不会告诉你它是 39ms 还是 287ms，而这个数字才决定你在架构评审时能不能说服别人。

## 从这个案例里能提炼的四条方法

1. **别从 `main.c` 通读。** 挑一个命令当入口（`APPEND` 就够你挖三层：t_string → db → sds），一个命令挖通，Redis 的骨架就通了大半。
2. **每个结论都写成一句可证伪的假设。** 写不出假设，说明你还没想清楚要读什么。
3. **看不懂就下断点或打日志。** 在 `createStringObject`、`dbUnshareStringValue` 下断点，一次调用胜过十遍阅读。Redis 是 C，调试成本比你想的低。
4. **用命令把内部状态暴露出来。** `OBJECT ENCODING`、`OBJECT REFCOUNT`、`DEBUG JMAP`、`INFO`、`LATENCY DOCTOR`——这些是源码和现实之间的望远镜。我每轮压测都回查一次 `OBJECT ENCODING`，就是为了确认自己没在测错东西。

## 一份按难度排开的阅读路径

| 顺序 | 文件 | 能搞懂什么 |
|:--:|--|--|
| 1 | `sds.c` | 动态字符串、预分配，最小闭环，成就感最快 |
| 2 | `object.c` | 类型与编码切换，所有数据结构的总入口 |
| 3 | `dict.c` | 哈希表、渐进式 rehash、字典扩容 |
| 4 | `t_string.c` / `t_hash.c` | 命令层怎么落到编码上（APPEND 那个坑就在这） |
| 5 | `adlist.c` / `zmalloc.c` | 双向链表、内存分配封装 |
| 6 | `ae.c` / `anet.c` | 事件循环、fd 就绪分发，理解"单线程为什么快" |
| 7 | `rdb.c` / `aof.c` | 持久化、fork 与 COW |
| 8 | `cluster.c` / `replication.c` | 槽位、迁移、主从同步 |

前四个文件加起来不到一万行，认真读一到两周就能把"数据结构 + 编码"这条主线打通——**这已经足够覆盖面试和日常调优 80% 的问题**。剩下的网络层和集群层，等你有具体问题时再挖，不要提前啃。

---

**一点诚实的补充**：上面的数据是单轮采样，max 是本次观测到的单次极值，绝对值当量级参考；也没记录内存分配器（jemalloc / libc）和 lazyfree 配置，它们会影响 malloc 相关路径的绝对耗时。**看相对差距，别拿这些数字和 redis-benchmark 对比。**

同一套方法我还测了 Hash、Set、ZSet 的编码对比，结论和八股文同样有出入（比如 field 逼近 128 时 hashtable 反而比 listpack 快 21%）。

**八股可以被背，结论只能被跑出来。** 源码读完记得跑一遍——这是读源码和背源码唯一的区别。
