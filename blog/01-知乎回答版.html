01-知乎回答版

前面几位把 Redis String 的编码原理、内存布局讲得很清楚了。我这篇只做一件事：把这套机制放到十几万 QPS 下压一遍，看这几种编码到底差多少钱。

先说结论：embstr 比 raw 的 SET 快 25.3%、GET 快 14.2%；INCR 最快，53 万 ops/s；但对 embstr 反复 APPEND，max 延迟会抖出 287ms 毛刺，而 raw 预分配只要 39ms——最后这个坑，原理向的回答里基本都没写。

测试条件：Redis 7 单体（无持久化）、Lettuce Pipeline（c=16、batch=100）、10 万 key 空间，每轮 5s 预热 + 10s 采样，每轮用 OBJECT ENCODING 回查编码确认没测错对象。绝对吞吐受客户端影响，请看相对差距。

一、三种编码的基础对比

操作 编码 ops/s avg p99 max
SET 整数 int 415,544 3.86ms 11.94ms 32.39ms
SET 40B embstr 448,159 3.58ms 9.15ms 33.72ms
SET 200B raw 357,566 4.49ms 12.01ms 32.91ms
GET 整数 int 429,694 3.73ms 11.26ms 31.12ms
GET 40B embstr 457,400 3.52ms 10.93ms 48.00ms
GET 200B raw 400,466 4.01ms 10.01ms 27.48ms
INCR int 532,654 3.02ms 7.85ms 29.02ms

三个结论：

1. embstr 确实比 raw 快，SET +25.3%、GET +14.2%。 根因就是大家都会讲的那条：embstr 一次 malloc 拿到连续内存，raw 要分两次。但为什么 SET 的差距（25%）比 GET（14%）大一倍，原理文章很少说——因为写入路径要多付一次 malloc + memcpy，分配器开销在写入时才被放大；读取两边都是 O(1) 查 dict 返回指针，差距只剩 cache 命中率的贡献。

2. INCR 是 Redis String 的最快路径：53 万 ops/s，p99 只有 7.85ms。 int 编码下 value 就是 RedisObject 里的一个 long，INCR 只做一次整数加法，零 malloc、零 memcpy、零 sds 操作。主线程纯算术，没有比这更便宜的了。

3. 顺便纠正一个流传很广的说法。 很多人写「SET k 0 是 int，SET k "0" 是字符串」——这是错的。Redis 在 RESP 协议层收到的是字节串，两者是同一个值，都走 int。真正的分界是这个字节串能否被 string2ll 解析成 64 位整数：SET k 100 是 int，但 SET k "100 "（带空格）、SET k 1.5、SET k 99999999999999999999（超出 64 位）都会退化成 embstr/raw。

二、value 变大时，raw 掉多少

真实业务里 raw 装的是 JSON、HTML 这种大块头，所以补了 1KB 对照组：

操作 value ops/s avg p99 相比 200B
SET raw 200B 357,566 4.49ms 12.01ms 基线
SET raw 1KB 218,997 7.32ms 15.50ms -38.8%
GET raw 200B 400,466 4.01ms 10.01ms 基线
GET raw 1KB 289,606 5.56ms 13.20ms -27.7%

value 从 200B 涨到 1KB（5 倍），吞吐掉了约三分之一。根因是 memcpy 数据量线性增长，而 Redis 主线程单线程——你每多拷 800 字节，全实例的每一个请求都在陪你等。SET 掉得比 GET 更狠，因为写入是"分配 + 拷贝"两次搬运。这也是大 value 容易踩 slowlog 的真正原因。

三、最有价值的发现：平均值骗了你

回到开头那个 287ms。我专门设计了两组 APPEND 对照：

  • APPEND_RAW：先 SET 一个足够大的初始值（raw，触发 sds 预分配），再反复 APPEND 小块
  • APPEND_EMBSTR：value 从 embstr 起步（≤44B），直接反复 APPEND

结果很有戏剧性——平均吞吐几乎一样，max 差了 7.3 倍：

操作 编码 ops/s avg p99 max
APPEND_RAW raw 预分配 410,066 3.92ms 11.22ms 39.31ms
APPEND_EMBSTR embstr→raw 409,705 3.93ms 9.71ms 286.79ms

只看 avg 和 p99，你会得出"两种写法没区别"的结论。但 max 一列暴露了真相：embstr 起步的 APPEND 会随机抖出 287ms 毛刺。

根因在编码的可变性上，这里补两个原理文章通常没讲的细节：

  • raw 的 sds 是几何扩容（sdsMakeRoomFor）：1MB 以内近似翻倍，超过 SDS_MAX_PREALLOC 后改成固定步长线性增长（避免大 value 浪费内存）。所以只要当前容量够用，后续 APPEND 就是 O(1) 原地追加，整体摊销 O(1)；
  • embstr 是只读编码（Redis 源码 t_string.c 里就是这么定义的）：它的 sds 一次性连续分配，alloc 等于 len，没有为增长预留任何 spare 空间。所以每次 APPEND 都必须新建 sds、全量拷贝旧值、释放旧内存——每次都是 O(N)。

而且这是跨编码的坑：int 起步也一样，APPEND 一个 int 编码的 key 会先转 raw 再操作，实测确认 encodingAfter = raw。一句话总结：只要起点不是"已预分配的 raw"，反复 APPEND 就是反复全量重分配，延迟长尾完全不可控。

这个点，面试题不考，官方文档只有一句 "embstr is read-only"，但生产上它就是那个查不出原因的毛刺。

四、生产选型速查

你要存的数据 该有的样子 实测依据
计数器 / 自增（浏览量、库存、频控） 纯整数 value，走 int 532K ops/s，p99 最低，零分配
短状态 / Token / 短配置（≤44B） 不用管，自动 embstr SET +25%，GET +14%
JSON / 长文本（>44B） 只能 raw，控制大小 1KB 比 200B 吞吐 -39%
增量拼接构建大字符串 先 SET 初始 raw 铺底，再 APPEND 摊销 O(1)，max 39ms
对 int / embstr 反复 APPEND ❌ 避开 max 延迟 287ms，长尾爆炸

四条原则：

  1. 能用整数就别用字符串：确保写入的是干净的十进制整数（无空格、无小数点、不超 64 位），计数场景优先直接 INCR/DECR；
  2. 短文本不用优化：Redis 自动帮你选了 embstr，这是机制内建的福利；
  3. 要拼接，先铺底：先 SET 一个预估大小的初始值把 sds 容量撑起来，后续 APPEND 全走预分配；如果拼接逻辑复杂，更稳的做法是改用 List / Stream 存片段、后台合并，或干脆在客户端拼好再一次写入；
  4. 盯 max，别只盯 avg：这次 287ms 的坑，p99 上完全看不出来。Redis 单线程，一个请求的长尾就是全实例的长尾。

五、30 秒自己验证

不用搭压测环境，redis-cli 四行命令就能看到编码转换：

SET k hello
OBJECT ENCODING k        # embstr
APPEND k , world
OBJECT ENCODING k        # raw —— 一次追加，编码已经换了

看到第二步变成 raw，你就明白为什么"对短字符串反复 APPEND"是坑了。

几句实话（局限）：数据为单轮采样，max 是本次观测到的单次极值，绝对值请当量级参考；未记录内存分配器（jemalloc / libc）与 lazyfree 配置，它们会影响 malloc 相关路径的绝对耗时；单机 + Pipeline 客户端会压低吞吐上限，所以别拿这些数字和 redis-benchmark 对比。要看的是相对差距。 同一套方法我还测了 Hash、Set、ZSet 的编码对比，结论同样和八股文有出入，改天写。

八股可以被背，结论只能被跑出来。有出入欢迎拿数据来抬杠。
