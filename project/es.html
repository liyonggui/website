Elasticsearch 源码研读

深入研读 Elasticsearch Java 源码：传输层、集群协调、搜索执行层 Query + Fetch 两阶段，梳理核心技术实现逻辑并整理成系列手册。传输层 / 集群协调

项目概述

源码研读按三条主线展开：传输层（节点间通信、REST 与 Transport 的分工）、集群协调（选主、分片分配算法、MurmurHash3 路由）、搜索执行（Query + Fetch 两阶段为什么这样切分）。

研读结论落到两份生产向产出：一套运维命令速查手册（集群架构 + 常用命令），一套分片倾斜应急处理步骤（线上可直接照做），另有 ILM 冷热分层、Reindex 重构、别名与 Rollover 的完整实操手册。

技术亮点与难点攻坚

  • 文档到底落在哪个分片难点：不清楚路由规则就没法解释倾斜与查询行为，读源码前只能猜。方案：从源码确认默认路由为 MurmurHash3(_id) % primary_count，并验证自定义 routing 的落点；据此定位多个倾斜案例的根因（路由键分布不均），应急处理步骤整理成可直接照做的手册。
  • 写入链路「丢没丢」说不清难点：refresh/translog/flush 各环节职责混在一起，数据可靠性与可见性争论没有依据。方案：沿 ES 7.17 写入全流程逐段梳理：index buffer → refresh 生成段 → translog 持久化 → flush 落盘，把「可见 ≠ 可靠」的分界讲清楚（ES7.17 写入全流程-2）。
  • 分片倾斜线上应急难点：节点磁盘/负载严重不均，直接 rebalance 可能引发更大抖动。方案：沉淀应急步骤：先查倾斜分布与路由键，再决定 move 分片 / reroute / 调整 watermarks 的顺序与风险点，形成照着操作的 checklist。
  • 索引重建期间的双写与切换难点：mapping 变更需要 reindex，直接切流量会丢数据或停服。方案：别名 + Rollover 方案：新索引 reindex 期间双写（别名切读/切写分步），验证一致后原子切换，完整手册覆盖参数与故障排查。
