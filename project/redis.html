Redis 高并发缓存架构

以 11 个实测场景覆盖 Redis 在高并发读写下的编码选型、Pipeline 边界、集群拓扑与热点治理，每个场景都给出对比数据与生产选型结论。11 场景压测

项目概述

这条线从 Lettuce 客户端的真实问题切入：Pipeline 批量写入为何反而变慢、跨槽命令在 Cluster 下如何报错、连接数与 maxclients 的边界在哪。每个场景都保留原始压测数据与排查过程，而不是只给结论。

除压测外，还沉淀了两份可直接照做的产出：一份 Redis 高并发缓存架构实战手册（缓存穿透/击穿/雪崩、双写一致性、热点探测），一份 11 场景总结汇总（每场景一句话结论 + 适用条件 + 反例）。

技术亮点与难点攻坚

  • Pipeline 在 Cluster 下直接报错难点：Pipeline 批量命令按 slot 分发，跨槽 key 混在一次批量里直接被节点拒绝（CROSSSLOT），批量收益瞬间归零。方案：客户端侧按 CRC16 slot 对 key 预分组：先本地计算每个 key 的槽位，同槽 key 才合进一个 Pipeline 分片，跨槽拆多次发送；实测拆分后吞吐恢复到接近单槽水平。
  • Lettuce Pipeline 线上变慢难点：批量写入吞吐不升反降，且延迟抖动剧烈，现象与「Pipeline 应该更快」的直觉相反。方案：逐层排查：连接复用、命令聚合粒度、flush 时机，定位到聚合批次过大导致单次网络往返载荷过重与响应排队；调小批次并配合并行连接后恢复正常，完整排查过程与数据见场景 1。
  • String 编码阈值照抄默认值踩坑难点：按默认 128/512 阈值估算内存与编码，实测 128 个短 member 并没有触发 listpack→skiplist 转换，容量预估直接失真。方案：实测确认阈值为「大于才转换」（129+/513+），且转换单向不可逆；生产上把安全余量压到 ≤127 / ≤511，并写进容量规划口径。
  • 热点 Key 计数打爆单分片难点：爆款商品的库存/计数 key 落在单个 slot，读写全压一个节点，加机器也没用。方案：Pipeline 自增合并写 + key 打散（后缀分片再聚合）双管齐下，实测热点分片负载显著摊平，具体数值见场景 8-1/8-2。

关键数据与亮点

  • 11 个压测场景Lettuce/Pipeline、Hash 批量、TTL 过期、分布式信号量、HGETALL vs HSCAN、maxclients 边界、跨槽 Pipeline、热点 Key、RTT 敏感度、哨兵 vs 集群、String 三种编码
  • 编码阈值实测128/512 阈值边界不可靠：128 个短 member 未触发 listpack→skiplist 转换（需 129+），生产建议留足余量
  • 选型结论哨兵 vs 集群写入阶段各有胜场，按「是否跨槽 + 写入模式」决策，不迷信单一方案
