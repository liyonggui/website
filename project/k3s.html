K3s / K8s 运维

从 Compose 迁移到 K3s：工作负载、配置、存储、网络全套 manifests，加 NetworkPolicy 默认拒绝与 Redis 白名单，配套滚动更新与高可用实践。manifests + 网络策略

项目概述

资源覆盖 Namespace / ConfigMap / Secret / Deployment / Service / Ingress，以及 Redis 用 StatefulSet + PVC 的有状态部署。网络策略做成了两层：默认拒绝所有入站，再按需放行（Redis 仅允许指定标签的应用访问）。

运维实践包括滚动更新（探针参数与 maxSurge/maxUnavailable 的配合）、Ingress + HPA 弹性伸缩、Redis 主从与哨兵在 K8s 里的部署差异，以及一份 K8s 学习路线图。

技术亮点与难点攻坚

  • Pod 间默认全通的安全风险难点：集群内任意 Pod 可互访，一次入侵即可横向移动，默认网络模型不满足最小权限。方案：NetworkPolicy 默认拒绝（deny-all 入站）+ 按标签白名单放行：Redis 只允许指定 label 的应用访问，规则用实测连通性逐条验证。
  • 有状态服务的部署差异难点：Redis 用 Deployment 重建后数据丢失，副本间身份也无法稳定。方案：改用 StatefulSet + PVC：稳定网络标识 + 独立存储，主从与哨兵两种拓扑分别落地并对比运维差异（redis-replication / redis-sentinel）。
  • 滚动更新期间的服务抖动难点：直接改镜像触发更新，新旧实例交替时出现 502 与请求失败。方案：探针参数（就绪/存活阈值）与 maxSurge/maxUnavailable 联动调优：新实例就绪才接流量，旧实例延迟退出，更新全程零失败（ROLLING-UPDATE）。

关键数据与亮点

  • 默认拒绝网络策略NetworkPolicy 默认 deny-all + 按标签白名单放行
  • 有状态部署Redis StatefulSet + PVC，主从/哨兵两种拓扑对比
  • 弹性伸缩Ingress + HPA 配置与压测验证
