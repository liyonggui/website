# 一个后端服务三个前端

这是第二个真实项目（已脱敏）的架构复盘。业务形态：**教育升学信息 + 在线考试**。一套单体后端，同时支撑管理后台、考生答题 Web 端、微信小程序和企业官网——四个端、两种业务域、两种数据库。

## 一、整体思路：单体，但按域切分

没有上微服务。原因很直接：团队规模小、部署目标是一台云主机，拆微服务只会把运维复杂度翻倍。但单体内部**严格按域分包**，并预留了拆分骨架：

```
org.example.app
├── common/            横切层：配置、切面、缓存门面
├── modules/           平台脚手架自带模块
│   ├── auth/          OAuth2 认证端点 + 多种授权器
│   ├── system/        用户/角色/菜单/部门/租户
│   ├── resource/      OSS 文件、短信资源服务
│   └── develop/       代码生成器
└── biz/               ★ 自研业务包（两域）
    ├── exam/          考试域 → MongoDB
    │     admin(管理端) / web(考生端) / service / repository / entity / cache
    └── normal/        内容与产品域 → MySQL
          admin(13 个 Controller) / wx(小程序 13 个) / service / sync
```

仓库里还留着一个未启用的多模块拆分骨架（`biz-common / biz-exam / biz-admin / biz-wx`）——**先按包隔离，等负载真到了再按模块拆部署**，这是单体演进的现实路径。

技术栈：JDK 17 + Spring Boot 3.2、基于一款成熟的开源企业级脚手架（提供认证/权限/代码生成等平台能力）、MyBatis-Plus、MySQL 8.4、MongoDB 8.0、Redis 7 + Caffeine、MinIO、Flowable、EasyExcel。

## 二、双存储：为什么考试域用 MongoDB

两个业务域的数据特征完全不同：

| | 内容/招生产品域 | 考试域 |
|---|---|---|
| 典型数据 | 院校、专业、课程、资讯、订单 | 题库、试卷、答题记录、收藏、统计 |
| 写入模式 | 低频管理操作 | **高频考生行为**（每道题一次作答写入） |
| 结构 | 关系性强（外键、多表查询） | 文档内嵌自然（试卷内嵌题目快照） |
| 增长 | 缓慢 | **随考生量线性膨胀** |

所以考试域整体放 MongoDB，并且做了两个关键设计：

1. **答题记录按月分集合**（`collectionForMonth`）——单集合不会无限膨胀，索引规模可控；统计类集合（按用户/按题目/按分类）同样按月分桶。
2. **索引在构造器中预建**——唯一索引 `idx_user_paper_submit`（用户×试卷）同时承担**交卷幂等**职责：重复提交直接被数据库拒掉。

MySQL 域则承担所有关系型查询：院校/院系/专业三级关联、订单、会员、站点配置。

## 三、四条核心链路

### 链路 1：组卷 → 发布（状态机 + 缓存失效）

```
智能组卷(/paper/smart-generate)
  → 试卷状态机: draft → published ⇄ unpublished → archived（含回收站）
  → Mongo 文档更新
  → ExamPaperCache 写后 evict（Redis 缓存失效维护一致性）
```

试卷内嵌**题目快照**而不是引用——题目后续被改不影响已发布试卷的稳定性。

### 链路 2：答题 → 判分 → 统计（安全贯穿全程）

```
登录: Redis 计数限流 → Lua 脚本原子单点登录 → 自签 JWT
答题: SecurityGuard 防抓取守卫 + BanService 设备指纹封禁
交卷: submit() → 幂等判分（唯一索引兜底）
统计: 增量统计服务 + 回填服务双写兜底 → 读聚合
```

考试系统的安全设计是重点：**防抓取守卫**（答题过程检测异常行为）、**用户/设备指纹封禁**、试卷答案防泄漏专项方案、Lua 脚本保证单点登录的原子性。

### 链路 3：招生目录大文件同步（本项目最值得讲的工程）

每年一次的招生目录是 18MB / 3.2 万行的 Excel，直接读会把堆打爆。方案分三步：

**第一步：EasyExcel SAX 流式解析。** 弃用 POI DOM 模式（pom 注释里明确记录了堆峰值优化的动机），逐行读、批量写。

**第二步：影子表原子切换。** 同步不直接改生产表——先写一张影子表，校验通过后 `RENAME TABLE` 原子切换。用户视角的服务要么是旧数据、要么是新数据，**没有中间态**：

```java
// 伪代码
createTask()            // @Transactional 建同步任务
executeAsync()          // 异步线程池执行
  parse()               // SAX 流式解析 xlsx
  batchInsert(shadow)   // 批量写影子表
  validate()            // 行数/关键列校验
  RENAME TABLE shadow TO prod   // 原子切换
rollback()              // 失败 = 表级改名回滚
cancel()                // 取消 = 乐观锁 CAS（WHERE status=RUNNING）
```

**第三步：僵尸任务自愈。** 应用启动时监听 `ApplicationReadyEvent`，清理上次进程崩溃遗留的 RUNNING 状态任务。

### 链路 4：文件上传（MinIO）

小程序端与后台共用一套 OSS 抽象：`OssBuilder` → `OssTemplate`（S3 协议）→ MinIO。配置里当前激活 MinIO，但抽象层同时兼容 S3/阿里 OSS/腾讯 COS——换存储只改配置。生产环境经过地址转换把内网 endpoint 换成外网域名。

## 四、双轨认证与三级缓存

### 双轨认证

| 端 | 方案 |
|---|---|
| 管理端 | 脚手架 OAuth2 密码模式 + 国密 SM2 验签，菜单级 `@PreAuth` + 接口权限 + 行级数据权限三套控制 |
| 考生端 | **自签 JWT + SM4 报文加密**，Redis 会话 TTL 与 JWT 过期强制相等，Lua 原子单点登录 |
| 小程序端 | 独立的微信登录 → JWT 链路，自动注册 |

三套认证互不干扰，每端只拿得到自己域的接口。

### 三级缓存（防雪崩是核心命题）

```
Caffeine 本地缓存（分类树等热点，5~15s 记忆化）
   ↓ miss
Redis（Protostuff 序列化，试卷详情 24h 兜底 TTL）
   ↓ miss
DB
```

两个细节：

1. **缓存 Key 枚举里的 TTL 全是互不相同的质数**——同一时刻建缓存的压力点被打散，从根上防雪崩；同时支持 yml 运行时覆盖单个 TTL。
2. **写后 evict + 兜底 TTL 双保险**——主动失效保证一致性，兜底 TTL 保证 evict 失败也不会脏太久；统计类缓存失效再加 10 秒节流。

分布式事务没有上 Seata，一致性靠组合拳：本地事务 + 影子表 RENAME 原子切换 + 乐观锁 CAS + 幂等唯一索引 + 统计增量/回填双写兜底。**每一条都对应具体场景**，而不是引入一个重框架解决所有问题。

## 五、可观测与压测

- Druid 慢 SQL 统计精准圈定业务包（`exam*,biz*`），配慢方法切面；
- MongoDB 侧自建慢查询监控（CommandListener 采集），管理页面可看；
- **k6 压测体系**：脚本自动生成器扫接口清单产出 k6 脚本，dev 全链路压测 + 对账脚本，pre 环境 QPS 专项，HTML 报告输出；
- SQL 迁移用 Flyway 风格编号管理（`V1.0.x__*.sql`），并备了 7 种数据库的兼容升级脚本。

## 六、部署形态

单机 Docker Compose 全家桶：应用 fat jar 容器 + nginx（三个前端静态目录 + TLS 反代）+ MySQL 8.4 / Redis 7 / MongoDB 8.0 / MinIO 四中间件，全部带资源限额。**敏感配置全部走环境变量注入**，镜像里只有占位符；发布有 healthcheck + 一键前端部署脚本（备份 → 解压 → reload）。

## 七、复盘

这个项目的主题是「**在单体里做出分布式级别的工程纪律**」：双存储是按数据特征分工而不是追新；影子表切换把「大数据量同步」这个最容易出事故的场景做成了原子操作；三级缓存的每个参数（质数 TTL、节流窗口、兜底时长）都有明确的防雪崩动机。单体不是终点，按域分包 + 拆分骨架让它随时可以继续演进。
