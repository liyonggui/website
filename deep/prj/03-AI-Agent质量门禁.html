AI Agent 质量门禁：CI 之外的智能分析链与代码生成链

2026-10-11工程实战 系列约 22 分钟阅读AI AgentCI/CDLLM质量工程

脱敏口径：gold 集结果、门禁阈值与归因流程的运行结论来自真实生产环境；示例代码、issue 样例与台账结构做了通用化示意处理。

AI Agent 质量门禁

第三个真实项目（已脱敏）。先纠正一个常见误解：它不是 Selenium/Playwright 那种 UI 自动化平台。它是一个 Spring Boot 常驻服务，定位是——

在云端确定性 CI（覆盖率硬门禁）之外，搭建第二条「智能 + 生成」链路： 分析链复跑门禁、用 LLM 归因失败、把结论回写到 PR； 生成链从 issue 出发，让 LLM 写实现和测试，过沙箱、跑门禁，达标才允许开 PR。

一、整体架构

服务约 41 个主类 / 7000 行，跑在一台内网机器上，通过内网穿透隧道接收代码托管平台的 Webhook：

代码托管平台 ──Webhook──▶ 隧道 ──▶ ┌─────────────────────────────┐
                                  │ webhook/  签名校验 + 事件过滤 │
                                  │ security/ 常量时间比对        │
                                  └──────────┬──────────────────┘
                                             │ GitEvent
                                  ┌──────────▼──────────────────┐
                                  │ queue/  Redis Stream 任务队列 │
                                  │   SETNX 窗口去重 + 孤儿回收    │
                                  └──────────┬──────────────────┘
                                             │ 单消费线程
                    ┌────────────────────────┴───────────────────┐
        ┌───────────▼────────────┐              ┌────────────────▼──────────┐
        │ 分析链 TestJobRunner    │              │ 生成链 codegen 包           │
        │  git worktree(只读)     │              │  issue 轮询 → 认领去重      │
        │  变更影响面分析          │              │  方案指纹 → 人工审批闸      │
        │  白名单执行 mvn test    │              │  LLM 生成 → 四道沙箱        │
        │  解析 Surefire/JaCoCo   │              │  提交 → 跑同一套门禁        │
        │  覆盖率门禁 → LLM 归因  │              │  失败回灌迭代 ≤3 轮         │
        └───────────┬────────────┘              └────────────────┬──────────┘
                    │   Markdown 报告 → PR 评论 / 钉钉通知         │ 证据包 + 台账
                    └────────────────────────────────────────────┘

技术栈：Java 17 + Spring Boot 3.3、Redis 7（Stream 队列 + 状态标记）、OpenAI 兼容协议的 LLM 端点、企业 Git 平台 API、钉钉机器人。

二、分析链：从 Webhook 到 PR 评论

一条 PR 事件进来后：

  1. 签名校验（明文 token 或 HMAC 双模式，常量时间比对防时序攻击）；
  2. 四道过滤：仓库身份闸 → 分支白名单 → PR 动作白名单 → 状态 open。被过滤的事件回 200（防止平台重投风暴）；
  3. 去重入队：去重身份是 pr-<号>:<headSha>，SETNX 抢位 → XADD 入队 → 两态标记（pending/queued），含孤儿回收（超时 pending 重入队）和入队失败撤销标记；
  4. 单消费线程串行处理：独立 git worktree 检出 → 变更影响面分析（纯文档变更直接跳过）→ 执行被测仓的 CI 脚本；
  5. 报告解析：退出码 + Surefire XML（带陈旧报告过滤，防止 worktree 复用残留污染）+ JaCoCo 覆盖率；
  6. 门禁判定 → LLM 失败归因 → Markdown 报告回写 PR 评论 + 钉钉通知。

覆盖率门禁：唯一实现，两处共用

这是全项目最重要的设计决策：门禁只有一个实现——被测仓里的一小段 Java 程序（新增行覆盖率 ≥70%、新增行分支覆盖率 ≥70%），云端流水线和本地 Agent 服务跑的是同一份代码。

反例是很多团队踩过的坑：云端一套 shell 脚本、本地工具另一套逻辑，两者口径微妙不一致，「图标绿了云端红了」的双口径 bug 永远查不完。

LLM 只建议、不判生死

失败归因确实用 LLM（把失败日志发给模型分析），但有硬约束：

  • LLM 输出只进报告的「建议」段落，红绿灯判定只吃确定性结果（退出码 + 覆盖率数值）；
  • LLM 输出非法时自动回退到规则基线结论；
  • 异常路径必发「🟠 未取得结论」——静默失败零容忍，「不可判定 ≠ 通过」（用例总数为 0 直接判 BROKEN）。

这条纪律划清了 AI 的边界：AI 负责解释世界，确定性代码负责做决定。

三、生成链：让人工审批闸拦在 LLM 之前

生成链更激进——让 LLM 直接写代码。安全设计层层递进：

issue 标题带 [ai] 前缀触发
  → Redis HSETNX 认领去重（多实例不重复生成）
  → 从需求文本定位目标类 + 参考范例
  → 计算方案指纹（base_sha + 规则哈希 + 目标）   ← 方案一变，旧批准作废
  → 人工审批闸：未批准，一个 token 都不会发给模型
  → LLM 生成（契约：{files:[{path,content}]}）
  → 四道沙箱校验
  → 提交 → 跑与云端相同的覆盖率门禁
  → 不绿？把门禁失败信息回灌 prompt，迭代 ≤3 轮
  → 默认不自动开 PR（auto-pr=false）

四道沙箱（纯函数，可单测）

# 防线 拦什么
1 路径白/黑名单 只许改 src/{main,test}/java/**.java，挡 pom/CI 脚本/配置/穿越路径
2 既有测试文件冻结 一律拒改——测试是验收 oracle，防止模型「自己改考卷」
3 覆盖风险检查 不许删除既有 public 方法（防验收能力被阉割）
4 运行时风险正则 拦 System.getenv/进程执行/网络/反射（文档坦诚：这是「把绕过变成刻意行为」，真隔离是待办）

证据包与台账

每轮生成落一个证据包（生成上下文、沙箱判定记录、代码补丁、模型结论）+ 追加式 JSONL 台账（方案指纹、人的审批决定、机器的门禁结论、人工复测结果）。任何一次 AI 写代码都可以完整复盘：谁批的、模型给了什么、门禁怎么判的。

四、执行安全：当被执行的是 LLM 写的代码

分析链要执行 mvn test，生成链要执行模型产出的代码——这个服务的威胁模型比普通 CI 严峻得多：

  • 固定 argv 白名单：执行的命令永远是预定义的参数数组，diff 内容和 LLM 输出绝不拼接进命令行（防注入）；
  • 子进程凭据剥离：启动子进程前，用正则删除环境变量里所有凭据类条目——防止模型生成的代码 System.getenv() 把令牌读出来外传；
  • 超时杀进程树：30 分钟硬顶，destroyForcibly 连子进程一起杀；
  • git 令牌脱敏：所有 git 输出过一遍掩码才落日志；
  • 物理隔离：分析链与生成链各用独立 worktree，checkout/reset 互不干扰。

五、线程模型的细节

线程分配看似随意，实际每个数都有理由：

  • Web 线程只做毫秒级的收事件 + 入队，重活全部丢队列；
  • 消费线程只有 1 个——分析链本身要跑几十分钟的构建，串行保证 worktree 不被并发踩；
  • 调度池 size=2——生成链一轮要占用几十分钟，如果和「隧道域名漂移自愈」共用调度器，域名同步任务会被饿死，Webhook 就断了。两个线程、两类任务，各走各的。

隧道自愈本身也是个亮点：内网穿透的公网域名会漂移，服务每 60 秒四级探测（面板 API → tunnels API → 日志 → 环境变量兜底），发现漂移就先建新 Hook 再删旧 Hook（避免空窗）地回写平台。

六、复盘

这个项目最大的收获不是「接入了 LLM」，而是为 AI 参与关键流程建立的纪律体系：

  1. 确定性优先：红绿灯永远由确定性结果决定，LLM 只做归因和建议；
  2. 人机协同闸门：方案指纹 + 人工审批，确保 AI 不会在无人知情的情况下改变生成策略；
  3. 生成物同等对待：模型写的代码和人类写的代码过同一套覆盖率门禁，没有特殊通道；
  4. 可复盘性：证据包 + 台账让每一次 AI 决策都有据可查。

AI 工程的可靠性从来不来自模型多强，而来自包围模型的工程护栏有多严。
