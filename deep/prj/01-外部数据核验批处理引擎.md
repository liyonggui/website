# 外部数据核验批处理引擎

这是一个真实生产项目（已脱敏）的架构复盘。它解决的问题很典型：**本地有一份业务名册，需要逐条到外部数据共享网关核验信息，并把每次调用的完整证据链留痕落库，最终产出可比对、可审计的结论表**。

## 一、整体思路

先说几个决定整个架构形态的前提：

1. **不是 Web 服务**。它不监听任何端口、不提供 HTTP 接口，而是一个**一次性命令行批处理作业**——进程生命周期 = 作业生命周期，跑完以语义化退出码结束，由外部调度器判断成败。
2. **调用配额宝贵且不稳定**。外部网关按调用计费、有隐性限流，且网络链路（政务专线）偶发超时、错误页、限流。这意味着**每一次调用都必须留下完整证据**，失败不能笼统处理。
3. **数据量在十万级**。单线程串行足够跑完，盲目上并发只会触发限流，得不偿失。

基于这三点，整体架构刻意「压薄」：

```
┌─────────────────────────────────────────────────────┐
│ AppRunner (ApplicationRunner + ExitCodeGenerator)   │
│   模式分发: run / retry-rounds / qps / limitprobe   │
└──────────────┬──────────────────────────────────────┘
               │
┌──────────────▼──────────────────────────────────────┐
│ RunFullJob / RoundRetryJob        （作业编排层）      │
│   分页读名册 → 逐条送查 → 失败分类 → 集中补打 → 落库  │
└──────────────┬──────────────────────────────────────┘
               │
┌──────────────▼──────────────────────────────────────┐
│ GatewayClient                      （网关接入层）     │
│   ├─ Signer          请求签名（ts+token+nonce）      │
│   ├─ GaTokenProvider OAuth2 令牌缓存/强刷/冷却      │
│   ├─ HttpTransport   连接池化 POST，全量读响应体      │
│   └─ classify()      失败分类 + 判定                 │
└──────────────┬──────────────────────────────────────┘
               │
┌──────────────▼──────────────────────────────────────┐
│ RosterDao / OnenetDao              （数据访问层）     │
│   分页读名册 / 批量写留痕·结果·批次台账（事务 flush）  │
└─────────────────────────────────────────────────────┘
```

技术栈同样克制：JDK 8 + Spring Boot 2.7.18（**刻意不引 web starter**）、JdbcTemplate + HikariCP（不用 ORM，SQL 全手写）、HttpClient 4 连接池、国产数据库 KingbaseES。没有 MQ、没有 Redis、没有定时框架——**队列就是内存 List + 数据库表**。

## 二、代码逻辑：五个关键设计

### 1. 失败分类学：先回答「该找谁」

失败不是一个布尔值。系统把失败分成六类，每类对应完全不同的处置策略：

| FailType | 含义 | 处置 |
|---|---|---|
| `OUR_PAYLOAD` | 我方报文不合法（网关 417） | 重试无意义，**不重试**，直接人工修 |
| `DATASOURCE` | 数源方故障（418/500） | 独立退避 10s→30s 封顶，最多 3 次 |
| `PLATFORM` | 网关平台故障 | 计入熔断 |
| `NETWORK` | 超时/连接失败 | 退避 1s/3s/9s 重试 3 次 |
| `RATE_LIMIT` | 限流 | 计入熔断，指数退避 |
| `UNKNOWN` | 无法识别 | 降级为「无法判定」，**绝不猜** |

分类的实现有两层兜底：一是响应里的业务错误码映射（`mapErrcode`）；二是**错误页指纹识别**——网关挂掉时经常返回 HTTP 200 + openresty/APISIX 错误页 HTML，靠 body 内容指纹也能认出来，避免把错误页当业务响应解析。

### 2. 后置集中重试：主扫失败不干等

最初版本是「失败→原地重试→再失败→再重试」，实测一个 5 万人的批次要多跑 7~9 小时——大量时间耗在退避 sleep 上。

改成**后置集中补打**：

- 主扫遇到失败，只登记进内存重试队列，立刻处理下一条；
- 每扫完一页（500 人），页尾集中补打一轮；
- 整批扫完，批尾再补一轮；
- 补打仍失败的，写入留痕表，供第二天的**轮次重试作业**从数据库推导失败清单继续翻盘。

轮次重试的关键设计：**失败清单不靠内存，而是从留痕表 SQL 推导**。作业中途被杀也无所谓，下次启动接着跑——留痕表本身就是持久化队列。

### 3. 两轮校对：跨天的一致性设计

核验结论要求「两轮独立送查、结果一致才可信」。但两轮**隔天分跑**（网关规定），跨进程一致性有三个坑，全部用机制堵死：

- **第二轮名单取自第一轮结果表**，而不是重新读名册——防止名册变动导致序号错位却静默出错；
- 第二轮**绝不 INSERT 新结果行**，只 UPDATE 第一轮的平行列——防止第二轮结论冒充第一轮；
- 启动前 `preflight` 前置校验：批次是否存在、第二轮是否跑在第一轮没跑完的批上、数据库结构是否符合预期，任何一个不满足直接退出。

### 4. 幂等与断点续传

- 结果表唯一键 + 「先 UPDATE 后 INSERT」的 upsert（Kingbase 对 `ON CONFLICT` 的支持与 MySQL 不一致，干脆不依赖）；
- 每条名册一个单调递增的序号，`max(seq_no)` 就是天然的续传锚点——中断后从锚点之后继续，不用重扫；
- 表名走配置常量拼接，支持 `_new` 后缀**整表切换**——目标库禁止 ALTER 时，零代码改动切到新结构表，旧表留作审计。

### 5. 不变量哨兵：宁可无法判定，不要假结论

有一条用真实事故换来的防线：某次网关超时，响应解析的兜底逻辑把空结果写成了「查无此人」——这是一个**错误的确定性结论**，比报失败严重得多。

修复方式是加一条不变量：`失败类型为空 但 命中数非法` 的响应，强制降级为 UNKNOWN。此后任何解析兜底都只能产生「无法判定」，永远不能产生假结论。

## 三、数据模型：四张表的证据链

| 表 | 角色 | 关键设计 |
|---|---|---|
| 批次台账表 | 一次跑批一行 | 计划/成功/失败/空值四格计数，起止时间 |
| 请求留痕表 | 每次调用一行 | 请求头/体、响应原文、错误码、失败类型；**一人×接口×轮次恰好一行**是不变量 |
| 重试明细子表 | 仅真重试过的调用写 | 逐次尝试值快照，报障时证据链完整 |
| 比对结果表 | 一人一行 | 两轮平行列、两轮一致性标记、逐接口结论 JSON、人工核查项 |

留痕的存储策略也很讲究：失败和命中存**全文**，成功但空结果只存 200 字符摘要——省 30% 存储，且空响应可逐字覆盖、不损证据。留痕里的认证头一律脱敏（前 6 位 + 长度）。

## 四、其他工程实践

- **熔断**：基准接口连续 10 条网络/限流失败即停机；各 C 系列接口独立熔断计数，基准接口正常不会掩盖其他接口的故障。
- **令牌治理**：OAuth2 令牌提前 300 秒刷新；收到 401 强刷一次并重打（每作业只允许刷一次，防止 401 风暴把 28 万次调用翻倍）；刷新失败进 30 秒冷却。
- **QPS 阶梯探测**：独立的探测作业按 1→2→5→10→20 并发压网关，输出 CSV，用数据定限流阈值而不是拍脑袋。
- **防误触**：不带模式参数启动只打印用法、退出码 2，一发请求都不会发。脚本层还有空环境变量护栏（空值会顶掉配置默认值 → 拦截）。
- **交付工程**：打包脚本做 CRLF 断言、MD5 清单、jar 内容断言（防止把没填凭据的包发出去）；目标机无 Maven/Docker，全部本机打包 + scp + 校验交付。

## 五、复盘

这个项目的价值不在技术栈多新，而在**把「不可靠外部依赖」的应对做成了体系**：失败分类是语言、分级重试是策略、留痕是证据链、熔断是保险丝、不变量哨兵是底线。跑批系统最怕的不是慢，而是**悄悄给出错误结论**——所有设计最终都服务于此。
