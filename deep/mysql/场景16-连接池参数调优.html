场景16：连接池参数调优（HikariCP）

2026-03-31mysql 系列约 5 分钟阅读MySQL

一、问题背景

连接池是应用访问 MySQL 的"水管"，参数直接影响高并发下的吞吐、排队与超时。本项目使用 HikariCP，演示不同连接池大小对高并发性能的影响及调优思路。

二、关键参数

参数 作用 调优要点
maximumPoolSize 最大连接数 过小→并发排队/超时；过大→浪费资源。经验公式 (核数*2 + 磁盘IO并发)，需 < MySQL max_connections 余量
minimumIdle 最小空闲连接 低峰时保留的连接，避免频繁建连；过高浪费
connectionTimeout 获取连接超时(ms) 排队超过此值抛异常，防止请求无限挂起
idleTimeout 空闲连接回收(ms) 需 < maxLifetime
maxLifetime 连接最大存活(ms) 避免复用超龄连接，需 < 数据库 wait_timeout
connectionTestQuery 连接有效性校验 高并发防拿到失效连接

三、演示接口

# 1. 查看当前主连接池配置
curl "http://localhost:8080/pool/config"

# 2. HikariCP 参数详解
curl "http://localhost:8080/pool/params"

# 3. 单池大小压测（并发50，持有连接10ms放大排队）
curl "http://localhost:8080/pool/bench?maxPoolSize=2&concurrency=50&total=3000&holdMs=10"
curl "http://localhost:8080/pool/bench?maxPoolSize=20&concurrency=50&total=3000&holdMs=10"

# 4. 多池大小对吞吐的影响对比（一次性跑 2/10/20/50）
curl "http://localhost:8080/pool/impact?concurrency=50&total=2000&holdMs=10"

四、实测结果（并发 50，持有连接 10ms）

池大小 QPS success avgWait maxWait p99
2 186 1932/2000（68 失败） 85ms 4880ms 5000ms
10 908 2000/2000 43ms 1466ms 755ms
20 1776 2000/2000 16ms 895ms 333ms
50 3831 2000/2000 1ms 105ms 67ms

结论： - 池过小（2）：高并发下 68 个请求失败（获取连接超时），吞吐仅 186，p99 高达 5s → 并发瓶颈。 - 池适中（20）：无失败，吞吐 1776，延迟明显下降。 - 池足够（50）：吞吐 3831（池2 的 20 倍），avgWait 仅 1ms，p99 67ms → 最优。

五、调优准则

  1. 先定位瓶颈再调参：看是连接等待/超时（池小）还是 MySQL CPU 高（池够但 SQL 慢），对症下药。
  2. 池大小匹配并发度：不是越大越好，过大浪费资源且 MySQL 连接数有限（max_connections）。
  3. 短连接 + 快事务 + 少等待：真正高并发靠业务 SQL 快、事务短、不持有连接，而非堆池大小。
  4. connectionTimeout 要合理：过大请求挂死、过小误杀偶发慢请求。
  5. maxLifetime < wait_timeout：防止连接被数据库超时回收后复用。
  6. 连接有效性校验：connectionTestQuery=SELECT 1 防高并发拿到失效连接。
  7. 多节点多数据源：分库/读写分离时每个数据源独立调优。

六、要点速览

连接池调优（HikariCP）：maximumPoolSize 不是越大越好，过小高并发排队/超时（实测池2吞吐186、68失败），适中（20）无失败 1776，足够（50）3831（20倍）且延迟极低。调优先定位瓶颈（连接等待/超时 vs MySQL CPU），池大小匹配并发度并 < max_connections，核心是短连接+快事务+少等待，而非堆池大小。connectionTimeout 防挂死、maxLifetime < wait_timeout 防复用失效连接、connectionTestQuery 防拿到失效连接。
