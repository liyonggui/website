# 场景1：连接池与超卖问题（四种扣减策略对比）

## 一、问题背景

高并发秒杀/抢购场景下，多个请求同时扣减同一商品的库存。若不加任何并发控制，会导致**超卖**（库存减为负数）；而错误的加锁策略又会带来性能损耗或死锁。

本场景在同一张 `t_stock` 表上，用相同并发量压测四种扣减策略，量化其**超卖率 / 成功数 / 吞吐 / 延迟**。

## 二、四种策略

### 1. `oversell` —— 先查后减（无锁，问题演示）

```sql
SELECT stock FROM t_stock WHERE product_no = ?;   -- 读到旧值
UPDATE t_stock SET stock = stock - ? WHERE product_no = ?;  -- 基于当前值递减
```

**先澄清一个常见误解**：这条 `UPDATE stock = stock - ?` 并不是"用旧值覆盖写"——存储引擎是基于**当前值**做原子递减的，多个线程并发执行也不会互相覆盖（不存在"最后写入者赢、扣减次数丢失"）。它真正的问题是：**WHERE 里没有 `stock >= ?` 条件，库存见底后请求会继续扣，把库存减成负数**（实测 `SKU-10001` 100 库存被扣成 -19）。

> 那"丢失更新"（lost update）什么时候出现？当**应用层**把"读旧值 → 减 1 → 整体写回"拆成两条语句时才会：`SET stock = 读到的旧值 - 1`，后一个请求拿前一个请求读到的旧值做计算，先到的扣减就被覆盖没了。本场景四种策略都不属于这一类——**超卖和丢失更新是两个不同的问题，别混成一个**。

### 2. `atomic` —— 原子条件更新（推荐，SQL 层保证）

```sql
UPDATE t_stock SET stock = stock - ?
WHERE product_no = ? AND stock >= ?;   -- 条件不满足则影响行数为 0
```

利用 InnoDB **行锁 + 条件判断**，在单条 UPDATE 内完成"检查库存 + 扣减"，天然原子，**杜绝超卖**。省掉的是**显式事务和重试**——注意行锁并没有消失（单条 UPDATE 同样要拿 InnoDB 行锁，与 pessimistic 同源），省的是 `BEGIN/COMMIT` 往返和应用层版本比对。

### 3. `pessimistic` —— 悲观锁（SELECT ... FOR UPDATE）

```sql
BEGIN;
SELECT stock FROM t_stock WHERE product_no = ? FOR UPDATE;  -- 行锁，阻塞其它写
UPDATE t_stock SET stock = stock - ? WHERE product_no = ?;
COMMIT;
```

事务内加**排他行锁**，其它事务必须等待锁释放，保证读改写一致。代价是**并发度受限、锁等待增加**，高并发下吞吐下降明显。

### 4. `optimistic` —— 乐观锁（版本号）

```sql
SELECT stock, version FROM t_stock WHERE product_no = ?;
UPDATE t_stock SET stock = stock - ?, version = version + 1
WHERE product_no = ? AND version = ? AND stock >= ?;
-- 影响行数 = 0 表示版本冲突，需重试
```

不加锁，通过**版本号比对**判断是否被并发修改，冲突时由应用层重试。适合**读多写少**、冲突不频繁的场景；冲突率高时重试开销会放大。

## 三、压测结果（实测）

> 压测方式：对 `SKU-10002`（单行热点）打满 1000 次扣减，并发 20，每种模式前重置库存为 1000。
> 运行脚本：`loadtester/run-single.ps1`（单模式） / `run-benchall.ps1`（四种模式一次性对比）。

| 策略 | 成功 | 冲突/失败 | QPS | P50 | P95 | P99 | 最终库存 | 结论 |
|------|------|-----------|-----|-----|-----|-----|----------|------|
| oversell | 1000 | 0 | **1126** | 153 | 197 | 212 | 0（可再扣为负） | ❌ 超卖，不可用 |
| optimistic（重试5） | 261 | **739 冲突** | 328 | 64 | 88 | 124 | 739 | ⚠️ 单行高冲突，正确性差 |
| pessimistic | 1000 | 0 | 114 | 171 | 209 | 226 | 0 | ✅ 正确，锁等待 |
| **atomic** | **1000** | **0** | 103 | 164 | 321 | 679 | **0** | ✅ **推荐** |

### 关键结论

1. **oversell 最快（1126 QPS）但超卖**：不检查库存下限，一旦见底继续扣就变负数（实测 `SKU-10001` 100 库存被扣成 **-19**）。**但它的问题只是"错"，不是"慢"——正确性不满足时，吞吐数字没有参考价值。**
2. **optimistic 在单行热点下冲突率高达 74%（739/1000）**：所有请求竞争同一行，版本号频繁自增，即使重试 5 次仍大量失败，最终只成功 261 次。**乐观锁不适合高并发单行热点**。
3. **atomic 与 pessimistic 均正确（0 超卖、0 冲突）**：都受限于单行 InnoDB 行锁串行化，性能相当（~100 QPS）。
4. **`atomic` 是正确方案里综合最简的基线**：单条 `UPDATE ... WHERE stock >= n` 原子完成"检查 + 扣减"，无需显式事务、无需重试。注意两点：① 它**不是"无锁"**——同样受 InnoDB 行锁串行化，单行热点下与 pessimistic 吞吐相当（本实验 103 vs 114 QPS，差异在单行串行化噪声范围内）；② "性能最优"要说清条件——**只在正确方案内部比较**，且随热点分布、事务边界、测试环境变化。

### 补充：多行分布式压测（消除单行热点干扰）

单行热点会掩盖各模式的真实性能差异（都被行锁串行化），故用 50 个商品、请求随机分布到各行的方式复测（并发 30，每模式 20000 请求）：

| 策略 | 成功 | 冲突/失败 | QPS | P50 | P95 | P99 | 结论 |
|------|------|-----------|-----|-----|-----|-----|------|
| oversell | 20000 | 0 | **2289** | 10 | 25 | 43 | ❌ 超卖，不可用 |
| **atomic** | **20000** | **0** | **2204** | **10** | **28** | **49** | ✅ 正确方案中吞吐最高 |
| optimistic | 19856 | 144 冲突(0.7%) | 2054 | 11 | 31 | 52 | ✅ 冲突率低，读多写少适用 |
| pessimistic | 20000 | 0 | 1765 | 13 | 35 | 62 | ✅ 正确，事务+锁开销略大 |

**结论**：
- 多行分布下 `atomic`（2204 QPS）与 `oversell`（2289 QPS）几乎持平，但 **atomic 正确**（0 超卖），**oversell 不可用**。在三个正确方案里 atomic 吞吐最高（2204 vs optimistic 2054 vs pessimistic 1765）。
- `optimistic` 在多行分布下冲突率骤降至 **0.7%**（vs 单行热点 74%），印证其**适合多行、读多写少**，不适合单行热点。
- `pessimistic` 因每个请求要 `BEGIN + FOR UPDATE + COMMIT` 事务开销，吞吐最低（1765 QPS）。
- **`atomic` 是"保证正确 + 代码最简"的基线方案**，生产首选；但"唯一解"谈不上——optimistic 在多行分布下冲突率仅 0.7%，读多写少的场景同样可用，选型看冲突率与重试成本。

## 四、生产建议

1. **首选 `atomic` 条件更新**：单条 SQL 原子扣减，无显式事务、无重试；**行锁仍在**（与悲观锁同源），本实验中两者吞吐相当（单行 103 vs 114 QPS），多行分布下 atomic 在正确方案中领先。
2. 悲观锁适合**必须依赖锁保证一致性**且并发不高的写场景；注意控制事务时长，避免长事务持锁。
3. 乐观锁适合**读多写少**；冲突率高时应考虑 `atomic` 或消息队列削峰。
4. 无论哪种策略，最终都要配合**唯一约束**（如订单号唯一）兜底防重复。

## 五、要点速览

> **超卖问题**：高并发下先查后减（无条件下扣减）会把库存扣成负数。用 `UPDATE ... WHERE stock >= n` 条件更新，借助 InnoDB 行锁保证原子性，单条 SQL 杜绝超卖；正确方案中它的综合成本最低（本实验多行分布吞吐第一、代码最简）。对比悲观锁（FOR UPDATE，并发受限）和乐观锁（版本号+重试，适合读多写少）。**注意**：超卖 ≠ 丢失更新——前者是缺条件下调，后者是应用层旧值回写。
