补测B6：深分页查询优化（LIMIT 深翻页 / 游标分页）

补测B6：深分页查询优化（LIMIT 深翻页 / 游标分页）

一、问题背景

高频慢查询源头：LIMIT 1000000,20 深分页。MySQL 需扫描并丢弃前 100 万行，offset 越大越慢，是列表页/管理后台最常见的慢查询。

二、深分页原理

-- 深分页慢：先扫描 offset+size 行，再丢弃前 offset 行
SELECT * FROM t_page ORDER BY id LIMIT 400000, 20;   -- 扫描 40 万行丢弃

-- 游标分页(keyset)快：基于主键/索引定位，只扫一页
SELECT * FROM t_page WHERE id > ? ORDER BY id LIMIT 20;  -- 走主键索引只扫一页
  • 深分页：LIMIT 大offset，扫描量 = offset + size，offset 越大越慢（线性增长）。
  • 游标分页：WHERE id > last_id，基于主键索引定位，无论翻多深只扫一页。
  • 延迟关联：子查询先取 id（走索引），再 JOIN 取全字段，减少深分页回表。

三、演示接口

# 1. 初始化大数据量（50万行）
curl "http://localhost:8080/page/init?rows=500000"

# 2. 深分页 LIMIT 400000,20（慢，扫描40万行丢弃）
curl "http://localhost:8080/page/deep?offset=400000&size=20"

# 3. 游标分页 WHERE id>400000 LIMIT 20（快）
curl "http://localhost:8080/page/cursor?lastId=400000&size=20"

# 4. 性能对比（多个深度）
curl "http://localhost:8080/page/bench?pages=5&size=20"

# 5. 状态
curl "http://localhost:8080/page/status"

四、实测结果（50万行）

环节 耗时
深分页 LIMIT 400000,20 149 ms（扫描40万行丢弃）
游标分页 WHERE id>400000 15 ms（主键定位只扫一页）
bench（5个深度平均） 深分页 93.6ms vs 游标 3.0ms，快 31.2 倍

结论：深分页 offset 越大扫描+丢弃越多，线性变慢；游标分页基于主键索引恒定快。50 万行下游标分页快约 31 倍，数据量越大差距越明显。

五、优化方案

  1. 游标分页（keyset）：WHERE id > last_id（或 create_time < 上一页末尾），走索引只扫一页，最推荐。
  2. 延迟关联：SELECT * FROM t JOIN (SELECT id FROM t ORDER BY id LIMIT ?,?) d ON t.id=d.id，先索引取 id 再回表。
  3. 覆盖索引：查询字段全部在索引内，避免回表。
  4. 禁止深翻页：前端限制页数/改用"加载更多"，避免用户翻到万级页。
  5. 业务折中：只允许查看前 N 页，超过则提示用条件筛选。

六、踩坑记录（bench 缓存失真）

最初用 20 万行数据 bench 对比，因数据全在 InnoDB buffer pool 缓存，深分页扫描也在内存完成，平均耗时被稀释到个位数 ms，深分页/游标差异失真。改用 50 万行 + 大 offset（400000）深翻后差异显著（深分页 149ms vs 游标 15ms）。

七、面试简述

深分页优化：LIMIT 大offset 扫描并丢弃大量行，offset 越大越慢。实测 50 万行：深分页 offset=400000 耗时 149ms，游标分页 WHERE id>last_id 仅 15ms，快约 31 倍。优化：游标分页（keyset 走索引）、延迟关联（先取 id 再回表）、覆盖索引、禁止深翻页。注意：小数据量+缓存会掩盖差异，需用大数据量深 offset 验证。
