场景 18 · 锁等待与死锁监控治理

2026-04-02mysql 系列约 5 分钟阅读MySQL锁
场景实测 · 主文单场景完整链路：问题 → 排查 → 修复 → 实测数据。

一、问题背景

高并发下，多个事务争用同一行/间隙锁会产生锁等待（事务串行化、吞吐下降），更严重的是死锁（事务互相持有对方需要的锁，死循环等待）。治理需要"制造 → 监控 → 诊断 → 治理"闭环。

二、核心概念

  • 锁等待：事务 A 持锁，事务 B 等待同一锁，直到 A 释放或超时（innodb_lock_wait_timeout）。
  • 死锁：事务 A 锁行1 等行2，事务 B 锁行2 等行1，互相等待。InnoDB 检测到死锁后自动回滚其中一个事务（错误码 1213），其余继续。

三、演示接口

# 1. 锁相关参数
curl "http://localhost:8080/lock-monitor/params"

# 2. 制造锁等待（事务 A 持锁，事务 B 等待）
curl "http://localhost:8080/lock-monitor/create-wait?holdMs=1500&waitMs=3000"

# 3. 制造死锁（InnoDB 自动回滚一个事务）
curl "http://localhost:8080/lock-monitor/create-deadlock"

# 4. 锁等待监控概览（sys.innodb_lock_waits：谁阻塞谁）
curl "http://localhost:8080/lock-monitor/status"

# 5. 当前事务与锁明细（information_schema.innodb_trx + performance_schema.data_locks）
curl "http://localhost:8080/lock-monitor/current"

# 6. 治理方案
curl "http://localhost:8080/lock-monitor/governance"

四、实测结果

1. 锁参数

innodb_lock_wait_timeout = 50（秒）
innodb_deadlock_detect   = ON（自动检测死锁）
innodb_deadlocks         = 有死锁记录（SHOW ENGINE INNODB STATUS 检测）

2. 制造锁等待

事务 A 持锁 1500ms，事务 B 等待 1502ms 后获得锁。 → 并发下锁等待会串行化，需监控定位阻塞者。

3. 制造死锁

事务 A 成功，事务 B 返回：

死锁回滚: Deadlock found when trying to get lock; try restarting transaction

→ InnoDB 检测到死锁后自动回滚一个事务（错误码 1213），应用需捕获并重试。

4. 监控诊断

  • sys.innodb_lock_waits：当前锁等待关系（waiting_pid 被 blocking_pid 阻塞）
  • information_schema.innodb_trx：当前活动事务状态
  • performance_schema.data_locks：当前数据锁明细（表/索引/锁类型/模式）

五、治理方案

  1. 监控定位：performance_schema.data_locks + sys.innodb_lock_waits 找阻塞者/被阻塞者。
  2. 减小锁粒度：用唯一索引/主键精确命中，避免间隙锁/全表锁。
  3. 缩短事务：事务内只做必要操作，避免慢查询/外部调用占锁。
  4. 固定加锁顺序：多行更新按主键升序，避免交叉等待死锁。
  5. 控制并发：热点行削峰，队列/乐观锁代替悲观锁。
  6. 超时兜底：调小 innodb_lock_wait_timeout，快速失败避免长等待。

六、要点速览

锁等待与死锁治理：锁等待=并发争用串行化（A 持锁 B 等待），死锁=事务互相持有对方所需锁、InnoDB 自动检测回滚一个（错误码 1213，需应用重试）。监控用 performance_schema.data_locks + sys.innodb_lock_waits 定位阻塞者/被阻塞者。治理核心：减小锁粒度（主键/唯一索引命中）、缩短事务、固定加锁顺序（防死锁）、控制并发、innodb_lock_wait_timeout 超时兜底。
