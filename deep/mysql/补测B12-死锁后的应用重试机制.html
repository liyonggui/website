补测B12：死锁后的应用重试机制

2026-05-10mysql 系列约 4 分钟阅读MySQL锁

一、问题背景

死锁（错误码 1213）时 InnoDB 会回滚一个事务，业务不处理则请求失败。高并发下死锁/锁等待是正常现象，应用需捕获 1213/1205 + 自动重试，否则业务失败率高。

二、重试原理

并发转账（反向更新两行）
    │
    ├── 死锁(1213) / 锁等待超时(1205)
    │       │
    │       └── 捕获 → 回滚 → 指数退避 → 自动重试(最多N次)
    │
    └── 成功提交
  • 捕获：e.getErrorCode()==1213(死锁) 或 40001。
  • 重试：回滚后按指数退避重试，直到成功或达最大次数。
  • 对比：不重试（失败率高）vs 重试（成功率显著提升）。

三、演示接口

# 1. 初始化临界区资源（两行 id=1,2）
curl "http://localhost:8080/retry/init?balance=100000"

# 2. 触发死锁（两个事务反向锁两行 → 一方 1213）
curl "http://localhost:8080/retry/deadlock"

# 3. 死锁自动重试（捕获 1213 指数退避重试）
curl "http://localhost:8080/retry/retry?maxRetries=3"

# 4. 并发转账：不重试 vs 重试 成功率对比
curl "http://localhost:8080/retry/bench?concurrency=20&total=2000"

# 5. 状态
curl "http://localhost:8080/retry/status"

四、实测结果（并发20，总量2000 转账）

方式 失败数 成功率
不重试 1157/2000 42.2%
重试（最多3次） 674/2000 66.3%

核心：并发反向转账产生大量锁冲突，不重试失败 1157 次（成功率42.2%），重试后失败降到 674 次（成功率66.3%）。重试机制把死锁/锁等待导致的失败大幅降低。

五、重试框架要点

  1. 只重试可恢复错误：死锁(1213)/锁等待超时(1205)，不重试业务错误（如参数错）。
  2. 指数退避：20ms → 40ms → 80ms，避免重试风暴加剧竞争。
  3. 限制次数：最大重试 N 次，防止无限重试。
  4. 幂等：重试的事务必须幂等（用唯一键/版本号），防止重复扣减。
  5. 随机抖动：重试间隔加随机，避免多线程同步重试。
  6. 监控：记录重试次数、死锁率，优化 SQL 减少死锁。

六、踩坑记录（编译错误）

Lambda 内 CountDownLatch.await() 抛 InterruptedException，但 catch 只捕获 SQLException，导致编译报错 Unhandled InterruptedException，应用启动失败。修复：lambda 内 catch Exception。注意 Maven 增量编译可能用旧 class 掩盖问题，需 clean 完整编译。

七、要点速览

死锁重试机制：死锁(1213)是正常现象，应用需捕获+自动重试。实测并发20转账2000：不重试失败1157(42.2%)，重试后失败674(66.3%)。要点：只重试死锁/锁等待、指数退避、限次数、幂等、随机抖动、监控死锁率。踩坑：lambda 内 await 抛 InterruptedException 需 catch Exception。
