# 场景3：悲观锁 vs 乐观锁

## 一、问题背景

高并发写场景下，保证数据一致性有两种主流方案：
- **悲观锁**：`SELECT ... FOR UPDATE` 先锁定数据行，阻塞其它写，再读改写。依赖 InnoDB 行锁。
- **乐观锁**：不加锁，通过 `version` 版本号比对，冲突时由应用层重试（CAS 思路）。

两种方案在**吞吐、延迟、冲突率、死锁风险**上有本质差异。本场景用并发压测 + 锁行为演示量化对比。

## 二、悲观锁与乐观锁实现

### 悲观锁（`SELECT ... FOR UPDATE`）

```sql
SET autocommit=0;
SELECT stock FROM t_stock WHERE id = ? FOR UPDATE;  -- 记录锁，阻塞其它写
UPDATE t_stock SET stock = stock - ? WHERE id = ?;
COMMIT;
```

### 乐观锁（版本号 CAS）

```sql
SELECT stock, version FROM t_stock WHERE product_no = ?;
UPDATE t_stock SET stock = stock - ?, version = version + 1
WHERE product_no = ? AND version = ? AND stock >= ?;
-- 影响行数 = 0 说明版本冲突，需重试
```

## 三、锁行为演示

### 1. 悲观锁锁等待（`/lock/wait`）

事务 A 持有行锁 800ms，事务 B 尝试 `FOR UPDATE` 同一行，实测：

| 项目 | 值 |
|------|-----|
| A 持锁时长 holdMs | 800ms |
| B 实际等待 waitMs | **801ms** |

**结论**：B 的 `FOR UPDATE` 被 A 的行锁阻塞，等待时长 ≈ A 的持锁时长。悲观锁通过阻塞保证"读改写"原子性，代价是并发请求排队。

### 2. 死锁演示（`/lock/deadlock`）

事务 A 锁定行 X，事务 B 锁定行 Y，然后 A 再要 Y、B 再要 X，形成循环等待：

```
事务A: 锁 idX → 要 idY
事务B: 锁 idY → 要 idX
```

实测结果：
- 事务 A：**deadlock:1213**（InnoDB 死锁检测回滚）
- 事务 B：**committed**（成功提交）

**结论**：InnoDB 通过**死锁检测**自动回滚代价较小的一个事务（错误码 1213），让另一个继续，避免无限等待。

> 注意：演示必须用**主键 id 加锁**（记录锁 `X,REC_NOT_GAP`）才能可靠触发死锁。若用非唯一索引等值查询，REPEATABLE READ 下会加 **Next-Key 间隙锁**（`X,GAP`），而**间隙锁不互相阻塞**，导致"看似死锁却不会死锁"。

## 四、并发度性能对比（实测 `/lock/compare`）

多行分布式（100 个商品，消除单行热点），并发 50，每模式 20000 请求：

| 模式 | success | fail | conflict | deadlock | QPS | P50 | P95 | P99 | avg |
|------|---------|------|----------|----------|-----|-----|-----|-----|-----|
| pessimistic | 20000 | 0 | 0 | 0 | 2478 | 16 | 40 | 68 | 19.6 |
| optimistic | 10000 | **10000** | **4934** | 0 | **4145** | 16 | 50 | 92 | 21.5 |

### 关键结论

1. **乐观锁吞吐更高（4145 vs 2478 QPS，快 67%）**：无锁等待，高并发下不排队，QPS 更高。
2. **但乐观锁正确性差**：版本冲突导致 **4934 次冲突**、**10000 个请求最终失败**（重试 3 次仍失败）。并发越高、冲突越多。
3. **悲观锁可靠**：20000 全部成功，0 冲突，0 死锁；延迟稳定（P99 68ms），但吞吐受锁等待限制。

## 五、选型建议

| 场景 | 推荐 | 原因 |
|------|------|------|
| 高并发写同一资源、冲突频繁 | **悲观锁**（或原子 UPDATE） | 冲突少、可靠，锁等待换取一致性 |
| 读多写少、冲突不频繁 | **乐观锁** | 无锁开销、吞吐高，冲突率低时重试代价小 |
| 简单扣减/状态机 | **原子 UPDATE**（`WHERE ... AND 条件`） | 单条 SQL 原子，无锁等待，最优 |

**核心**：
- **乐观锁的吞吐优势只在冲突率低时成立**；冲突率 > 一定阈值时，重试风暴反而拖垮系统。
- **悲观锁的死锁风险**可通过固定加锁顺序、缩短事务时长规避。
- 生产中最优往往是**原子 UPDATE**（场景1已证明），悲观/乐观锁用于更复杂的读改写逻辑。

## 六、要点速览

> **悲观锁 vs 乐观锁**：悲观锁 `FOR UPDATE` 先锁后改，靠 InnoDB 行锁保证一致性，高并发下阻塞排队（实测锁等待 = 持锁时长），可触发死锁（InnoDB 自动回滚一个事务，错误码 1213）；乐观锁用 version CAS，无锁等待吞吐高，但高并发冲突率飙升导致大量失败（实测冲突 4934 次、失败 10000）。选型看冲突率：冲突高用悲观锁/原子 UPDATE，冲突低用乐观锁。
