# 场景6：读写分离与主从延迟

## 一、问题背景

在 MySQL 高并发场景下，**读多写少**是常态。单库既要扛读又要扛写，容易出现读压力拖垮主库、写性能下降。生产常用**读写分离**：**写走主库、读走从库**，把读压力分摊到只读副本上。

但读写分离引入一个新问题——**主从延迟**：主库写入后，从库需要经过复制（binlog → relay log → SQL apply）才能同步，这个时间窗口内从库读到的是**旧数据**（最终一致）。若业务强依赖"写后立即可见"（如下单后立即查订单），延迟会造成数据不一致。

本场景搭建**1 主 1 从**复制拓扑，量化主从延迟，并演示强一致 vs 最终一致的差异。

## 二、主从复制拓扑搭建

- **主库 `mysql`**（server-id=1）：开启 binlog（ROW 格式）+ GTID，创建复制用户 `repl`
- **从库 `mysql-slave`**（server-id=2，端口 3307）：`read_only=ON`，冷启动时用 `mysqldump` 从主库拉全量，再建立 **GTID 自动定位复制**（`MASTER_AUTO_POSITION=1`）
- **连接方式**：`Source_Host=mysql:3306`，`Get_Source_public_key=1`（解决 caching_sha2_password 认证的 RSA 公钥交换）

复制状态验证：

```
Replica_IO_Running: Yes      # IO 线程：从主库拉 binlog
Replica_SQL_Running: Yes     # SQL 线程：应用 relay log 到从库
Seconds_Behind_Source: 0     # 主从延迟秒数
Auto_Position: 1             # GTID 自动定位
```

## 三、实测结果

### 1. 主从复制状态（`/replication/status`）

通过"**主库写 + 从库读**"的业务验证方式判定复制健康（不依赖 performance_schema 的 JDBC 会话差异）：

| 项目 | 值 |
|------|-----|
| masterWriteOk | true（写主库成功） |
| replicaVisible | true（从库能读到刚写入数据） |
| replicaDelayMs | **6ms**（从库可见延迟） |
| Seconds_Behind_Source | 0 |
| replicaHealthy | true（复制正常） |

**结论**：写入主库后约 6ms，从库即可读到，复制链路健康。

### 2. 主从延迟量化（`/replication/delay`）

写主库后高频轮询从库，测量"从库多久能读到"：

| 项目 | 值 |
|------|-----|
| masterWriteMs | 7ms（写主库耗时） |
| replicaDelayMs | **1ms**（从库可见延迟） |
| masterVisibleImmediately | true（读主库即时可见，强一致） |

**结论**：本地 1 主 1 从（同 Docker 网络）延迟极低，约 1ms 级；但真实跨机房/高负载下延迟可达数十~数百 ms，此时"写后立即读从库"会读到旧数据。

### 3. 强一致 vs 最终一致（`/replication/consistency`）

30 轮写主库后，分别立即读主库、立即读从库、延迟 100ms 再读从库：

| 读路径 | 命中率 |
|------|------|
| 读主库（强一致） | **30/30**（100% 即时可见） |
| 读从库（立即） | 30/30 |
| 读从库（延迟 100ms） | 30/30 |

**结论**：读主库 100% 强一致；读从库在低延迟复制下也基本即时可见。**关键认知**：主从延迟是"最终一致"的来源——在延迟窗口内读从库会读到旧值。本地延迟极低导致窗口不可见，但**生产跨机房/高负载下窗口显著**，业务需权衡：强一致场景读主库，可容忍最终一致场景读从库。

### 4. 读写分离读吞吐对比（`/replication/bench`）

并发 50、各 2 万次读，对比读从库与读主库：

| 读路径 | QPS | P99 |
|------|------|------|
| 读从库（replica） | 11641 | 52ms |
| 读主库（master） | 15810 | 45ms |

**结论**：从库能独立承载高并发读（QPS 破万）。读写分离的核心价值是**把读压力从主库分流**，让主库专注写，整体吞吐与稳定性更高。

## 四、生产避坑准则

1. **写必须走主库、读走从库**：通过数据源路由（如 ShardingSphere / MyBatis 插件 / 双数据源）按读写分离
2. **强一致读走主库**：下单后立即查订单、支付回调等"写后即读"场景，读主库避免读到旧数据
3. **容忍最终一致读走从库**：列表、报表、统计等非关键读可走从库，摊薄主库压力
4. **监控主从延迟**：`SHOW REPLICA STATUS` 的 `Seconds_Behind_Source` 超过阈值需告警；延迟过大时读走主库兜底
5. **从库只读**：从库 `read_only=ON`，防止误写破坏复制
6. **GTID 复制**：用 `MASTER_AUTO_POSITION=1` 免去手动记录 binlog 位置，主从切换更简单

## 五、面试简述

> **读写分离与主从延迟**：搭建 1 主 1 从，主库开 binlog+GTID，从库 `mysqldump` 拉全量后 `MASTER_AUTO_POSITION=1` 建立复制。实测写主库后从库约 1~6ms 可见，`Replica_IO_Running/SQL_Running` 均 Yes；读主库 100% 强一致，读从库为最终一致（延迟窗口内可能读旧值）。读写分离把读压力分流到从库（并发 50 下从库读 QPS 超 1 万），但引入主从延迟——强一致场景读主库，可容忍最终一致场景读从库，并监控 `Seconds_Behind_Source`。
