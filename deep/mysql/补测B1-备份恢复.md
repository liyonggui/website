# 补测B1：备份恢复（binlog PITR / 误删误更新恢复）

## 一、问题背景

高并发治理除了"读写/一致性"，还需**数据保底**：线上误删/误更新、硬件故障时的数据恢复能力。基于 MySQL binlog 的**时间点恢复（PITR）**是核心兜底方案。

## 二、PITR 原理

```
全量备份(定期 mysqldump) + binlog增量(记录每次DML) = 恢复到任意时间点
     │                          │
     └──> 恢复到误操作前时间点，找回被删/被改数据
```

- **全量备份**：mysqldump / Xtrabackup，导出某一时刻数据快照。
- **binlog 增量**：ROW 格式记录每次 INSERT/UPDATE/DELETE，含位置(Pos)与 GTID。
- **PITR**：`mysqlbinlog --stop-datetime` 重放 binlog 到误操作前，恢复数据。
- **RPO** = 备份频率与 binlog 保留期（本项目 `binlog_expire_logs_seconds=600`）。

## 三、演示接口

```bash
# 1. 初始化演示数据（1万账号）
curl "http://localhost:8080/backup/init?rows=10000"

# 2. 全量备份（逻辑快照，等价 mysqldump，记录 binlog 位置）
curl "http://localhost:8080/backup/full-backup"

# 3. 模拟误删/误更新事故
curl "http://localhost:8080/backup/simulate-damage?delRows=3000"

# 4. binlog 事件定位（SHOW BINLOG EVENTS，看误操作位置）
curl "http://localhost:8080/backup/binlog?limit=10"

# 5. PITR 恢复（基于全量备份恢复到事故前）
curl "http://localhost:8080/backup/pitr-restore"

# 6. 状态概览
curl "http://localhost:8080/backup/status"
```

## 四、实测结果

| 环节 | 结果 |
|------|------|
| 初始化 | 10000 行 |
| 全量备份 | 10000 行，binlogFile=`mysql-bin.000005` |
| 模拟误删 | beforeRows=10000 → deletedRows=3000 → afterRows=**7000** |
| **PITR 恢复** | **10000 行**（数据全部找回） |

**binlog 事件定位**（SHOW BINLOG EVENTS）：正确列出 Gtid/Query 事件与位置(Pos)，可定位误操作点。

## 五、如何定位误操作

> **定位 → 恢复 全流程速览：**
> ```
> 发现异常(数据少了/被改) 
>   → ① 看 binlog 当前文件位置( SHOW BINARY LOG STATUS )
>   → ② 用 SHOW BINLOG EVENTS / mysqlbinlog 过滤出误操作的 时间点 + 位置(Pos) + GTID
>   → ③ 确定"误操作前"的恢复点( --stop-datetime / --stop-position )
>   → ④ 全量备份恢复 + binlog 重放到恢复点( 方案A ) 或 单独回捞被删行( 方案B/C )
>   → ⑤ 恢复后核对行数与业务值
> ```

线上发现数据被误删/误更新后，第一要务是**精确定位"误操作发生在哪个时间点 / binlog 哪个位置"**，才能确定恢复到哪一刻。

### 1. 发现异常
```sql
-- 业务反馈数据少了 / 金额不对 → 先看当前数据与最近状态
SELECT COUNT(*) FROM t_pitr;                    -- 行数骤减 → 疑似误删
SELECT * FROM t_pitr WHERE balance = 0 LIMIT 5; -- 大量余额清零 → 疑似误更新
```

### 2. 查看当前 binlog 文件与位置
```sql
-- MySQL 8.4 用 SHOW BINARY LOG STATUS（旧名 SHOW MASTER STATUS 已废弃）
SHOW BINARY LOG STATUS;   -- 返回 File: mysql-bin.000005, Position: 1099539
```

### 3. 按时间 / 按表定位 binlog 事件
```sql
-- 列出某 binlog 文件的所有事件，按 Pos 顺序看 DML
SHOW BINLOG EVENTS IN 'mysql-bin.000005';

-- 更精准：用 mysqlbinlog 过滤指定库表 + 时间段，定位误操作的 GTID 和位置
mysqlbinlog --base64-output=decode-rows -v \
  --start-datetime='2026-08-19 12:37:00' --stop-datetime='2026-08-19 12:38:00' \
  mysql-bin.000005 | grep -A3 't_pitr'
```

### 4. 判断"误操作前"的时间点 / 位置
- **时间点**：误操作语句的 `SET TIMESTAMP=...` / 事务开始时间的前一刻，即 `--stop-datetime`。
- **位置**：误操作事务前的 `Pos`（事件序号的上一事件位置），即 `--stop-position`。
- **GTID**：误操作事务的 GTID 序号 -1。

### 5. 本项目演示的定位
接口 `/backup/binlog` 内部用 `SHOW BINLOG EVENTS` 展示事件及 `Pos`，对应上述第 3 步的定位动作：
```
pos: 1098771  event: Query  info: CREATE TABLE ...   -- 误操作前的正常 DDL
pos: 1099156  event: Gtid   info: SET @@SESSION.GTID_NEXT='...:185255'
```

## 六、如何恢复（PITR 具体流程）

恢复核心 = **先用全量备份恢复出事故前快照，再用 binlog 重放到"误操作前一刻"**。

### 方案 A：恢复到最近一次全量备份 + binlog 重放到误操作前（推荐，RPO 最小）
```bash
# 1. 全量备份恢复到临时库/原库（先还原最近一次全量备份）
mysql -uroot -proot mysql_bench < backup_full.sql

# 2. binlog 重放：从全量备份的 binlog 位置，重放到误操作前时间点
mysqlbinlog --start-position=<全量备份时记录的Position> \
  --stop-datetime='2026-08-19 12:37:10' \
  mysql-bin.000005 | mysql -uroot -proot mysql_bench
```
> 关键：`--start-position` 取**全量备份那一刻**记录的 binlog 位置（本项目 `/backup/full-backup` 返回 `binlogPosition`），`--stop-datetime` 取**误操作前**时间点。

### 方案 B：仅找回被误删的数据（不整体回滚，风险小）
```sql
-- 1. 从 binlog 逆向解析出误删的数据（mysqlbinlog 过滤 DELETE，翻转成 INSERT）
mysqlbinlog --base64-output=decode-rows -v --stop-position=<误操作Pos> mysql-bin.000005 \
  | grep -A3 '### DELETE FROM t_pitr'    -- 找到被删的每一行

-- 2. 手动把被删行补插回原表（或脚本批量 INSERT）
INSERT INTO t_pitr (id, acct_no, balance, remark, create_time) VALUES (...);
```

### 方案 C：误更新恢复（把错误值改回）
```sql
-- 从 binlog 解析出 UPDATE 前的旧值，生成 UPDATE 回滚语句
mysqlbinlog --base64-output=decode-rows -v mysql-bin.000005 \
  | grep -B3 '### SET'   -- 每行显示旧值(before) / 新值(after)
-- 用 before 值反写 UPDATE 回滚
```

### 本项目演示的恢复（方案 A 简化版）
接口 `/backup/pitr-restore` 用内存中的全量备份快照恢复到事故前：
```
模拟误删: 10000 → 7000
PITR恢复: 10000（数据全部找回）
```

### 恢复操作注意事项
1. **先备份现场**：恢复前先导出当前错误数据，防止二次破坏。
2. **只读维护**：恢复期间暂停写入（`SET GLOBAL read_only=ON`），避免新数据污染。
3. **逐条核对**：恢复后比对行数与关键业务值（余额/状态）。
4. **双写验证**：恢复期间用临时库演练，确认无误再对线上执行。
5. **binlog 保留期**：`binlog_expire_logs_seconds` 决定了能恢复多早，需 ≥ 全量备份周期，否则备份后到误操作间的 binlog 已过期无法重放。

## 七、工程要点

1. **定期全量备份**：mysqldump 或 Xtrabackup，配合 cron/定时任务。
2. **binlog 必须开启**：`log_bin=ON` + ROW 格式，是 PITR 的前提。
3. **binlog 保留期**：`binlog_expire_logs_seconds` 决定可恢复到多早，需与备份频率匹配。
4. **恢复流程**：全量备份恢复 + `mysqlbinlog` 重放到误操作前时间点（`--stop-datetime` / `--stop-position`）。
5. **验证备份有效性**：定期做恢复演练，确保备份可用（防"纸面备份"）。
6. **生产用 MySQL8.4**：`SHOW MASTER STATUS` 已改名 `SHOW BINARY LOG STATUS`，binlog 事件用 `SHOW BINLOG EVENTS`。

## 八、要点速览

> **备份恢复（PITR）**：数据安全兜底。全量备份（mysqldump/Xtrabackup）+ binlog 增量 + 时间点恢复，可把误删/误更新恢复到任意时间点。RPO 取决于备份频率与 binlog 保留期（binlog_expire_logs_seconds）。实测误删 3000 行后 PITR 恢复 10000 行全部找回。要点：binlog 必须 ON + ROW 格式、定期备份、恢复演练验证备份有效性。MySQL8.4 中 `SHOW MASTER STATUS` 改名 `SHOW BINARY LOG STATUS`。
