写入路径对比：单体 MySQL 批量 vs 本地磁盘追加

2026-03-08mysql 系列约 6 分钟阅读MySQL
对比实测两种方案的对比实测，结论边界明确。

一、问题背景

同样的数据写入，两条线路性能差异巨大： - 线路1：单体 MySQL 批量写入（JDBC batch + rewriteBatchedStatements，落 InnoDB）。 - 线路2：直接追加写入本地磁盘文件（顺序 append）。

对比两者吞吐，并加大并发测拐点（吞吐不再随并发提升的临界点）。

二、原理

线路 写入路径 主要开销
MySQL 批量 连接池 → SQL → 事务 → redo/binlog → 索引 → 刷盘 网络、事务、redo 刷盘、B+树索引、锁竞争
磁盘追加 内存 buffer → 顺序 append 文件 顺序写，几乎无额外开销
  • 磁盘顺序追加利用顺序 IO，极快（可达百万行/s）。
  • MySQL 需保证事务持久性（redo）、索引维护、主从一致，开销大，且并发增大到一定程度后因连接池/锁/刷盘瓶颈出现拐点。

三、演示接口

# 初始化（清空测试表与磁盘目录）
curl "http://localhost:8080/write-compare/init"

# 对比压测：总行数 / 并发 / 批量大小
curl "http://localhost:8080/write-compare/compare?total=100000&concurrency=8&batchSize=500"

# 拐点扫描：每线程行数 / 最大并发 / 批量大小
curl "http://localhost:8080/write-compare/scale?perThreadRows=50000&maxConcurrency=50&batchSize=500"

四、实测结果

基础对比（10 万行，并发 8，batch 500）

线路 吞吐
MySQL 批量 120918 行/s
磁盘追加 1694915 行/s（169 万行/s）

磁盘快约 14 倍（顺序写 vs 事务+日志+索引+刷盘）。

并发对比（行/s）——找拐点

并发 MySQL 批量 磁盘追加
1 97276 4000000（400万）
8 215053（峰值） 11111111（1111万，峰值）
32 122850（下降） 4761904

拐点扫描

指标 值
MySQL 拐点并发 32（超过后吞吐不增反降）
磁盘拐点并发 8（顺序写太快，低并发即达带宽极限）

五、核心结论

  1. 磁盘追加远快于 MySQL：约 14 倍。磁盘顺序写几乎零额外开销，MySQL 需事务/redo/索引/锁/刷盘，写入成本高。
  2. MySQL 有清晰拐点：并发 8 达峰值（21.5 万行/s），并发 32 下降（12.2 万行/s）——受连接池竞争、redo 刷盘、B+树索引维护、锁竞争限制。
  3. 磁盘拐点更低：顺序写太快，单线程/低并发已达文件系统带宽极限，高并发反而因 IO 竞争导致吞吐波动。
  4. 业务启示：高吞吐写入优先用磁盘批量/日志追加（如消息日志、临时数据）；必须落库的场景用 MySQL batch + 大事务 + rewriteBatchedStatements 提升吞吐。

六、工程要点

  1. MySQL 批量：PreparedStatement.addBatch/executeBatch + rewriteBatchedStatements（驱动合并多值）。
  2. 磁盘追加：BufferedWriter append（顺序写），每线程独立文件避免竞争。
  3. 拐点成因：连接池连接数上限、redo 刷盘压力、B+树索引维护、行锁/间隙锁竞争、网络 IO。
  4. 大批量落盘 vs 落库：根据数据重要性与查询需求选路。

七、踩坑记录（executeBatch 返回负数）

executeBatch() 在 rewriteBatchedStatements 下对成功批次返回 SUCCESS_NO_INFO (-2)，导致累加行数为负。修复：判断 v > 0 || v == SUCCESS_NO_INFO 视为批次成功，按批次数累加。

八、要点速览

MySQL 批量 vs 磁盘追加写入：同样的数据，MySQL 批量 12 万行/s，磁盘顺序追加 169 万行/s（快 14 倍）。加大并发找拐点：MySQL 并发 8 达峰值（21.5 万行/s），32 时降到 12 万（连接池/锁/刷盘瓶颈）；磁盘低并发即达带宽极限。启示：高吞吐写入优先磁盘追加，落库场景用 batch + 大事务 + rewriteBatchedStatements。
