补测B11：冷热分离的查询路由

补测B11：冷热分离的查询路由

一、问题背景

数据冷热分离后（热表存近期高频数据、归档表存历史冷数据），查询需应用层路由：热数据查热表、历史数据查归档表，避免查询扫全量大表。

二、路由原理

业务查询(create_time/距今天数)
    │
    ├── 距今 ≤ 热边界(如7天) → 热表 t_order_data
    └── 距今 >  热边界        → 归档表 t_order_archive
  • 路由规则：按业务时间（create_time 距今天数）判断冷热。
  • 路由查询：只查目标单表，走 create_time 索引范围查询，避免扫全量。

三、演示接口

# 1. 冷热表状态
curl "http://localhost:8080/hotcold/status"

# 2. 路由查询：距今2天（应走热表）
curl "http://localhost:8080/hotcold/route?daysAgo=2&hotBoundaryDays=7"

# 3. 路由查询：距今100天（应走归档表）
curl "http://localhost:8080/hotcold/route?daysAgo=100&hotBoundaryDays=7"

# 4. 路由 vs 全表查询性能对比
curl "http://localhost:8080/hotcold/bench?rounds=50"

依赖场景17的表（t_order_data + t_order_archive），需先 curl "http://localhost:8080/archive/init?months=12&perDay=300" 初始化 + curl "http://localhost:8080/archive/archive?archiveDays=30" 归档。

四、实测结果（10.8万行）

环节 结果
路由：距今2天 → 热表 t_order_data、命中=true
路由：距今100天 → 归档表 t_order_archive、命中=true
性能对比 路由 0.9ms vs 全表 2.1ms，快 2.1 倍

核心：路由按时间正确分派到热表/归档表并命中；10.8万行数据下路由只扫单表，快 2.1 倍（数据量越大差距越大）。

五、工程要点

  1. 路由字段：用业务时间（create_time）做冷热分界，语义清晰。
  2. 索引：热表/归档表的 create_time 需建索引，路由用范围查询走索引。
  3. 避免函数：DATE(create_time)=? 会使索引失效，用 create_time >= ? AND < ? 范围。
  4. 冷热边界：可配置（如 7 天/30 天），按访问频率定。
  5. 路由兜底：目标表未命中时可 fallback 查另一张表（防误路由）。
  6. 大数据量才体现优势：小数据量全缓存时路由/全表差异小。

六、踩坑记录（性能对比失真）

小数据量（9000行）全在 buffer_pool 缓存，全表 COUNT 也快，路由/全表差异失真。需大数据量（10.8万行）才体现路由优势。且路由查询用 DATE(create_time) 会索引失效，改为范围查询后走索引更快。

七、面试简述

冷热分离查询路由：按业务时间把热数据路由到热表、历史冷数据路由到归档表，避免查全量大表。实测10.8万行：路由查询0.9ms vs 全表2.1ms（快2.1倍）。要点：按 create_time 分界路由、建索引、范围查询避免索引失效、大数据量才体现优势。
