场景11：主从延迟治理（写后读一致性方案）

2026-03-23mysql 系列约 5 分钟阅读MySQL

一、问题背景

读写分离（场景6）把读压力分流到从库，但引入主从延迟：写主库后，从库需要经复制（binlog → relay log → SQL apply）才能同步，延迟窗口内从库读到的是旧数据。若业务"写后立即读"（如下单后查订单），会读到旧值，造成数据不一致。

本场景聚焦如何治理"写后读"不一致，对比三种读方案：强一致读主库 / 最终一致读从库 / 延迟双读（Read-Your-Writes）。

二、核心机制

  • 主从延迟：写主库提交后，从库滞后 Seconds_Behind_Source 才应用，窗口内读从库读到旧值
  • 强一致读：写后读主库，100% 读到最新，但读压力全集中主库
  • 最终一致读：写后读从库，分流读压力，但延迟窗口内可能读不到刚写的数据
  • 延迟双读：写后先读从库，读不到（延迟）则回主库重读，兼顾一致性与读分流

三、实测结果

演示表 t_delay_read，人为设置从库复制延迟 SOURCE_DELAY=2（2秒）放大效果。

1. 写后读一致性对比（/delay-read/write-then-read）

读路径 结果 一致性
写主库后立即读从库 NULL（读不到） ❌（最终一致，延迟窗口内不一致）
写主库后立即读主库 v80365（读到最新） ✅（强一致）

结论：从库延迟 2s 时，写主库后立即读从库读不到刚写的数据，读主库读到最新。强一致读主库、最终一致读从库的取舍。

2. 延迟双读（Read-Your-Writes，/delay-read/delay-double-read）

指标 结果
直接从从库读到 0/10（延迟 2s 读不到）
回主库读到 10/10
总一致性命中 10/10（100%）

结论：延迟双读先读从库，未命中（延迟）回主库，保证 100% 一致性，且大部分读请求分流到从库（延迟<窗口时）。

3. 三种方案一致性命中率（/delay-read/bench）

并发 10、1000 请求、从库延迟 2s：

方案 QPS P99 一致性命中
最终一致读从库 542 4ms 0/1000（延迟窗口全不一致）
强一致读主库 543 4ms 1000/1000
延迟双读 380 10ms 1000/1000

结论： - 最终一致读从库性能最好（QPS 542），但延迟窗口内一致性命中 0% - 强一致读主库 100% 一致、性能好（QPS 543），但读压力全压主库 - 延迟双读 100% 一致，但回主库有额外开销（QPS 380、P99 10ms）

四、生产避坑准则

  1. 关键"写后读"走主库：下单后立即查订单、支付回调等，写后读主库保证强一致
  2. 可容忍延迟的读走从库：列表、报表、统计等，读从库摊薄主库压力
  3. 延迟双读保一致：无法接受最终一致的读，用"先从库、读不到回主库"的延迟双读
  4. 监控主从延迟：Seconds_Behind_Source 超过阈值（如 2s）告警，延迟过大时读走主库兜底
  5. 半同步复制：对数据一致性要求高时，用半同步复制（从库确认后主库才提交）缩短延迟窗口

五、要点速览

主从延迟治理（写后读一致性）：读写分离引入"写主库后读从库读不到刚写数据"的不一致（从库延迟 Seconds_Behind_Source）。实测设置从库延迟 2s：写后立即读从库返回 NULL（不一致）、读主库读到最新（强一致）；延迟双读（先读从库读不到回主库）总一致性命中 100%；并发对比：最终一致读从库 QPS 最高但一致 0%、强一致读主库 100% 一致但全压主库、延迟双读 100% 一致但略有开销。核心：关键写后读走主库或延迟双读，可容忍延迟读从库，监控延迟阈值并及时切换兜底。
