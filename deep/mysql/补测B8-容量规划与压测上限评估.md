# 补测B8：容量规划与压测上限评估

## 一、问题背景

高并发系统上线前需**量化容量上限**：能支撑多少 QPS/TPS、连接数上限、buffer_pool/IO 饱和点，支撑容量预估与扩容决策。否则无法回答"系统能扛多少并发"。

## 二、评估思路

```
容量 = f(CPU核数, buffer_pool, IO, 连接数)
    │
    ├── 硬件/配置基线 (SHOW VARIABLES/STATUS)
    ├── 实测单连接吞吐 (TPS/QPS 压测)
    └── 推算上限：单连接吞吐 × 可用连接数
```

- **基线**：buffer_pool、max_connections、innodb_io_capacity、CPU 核数。
- **实测**：并发压测写(TPS)/读(QPS)，得到单连接吞吐。
- **推算**：上限 ≈ 单连接吞吐 × max_connections × 余量系数(80%)。

## 三、演示接口

```bash
# 1. 硬件与配置基线
curl "http://localhost:8080/capacity/baseline"

# 2. 写吞吐实测（TPS）
curl "http://localhost:8080/capacity/bench-write?concurrency=20&total=2000"

# 3. 读吞吐实测（QPS）
curl "http://localhost:8080/capacity/bench-read?concurrency=20&total=2000"

# 4. 容量评估报告（推算上限）
curl "http://localhost:8080/capacity/report"
```

## 四、实测结果

| 环节 | 结果 |
|------|------|
| 基线 | version=8.4.9、CPU=8核、buffer_pool=**1024MB**、max_connections=**1000** |
| 写吞吐 | 并发20写 **TPS≈1976** |
| 读吞吐 | 并发20读 **QPS≈15504** |
| 推算上限 | 理论写上限 **≈184万 TPS**、读上限 **≈20万 QPS**（按 1000 连接 80% 可用） |

**结论**：读吞吐远高于写（15504 vs 1976，约 8 倍），符合 InnoDB 读多写少特性。容量上限受连接数、buffer_pool、IO 综合制约，需结合锁/IO 饱和点修正理论值。

### 补充：连接复用对 QPS 的影响（实测）

**连接建立是固定开销（本次约 3.5ms/次），高频短查询下复用的收益极大：**

| 读方式（并发20，总量2000） | QPS |
|------|-----|
| 每次新建连接（DriverManager） | **1148** |
| 连接池复用（长连接） | **13513** |
| **提升倍数** | **11.8 倍** |

**结论**：连接复用省掉「连接建立」固定开销（TCP 握手 + 认证约 3.5ms）。查询本身仅约 0.1ms，高频场景下连接开销占比高，复用使 QPS 提升近 12 倍。

```bash
# 连接复用 vs 新建连接 读吞吐对比
curl "http://localhost:8080/capacity/bench-read-compare?concurrency=20&total=2000"
```

## 五、容量规划要点

1. **buffer_pool**：设为物理内存 60%-75%，决定数据缓存能力。
2. **连接数**：max_connections 需 > 应用连接池总上限，预留余量。
3. **读写分离**：读 QPS 高可扩展从库，线性扩容。
4. **分库分表**：TPS 高可水平扩展，突破单实例上限。
5. **压测定点**：定期压测定位饱和点（CPU/IO/锁/连接），修正理论值。
6. **IO 优化**：innodb_io_capacity / flush_method 适配 SSD。

## 六、面试简述

> **容量规划与压测**：评估系统 QPS/TPS/连接数上限。实测（并发20）：写 TPS≈1976、读 QPS≈15504（读比写高约8倍）。按 max_connections=1000 的 80% 推算写上限≈184万 TPS。容量 = f(CPU、buffer_pool、IO、连接数)；读多用读写分离、写多用分库分表线性扩容；定期压测定点修正。
