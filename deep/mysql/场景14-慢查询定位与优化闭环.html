场景14：慢查询定位与优化闭环

2026-03-28mysql 系列约 6 分钟阅读MySQL

一、问题背景

慢查询是线上性能问题的常见根源。一次全表扫描可能拖垮整个库。治理慢查询需要完整闭环：定位 → 分析 → 优化 → 验证，而不是拍脑袋改。

本场景用表 t_slow_demo（20 万行，初态无索引）演示完整闭环。

二、闭环四步

步骤 手段 目的
定位 performance_schema.events_statements_summary_by_digest / 慢日志 找出 TOP N 慢语句
分析 EXPLAIN（type/key/rows/Extra） 判断是否全表扫描 / 文件排序 / 回表
优化 加索引 / 改写 SQL / 覆盖索引 消除瓶颈
验证 优化前后耗时/吞吐对比 量化收益

三、演示接口

# 1. 初始化演示数据（20万行，初态不加索引 → 制造全表扫描慢查询）
curl "http://localhost:8080/slow-query/init?rows=200000"

# 2. 定位慢查询：performance_schema 按 SQL 指纹聚合 TOP N 慢语句
curl "http://localhost:8080/slow-query/diagnose?limit=10"

# 3. EXPLAIN 分析指定 SQL（看 type/key/rows/Extra）
curl "http://localhost:8080/slow-query/explain?sql=SELECT%20*%20FROM%20t_slow_demo%20WHERE%20user_id%20%3D%2015000"

# 4. 优化：为 order_no 加索引，展示前后 EXPLAIN 对比
curl "http://localhost:8080/slow-query/optimize"

# 5. 优化前后 吞吐对比（量化收益）
curl "http://localhost:8080/slow-query/bench?concurrency=50&total=2000"

# 6. 慢查询日志状态
curl "http://localhost:8080/slow-query/slow-log"

四、实测结果

1. EXPLAIN 定位（优化前）

type=ALL, key=NULL, rows=200000, Extra=Using where

→ type=ALL 全表扫描，rows 扫描 20 万行，这是慢查询主因。

2. 优化：加索引 idx_slow_order_no(order_no)

type=ref, key=idx_slow_order_no, rows=1

→ 从 全表扫描 20 万行 降到 索引命中 1 行。

3. 优化前后吞吐对比（并发 50）

方案 QPS avgMs p99Ms
优化前（全表扫描） 46 21 1967
优化后（走索引） 10695 0 25
提升 约 232 倍 — 78 倍

4. 定位（diagnose）

performance_schema 聚合出 TOP 慢语句，全表扫描型 SELECT * FROM t_slow_demo WHERE user_id=?：

count=21834, avgMs=989.8, rowsExamined=43.6亿

→ avgMs 大 + rows_examined 巨大 = 全表扫描型慢查询，优先优化。

五、优化准则

  1. 优先加索引：为 WHERE/ORDER BY/GROUP BY 过滤列建索引（最左前缀）。
  2. 避免 SELECT *：只查需要的列，减少回表与 IO，必要时建覆盖索引。
  3. EXPLAIN 看 type：ALL（全表扫描）/index（全索引扫描）需优化；ref/const/eq_ref 为佳。
  4. 看 Extra：Using filesort（排序未走索引）、Using temporary（临时表）是隐藏瓶颈。
  5. 看 rows：扫描行数巨大即使走了索引也可能慢（如低选择性索引），考虑选择性或覆盖索引。
  6. 生产定位：开 slow_query_log + long_query_time，用 pt-query-digest/mysqldumpslow 分析慢日志，结合 performance_schema 定位。
  7. 验证闭环：优化后必须压测对比，量化收益并回归（防止优化引入新问题）。

六、要点速览

慢查询治理闭环：定位（慢日志 / performance_schema.events_statements_summary_by_digest 聚合 TOP 慢语句）→ 分析（EXPLAIN 看 type 是否 ALL、rows 扫描行数、Extra 是否有 filesort/temporary）→ 优化（加索引、避免 SELECT 、覆盖索引、改写 SQL）→ 验证（压测对比）。实测全表扫描型慢查询优化后 QPS 从 46 提到 10695（约 232 倍），定位信号是 avgMs 大 + rows_examined 巨大*。EXPLAIN 的 type=ALL + rows 巨大是该优化最强信号。
