# MySQL 高并发场景 1-18 结论汇总（只要结论）

> 仅保留每个场景的核心结论与关键实测数据，过程细节见各场景独立文档。

---

## 场景1：连接池与超卖问题

**结论**：并发扣减必须防超卖，四种策略按"原子性→吞吐→可扩展"递进。
- **oversell（裸扣减）**：有超卖，不可用。
- **atomic（原子 UPDATE）**：`UPDATE t_stock SET stock=stock-1 WHERE stock>0`，单行原子、无超卖、吞吐最高，单库首选。
- **pessimistic（悲观锁）**：`SELECT FOR UPDATE`，无超卖、安全，但并发锁等待、吞吐低。
- **optimistic（乐观锁版本号）**：无超卖，高冲突下重试开销大。

**实测**：多行分布式下 atomic 吞吐 > pessimistic > optimistic；单行热点 atomic 远胜悲观锁。
**工程结论**：单行热点优先 atomic；多行/分布式用乐观锁或分库；悲观锁仅一致性要求极高时用。

## 场景2：事务隔离级别

**结论**：隔离级别越高、并发越低，用"多读少写"判断。
- **脏读**：只有 READ UNCOMMITTED 出现。
- **不可重复读**：RC 出现，RR 不出现。
- **幻读**：RC 出现；RR 靠间隙锁/Next-Key Lock 避免（但纯快照读"看到幻行"仍可能，需锁/串行化）。

**实测**：RC vs RR 写吞吐：RC 明显更高（RR 的间隙锁加锁更重）。
**工程结论**：默认 RR（MySQL）；对一致性要求不苛刻、追求吞吐可用 RC；账务等强一致用 RR + 显式锁。

---

## 场景3：悲观锁 vs 乐观锁

**结论**：
- **悲观锁**：适合**写冲突多**、行锁竞争可接受，语义直观，但并发低、可能死锁。
- **乐观锁**：适合**读多写少**、冲突低，无锁无死锁，但高冲突下重试开销大。

**实测**：并发写下悲观锁吞吐低于乐观锁（乐观锁无锁等待），高冲突时乐观锁重试率上升。
**工程结论**：读多写少用乐观锁；写冲突大用悲观锁或原子操作；都可配合 `version` 版本号。

---

## 场景4：间隙锁 / Next-Key Lock 与死锁

**结论**：
- **间隙锁/临键锁**：RR 下对**非唯一索引/范围**加锁时锁区间，防幻读，代价是**阻塞并发插入**、易死锁。
- **Next-Key Lock** = 记录锁 + 间隙锁（左开右闭），是 RR 防幻读的关键。
- **插入意向锁**：间隙锁与插入意向锁互斥，导致并发插入互相等待。
- **死锁**：两个事务锁不同区间后互相插入/锁对方所需 → InnoDB 检测并回滚一个（错误码 1213）。

**工程结论**：精确用主键/唯一索引等值命中可避免间隙锁；固定加锁顺序防死锁；高并发写用 RC 减少锁区间。

## 场景5：索引失效与慢查询

**结论**：九类索引失效 → 全表扫描 → 慢查询：
1. 函数运算（`LEFT(name,6)=`）
2. 隐式类型转换（`phone=138...` 数字）
3. LIKE 前导通配符（`LIKE '%xx'`）
4. OR 连接（分支无索引）
5. 联合索引不满足最左前缀
6. 范围查询后列失效
7. 不等值（`<>`/`NOT IN`）
8. 索引列算术运算
9. `IS NOT NULL`

**实测**：索引失效全表扫描 QPS 远低于走索引（数倍~数十倍差距）。
**工程结论**：写 SQL 避免函数/隐式转换/前导 LIKE；联合索引保最左前缀；用 EXPLAIN 验证 `type=ALL` 即全表扫描。

---

## 场景6：读写分离与主从延迟

**结论**：
- 主从复制 + 读写分离**分摊读压力、提升读吞吐**。
- 引入**主从延迟**：写主库后读从库可能短暂读不到（最终一致）。

**实测**：写主库后从库约数 ms~数十 ms 可见；读从库吞吐可高于读主库（主库还承担写）。
**工程结论**：读多写少用读写分离；对一致性敏感的业务读主库或用延迟双读；监控 `Seconds_Behind_Source`。

---

## 场景7：分库分表

**结论**：
- **分表**：单表数据量大→按 `user_id%N` 拆多物理表，精确路由查询只在单表、快。
- **分库**：再按 `user_id/N%M` 拆多库，进一步分散 IO。
- **精确路由 vs 跨分片扫描**：精确路由吞吐远高于跨分片扫描；跨分片聚合（COUNT/SUM）需应用层合并。

**实测**：精确路由 QPS 远高于全分片扫描；分库分表把数据量和并发分散。
**工程结论**：数据量大/写并发高才分库分表；路由键设计（user_id）决定查询能否精确路由；跨分片查询复杂，避免。

---

## 场景8：批量写入优化

**结论**：写入吞吐核心是减少 fsync 次数与网络往返。
- 逐条 INSERT（autocommit）：最慢（每条 fsync）。
- 事务内逐条：减少提交，提升大。
- 单条多值 INSERT：减少 SQL 次数。
- **JDBC addBatch + `rewriteBatchedStatements`**：最快。

**实测**（1万行）：逐条 43 行/s → 事务内 3606 → 单条多值 10204 → JDBC Batch **11049**（比逐条快 257 倍）。
**工程结论**：严禁逐条 INSERT；批量必开 `rewriteBatchedStatements=true`；batchSize 取 500~1000。

---

## 场景9：InnoDB 并发控制（MVCC）

**结论**：
- MVCC 用 undo 版本链实现**一致性读（快照读）不加锁**，读写不互斥。
- **快照读**（SELECT）读旧版本；**当前读**（FOR UPDATE/LOCK IN SHARE MODE）读最新并加锁。
- RR 下快照在事务首读建立，可重复读；RC 每次读新快照，不可重复读。
- 可见性规则保证读不到未提交事务（防脏读）。

**工程结论**：MVCC 让读不阻塞写，是 InnoDB 高并发读的基石；对一致性敏感用当前读/加锁。

---

## 场景10：Redis 缓存 + MySQL 双写一致性

**结论**：
- **Cache Aside**：读先查缓存，未命中查库回填；写先更新库再删缓存。
- **只更新库不删缓存** → 缓存旧值（不一致）。
- **延迟双删**：更新库→删缓存→延迟→再删，解决并发读写竞态。

**工程结论**：缓存一致性做不到绝对，用 Cache Aside + 延迟双删 + 过期兜底；对强一致要求不放缓存。

---

## 场景11：主从延迟治理（写后读一致性）

**结论**：
- **最终一致读从库**：性能好，但延迟窗口内读不到刚写的数据。
- **强一致读主库**：100% 读到最新，但读压力集中主库。
- **延迟双读（Read-Your-Writes）**：先读从库，读不到回主库，兼顾一致与分流。

**实测**：设置从库延迟 2s，写后读从库 NULL、读主库读到；延迟双读一致性命中 100%。
**工程结论**：写后读强一致读主库；兼顾性能用延迟双读；对一致性要求高用半同步复制。

---

## 场景12：分布式锁（基于 MySQL 唯一索引）

**结论**：
- **唯一索引抢锁**：INSERT 成功=加锁，唯一键冲突=占用，天然互斥。
- **owner 防误删**：释放校验 owner，防误删他人锁。
- **过期续期**：expire 防持有者宕机死锁，可续期。
- **悲观锁 FOR UPDATE**：行锁互斥临界区。

**实测**：分布式锁下临界区 0 丢失更新；无锁则丢失更新（lostUpdates=-949）。吞吐：分布式锁 166 vs 无锁 11467（一致性换吞吐）。
**工程结论**：MySQL 锁表简单可靠，适合一致性高、并发中等；超高并发用 Redis/Redisson。注意：Seata（分布式事务）≠ 分布式锁，解决不同问题。

## 场景13：InnoDB 参数调优

**结论**：调优本质是**「性能 vs 持久性」权衡**。
- `innodb_flush_log_at_trx_commit`：1=每次提交刷盘(最安全最慢)、2=写OS缓存每秒刷、0=后台每秒刷(最快丢1s)。
- `sync_binlog`：控制 binlog 刷盘，1 最安全最慢，0/N 换吞吐。
- `innodb_buffer_pool_size`：设 60%~75% 内存，提升读命中。

**实测**：调低刷盘频率后写入吞吐提升约 20~35%（容器缓存环境；生产高 IO 压力可到数倍）。
**工程结论**：账务类保 `(1,1)` 强持久；日志/缓存类可降 `(2,0)/(0,0)`；生产 `SET GLOBAL` 需写 my.cnf 重启持久化，先压测后上线。

## 场景14：慢查询定位与优化闭环

**结论**：闭环 = **定位 → 分析 → 优化 → 验证**。
- **定位**：`performance_schema.events_statements_summary_by_digest` 按 SQL 指纹聚合 TOP 慢语句。
- **分析**：EXPLAIN 看 `type=ALL`（全表扫描）、rows 巨大、`Using filesort/temporary`。
- **优化**：加索引/避免 SELECT */覆盖索引/改写 SQL。
- **验证**：压测对比。

**实测**：全表扫描慢查询（rows 43.6 亿）加索引后 `type ALL→ref`、rows 20万→1；QPS 从 46 提到 **10695**（约 232 倍）。
**工程结论**：`type=ALL + rows 巨大` 是最强优化信号；定位信号是 avgMs 大 + rows_examined 巨大。

## 场景15：MySQL 高可用

**结论**：
- **读高可用**：读写分离，主库故障读自动切从库（可用性 100%）。
- **写高可用**：主从切换（STOP REPLICA→RESET→关只读→重挂复制→应用切新主），常由 MHA/Orchestrator 自动完成。

**实测**：主库故障模拟下读全切从库、可用性 100%；切从库读吞吐 16722 > 读主库 8892。
**工程结论**：从库容量要够承接故障读流量；切换前数据追平（Seconds_Behind_Source=0）；半同步复制降 RPO；VIP 漂移让应用无感；定期故障演练。生产选 Orchestrator（自动秒级）/ InnoDB Cluster（官方）/ MHA。

---

## 场景16：连接池参数调优（HikariCP）

**结论**：池大小不是越大越好，需匹配并发度与 MySQL `max_connections`。
- 过小 → 高并发排队/超时。
- 适中 → 吞吐最优。
- 过大 → 资源浪费、收益不再增加。

**实测**（并发50）：池2 QPS 186（68失败）；池20 QPS 1776；池50 QPS 3831（avgWait 1ms）。
**工程结论**：先定位瓶颈（连接等待 vs MySQL CPU）再调参；真正高并发靠短连接+快事务+少等待；`connectionTimeout` 防挂死、`maxLifetime<wait_timeout`。

## 场景17：数据归档与冷热分离

**结论**：数据累积使大表查询慢，把超期冷数据归档、热表瘦身提升性能。
- 按时间归档冷数据到归档表，热表只留近期高频数据。
- 热表瘦身 → 索引有效 + 缓存命中高 → 查询快。

**实测**：18 万行订单归档 30 天前冷数据后，热表瘦身到 1.55 万行（11.6 倍），查询 QPS 从 108 提到 **1223**（约 11 倍）。
**工程结论**：冷热边界按业务定（订单90天/日志30天）；用定时任务分批归档或 MySQL 分区表 DROP 过期分区；冷数据放数仓/OSS 按需查询。

## 场景18：锁等待与死锁监控治理

**结论**：
- **锁等待**：A 持锁 B 等待，事务串行化、吞吐下降。
- **死锁**：事务互相持有对方所需锁，InnoDB 自动检测并回滚一个（错误码 1213，应用需重试）。

**实测**：制造锁等待 A 持 1500ms、B 等待 1502ms；制造死锁一个事务回滚。
**监控**：`performance_schema.data_locks` + `sys.innodb_lock_waits`（谁阻塞谁）+ `information_schema.innodb_trx`。
**治理**：减小锁粒度（主键/唯一索引命中）、缩短事务、固定加锁顺序（防死锁）、控制并发、`innodb_lock_wait_timeout` 超时兜底。

## 全项目一句话总结

**MySQL 高并发治理 = 事务隔离/锁控数据一致性 + 索引/慢查询控查询效率 + 读写分离/分库分表/缓存/归档控数据规模 + 连接池/批量写/参数调优控吞吐 + 高可用/故障转移/锁死锁监控保稳定。**
