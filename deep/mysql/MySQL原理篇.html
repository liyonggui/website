一、MySQL 整体架构与执行流程

1.1 四层架构

客户端 / 应用
    │
    ▼
┌─────────────────────────────────────────┐
│ ① 连接层 (Connection)                    │
│    连接池、认证鉴权、SSL、线程管理          │
│    max_connections / thread_cache         │
├─────────────────────────────────────────┤
│ ② 服务层 (Server Layer)                  │
│    解析器(语法) → 优化器(执行计划) → 执行器  │
│    查询缓存(8.0移除)、权限、内置函数         │
├─────────────────────────────────────────┤
│ ③ 存储引擎层 (Storage Engine)            │
│    InnoDB(默认)、MyISAM、Memory...        │
│    负责数据存取、索引、锁、事务、MVCC        │
├─────────────────────────────────────────┤
│ ④ 文件系统层 (Storage)                   │
│    .frm/ibd 数据文件、redo log、undo log、  │
│    binlog、slow log、data dictionary       │
└─────────────────────────────────────────┘
  • Server 层与引擎层分离：解析、优化、执行通用；引擎决定数据组织方式。
  • InnoDB 是 MySQL 默认且最常用的引擎，本文主要讲 InnoDB。

1.2 一条 SELECT 的完整旅程

SELECT * FROM t WHERE id = 5;
    │
    ├─ ① 连接层：鉴权、建立连接(复用连接池)
    ├─ ② 解析器：词法/语法分析 → 生成语法树
    ├─ ③ 优化器：选索引、定执行计划(走主键索引)
    ├─ ④ 执行器：调用 InnoDB 接口，打开表、按索引取行
    ├─ ⑤ InnoDB：查 Buffer Pool → 未命中则读磁盘页 → 返回行
    └─ ⑥ 返回结果给客户端(缓存/网络发送)

1.3 一条 UPDATE 的完整旅程（关键）

UPDATE t SET a=10 WHERE id=5;
    │
    ├─ ① 解析、优化、执行（同 SELECT，但走当前读加锁）
    ├─ ② InnoDB 加行锁(排他锁)
    ├─ ③ 写 undo log（记录旧值，用于回滚/MVCC）
    ├─ ④ 修改 Buffer Pool 中的页（脏页）
    ├─ ⑤ 写 redo log（WAL：先写日志再刷盘，崩溃恢复用）
    ├─ ⑥ 写 binlog（逻辑日志，主从复制/归档用）
    ├─ ⑦ COMMIT：两阶段提交 redo+binlog 保证一致性
    └─ ⑧ 后台线程异步刷脏页到磁盘

核心概念：WAL（Write-Ahead Logging）——先写 redo log 再写数据页。数据落盘是异步的，但日志是同步的，保证崩溃后能恢复，同时大幅提升写入性能（顺序写日志远快于随机写数据页）。

1.4 执行器与存储引擎的协作

  • 执行器（Server 层）负责：解析结果集、过滤条件（如 WHERE 不满足的行）、返回数据。
  • 存储引擎（InnoDB）负责：按索引取行、加锁、管理事务、MVCC 版本。
  • 执行器按主键/二级索引一步步取行，交给引擎过滤条件，直到没有更多行。

1.5 Join 三种算法（MySQL 8.0）

算法 全称 适用 原理
NLJ Nested Loop Join 驱动表小、被驱动表有索引 外层驱动表每行，内层按索引查找被驱动表
BNL Block Nested Loop 被驱动表无索引 驱动表结果存 join buffer，批量匹配
HASH JOIN Hash Join（8.0） 大表等值连接 建哈希表 O(1) 匹配，替代 BNL
  • NLJ：被驱动表有索引时最优，回表次数少。
  • BNL/HASH：无索引时用，避免全表扫多次。
  • 优化器选型：根据表大小、索引、join 条件自动选择。
  • 驱动表选择：小表作驱动表（减少外层循环）。

二、InnoDB 存储引擎原理

2.1 存储结构：页 → 区 → 段 → 表空间

层级 大小 说明
页 Page 默认 16KB 最小存储单元，B+树节点即页
区 Extent 1MB（64页） 连续页，批量分配提升顺序 IO
段 Segment — 索引段/数据段/回滚段，叶子节点存数据
表空间 — .ibd 数据文件，含系统表空间/用户表空间
  • 页是 InnoDB 读写的最小单位，一次至少读写一个页。
  • B+树每个节点对应一个页，页内按主键有序存储记录。

2.2 Buffer Pool（缓冲池）

Buffer Pool（内存缓存数据页）
    ├── LRU 链表（管理热/冷页）
    ├── 脏页链表（待刷盘）
    └── free 链表（空闲页）
  • 作用：缓存数据页，避免每次访问都读磁盘，大幅提升性能。
  • 预读：顺序读时把相邻页一次性读入。
  • LRU 淘汰：8.0 用 LRU+分区（young/old），防全表扫把热点挤出。
  • 脏页刷盘：后台线程异步把脏页写回磁盘（与 WAL 配合）。
  • 调优：innodb_buffer_pool_size 建议物理内存 60%-75%（见 补测B8-容量规划）。

2.3 InnoDB 三大优化组件（高频）

组件 作用 原理
Change Buffer（变更缓冲） 优化二级索引的随机写 二级索引不在内存时，先缓存变更，合并后批量刷盘，减少随机 IO
自适应哈希索引 AHI 加速热点等值查询 监控热点，自动为频繁访问的索引建立内存哈希，O(1) 查找
Doublewrite Buffer（双写缓冲） 防页断裂（崩溃恢复） 先整页写共享表空间再写数据文件，避免写一半导致页损坏

Change Buffer（变更缓冲，重点）

  • 适用：二级索引的 INSERT/UPDATE/DELETE（随机 IO 场景）。
  • 原理：二级索引页不在 Buffer Pool 时，不立即写磁盘，先把变更缓存到 Change Buffer，待页被读入时合并，或后台批量刷盘。
  • 价值：把随机写变为顺序写，大幅提升二级索引写入性能。
  • 注意：innodb_change_buffering 可配；二级索引较多的表收益明显。

自适应哈希索引 AHI

  • InnoDB 监测索引访问模式，对高频等值查询自动在内存建哈希索引。
  • 是 B+树的内存加速层，不持久化，无空间代价但需监控维护。
  • 适合等值热点；范围查询/全表扫用不到。

Doublewrite Buffer（双写缓冲）

  • 解决"写一半断电导致页损坏（partial page）"问题。
  • 数据页先整页写入双写缓冲（共享表空间），再写实际数据文件。
  • 崩溃恢复时若页损坏，从双写缓冲还原。8.0.20+ 默认启用。

关联 场景13-InnoDB参数调优、补测B8-容量规划。

2.4 三大日志：redo / undo / binlog

日志 类型 作用 刷盘时机
redo log 物理日志 崩溃恢复（持久性），记录页的物理修改 innodb_flush_log_at_trx_commit 控制
undo log 逻辑日志 回滚（原子性）+ MVCC 版本链（隔离性） 随事务
binlog 逻辑日志（Server层） 主从复制、数据归档、PITR 恢复 sync_binlog 控制

2.4.1 redo log（重做日志）

  • WAL 核心：事务提交前先写 redo log，崩溃后用 redo 重放恢复。
  • 环形复用（ib_logfile），LSN（Log Sequence Number）标记进度。
  • innodb_flush_log_at_trx_commit：
  • 1（默认）：每次提交刷盘，最安全但最慢。
  • 0：每秒刷盘，最快但可能丢 1 秒数据。
  • 2：写 OS 缓存，每秒刷盘。

关联 场景13-InnoDB参数调优 的刷盘参数对比。

2.4.2 undo log（回滚日志）

  • 记录事务修改前的旧值，用于回滚和MVCC 版本链。
  • 行头 roll_ptr 指向 undo 链，可回溯历史版本。
  • 回滚段（rollback segment）管理，事务结束且无快照引用后清理。

2.4.3 binlog（二进制日志）

  • Server 层日志，记录所有变更（逻辑）。
  • 三种格式：STATEMENT（记录 SQL）、ROW（记录行变更，默认推荐）、MIXED。
  • 用于：主从复制、PITR 时间点恢复（补测B1）、数据归档。

2.5 两阶段提交（redo + binlog 一致性）

事务提交：
    │
    ├─ ① 写 redo log（prepare 阶段）
    ├─ ② 写 binlog
    └─ ③ 写 redo log（commit 阶段）
  • 目的：保证 redo（InnoDB）与 binlog（Server）数据一致，避免崩溃时主从不一致。
  • 崩溃恢复规则：binlog 完整则提交（redo 补 commit），binlog 不完整则回滚。
  • 这是 MySQL 主从复制的正确性基础（场景6、补测B2）。

2.6 崩溃恢复流程

启动时：
    ├─ ① 扫描 redo log 的 LSN 位置
    ├─ ② 重放 redo（把未刷盘的修改重新应用）
    ├─ ③ 结合两阶段提交判断哪些事务 binlog 完整
    ├─ ④ binlog 完整 → 提交；不完整 → 回滚(用 undo)
    └─ ⑤ 恢复到崩溃前一致状态

关联 补测B1-备份恢复：全量备份 + binlog 增量 + 时间点恢复（PITR）。

三、索引原理

3.1 B+树索引结构

B+树（聚簇索引，叶子存全行数据）
    ┌──────────────┐
    │  根节点(页)    │  键值 + 指向子页
    └───┬──────┬────┘
    ┌────▼─┐ ┌─▼────┐
    │ 内节点 │ │ 内节点 │  键值 + 指针
    └──┬────┘ └──┬────┘
    ┌──▼─┐     ┌─▼──┐
    │叶子 │     │叶子 │  键值 + 数据(聚簇) / 主键(二级)
    └────┘     └────┘  叶子之间双向链表(有序)

为什么用 B+树（而非 B树/哈希）： - 矮胖：高度低（几百万行高度约 3-4），查询 IO 次数少（等于树高）。 - 叶子有序链表：范围查询、排序高效（顺序 IO）。 - 非叶子只存键：一页能存更多键，扇出大，树更矮。

3.2 聚簇索引 vs 二级索引

类型 叶子存储 特点
聚簇索引（主键） 完整数据行 数据即索引，主键查询直接得行
二级索引（普通索引） 索引键 + 主键值 需回表（再查聚簇索引）取全行
  • 回表：二级索引查到主键 → 再按主键查聚簇索引 → 取全行。
  • 覆盖索引：查询列全在二级索引内，无需回表（性能最优）。
  • 联合索引：多个字段，最左前缀原则。

回表优化技术： - 覆盖索引：查询列全在索引内，无需回表。 - MRR（Multi-Range Read，多范围读）：回表时把多个主键排序后批量回表，把随机 IO 变顺序 IO，减少回表次数（mrr_cost_based 控制）。 - 索引下推 ICP：把 WHERE 中索引能判断的条件下推到引擎，减少回表（见 3.4）。

关联 补测B6-深分页查询优化：深分页 LIMIT 大offset 扫描多行，用覆盖索引/延迟关联优化。

3.3 索引分类

  • 主键索引：唯一、非空，聚簇。
  • 唯一索引：值唯一，二级索引。
  • 普通索引：允许重复，二级索引。
  • 联合索引：多列，最左前缀。
  • 全文索引：文本模糊匹配（FULLTEXT）。
  • 空间索引：地理数据。

3.4 联合索引最左前缀

联合索引 (a, b, c) 可命中：
    ✓ a
    ✓ a, b
    ✓ a, b, c
    ✗ b
    ✗ c
    ✗ b, c
    ✗ a, c  (跳过 b，只能用到 a)
  • 最左前缀：查询条件从最左列开始连续命中才走索引。
  • 索引下推 ICP：把 WHERE 条件中索引能判断的部分下推到引擎，减少回表。
  • 回表优化：把高频查询列加入索引做覆盖索引。

3.5 索引失效场景（重点）

场景 原因 优化
WHERE name LIKE '%xx' 前模糊，无法用 B+树前缀定位 改后模糊/全文索引
WHERE FUNC(col)=... 函数导致索引列失效 避免对列用函数
WHERE col + 1 = 10 运算导致失效 改 col=9
WHERE a OR b 多条件 or 可能全表扫 改 union/重建索引
隐式类型转换 col=varchar 但传数字 保证类型一致
联合索引不满足最左前缀 未从最左列开始 调整条件顺序
!= / NOT IN 无法用索引区间 评估选择性

关联 场景5-索引失效与慢查询、补测B7-统计信息过期。

3.6 优化器与统计信息

  • 优化器根据统计信息（cardinality 基数）估算行数、选索引。
  • 统计信息过期 → 选错索引 → SQL 突然变慢。
  • 处理：ANALYZE TABLE 刷新、直方图精确统计倾斜数据（补测B7）。

四、事务与隔离原理

4.1 ACID 实现

特性 实现机制
原子性 Atomicity undo log 回滚
一致性 Consistency 约束 + undo/redo 保证不破坏约束
隔离性 Isolation 锁 + MVCC
持久性 Durability redo log（WAL）

4.2 事务的 ACID 由谁保证

  • 原子性：undo log——事务失败回滚到旧状态。
  • 持久性：redo log——事务提交后崩溃也能恢复。
  • 隔离性：MVCC（快照读）+ 锁（当前读）。
  • 一致性：上述三者共同保证 + 数据库约束（外键/唯一/非空）。

4.3 MVCC（多版本并发控制）

MVCC = 快照读（普通 SELECT）无锁，基于 undo 版本链
行头隐藏列：
    trx_id    最后修改该行的事务 id
    roll_ptr  指向 undo 版本链（历史版本）
    DB_ROW_ID 聚簇索引无主键时的隐藏行 id

ReadView（读视图）： - 记录事务启动时的活跃事务列表 + 最大/最小事务 id。 - 判断版本是否可见：trx_id 在 ReadView 前且未提交则不可见，回退到 undo 链旧版本。

隔离级别的快照时机： - RC（读已提交）：每次 SELECT 生成新 ReadView。 - RR（可重复读）：事务第一次 SELECT 生成 ReadView，全程复用。

关联 场景9-InnoDB并发控制MVCC、场景2-事务隔离级别。

4.4 快照读 vs 当前读

类型 SQL 加锁 ReadView
快照读 普通 SELECT 不加锁 生成 ReadView，读历史版本
当前读 SELECT...FOR UPDATE / LOCK IN SHARE MODE / UPDATE / DELETE / INSERT 加锁 不生成，读最新数据
  • 快照读：基于 MVCC，无锁，并发高，读到的可能是旧版本。
  • 当前读：读最新数据并加锁，避免并发写冲突。

4.5 四大隔离级别

级别 脏读 不可重复读 幻读 实现
读未提交 RU 允许 允许 允许 无 MVCC 保护
读已提交 RC 禁止 允许 允许 每次 SELECT 新 ReadView，无间隙锁
可重复读 RR（默认） 禁止 禁止 特殊处理 事务级 ReadView + 临键锁
串行化 禁止 禁止 禁止 快照读视为锁定读，全串行

三大并发问题： - 脏读：读未提交数据。 - 不可重复读：同事务两次读同一行，被 UPDATE 提交后不一致。 - 幻读：同事务范围查询，被 INSERT/DELETE 提交后行数变化。

4.6 幻读与间隙锁（RR 的"特殊处理"）

  • 快照读：RR 靠事务级 ReadView 解决逻辑幻读（读到一致快照）。
  • 当前读：RR 靠 临键锁（gap + next-key） 阻止插入，解决物理幻读。
  • RC 无间隙锁：并发高但可能幻读，锁范围更小。

关联 场景4-间隙锁与Next-KeyLock、场景4-补强-InnoDB锁完整体系。

4.7 长事务 / 大事务的危害（重点）

危害 原因
undo 膨胀 长事务持续持有 ReadView，undo 版本链无法清理，占用大量空间
锁持有久 长事务持有行锁/间隙锁，阻塞其他事务，扩大锁等待/死锁概率
redo/日志量大 大事务产生海量 redo，刷盘压力大
主从延迟 大事务在从库串行重放慢，造成主从延迟（补测B10）
binlog 庞大 ROW 格式大事务 binlog 巨大，占用空间

治理： - 拆分大事务为小事务（分批提交）。 - 避免长事务（及时提交/回滚）。 - 监控 innodb_history_list_length（undo 链长度）和长事务。

关联 补测B9-连接泄漏、场景18-锁等待与死锁监控治理。

五、锁机制原理

5.1 锁类型总览

锁 说明
共享锁 S 读锁，可多个事务共享（S+S 兼容）
排他锁 X 写锁，互斥（X 与 X/S 都冲突）
意向锁 IS/IX 表级意向，表示"事务要加行锁"，提升表级锁判断效率
记录锁 Record 锁单个索引记录
间隙锁 Gap 锁索引记录之间的间隙，防止插入（防幻读）
临键锁 Next-Key 记录锁 + 间隙锁，RR 默认，防幻读
插入意向锁 间隙锁内的插入意向，多个可共存但互不冲突
自增锁 控制 AUTO_INCREMENT 并发

5.2 S/X 锁兼容矩阵

S X
S 兼容 冲突
X 冲突 冲突
  • S+S：可多个事务同时读。
  • S/X、X/X：互斥，需等待。

5.3 行锁与表锁

  • InnoDB 行锁：基于索引实现（无索引则退化为表锁/全表锁）。
  • MyISAM 只有表锁：并发写性能差。
  • 无索引条件 UPDATE：会锁全表（补测4 相关），危险。

5.4 间隙锁 / 临键锁（重点）

记录:  ... 10 | 20 | 30 ...
间隙:      ↑gap ↑gap
临键锁范围: (10,20], (20,30] 等
  • 临键锁 = 记录锁 + 前一间隙锁，RR 默认。
  • 间隙锁：只锁间隙，不锁记录，防止其他事务在间隙插入（防幻读）。
  • 唯一索引等值：命中唯一记录时退化为记录锁（不锁间隙）。
  • 非唯一索引/范围：加临键锁或间隙锁。

关联 场景4-间隙锁与Next-KeyLock、场景4-补强-InnoDB锁完整体系。

5.5 锁降级（RR → RC）

  • RC 隔离级别：只锁匹配的记录（记录锁），不加间隙锁，并发更高。
  • RR 隔离级别：加临键锁/间隙锁，防幻读但并发低、死锁多。
  • 半一致性读：RC 下 UPDATE 先快照读判断，减少锁范围。

5.6 死锁原理

事务A: 锁行1 → 要行2
事务B: 锁行2 → 要行1
       └── 循环等待 → 死锁
  • 死锁检测：innodb_deadlock_detect=ON，检测到回滚代价小的一方（错误码 1213）。
  • 避免死锁：按固定顺序加锁、减少锁范围、用 RC、合理索引。
  • 死锁重试：业务捕获 1213 自动重试（补测B12）。

5.7 锁等待超时（1205）vs 死锁（1213）

锁等待超时 死锁
错误码 1205 1213
本质 事务等锁超过 innodb_lock_wait_timeout（默认50s） 循环等待，InnoDB 主动回滚一方
是否主动 被动超时 主动检测 + 回滚
处理 增加超时/减少锁等待/拆分事务 捕获 1213 自动重试
SQLSTATE HY000 (40001?) 40001
  • 1205：锁等待太久超时，事务可能已部分执行，需回滚重试。
  • 1213：死锁检测主动回滚代价小的事务，业务应立即重试。
  • 两者都建议重试：捕获错误码，指数退避重试（补测B12）。

关联 场景18-锁等待与死锁监控治理、补测B12-死锁后的应用重试机制。

六、复制与高可用原理

6.1 binlog 三种格式

格式 记录内容 特点
STATEMENT SQL 语句 日志小，但非确定函数/存储过程可能不一致
ROW（推荐） 行变更前后值 精确、安全，但日志大
MIXED 自动选择 语句级为主，必要时行级

6.2 主从复制原理

主库 Master                            从库 Slave
    │                                    │
    ├─ 写 binlog (逻辑日志)              │
    │                                    │
    └─ 客户端推送                        │
          │    ┌─────────────────────────▼──────────┐
          └──► │ IO 线程：拉取 binlog → 写 relay log │
               └─────────────────────────▲──────────┘
                                        │
                               ┌────────▼─────────┐
                               │ SQL 线程：重放     │
                               │ relay log → 数据   │
                               └──────────────────┘
  • 主库：写 binlog。
  • 从库：IO 线程拉取 binlog 存 relay log；SQL 线程重放 relay log。
  • 延迟：主从网络、从库 SQL 线程重放速度、大事务等导致。

6.3 复制模式

模式 说明
异步复制 主库不确认从库收到，延迟可能大，主宕机丢数据
半同步复制 主库等至少一个从库 ack 才提交，减少丢失
GTID 复制 全局事务 id，自动定位，切换更简单
组复制 MGR 多主，基于 Paxos，强一致

6.4 主从延迟的根源与治理

延迟根源： - 从库 SQL 线程串行重放（单线程瓶颈）。 - 大事务、DDL、慢 SQL 在主库耗时。 - 从库负载高、硬件弱。

治理方案： - 并行复制（多线程 SQL 线程）。 - 避免大事务、优化慢 SQL。 - 读写分离 + 延迟监控 + 从库自动摘除（补测B10）。 - 写后读一致性方案（强一致读 / 延迟双读，场景11）。

并行复制 MTS（Multi-Threaded Slave，重点）

从库 SQL 重放演进：
    单线程（老）: relay log ──串行──► 数据
    并行（MTS） : relay log ──┬──► 线程1 按库/按事务
                              ├──► 线程2
                              └──► 线程3
  • 原理：把 SQL 线程拆成协调线程 + 多个应用线程，并行重放不同库/不同事务。
  • 并行维度（slave_parallel_type）：
  • DATABASE：按库并行（各库独立）。
  • LOGICAL_CLOCK（8.0 推荐）：按事务提交顺序并行，主库并行事务在从库并行重放。
  • 并行度：slave_parallel_workers（如 8/16）。
  • 注意：同一行/同一库的修改仍串行（依赖关系），并行度受业务并发事务数限制。

6.5 主从一致性校验与修复

  • 校验：CHECKSUM TABLE / pt-table-checksum 对比主从数据。
  • 修复：pt-table-sync 按差异修复（补测B2）。

6.6 高可用架构

主从切换流程（故障转移，重点）

主库宕机 → 主从切换：
    ├─ ① 检测：健康探测/延迟监控发现主库故障
    ├─ ② 选新主：选数据最全、延迟最小的从库
    ├─ ③ 提升：新主停止复制、开启写入、通知其他从库重新指向新主
    ├─ ④ 应用切换：读写分离路由切到新主
    └─ ⑤ 恢复：旧主修复后作为新主的从库重新加入
  • 工具：MHA / Orchestrator / MGR（组复制自动选主）。
  • 关键：选新主需保证数据最全（用 GTID 定位到一致位置），避免丢数据。
  • 读多写少 failover：主故障读写都切从库（场景15）。
  • PITR 恢复：全量备份 + binlog 增量恢复到任意时间点（补测B1）。

关联 场景15-MySQL高可用、补测B10-主从延迟告警与从库自动摘除。

七、生产环境各种问题排查

基于原理定位生产问题。核心思路：先看监控指标，再用 EXPLAIN/日志定位，最后用原理分析根因。

7.1 慢查询排查流程

① 开启慢查询日志（long_query_time>1s, log_queries_not_using_indexes）
② 从 slow log 提取高频/超长 SQL
③ EXPLAIN 看执行计划（type/rows/possible_keys/key）
④ 看是否走错索引/全表扫/统计信息过期
⑤ 优化：加索引/覆盖索引/改写 SQL/冷热分离
  • 工具：performance_schema、EXPLAIN ANALYZE（8.0）。
  • 根因分类：索引失效、统计过期（补测B7）、深分页（补测B6）、大表无路由（补测B11）。

关联 场景5-索引失效与慢查询、场景14-慢查询定位与优化闭环。

7.2 连接相关问题排查

问题现象                     排查方向
    ├─ 连接数过高(Too many connections) → max_connections、Threads_connected
    ├─ 连接池耗尽(POOL_EXHAUSTED)      → 连接池大小、慢 SQL 占用连接
    ├─ 连接泄漏(连接数缓慢上涨)          → 代码未释放、max-lifetime、leakDetection
    └─ 连接被中断                     → wait_timeout、网络、防火墙
  • 核心指标：Threads_connected（当前连接）、Threads_running（运行中）。
  • 连接泄漏：监控连接数持续增长（补测B9）。
  • 连接耗尽：查看最慢 SQL/长事务占用连接（补测B5）。

关联 场景1-连接池与超卖问题、补测B5-连接耗尽治理、补测B9-连接泄漏。

7.3 锁等待与死锁排查

① 发现：业务报 1213(死锁)/1205(锁等待超时)/慢查询
② 定位：information_schema 的 INNODB_TRX / data_locks / data_lock_waits
③ 分析：谁持有锁、谁在等待、锁在哪行/哪间隙
④ 根因：事务过长、锁范围过大、顺序不一致、无索引全表锁
⑤ 治理：缩短事务、RC隔离、固定加锁顺序、加索引、死锁重试
  • 死锁日志：SHOW ENGINE INNODB STATUS 看最近死锁。
  • 锁监控：data_locks / data_lock_waits（8.0）。
  • 治理：死锁重试（补测B12）、锁监控（场景18）。

关联 场景18-锁等待与死锁监控治理、场景4-锁体系、补测B12。

7.4 主从延迟排查

① 指标：SHOW REPLICA STATUS 的 Seconds_Behind_Source
② 判断：延迟持续 >阈值 → 告警 + 摘除从库（补测B10）
③ 根因：大事务/慢SQL/从库负载高/并行复制未开启
④ 治理：并行复制MTS、拆分大事务、优化慢SQL、读写分离

关联 场景6、场景11、补测B10。

7.5 内存/IO/磁盘问题排查

问题 排查指标 根因/治理
内存不足 Buffer Pool 命中率低、swap 调 buffer_pool、排查大查询
IO 高 iostat、innodb_io_capacity 随机 IO 多（Change Buffer）、磁盘慢
磁盘满 binlog、undo、临时表膨胀 清理 binlog/归档、优化大事务
CPU 高 慢查询、SHOW PROCESSLIST 全表扫、缺索引、复杂 JOIN

关联 补测B8-容量规划与压测上限（评估 IO/CPU/磁盘饱和点）。

7.6 排查工具汇总

工具/视图 用途
EXPLAIN / EXPLAIN ANALYZE 执行计划、实际耗时
performance_schema 等待事件、SQL 统计、锁
information_schema.INNODB_TRX / data_locks 事务、锁等待
SHOW ENGINE INNODB STATUS 死锁、缓冲池状态
SHOW PROCESSLIST 当前连接/SQL 状态
slow log / binlog 慢 SQL、变更追踪
pt-query-digest / pt-table-checksum 慢查询分析、主从校验

八、生产环境各种参数调优

基于原理配置 MySQL 参数。核心原则：监控驱动调优，改参数前先看现状，改后验证。

8.1 核心参数总览

参数 建议 说明
innodb_buffer_pool_size 物理内存 60%-75% 数据缓存，最重要
innodb_flush_log_at_trx_commit 1（安全）/2（性能） redo 刷盘时机
sync_binlog 1（安全）/0（性能） binlog 刷盘
max_connections 按连接池上限+余量 连接上限
innodb_io_capacity 按磁盘（SSD 高） 刷脏页 IO 上限
innodb_flush_method O_DIRECT（SSD） 刷盘方式
slave_parallel_workers 8-16 从库并行复制
long_query_time 1s 慢查询阈值
innodb_lock_wait_timeout 5-50s 锁等待超时
innodb_deadlock_detect ON 死锁检测

8.2 读写性能调优

写优化（牺牲一点安全换吞吐）：

innodb_flush_log_at_trx_commit = 0/2   # redo 异步刷盘
sync_binlog = 0                          # binlog 异步刷盘
innodb_flush_method = O_DIRECT           # 绕过 OS 缓存直写
innodb_io_capacity = 2000+               # SSD 提高刷盘上限

读优化：

innodb_buffer_pool_size = 物理内存 60-75%   # 提高缓存命中
innodb_buffer_pool_instances = 8            # 多实例减少锁竞争
innodb_read_ahead_threshold                  # 预读

关联 场景13-InnoDB参数调优、补测B8-容量规划。

8.3 连接与线程调优

max_connections = 按应用连接池上限 ×1.2~1.5   # 预留余量
thread_cache_size = 适量（如 16-32）           # 复用线程
wait_timeout = 60-300s                        # 空闲连接超时
innodb_thread_concurrency                     # 并发线程数

关联 场景16-连接池参数调优、补测B9-连接泄漏。

8.4 事务与锁调优

innodb_lock_wait_timeout = 5-50s   # 锁等待超时，过长拖死业务
innodb_deadlock_detect = ON        # 保持死锁检测
transaction-isolation = RR/RC      # 选隔离级别
binlog_format = ROW                # 复制安全
gtid_mode = ON                     # 便于切换

关联 补测B12-死锁重试、场景2-事务隔离。

8.5 复制调优

sync_binlog = 1                  # 主库 binlog 刷盘（安全）
slave_parallel_type = LOGICAL_CLOCK  # 从库并行复制
slave_parallel_workers = 8-16       # 并行线程
binlog_expire_logs_seconds = 604800  # binlog 保留时间
log_replica_updates = ON             # 从库级联复制

关联 补测B10-主从延迟、场景15-高可用。

8.6 调优原则（加分项）

  1. 监控先行：调参前先看当前值、监控指标（命中率、IO、连接）。
  2. 一次一改：每次只改一个参数，便于验证效果。
  3. 备份可回滚：改前记录原值，可回滚。
  4. 动态 vs 持久：SET GLOBAL（运行态，重启失效）vs my.cnf（持久）。
  5. 权衡取舍：安全 vs 性能（刷盘）、一致 vs 性能（同步复制）。
  6. 压测验证：调优后用压测量化收益（补测B8）。

总结：八大板块内在关联

连接 → Server解析/优化/执行 ──► InnoDB(数据存取/索引/事务/锁/MVCC)
                                  │
       binlog ◄── 主从复制 ◄──────┘
       redo/undo ◄── InnoDB崩溃恢复/事务
  1. 一条 SQL 的生命周期贯穿所有板块（架构 → 索引 → 事务 → 锁）。
  2. InnoDB 是核心，承载索引、事务、锁、MVCC。
  3. 索引决定查询效率，统计信息影响优化器选索引。
  4. 事务/锁/MVCC 保证并发下的隔离与正确性。
  5. 复制/高可用 依赖 binlog + redo 两阶段提交保证一致性。
