场景10：Redis 缓存 + MySQL 双写一致性

2026-03-17mysql 系列约 5 分钟阅读MySQLRedis缓存

一、问题背景

Redis 缓存能大幅提升读性能（内存读 vs 磁盘读），但引入缓存与数据库双写一致性问题：更新 MySQL 后，缓存若不更新，业务会读到过期数据（脏数据）。本场景演示双写不一致的成因，以及 Cache Aside、延迟双删等解决策略。

演示表 t_cache_goods（商品），缓存 key：goods:GOODS-001。

二、双写一致性核心问题

Cache Aside（旁路缓存）模式： - 读：先查缓存，未命中则查 MySQL 并回填缓存 - 写：先更新 MySQL，再删除缓存（下次读重新回填）

不一致成因：只更新 MySQL 不删缓存 → 缓存残留旧值，业务读到脏数据；或删缓存与读回填之间存在并发窗口，读请求把旧值写回缓存。

三、实测结果

1. Cache Aside 读（/cache/read）

读取次数 source 缓存命中 数据
第 1 次 db ❌ iPhone 5999.00/100
第 2 次 cache ✅（2ms） 5999.00:100

结论：首次未命中查 MySQL 并回填，后续直接命中缓存（2ms）。

2. 双写不一致演示（/cache/inconsistent）

项目 值
MySQL 更新后 6099（价格 +100）
缓存（未删） 5999.00:100（旧值！）

结论：只更新 MySQL 不删缓存 → 缓存仍是旧值（5999），业务读到脏数据。必须更新后删缓存。

3. Cache Aside 正确写（/cache/cache-aside）

步骤 结果
更新 MySQL 到 6049 ✅
删除缓存 ✅
下次读 缓存未命中 → 查 MySQL 返回 6049 并回填

结论：先更新 DB 再删缓存，下次读会重新查库回填最新值，不会读到旧数据。

4. 延迟双删（/cache/delay-double-delete）

步骤 结果
更新 DB 到 6079 ✅
第一次删缓存 ✅
延迟 200ms ✅
第二次删缓存 ✅（缓存已清除）

结论：延迟双删清除"删缓存后、读回填前"窗口内回填的旧值，避免并发读把旧数据写回缓存。

5. 缓存命中 vs 未命中吞吐（/cache/bench）

并发 50、各 2 万次：

方式 QPS P99
缓存命中（读 Redis） 10432 21ms
缓存未命中（读 MySQL） 8410 62ms

结论：缓存命中比未命中 QPS 高约 1.2 倍、P99 从 62ms 降到 21ms（约 3 倍延迟改善）。缓存显著提升读性能。

四、生产避坑准则

  1. 写用 Cache Aside：先更新 DB，再删缓存（而非更新缓存），避免"更新缓存"与"读回填"竞争
  2. 延迟双删或 Canal：高并发下"删缓存 → 读回填"窗口会写回旧值，用延迟双删或订阅 binlog（Canal）异步删缓存
  3. 缓存过期兜底：给缓存设过期时间，即使删缓存失败最终也会失效，避免永久脏数据
  4. 避免缓存穿透/击穿/雪崩：空值也缓存（防穿透）、互斥重建（防击穿）、过期时间随机（防雪崩）
  5. 强一致场景可缓存旁路 + 事务消息：缓存与 DB 一致性要求极高时，可用可靠消息最终一致

五、要点速览

Redis 缓存 + MySQL 双写一致性：Cache Aside 模式——读先查缓存未命中查 DB 回填，写先更新 DB 再删缓存。实测：只更新 DB 不删缓存会导致缓存残留旧值（如 DB 6099、缓存仍 5999）；Cache Aside 先更新 DB 再删缓存可保证下次读回填最新值；高并发下需延迟双删或 Canal 订阅 binlog 规避"删缓存→读回填"写回旧值的窗口。缓存命中读 QPS 10432、未命中 8410，命中 P99 21ms vs 未命中 62ms。核心：写 DB 后必须删缓存，用延迟双删 + 缓存过期兜底保证最终一致。
