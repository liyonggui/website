# 补测B7：统计信息过期与执行计划优化

## 一、问题背景

优化器依赖**统计信息**选索引。数据量突变/统计信息过期时，优化器可能**选错索引**（type=ALL 全表扫）或 rows 严重高估，SQL 突然变慢。特别是**高度倾斜数据**（一个值占绝大部分），InnoDB 基数采样严重失真。

## 二、原理

```sql
-- EXPLAIN 关键字段
type           -- ALL(全表扫)/range/ref(走索引)/const，越靠左越差
possible_keys  -- 可能用的索引
key            -- 实际用的索引
rows           -- 优化器估算的扫描行数（统计信息决定）

-- 刷新统计信息
ANALYZE TABLE t_plan;                          -- 常规刷新
ANALYZE TABLE t_plan UPDATE HISTOGRAM ON category;  -- 生成直方图，精确统计倾斜分布
```

- **ANALYZE**：刷新索引基数（cardinality），常规手段。
- **直方图**：MySQL 8.0+，统计各值占比，对倾斜数据比基数采样精确。

## 三、演示接口

```bash
# 1. 初始化数据（热分类30万 + 冷1千，高度倾斜）
curl "http://localhost:8080/plan/init?hotRows=300000&coldRows=1000"

# 2. EXPLAIN 执行计划（看 rows 估算 vs 实际）
curl "http://localhost:8080/plan/explain?category=0"

# 3. ANALYZE 刷新统计信息
curl "http://localhost:8080/plan/analyze"

# 4. ANALYZE 前后对比（rows 偏差 + 直方图）
curl "http://localhost:8080/plan/before-after?category=0"

# 5. 状态
curl "http://localhost:8080/plan/status"
```

## 四、实测结果（热分类30万 + 冷1千）

| 环节 | 结果 |
|------|------|
| EXPLAIN category=0 | type=ref、key=idx_category、**rows估算=150380**、**实际=300000** |
| ANALYZE 后 | rows 估算仍 **150112**，偏差 **49.9%**（InnoDB 基数采样失真） |
| **直方图** | `buckets=[[0, 0.9967],[1, 1.0]]` → **category=0 占 99.67%**（精确揭示倾斜） |

**核心**：普通 ANALYZE 的基数采样对高度倾斜数据严重失真（估算 50% vs 实际 99.7%），**直方图能精确统计各值占比**（99.67%），是处理倾斜数据的进阶手段。

## 五、优化方案

1. **ANALYZE 常规刷新**：大批量 DML 后执行 `ANALYZE TABLE`，刷新基数统计。
2. **直方图**：倾斜数据用 `ANALYZE TABLE ... UPDATE HISTOGRAM ON 列`，精确统计分布。
3. **EXPLAIN 定位**：定期 EXPLAIN 巡检慢查询，看 type/rows 是否走错索引。
4. **强制索引**：必要时 `FORCE INDEX (idx)` 或优化 SQL 谓词。
5. **统计信息过期检测**：监控 `information_schema_stats_expiry`、索引 cardinality 异常。
6. **索引优化**：复合索引顺序、覆盖索引，减少回表。

## 六、要点速览

> **统计信息与执行计划**：优化器靠统计信息选索引，数据倾斜/过期会走错索引。实测热分类30万+冷1千，EXPLAIN rows 估算 15万 vs 实际 30万（偏差 50%），普通 ANALYZE 采样基数仍失真；**直方图** `[[0,0.9967],[1,1.0]]` 精确揭示 category=0 占 99.67%。优化：ANALYZE 刷新、直方图统计倾斜、EXPLAIN 巡检、FORCE INDEX。
