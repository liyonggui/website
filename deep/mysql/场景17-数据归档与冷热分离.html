场景17：数据归档与冷热分离

2026-04-01mysql 系列约 4 分钟阅读MySQL

一、问题背景

业务数据随时间持续累积，大表（订单/日志）行数越来越大，导致： - 查询需扫全表（含大量历史冷数据），性能下降 - 索引变大，缓存命中率降低 - 备份、迁移、统计耗时

冷热分离归档：把超期历史冷数据搬到归档表，热表只保留近期高频数据，实现"热表瘦身 → 查询快"。

二、核心思路

订单大表（冷热混合，180000行）
        │  按时间归档（30天前=冷数据）
        ├──> t_order_archive（归档表，冷数据，量大，少访问）
        └──> t_order_data（热表，近期热数据，瘦身，高频访问）

三、演示接口

# 1. 初始化冷热混合数据（12个月，每天500行，近30天为热）
curl "http://localhost:8080/archive/init?months=12&perDay=500&hotDays=30"

# 2. 冷热分布分析（按月统计，识别冷热边界）
curl "http://localhost:8080/archive/analyze"

# 3. 执行冷热分离归档（30天前为冷数据）
curl "http://localhost:8080/archive/archive?archiveDays=30"

# 4. 冷热表状态概览
curl "http://localhost:8080/archive/status"

# 5. 冷热查询性能对比
curl "http://localhost:8080/archive/bench?concurrency=50&total=10000"

# 6. 重置
curl "http://localhost:8080/archive/reset"

四、实测结果

1. 初始化与归档

环节 热表行数 归档表行数
归档前（冷热混合） 180000 0
归档后（30天前为冷） 15500（瘦身 11.6 倍） 164500

归档 164500 条冷数据，热表从 18 万瘦身到 1.55 万行。

2. 冷热查询性能对比（并发50）

方案 QPS p99Ms
归档表（冷数据，量大 164500 行） 108 1998
热表（瘦身后，量小 15500 行） 1223 148
提升 约 11 倍 13 倍

数据量小 → 索引有效 + 缓存命中高 → 查询快。冷热分离把高频热数据单独存放，是典型的"以空间/管理成本换查询性能"。

五、工程要点

  1. 冷热边界按业务定：如订单 90 天、日志 30 天、交易流水按账期。
  2. 归档方式：INSERT INTO 归档表 SELECT ... WHERE create_time < 边界 + 删除热表冷数据，放事务/分批执行。
  3. 归档表设计：与热表同构 + archive_time 记录归档时间，冷数据按需查询。
  4. 更优方案：MySQL 分区表（按时间分区，DROP 过期分区），或归档到数仓/OSS/ES。
  5. 冷数据访问：归档后从归档表/数仓查历史，热表只服务高频实时查询。
  6. 定时任务：用定时任务（cron/XXL-JOB）周期归档，避免一次性大事务。

六、要点速览

冷热分离归档：数据累积导致大表查询慢，把超期冷数据归档到归档表、热表瘦身。实测 18 万行订单表归档 30 天前冷数据后，热表瘦身到 1.55 万行（11.6 倍），查询吞吐从 108 提到 1223（约 11 倍），p99 从 1998ms 降到 148ms。原理：数据量小→索引有效+缓存命中高。工程上用定时任务按业务边界归档，或 MySQL 分区表 DROP 过期分区，冷数据放数仓/OSS 按需查询。
