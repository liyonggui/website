# 补测B9：连接泄漏与长连接治理

## 一、问题背景

**连接泄漏**：获取数据库连接后忘记释放，连接池/数据库连接被**慢性耗尽**，最终报 `Too many connections` 雪崩。是生产环境最常见的"隐藏故障"（进程运行几天/几周后连接缓慢涨满）。

## 二、原理

```
复用(正确释放)                        泄漏(忘记释放)
try (Connection c = pool.get()) {      Connection c = pool.get();  // 不关闭
    ...                                ...
}   // 自动 close，连接回池复用         // 永不释放，连接一直占用

连接数稳定                             连接数持续增长
                                       → 连接池耗尽 → Too many connections 雪崩
```

- **长连接复用**：try-with-resources 正确释放，连接回池复用，连接数稳定。
- **连接泄漏**：获取不释放，连接永久占用，慢性耗尽。

## 三、演示接口

```bash
# 1. 初始连接状态
curl "http://localhost:8080/conn-leak/compare"

# 2. 长连接复用（正确释放,50次）— 连接数应稳定
curl "http://localhost:8080/conn-leak/reuse?count=50"

# 3. 模拟泄漏（50个不释放）— 连接数应 +50
curl "http://localhost:8080/conn-leak/leak?count=50"

# 4. 泄漏后对比（连接数增长、使用率攀升）
curl "http://localhost:8080/conn-leak/compare"

# 5. 治理:释放泄漏连接
curl "http://localhost:8080/conn-leak/recover"

# 6. 治理后对比（连接回落）
curl "http://localhost:8080/conn-leak/compare"
```

## 四、实测结果

| 环节 | 连接数变化 | 说明 |
|------|-----------|------|
| 初始 | 9（使用率0.9%） | 健康 |
| **复用**（正确释放50次） | **9 → 9（+0）** | 连接池复用，不增长 |
| **泄漏**（50个不释放） | **9 → 59（+50）** | 连接慢性耗尽 |
| 泄漏后 | 59（使用率5.9%） | 连接池被占用 |
| **治理**（释放） | **→ 9** | 连接回落，恢复健康 |

**核心对比**：复用 50 次连接数 **+0**，泄漏 50 个连接数 **+50**。泄漏会慢性耗尽连接池，正确释放（复用）是根治。

## 五、治理方案

1. **try-with-resources**：Java 用 try-with-resources 保证连接自动释放，杜绝泄漏。
2. **连接池生命周期**：设 `max-lifetime`（如 30 分钟）、`idle-timeout`，过期/空闲连接自动回收。
3. **监控告警**：监控 `Threads_connected`，使用率超 80% 告警，提前发现泄漏。
4. **泄漏检测**：HikariCP `leakDetectionThreshold` 检测连接泄漏并告警。
5. **快速失败**：连接池 `connectionTimeout` 快速失败，不无限等待。
6. **代码审查**：排查所有获取连接未释放的路径（异常分支尤其容易漏）。

## 六、面试简述

> **连接泄漏治理**：获取连接不释放会慢性耗尽连接池，最终 Too many connections 雪崩。实测复用（try-with-resources）50 次连接数 0 增长，泄漏 50 个连接数 +50。治理：try-with-resources 保证释放、连接池设 max-lifetime/leakDetectionThreshold、监控 Threads_connected 使用率超 80% 告警、快速失败。
