# 场景8：批量写入优化

## 一、问题背景

MySQL 单条 INSERT 的瓶颈主要在**网络往返**和**事务提交**：逐条插入时每条 SQL 一次网络往返 + 一个事务（autocommit），高并发/大批量导入时性能极差。**批量写入**通过减少 SQL 次数、合并事务、驱动级优化，可带来数量级的吞吐提升。

本场景用表 `t_batch_test`，对比四种写入方式在同样 1 万行下的耗时与吞吐。

## 二、四种写入方式

| 方式 | 说明 | SQL/事务 |
|------|------|------|
| 1. singleInsert | 逐条 INSERT + autocommit | 每条一个事务、一次网络往返 |
| 2. txInsert | 事务内逐条 INSERT | 多条包一个事务，减少提交，但逐条执行 |
| 3. multiValues | 单条多值 INSERT | 一条 SQL 插多行，减少 SQL 次数 |
| 4. jdbcBatch | JDBC addBatch + rewriteBatchedStatements | 驱动把多条 INSERT 合并成多值语句执行 |

## 三、实测结果（1 万行，batchSize=500）

| 写入方式 | 耗时 (ms) | 吞吐 (行/秒) | 相对逐条 |
|------|------|------|------|
| **singleInsert（逐条）** | 229363 | **43** | 基准 |
| **txInsert（事务内逐条）** | 2773 | 3606 | **快 84 倍** |
| **multiValues（单条多值）** | 980 | 10204 | **快 237 倍** |
| **jdbcBatch（JDBC Batch）** | 905 | **11049** | **快 257 倍** |

**结论**：
- **逐条 INSERT 极慢**（43 行/秒）：每条一个事务 + 一次网络往返，磁盘 fsync 成为瓶颈
- **事务内逐条**（3606 行/秒）：减少提交次数，提升显著（快 84 倍）
- **单条多值**（10204 行/秒）：一条 SQL 插多行，减少 SQL 与网络往返（快 237 倍）
- **JDBC Batch + rewriteBatchedStatements**（11049 行/秒）：驱动级多值合并，**最快（快 257 倍）**

> 逐条 INSERT 耗时 229 秒是 autocommit 下每条强制 fsync 的典型表现；批量写入把 fsync 次数从 N 次降到 N/batchSize 次，是吞吐暴涨的根源。

## 四、生产避坑准则

1. **严禁逐条 INSERT**：循环里逐条 `INSERT` + autocommit 是写入性能杀手（大数据量下数百倍差距）
2. **批量必须开 rewriteBatchedStatements**：JDBC URL 加 `rewriteBatchedStatements=true`，驱动才会把多条 INSERT 合并成多值语句；否则 executeBatch 只是逐条发送
3. **batchSize 适中**：一般 500~1000 为宜，过大导致单条 SQL 过长、内存占用高；过小优化不明显
4. **批量事务提交**：批量写入放在一个事务里（或分批提交），减少 fsync 次数
5. **单条多值 SQL 注意长度**：`max_allowed_packet` 限制单条 SQL 大小，批量别超限
6. **大批量导入**：可考虑 `LOAD DATA INFILE`（比 INSERT 更快），或分片并行写入

## 五、要点速览

> **批量写入优化**：逐条 INSERT（autocommit）每条一个事务 + 一次网络往返，1 万行耗时 229 秒、仅 43 行/秒；事务内逐条 3606 行/秒（减少提交）；单条多值 INSERT 10204 行/秒（减少 SQL 次数）；**JDBC addBatch + rewriteBatchedStatements** 11049 行/秒，比逐条快 **257 倍**。核心：批量写入减少 fsync 次数与网络往返，`rewriteBatchedStatements=true` 是关键开关，batchSize 取 500~1000 最佳。
