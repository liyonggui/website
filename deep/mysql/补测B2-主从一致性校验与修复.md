# 补测B2：主从数据一致性校验与修复（pt-table-checksum / pt-table-sync）

## 一、问题背景

主从复制可能**静默丢数据/漂移**：某条 SQL 在从库执行失败被跳过、人为改库、DDL 不同步，都会导致**主从数据不一致而不自知**。复制线程 Running 只代表"复制在跑"，**不代表数据一致**。需定期用 checksum 校验主从一致性，发现漂移立即修复。

## 二、核心思路

```
主库(数据权威)  --复制-->  从库(只读副本)
      │                        │
      └── CHECKSUM TABLE 校验 ──┘
            │ 不一致(漂移)
            └──> 用主库数据覆盖从库 (等价 pt-table-sync) → 恢复一致
```

- **一致性校验**：主库、从库分别执行 `CHECKSUM TABLE t_consistency`，对比校验和。
- **制造漂移**：临时关从库 `read_only`，故意改/删从库数据。
- **修复**：从主库导出全量 → 从库 TRUNCATE → 导入 → 复核（等价 pt-table-sync 的 INSERT/UPDATE/DELETE 对齐）。

## 三、演示接口

```bash
# 1. 初始化主从一致数据
curl "http://localhost:8080/consistency/init?rows=5000"

# 2. 主从一致性校验（CHECKSUM 对比）
curl "http://localhost:8080/consistency/check"

# 3. 制造主从不一致（模拟复制漂移：改/删从库）
curl "http://localhost:8080/consistency/damage?damageRows=2000"

# 4. 再校验（应检测出不一致）
curl "http://localhost:8080/consistency/check"

# 5. 修复（pt-table-sync：用主库覆盖从库）
curl "http://localhost:8080/consistency/fix"

# 6. 复核（应恢复一致）
curl "http://localhost:8080/consistency/check"

# 7. 复制状态与一致性概览
curl "http://localhost:8080/consistency/status"
```

## 四、实测结果（校验 → 制造漂移 → 修复闭环）

| 环节 | 主库 | 从库 | 是否一致 |
|------|-----|-----|---------|
| init 5000 | 5000 | 5000 | ✅ true |
| damage 2000（只改从库） | **5000**（不受影响） | **3000**（改2千+删2千） | ❌ **false**（检测出漂移） |
| fix（pt-table-sync） | 5000 | 5000 | ✅ true（修复后一致） |

**关键**：damage 只影响从库（主库保持 5000），`CHECKSUM` 成功检测到不一致，`fix` 用主库覆盖从库后恢复一致。

## 五、工程要点

1. **复制健康 ≠ 数据一致**：`Replica_SQL_Running=Yes` 不代表主从数据一致，需定期 checksum。
2. **校验工具**：`pt-table-checksum`（Percona）最常用；也可用 `CHECKSUM TABLE` 或自建比对脚本。
3. **修复工具**：`pt-table-sync`，只同步差异行；演示用"全量覆盖"简化。
4. **定期任务**：低峰期跑校验（checksum 有开销），发现漂移告警并自动/手动修复。
5. **从库写保护**：从库必须 `read_only=ON`，防人为漂移；本演示需临时关闭模拟漂移。
6. **GTID 复制**：用 GTID 自动定位断点，漂移后从主库 dump + `CHANGE REPLICATION SOURCE` 重挂。

## 六、踩坑记录（多 DataSource 注入）

ConsistencyService 最初用 Lombok `@RequiredArgsConstructor` + 字段 `@Qualifier("replicaDataSource")`，因 Lombok 不会把字段注解复制到构造器参数，**多 DataSource 构造器注入发生歧义，从库连到了主库**（damage 反而改坏了主库）。
**修复**：改用显式构造器 + `@Qualifier`，日志确认注入 `replica=jdbc:mysql://mysql-slave:3306/...` 正确。

## 七、面试简述

> **主从一致性校验与修复**：复制线程 Running ≠ 数据一致，复制可能静默漂移（SQL 在从库失败被跳过、人为改库）。用 `pt-table-checksum`/`CHECKSUM TABLE` 定期校验主从一致，发现漂移用 `pt-table-sync` 用主库数据对齐从库。实测制造从库漂移后 checksum 检测出不一致（主5000/从3000），修复后恢复一致。从库必须 read_only=ON 防人为漂移。
