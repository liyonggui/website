场景5：索引失效与慢查询

2026-04-17mysql 系列约 13 分钟阅读MySQL索引

一、问题背景

MySQL 在数据量大时，若查询未命中合适的索引，会退化为全表扫描（type=ALL），导致慢查询、CPU 打满、锁表。索引失效通常源于写法问题（函数、隐式转换、like 前导、or、最左前缀、范围等），而非索引本身失效。

本场景用大数据量表 t_idx_test（20 万行）系统性复现六类索引失效，并通过 EXPLAIN + 实测耗时 + 并发压测量化"索引失效 → 慢查询"的因果链。

演示表 t_idx_test：

字段 类型 索引
id BIGINT PK 主键
user_id BIGINT 联合索引 (user_id,type,status)
name VARCHAR(32) idx_name
phone VARCHAR(20) idx_phone
type INT 联合索引
status TINYINT 联合索引

二、九类索引失效实测（20 万行）

type=ALL 表示全表扫描、key=null 表示未使用索引；type=ref/range、key 非空表示走索引。

1. 函数操作导致索引失效（/index-invalid/function）

-- ❌ 坏：LEFT() 包裹索引列 → 索引失效
SELECT * FROM t_idx_test WHERE LEFT(name, 6) = '用户000';
-- ✅ 好：等值 → 走 idx_name
SELECT * FROM t_idx_test WHERE name = '用户000001';
项目 type key rows 耗时
坏（LEFT 函数） ALL null 20 万 66ms
好（等值） ref idx_name 1 1ms

结论：对索引列做函数运算，索引立即失效，退化为全表扫描。

2. 隐式类型转换导致索引失效（/index-invalid/implicit-cast）

-- ❌ 坏：phone 是 VARCHAR，用数字比较 → 隐式转换、索引失效
SELECT * FROM t_idx_test WHERE phone = 13800000000;
-- ✅ 好：字符串字面量 → 走 idx_phone
SELECT * FROM t_idx_test WHERE phone = '13800000000';
项目 type key rows 耗时
坏（数字） ALL null 20 万 53ms
好（字符串） ref idx_phone 1 0ms

结论：索引列类型与参数类型不一致，触发隐式转换，索引失效。

3. like 前导通配符导致索引失效（/index-invalid/like-leading）

-- ❌ 坏：% 在前 → 无法利用 B+ 树最左匹配
SELECT * FROM t_idx_test WHERE name LIKE '%000001';
-- ✅ 好：% 在右 → 走 idx_name 范围扫描
SELECT * FROM t_idx_test WHERE name LIKE '用户000001%';
项目 type key rows 耗时
坏（前导通配） ALL null 20 万 89ms
好（前缀匹配） range idx_name 1 1ms

结论：LIKE '%xxx' 不满足最左匹配原则，索引失效；LIKE 'xxx%' 走索引。

4. or 连接导致索引失效（/index-invalid/or）

-- ❌ 坏：name 走索引，但 status 无单列索引 → 整体降级全表扫描
SELECT * FROM t_idx_test WHERE name = '用户000001' OR status = 1;
-- ✅ 好：拆 UNION ALL，name 分支走索引
SELECT * FROM t_idx_test WHERE name = '用户000001'
UNION ALL SELECT * FROM t_idx_test WHERE status = 1;
项目 type key 耗时
坏（or） ALL null 110ms
好（UNION ALL） ref idx_name 93ms

结论：or 连接的多个条件只要有一个无法走索引，整体就可能退化为全表扫描。

5. 联合索引最左前缀失效（/index-invalid/leftmost-prefix）

-- ❌ 坏：直接查 status（跳过最左列 user_id,type）→ 索引失效
SELECT * FROM t_idx_test WHERE status = 1;
-- ✅ 好：按最左列 user_id 查询 → 走联合索引
SELECT * FROM t_idx_test WHERE user_id = 100;
项目 type key rows 耗时
坏（跳过最左列） ALL null 20 万 111ms
好（最左列） ref idx_user_type_status 20 1ms

结论：联合索引必须遵循最左前缀原则，跳过最左列直接查后面的列，索引失效。

6. 范围查询导致索引失效（/index-invalid/range）

-- ❌ 坏：user_id 等值 + type 范围，type 之后 status 无法继续用索引
SELECT * FROM t_idx_test WHERE user_id = 100 AND type > 2 AND status = 1;
-- ✅ 好：等值匹配，三列都可用索引
SELECT * FROM t_idx_test WHERE user_id = 100 AND type = 2 AND status = 1;
项目 type key Extra
坏（范围） range idx_user_type_status Using index condition
好（等值） ref idx_user_type_status -

结论：联合索引中范围条件之后的列无法继续走索引（只能回表过滤）。范围前用等值，可最大限度利用联合索引。

7. 不等值判断导致索引失效（/index-invalid/inequality）

-- ❌ 坏：user_id <> 100 → 需扫描全部非目标行，索引失效
SELECT * FROM t_idx_test WHERE user_id <> 100;
-- ✅ 好：等值 → 走联合索引
SELECT * FROM t_idx_test WHERE user_id = 100;
项目 type key rows 耗时
坏（<>） ALL null 20 万 144ms
好（等值） ref idx_user_type_status 20 1ms

结论：!=、<>、NOT IN、NOT LIKE 等"取反"运算通常无法走索引（需扫描全部不匹配行），优化器一般选全表扫描。

8. 索引列算术运算导致索引失效（/index-invalid/arithmetic）

-- ❌ 坏：对主键列做算术运算 → 索引失效
SELECT * FROM t_idx_test WHERE id + 1 > 2;
-- ✅ 好：运算移到条件右侧 → 走主键索引
SELECT * FROM t_idx_test WHERE id > 1;
项目 type key rows 耗时
坏（id+1） ALL null 20 万 204ms
好（id） range PRIMARY 10 万 94ms

结论：对索引列做 + - * / 等运算，等价于对索引列套函数 → 索引失效。把运算移到等号/条件右侧即可恢复索引。

9. IS NOT NULL 判断导致索引失效（/index-invalid/is-not-null）

-- ❌ 坏：phone IS NOT NULL → 需扫描绝大多数非空行，走全表扫描
SELECT * FROM t_idx_test WHERE phone IS NOT NULL;
-- ✅ 好：等值匹配 → 走 idx_phone
SELECT * FROM t_idx_test WHERE phone = '13800000000';
项目 type key rows 耗时
坏（IS NOT NULL） ALL null 20 万 116ms
好（等值） ref idx_phone 1 1ms

结论：IS NULL 通常可走索引（扫描空值区间），但 IS NOT NULL 因需扫描大量非空行，优化器常放弃索引走全表扫描。

三、并发压测：索引失效 vs 生效（/index-invalid/bench）

在 20 万行数据上，并发 50、各 2 万次请求，对比索引失效（全表扫描）与索引生效（索引定位）：

指标 坏 SQL（status=1 全表扫） 好 SQL（user_id=100 走索引）
QPS 8643 21810
P99 延迟 57ms 22ms

结论：同一并发下，索引失效导致 QPS 降低约 2.5 倍、P99 延迟升高约 2.6 倍。索引失效是高并发下慢查询与吞吐骤降的核心诱因。

四、生产避坑准则

  1. 索引列禁用函数/算术运算：WHERE LEFT(name,n)=...、WHERE id+1>2 → 改写 LIKE 'xxx%'/等值，或把运算移到条件右侧
  2. 类型严格一致：字符串字段用字符串字面量，杜绝隐式转换（phone = 138... 改为 phone = '138...'）
  3. like 避免前导通配符：LIKE '%xxx' 改为 LIKE 'xxx%' 或走搜索引擎
  4. or 拆分 UNION ALL：或让 or 的所有条件都能走索引
  5. 联合索引遵守最左前缀：查询条件从最左列开始；范围条件尽量放最后或用等值
  6. 少用不等值/取反：!=、<>、NOT IN、NOT LIKE 尽量改写成范围或等值
  7. 避免 IS NOT NULL 大范围：非空字段筛选优先用等值/范围，而非 IS NOT NULL
  8. 用 EXPLAIN 兜底：上线前检查 type 是否为 ALL、key 是否为 null

五、要点速览

索引失效九大场景：① 函数操作（LEFT(name) 包裹索引列）；② 隐式类型转换（VARCHAR 字段用数字比较）；③ like 前导通配符（LIKE '%xx'）；④ or 连接（部分条件无法走索引时整体失效）；⑤ 联合索引不满足最左前缀；⑥ 联合索引范围条件之后的列失效；⑦ 不等值判断（!=/<>/NOT IN/NOT LIKE）；⑧ 索引列算术运算（id+1>2）；⑨ IS NOT NULL。实测 20 万行数据下，失效时全表扫描（type=ALL）单次约 50-200ms，生效时走索引（type=ref/range）约 0-1ms，相差约百倍；并发 50 下 QPS 从 21810 降到 8643、P99 从 22ms 升到 57ms。生产用 EXPLAIN 检查 type/key，杜绝全表扫描。
