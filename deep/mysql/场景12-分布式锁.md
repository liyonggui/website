# 场景12：分布式锁（基于 MySQL 唯一索引 / 锁表）

## 一、核心原理

在分布式/多实例场景下，单机 `synchronized`/`ReentrantLock` 无法跨进程互斥，需要**分布式锁**。MySQL 分布式锁的核心：

- **唯一索引抢锁**：`lock_key` 建唯一索引，`INSERT` 成功 = 加锁成功；主键冲突（错误码 1062）= 锁已被占用。MySQL 靠唯一索引天然保证互斥。
- **owner 防误删**：每把锁记录持有者 `owner`，释放时 `DELETE ... WHERE owner = ?`，防止 A 释放了 B 刚重新持有的锁。
- **expire 过期**：加锁带过期时间，防止持有者宕机后锁永远不释放（死锁）。过期后可被抢占。
- **续期**：长任务在过期前续期，避免临界区未完成锁先失效。

## 二、实现方式对比

| 方式 | 加锁 | 释放 | 优点 | 缺点 |
|------|------|------|------|------|
| **唯一索引 INSERT** | 插入成功即获锁 | DELETE + owner 校验 | 实现简单、天然互斥、无死锁（配合过期） | 需处理过期锁抢占 |
| **悲观锁 FOR UPDATE** | 锁表行 | COMMIT 自动释放 | 语义直观、阻塞式获取 | 连接需长事务、占用连接 |
| **乐观锁版本号** | 期望版本 UPDATE | 失败重试 | 无锁、吞吐高 | 冲突多时重试开销大 |
| **Redis SETNX** | SET NX EX | 校验值后 DEL | 吞吐高、内存操作快 | 需额外 Redis 组件 |

> 本项目聚焦 MySQL 方案（唯一索引 + 悲观锁），并展示 owner/过期/续期工程细节。

## 三、演示接口

```bash
# 1. 唯一索引非阻塞抢锁（INSERT 唯一索引）
# 两次同 lockKey 第二次会失败（唯一索引冲突）
curl "http://localhost:8080/dist-lock/try-lock?lockKey=ORDER-001&owner=node-1&expireSec=10"
curl "http://localhost:8080/dist-lock/try-lock?lockKey=ORDER-001&owner=node-2&expireSec=10"

# 2. 阻塞式加锁（带超时重试）
curl "http://localhost:8080/dist-lock/lock?lockKey=ORDER-001&owner=node-1&expireSec=10&waitMs=3000"

# 3. 释放锁（owner 校验：owner 不匹配不会误删）
curl "http://localhost:8080/dist-lock/unlock?lockKey=ORDER-001&owner=node-1"

# 4. 续期（仅 owner 可续，防误续他人锁）
curl "http://localhost:8080/dist-lock/renew?lockKey=ORDER-001&owner=node-1&expireSec=20"

# 5. 悲观锁（SELECT ... FOR UPDATE 行锁互斥）
curl "http://localhost:8080/dist-lock/pessimistic?lockKey=LOCK-PESS&owner=owner-a&waitMs=3000"

# 6. 临界区并发验证：分布式锁互斥（串行扣减） vs 无锁（数据竞争）
curl "http://localhost:8080/dist-lock/critical-section?concurrency=20&perThread=50&useLock=true"
curl "http://localhost:8080/dist-lock/critical-section?concurrency=20&perThread=50&useLock=false"

# 7. 无锁 vs 分布式锁 吞吐对比
curl "http://localhost:8080/dist-lock/bench?concurrency=50&total=20000"

# 8. 当前锁表状态
curl "http://localhost:8080/dist-lock/status"
```

## 四、关键现象

### 1. 唯一索引互斥
`try-lock` 两次同一 `lockKey`，第二次返回 `acquired=false`：
> INSERT 唯一索引成功 = 加锁成功；主键冲突（1062）= 锁已被占用。MySQL 唯一索引天然保证同一时刻只有一把锁。

### 2. owner 防误删
先 `node-1` 加锁，再用 `node-2` 尝试 unlock：因 `WHERE owner='node-2'` 不匹配，**不会误删** node-1 的锁。

### 3. 过期抢占
持有者宕机导致锁过期后，新持有者通过 `tryTakeExpired`（`DELETE ... WHERE expire_time < NOW()` 后重 INSERT）抢占过期锁，避免死锁。

### 4. 临界区并发
- `useLock=true`：20 线程 × 50 次 = 1000 次扣减，`finalBalance = initBalance - 1000`，**0 丢失更新**。
- `useLock=false`：无锁裸扣减（读-改-写非原子），出现**丢失更新**，`lostUpdates ≠ 0`。

### 5. 吞吐权衡
分布式锁为保互斥串行化临界区，`qps` 显著低于无锁读。这是"一致性换吞吐"的本质——只有必须互斥的操作才需加锁。

## 五、工程注意点

1. **过期时间要合理**：太短→任务未完锁失效；太长→宕机后锁占太久。
2. **owner 必须唯一且校验**：用 进程ID/实例ID + UUID，防止误删他人锁。
3. **锁粒度要小**：粒度越小并发越高；尽量用业务 key（如 `ORDER-{id}`）而非全局一把锁。
4. **依赖数据库可用性**：数据库抖动会导致抢锁/释放失败，适合一致性要求高、并发可控的场景；超高吞吐可改用 Redis。
5. **连接占用**：悲观锁 FOR UPDATE 需持有连接至事务结束，注意连接池水位。
6. **与本地缓存锁/DB 事务锁区别**：MySQL 分布式锁跨实例生效，而 DB 行锁仅在单个数据库实例内有效。

## 六、结论

MySQL 分布式锁借助**唯一索引冲突**实现跨节点互斥，实现简单、可靠，配合 **owner 校验 + 过期时间 + 续期** 可覆盖宕机、误释放等工程问题。适合对一致性要求高、并发量中等的场景；对极致吞吐可用 Redis 分布式锁。核心取舍：**用串行化的吞吐代价换取跨实例的数据一致性**。
