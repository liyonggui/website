场景1：连接池与超卖问题（四种扣减策略对比）

2026-03-11mysql 系列约 8 分钟阅读MySQL

一、问题背景

高并发秒杀/抢购场景下，多个请求同时扣减同一商品的库存。若不加任何并发控制，会导致超卖（库存减为负数）；而错误的加锁策略又会带来性能损耗或死锁。

本场景在同一张 t_stock 表上，用相同并发量压测四种扣减策略，量化其超卖率 / 成功数 / 吞吐 / 延迟。

二、四种策略

1. oversell —— 先查后减（无锁，问题演示）

SELECT stock FROM t_stock WHERE product_no = ?;   -- 读到旧值
UPDATE t_stock SET stock = stock - ? WHERE product_no = ?;  -- 覆盖写

多个线程同时读到 stock=100，各自 UPDATE stock=stock-1，最终结果取决于最后写入者，导致扣减次数丢失、库存减为负数。

2. atomic —— 原子条件更新（推荐，SQL 层保证）

UPDATE t_stock SET stock = stock - ?
WHERE product_no = ? AND stock >= ?;   -- 条件不满足则影响行数为 0

利用 InnoDB 行锁 + 条件判断，在单条 UPDATE 内完成"检查库存 + 扣减"，天然原子，杜绝超卖，且无显式事务/锁开销，性能最优。

3. pessimistic —— 悲观锁（SELECT ... FOR UPDATE）

BEGIN;
SELECT stock FROM t_stock WHERE product_no = ? FOR UPDATE;  -- 行锁，阻塞其它写
UPDATE t_stock SET stock = stock - ? WHERE product_no = ?;
COMMIT;

事务内加排他行锁，其它事务必须等待锁释放，保证读改写一致。代价是并发度受限、锁等待增加，高并发下吞吐下降明显。

4. optimistic —— 乐观锁（版本号）

SELECT stock, version FROM t_stock WHERE product_no = ?;
UPDATE t_stock SET stock = stock - ?, version = version + 1
WHERE product_no = ? AND version = ? AND stock >= ?;
-- 影响行数 = 0 表示版本冲突，需重试

不加锁，通过版本号比对判断是否被并发修改，冲突时由应用层重试。适合读多写少、冲突不频繁的场景；冲突率高时重试开销会放大。

三、压测结果（实测）

压测方式：对 SKU-10002（单行热点）打满 1000 次扣减，并发 20，每种模式前重置库存为 1000。 运行脚本：loadtester/run-single.ps1（单模式） / run-benchall.ps1（四种模式一次性对比）。

策略 成功 冲突/失败 QPS P50 P95 P99 最终库存 结论
oversell 1000 0 1126 153 197 212 0（可再扣为负） ❌ 超卖，不可用
optimistic（重试5） 261 739 冲突 328 64 88 124 739 ⚠️ 单行高冲突，正确性差
pessimistic 1000 0 114 171 209 226 0 ✅ 正确，锁等待
atomic 1000 0 103 164 321 679 0 ✅ 推荐

关键结论

  1. oversell 最快（1126 QPS）但超卖：先查后减不检查条件，一旦库存见底继续扣就变负数（实测 SKU-10001 100 库存被扣成 -19）。性能最优但错误。
  2. optimistic 在单行热点下冲突率高达 74%（739/1000）：所有请求竞争同一行，版本号频繁自增，即使重试 5 次仍大量失败，最终只成功 261 次。乐观锁不适合高并发单行热点。
  3. atomic 与 pessimistic 均正确（0 超卖、0 冲突）：都受限于单行 InnoDB 行锁串行化，性能相当（~100 QPS）。
  4. atomic 为最优解：单条 UPDATE ... WHERE stock >= n 原子完成"检查 + 扣减"，无显式事务/锁/重试开销，代码最简、生产首选。

补充：多行分布式压测（消除单行热点干扰）

单行热点会掩盖各模式的真实性能差异（都被行锁串行化），故用 50 个商品、请求随机分布到各行的方式复测（并发 30，每模式 20000 请求）：

策略 成功 冲突/失败 QPS P50 P95 P99 结论
oversell 20000 0 2289 10 25 43 ❌ 超卖，不可用
atomic 20000 0 2204 10 28 49 ✅ 推荐（正确且最快）
optimistic 19856 144 冲突(0.7%) 2054 11 31 52 ✅ 冲突率低，读多写少适用
pessimistic 20000 0 1765 13 35 62 ✅ 正确，事务+锁开销略大

结论： - 多行分布下 atomic（2204 QPS）与 oversell（2289 QPS）几乎持平，但 atomic 正确（0 超卖），oversell 不可用。 - optimistic 在多行分布下冲突率骤降至 0.7%（vs 单行热点 74%），印证其适合多行、读多写少，不适合单行热点。 - pessimistic 因每个请求要 BEGIN + FOR UPDATE + COMMIT 事务开销，吞吐最低（1765 QPS）。 - atomic 是"保证正确 + 性能最优"的唯一解，为生产首选。

四、生产建议

  1. 首选 atomic 条件更新：单条 SQL 原子扣减，无锁竞争、无死锁、性能最优。
  2. 悲观锁适合必须依赖锁保证一致性且并发不高的写场景；注意控制事务时长，避免长事务持锁。
  3. 乐观锁适合读多写少；冲突率高时应考虑 atomic 或消息队列削峰。
  4. 无论哪种策略，最终都要配合唯一约束（如订单号唯一）兜底防重复。

五、要点速览

超卖问题：高并发下先查后减会超卖。用 UPDATE ... WHERE stock >= n 条件更新，借助 InnoDB 行锁保证原子性，单条 SQL 杜绝超卖且性能最优；对比悲观锁（FOR UPDATE，并发受限）和乐观锁（版本号+重试，适合读多写少）。
