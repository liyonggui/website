场景4：间隙锁 / Next-Key Lock

场景4：间隙锁 / Next-Key Lock

一、问题背景

InnoDB 在 REPEATABLE READ 隔离级别下，通过间隙锁（Gap Lock）和 Next-Key Lock 防止幻读，但也因此引入了锁范围扩大与间隙锁死锁等并发问题。生产上常因对锁机制理解不清，出现插入被阻塞、死锁频发或锁范围过大拖垮并发。

本场景用专用表 t_gap_lock（含非唯一索引）演示 InnoDB 的间隙锁行为。

二、三种锁类型

锁类型 mode 说明
记录锁（Record Lock） X,REC_NOT_GAP 锁住具体记录，主键/唯一索引等值命中时产生
间隙锁（Gap Lock） X,GAP 锁住索引记录间的间隙，防止其它事务在间隙插入
Next-Key Lock X 记录锁 + 间隙锁的组合，锁住记录及其前向间隙，防止幻读

关键：间隙锁不互相阻塞（间隙锁是共享的，只阻塞"插入"），只有记录锁/Next-Key 的记录部分才互斥。这是场景3死锁演示"不触发"的根因。

三、Next-Key Lock 产生的条件

  • 主键 / 唯一索引等值命中：只加记录锁（X,REC_NOT_GAP），不加间隙锁
  • 非唯一索引等值 或 范围查询：加 Next-Key Lock（X）+ 间隙锁（X,GAP），锁范围扩大
  • 无索引条件：锁全表（所有间隙）

四、实测结果

演示表：t_gap_lock（category 非唯一索引），A 分类有 score=10/20/30。

1. 间隙锁阻塞插入（/gaplock/insert-block）

事务 A SELECT ... WHERE category='A' FOR UPDATE（锁 A 范围），事务 B 往 A 的间隙插入 ('A', 25)：

项目 值
B 插入等待 约 2001ms（被 A 的间隙锁阻塞，直到 A 释放）
最终结果 B 在 A 释放锁后插入成功

结论：A 的 Next-Key Lock 覆盖了 category='A' 的记录及间隙，阻塞了 B 往该间隙插入，直到 A 提交/回滚。

2. 间隙锁死锁（/gaplock/deadlock）

事务 A 锁 category='A' 范围，事务 B 锁 category='B' 范围，然后 A 向 B 范围插入、B 向 A 范围插入：

事务A: 锁 A范围 → 向B范围插入
事务B: 锁 B范围 → 向A范围插入

实测：txB deadlock:1213（回滚），txA committed。

结论：两个事务的间隙锁形成循环等待，InnoDB 死锁检测回滚代价较小的事务（错误码 1213）。

3. Next-Key Lock 范围（/gaplock/locks）

WHERE category='A' FOR UPDATE 产生的锁（data_locks）：

TABLE, IX                意向排他锁
RECORD, X,GAP            间隙锁 ×1
RECORD, X                 Next-Key Lock ×3（A 的 3 条记录 + 间隙）
RECORD, X,REC_NOT_GAP   记录锁 ×3（A 的 3 条记录）

结论：非唯一索引等值查询会锁住该分类的所有记录 + 相邻间隙（3 Next-Key + 1 Gap + 3 Record），比主键等值（仅 1 Record Lock）锁范围大得多。

五、生产启示

  1. 间隙锁是幻读防护的必要代价：REPEATABLE READ 下范围查询会扩大锁范围。
  2. 用主键/唯一索引等值查询可减小锁范围：只锁记录，不锁间隙，减少阻塞。
  3. 非唯一索引的等值/范围操作易引发间隙锁死锁：两个事务锁不同分类的间隙后互相插入，触发死锁。
  4. 减少间隙锁的策略：
  5. 尽量用主键/唯一索引做等值更新
  6. 避免大范围 UPDATE/DELETE（会锁大量间隙）
  7. 必要数据可拆分小事务，缩短持锁时间
  8. 死锁规避：固定加锁顺序、缩短事务时长、避免"先查后插"跨分类操作。

六、面试简述

间隙锁 / Next-Key Lock：InnoDB 在 REPEATABLE READ 下，非唯一索引等值或范围查询会加 Next-Key Lock（记录锁+间隙锁），防止幻读但扩大锁范围。实测：A 锁某分类范围会阻塞 B 在该分类插入（等待 2 秒）；两个事务锁不同分类后互相插入会触发死锁（错误码 1213）。主键等值只加记录锁，锁范围最小；生产应多用主键/唯一索引等值，避免大范围 UPDATE。
