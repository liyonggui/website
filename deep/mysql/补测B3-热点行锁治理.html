补测B3：热点行锁治理（Redis 缓存前置 / 分段锁）

2026-10-11mysql 系列约 4 分钟阅读MySQLRedis锁缓存

一、问题背景

真实并发最大瓶颈是热点行锁争用：单行库存/账户（如 t_hot_single WHERE id=1）被大量并发 UPDATE，同一行锁串行化，吞吐骤降。MySQL 行锁粒度是行，热点行永远是瓶颈。治理思路：分散锁争用（分段锁）或彻底绕开 MySQL 行锁（Redis 内存原子操作）。

二、三种方案对比

方案 原理 锁争用 适用
baseline 裸UPDATE 并发 UPDATE 同一行 WHERE stock>0 严重（单行串行） 低并发
segment 分段锁 热点库存拆 N 分桶行，并发随机打散到不同行 降低（N 倍分散） 中高并发
redis Redis前置 库存预热到 Redis，DECR 原子扣减，MySQL 仅兜底 无（内存原子） 高并发

三、演示接口

# 1. 初始化热点库存（单行=分桶=Redis 一致）
curl "http://localhost:8080/hot/init?total=1000000&buckets=32"

# 2. 三方案吞吐对比（baseline / segment / redis）
curl "http://localhost:8080/hot/bench?concurrency=50&total=2000"

# 3. 单独测某方案吞吐
curl "http://localhost:8080/hot/bench-mode?mode=redis&concurrency=50&total=2000"

# 4. 热点库存状态
curl "http://localhost:8080/hot/status"

四、实测结果（并发50，总量2000）

方案 QPS 相对 baseline
baseline（单行裸UPDATE） 282 1x
segment（分段锁32桶） 335 ~1.2x
redis（Redis前置DECR） 4938 ~17.5x

结论：热点行锁是 MySQL 写瓶颈。baseline 单行裸 UPDATE 锁争用吞吐最低；分段锁分散行锁提升约 1.2 倍；Redis 前置内存原子 DECR 彻底绕开 MySQL 行锁，吞吐提升约 17.5 倍。

五、工程要点

  1. 热点识别：先定位热点行（订单/秒杀/账户 TopN），再针对治理。
  2. 分段锁（分桶）：库存拆 N 桶，随机/取模路由到桶，WHERE bucket_no=? AND stock>0 扣减；需按桶统计和剩余库存汇总。
  3. Redis 前置：库存预热到 Redis，DECR 原子扣减返回余量，<0 则超卖拒绝；异步回写 MySQL 兜底；注意 Redis 宕机时降级回 DB。
  4. 一致性：Redis 与 DB 最终一致，需回写任务或延迟双删；强一致场景谨慎。
  5. 兜底：Redis 前置需保留 DB 兜底路径（Redis 故障降级），防单点。

六、面试简述

热点行锁治理：热点单行被并发 UPDATE 行锁串行化是最大写瓶颈。实测（并发50）：单行裸 UPDATE 282 QPS，分段锁（拆32桶）335，Redis 前置 DECR 4938（提升 17.5 倍）。分段锁把热点拆多行分散锁争用；Redis 前置用内存原子 DECR 彻底绕开 MySQL 行锁，最高效但需 DB 兜底和最终一致性处理。
