ES路由机制+分片分配+冷热分层+故障排障 全套整合手册（生产通用）

前言

本文打通ES文档路由寻址、哈希算法、分片倾斜治理、冷热分层、分片节点分配、线上故障排障全链路，同时联动MySQL分库分表、Redis/Kafka分片通用思想，区分两大核心倾斜：路由数据倾斜（分片内数据不均）、节点分片分配倾斜（分片个数摆放不均），全覆盖日常开发、线上运维场景。

一、ES核心路由底层原理（必背）

1. 路由寻址固定公式（源码不可变）

// 1.确定路由key：无自定义routing则用文档_id
String routingKey = routing != null ? routing : docId;
// 2.固定32位哈希运算
int hash = Murmur3HashFunction.hash(routingKey);
// 3.取模得到目标主分片
int shardId = Math.abs(hash) % number_of_primary_shards;

2. 核心硬性规则

  1. 主分片数创建索引后永久不可修改，分片一变，所有文档路由全部错乱，数据无法查找

  2. 副本数可随时动态调整，不影响路由寻址

  3. 同一条文档，路由key不变，分片位置永远不变

3. 路由字符串长度规范（避坑）

  • 不是越长越好：MurmurHash固定输出32位整数，超长字符串不会降低哈希碰撞，只会增加CPU计算开销、触发URI超长报错

  • 不是越短越好：过短路由key样本空间小，容易哈希扎堆

  • 生产最优：6\~30字符，业务可读+性能均衡

二、MurmurHash3 哈希算法全解（高频）

1. 两个版本及使用场景

算法版本 输出位数 ES使用场景 核心说明
MurmurHash3_x86_32 32位int 分片路由（唯一） 速度快，哈希碰撞无害，只负责打散有序数据
MurmurHash3_x64_128 128位 cardinality基数去重聚合 超大哈希空间，极致降低碰撞，保证统计准确

2. 哈希碰撞核心答疑

  • 碰撞现象：不同路由key，算出相同哈希，进入同一个分片

  • 碰撞完全无害：分片内部依靠原始文档_id区分数据，不会出现文档覆盖、更新错乱

  • 算法核心目的：解决有序ID分片倾斜，不是消除哈希碰撞

3. 高频误区纠正

  1. ❌ 误区：路由用128位哈希 → ✅ 纠正：路由永远只用32位

  2. ❌ 误区：哈希碰撞会丢数据 → ✅ 纠正：无任何业务影响

  3. ❌ 误区：路由字符串越长打散越好 → ✅ 纠正：长度适中即可

三、两类分片倾斜根源+解决方案（核心重难点）

1. 倾斜1：路由数据倾斜（业务层，分配算法无法解决）

产生原因

业务为了减少跨分片聚合，自定义路由key：日期、地区、品牌、商家，一个热点key永久绑定一个分片，头部热点数据量过大，导致单分片爆满。

典型场景

  • 日期路由：当日写入分片压力爆炸，历史分片闲置

  • 地区路由：广东/浙江等大省分片热点，偏远省份分片空闲

  • 品牌路由：头部爆款商家单分片打爆

根治方案：路由二次打散（生产通用）

给原始业务路由拼接数字后缀，拆分热点流量，一个业务key分散到多个分片：

  • 原始路由：guangdong → 固定1个分片

  • 打散路由：guangdong_0 / guangdong_1 / guangdong_2 → 分散至多个分片

完整可用工具类

import java.util.ArrayList;
import java.util.List;

/**
 * ES路由二次打散工具类，适配雪花ID，路由永久固定
 */
public class RoutingSplitUtil {
    // 写入：生成打散路由
    public static String getSplitRouting(String bizKey, int splitNum, Long snowflakeId) {
        if (splitNum <= 1) return bizKey;
        int suffix = Math.abs(snowflakeId % splitNum);
        return bizKey + "_" + suffix;
    }
    // 查询：获取该维度全部路由，并行查询多分片
    public static List<String> listAllRouting(String bizKey, int splitNum) {
        List<String> list = new ArrayList<>(splitNum);
        for (int i = 0; i < splitNum; i++) list.add(bizKey + "_" + i);
        return list;
    }
}

关键答疑：打散后能否关联MySQL原始数据？

完全可以：仅修改ES内部_routing寻址字段，不改动文档_id、不改动业务字段，ES和MySQL依靠雪花ID主键关联，无任何影响。

2. 倾斜2：节点分片分配倾斜（集群层，ES内置算法可解决）

产生原因

分片在集群节点上摆放数量不均，比如3节点、9主9副本（18分片），理论每节点6分片，实际节点A10片、节点B5片、节点C3片。

ES三大前置过滤规则（优先级最高）

  1. 主分片和对应副本分片禁止同节点部署，防止单机宕机双丢

  2. 磁盘水位超限节点，直接拒绝分片迁入

  3. 冷热分层节点角色匹配校验，分片不能跨冷热池乱跑

两大分片打分均衡算法

  1. 索引均衡算法（权重0.55）：保证同一个索引的分片均匀打散到各个节点

  2. 全局分片均衡算法（权重0.45）：保证集群所有节点总分片数量均衡

ES打分规则：分数越低，节点越空闲，越优先分配分片

四、ES冷热分层+ILM全自动方案（节约机器成本）

1. 四层节点角色划分

  • hot热节点：SSD高配，承接实时写入、高频查询

  • warm温节点：普通SSD，无写入、低频查询，合并分片、缩分片数

  • cold冷节点：HDD大容量机械盘，归档极少访问数据

  • frozen冻结节点：超低成本归档，几乎无查询

2. 完整ILM生命周期策略（直接复制上线）

PUT _ilm/policy/order_hot_cold_policy
{
  "policy": {
    "phases": {
      "hot": {
        "min_age": "0ms",
        "actions": {"rollover": {"max_age": "7d","max_primary_shard_size": "45gb"}}
      },
      "warm": {
        "min_age": "7d",
        "actions": {"allocate":{"require":{"data_tier":"warm"}},"forcemerge":{"max_num_segments":1}}
      },
      "cold": {
        "min_age": "30d",
        "actions": {"allocate":{"require":{"data_tier":"cold"}},"freeze":{}}
      },
      "delete": {"min_age": "90d","actions": {"delete": {}}}
    }
  }
}

3. 冷热分层核心结论

  • 冷热分层只解决存储成本问题，无法解决热数据路由分片倾斜

  • 只有热数据需要做路由二次打散，温/冷数据极少访问，倾斜无需处理

五、索引分片规划黄金规范（前期避坑，拒绝后期重构）

1. 分片数量计算公式

推荐主分片数 = 业务3年预估总数据量 ÷ 40GB

单分片最优容量：30\~50GB，热数据建议偏小，冷数据可适当放大

2. 核心选型建议

  1. 前期分片宁可多，不可少：主分片无法修改，偏少后期只能重建索引、双写迁移，成本极高

  2. 无聚合查询需求：直接使用雪花ID作为默认路由，天然均匀，零分片倾斜（最优方案）

  3. 必须自定义路由：强制配套路由二次打散

  4. 时序数据：放弃单索引分片，采用滚动索引+ILM冷热分离

3. 分片副本配置说明

示例：9主分片 + 1副本 = 总分片18片，一对一主副配对，副本数可随时动态修改，主分片永久固定

六、线上分片故障一页速查手册（现象→命令→解决方案）

故障现象 根因 一键排查命令 快速解决方案
节点分片数量分布不均 集群均衡阈值保守、搬迁并发过低 GET _cat/nodes?v\&h=name,shards 低峰调大rebalance并发，降低均衡阈值

七、全技术栈通用分片思想（ES+MySQL+Redis+Kafka）

  1. 所有中间件、数据库分片底层逻辑一致：分片键→哈希/取模→固定分片

  2. 只要分片键是热度不均的字段（时间、地区、商家），无论哈希算法多优秀，必然出现分片倾斜

  3. 通用最优解：优先选用高离散主键（雪花ID）；业务必须绑定热点维度，统一做分片键二次打散

  4. 分布式架构通用原则：前期分片预留充足余量，永远好过后期拆分迁移

八、3 分钟要点总结

ES分片分为路由数据倾斜和节点分配倾斜两类。首先ES路由采用MurmurHash3_32位哈希，核心作用是打散有序ID避免倾斜，哈希碰撞无害；业务为了减少跨分片查询，使用日期、地区做自定义路由，会产生热点分片倾斜，解决方案是路由二次打散。

然后ES分片分配依靠两大均衡算法，只能均衡节点上分片的摆放个数，解决不了分片内部的数据容量倾斜。同时ES支持原生冷热分层ILM，自动迁移冷热数据节约成本，但冷热分层无法解决热数据热点倾斜。

另外ES主分片创建后不可修改，所以前期一定要预估3年数据量设置充足分片，宁可多不可少；和MySQL分库分表、Redis集群分片逻辑完全一致，热点分片问题统一通过分片键二次打散解决。

ES 路由&分片速记提纲

一、路由核心原理

  1. 分片路由公式：shardId = abs(Murmur3Hash(routing/_id)) % 主分片数
  2. 关键规则：主分片创建后不可修改，副本数可随时动态调整；同一条文档路由不变，分片位置永久不变。
  3. 路由字符串不是越长越好：适中（6~30字符）最优，过长耗CPU、易URI超长；过短容易哈希扎堆。

## 二、MurmurHash3 考点 4. 两个版本 - MurmurHash3_x86_32：ES分片路由专用，32位int，速度快 - MurmurHash3_x64_128：仅 cardinality 基数统计，降低哈希碰撞 2. 哈希碰撞：不同key哈希相同进同一个分片，无害，分片内部靠_id区分文档，不会覆盖数据。 3. 算法初衷：打散有序ID，解决基础分片倾斜，不是消除哈希碰撞。

## 三、两种分片倾斜（必区分）

### 1）路由数据倾斜（业务问题，分配算法解决不了） - 成因：自定义routing用省份、日期、商家等热度不均字段，一个热点key固定一个分片 - 方案：路由二次打散（原key拼接后缀分流）；存量数据Reindex迁移 - 补充：打散仅修改_routing，_id不变，和MySQL主键关联完全不受影响

### 2）节点分片分配倾斜（集群层面，ES可自动均衡） - 表现：节点上分片总数有多有少 - 两大打分算法 ① IndexBalance（权重0.55）：同一个索引分片在节点均匀分布 ② ShardBalance（权重0.45）：集群全局总分片数量均衡 - 前置硬性过滤优先级最高： ① 主、副本不能同节点；② 磁盘水位超限禁止迁入；③ 冷热节点角色匹配校验

## 四、冷热分层 ILM 1. 四层节点：hot热（写入高频查询）→ warm温（低频查询、合并分段缩分片）→ cold冷（归档少访问）→ frozen冻结归档 2. ILM自动流转，定时迁移、收缩、删除索引，降低存储成本 3. 核心结论：冷热分层只省存储成本，解决不了热数据路由倾斜，只有热分片需要做热点打散。

## 五、分片前期规划原则 4. 计算公式：推荐主分片数 ≈ 预估3年总数据量 ÷ 40GB，单分片合理区间30~50GB 5. 策略：分片宁多勿少，主分片后期不能改，分片偏少后期只能重建索引+双写迁移，成本极高 6. 最优路由选型：无跨分片聚合需求，直接雪花ID当_id，天然均衡无倾斜；必须自定义路由则配套二次打散 7. 副本配置：9主+9副本 = 副本数=1，一对一主副配对

## 六、线上故障快速判断口诀 8. 节点分片数量不均：调大rebalance并发、收窄均衡阈值，等待自动收敛 9. 集群黄/红分片未分配：用allocation explain排查，常见原因磁盘水位、主副同节点、冷热层级不匹配、节点不足放不下副本 10. 分片迁移太慢：调高迁入迁出并发、放开恢复带宽限速 11. 分片个数均衡、单分片容量爆满：路由热点倾斜，做路由打散重建索引 12. 高峰期IO暴涨：临时关闭集群分片自动均衡

## 七、跨中间件通用思想（进阶）
  1. ES、MySQL分库分表、Redis集群、Kafka分区底层分片逻辑完全一致：分片键→哈希/取模→绑定固定分片
  2. 分片键是热度不均衡字段，再好哈希也会倾斜

  3. 通用解法：优先高离散主键；必须用热点维度则做分片键二次打散；前期分片预留余量，避免后期重构

    八、3分钟口述总结（背这个即可应对连环提问）

    ES路由基于MurmurHash3 32位哈希取模定位分片，哈希碰撞不会造成数据覆盖，算法主要用来打散有序ID。分片倾斜分两类：一是自定义省份、日期路由带来的热点数据倾斜，用路由二次打散解决；二是节点分片摆放不均，依靠ES两套均衡算法自动调节。ES主分片创建后无法修改，上线前要按3年数据预估充足分片，宁多勿少。同时可搭配ILM冷热分层节约存储，但冷热分层不能解决热分片热点问题。这套分片逻辑在MySQL分库分表、Redis、Kafka通用，热点分片统一采用分片键打散思路治理。 需要我再压缩成半页纸极简版（仅300字内考场速背）吗？
