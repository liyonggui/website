协同遗漏（Coordinated Omission）—— 压测里最隐蔽的谎言

2026-08-18bench 系列约 7 分钟阅读压测

记录日期：2026-09-08 ｜ 来源：Gil Tene《How NOT to Measure Latency》(Strange Loop 2015) 关联实验：demo 高并发写入链路（k6 250 VU 闭环压测）

一、一句话定义

闭环压测中，客户端要等上一个请求返回才发下一个。于是当系统变慢时，客户端"自动配合"降低了施压速率——最慢的那批请求根本没被完整计入样本。结果：系统越卡，你测到的延迟越好看。

这就是"协同（coordinated）"的含义：压测工具和被测系统"协作"把问题隐藏了。

二、一个能算清楚的例子

假设某服务真实性质：99% 请求 1ms，1% 请求 1000ms（每 100 个有 1 个慢 1 秒）。

用 1 个 VU 闭环压测 10 秒：

发生了什么 样本数
快请求（1ms） 1 秒内能连发约 1000 个 ~9,900 个
慢请求（1000ms） 每碰到一次，这 1 秒就"什么都没发" ~10 个

测出来：慢请求占比 = 10 / 9,910 ≈ 0.1%

真实情况：慢请求占比 = 1%

慢请求被系统性降权了 10 倍。 你想看 p99，结果 p99 附近的那条尾巴被压测工具自己"协调"掉了。

极端化一下更直观：如果慢请求是 10 秒，那 1 个 VU 在整个测试期间只能发出个位数次慢请求——你测出的 p99.9 可能一次都没覆盖到它。

三、闭环 vs 开环：回答的是两个不同问题

闭环（closed workload） 开环（open / arrival-rate）
施压方式 固定 VU 数，等返回再发下一个 固定速率发请求，不等返回
系统变慢时 施压速率自动下降 请求照发，开始排队/超时
QPS 由谁决定 系统响应速度（Little 定律：QPS ≈ VU / 平均响应时间） 你设定的速率
延迟测量 偏乐观（有协同遗漏） 真实（慢请求被完整记录）
适合回答 "这个并发下，系统能跑多快？" "这个速率下，用户实际感受到多少延迟？"

关键认知：两者不是"对错"关系，是"问的问题不同"。 闭环测吞吐上限是合理的；用闭环测出的延迟分布去承诺 SLA，就是错的。

四、我的实验里有没有这个问题

有。 demo 用的是 k6 vus: 250, duration: 60s + sleep(0.01)，标准闭环模型。

影响评估（三层）：

  1. 绝对延迟值偏乐观 —— 尤其 max 和 p99。真实生产里，慢请求发生时用户不会"配合地不发请求"
  2. QPS 数字仍然有意义 —— 但它回答的是"250 并发下系统能跑多快"，不是"系统能扛多大速率"
  3. A/B/C 三方案的相对结论不受影响 —— 因为三个版本用的是同一套施压模型，偏差方向一致，对比是公平的

第二篇里我已经把这条写进"局限"段。

五、怎么修（下次实验用）

k6 改开环执行器：

export const options = {
  scenarios: {
    steady_load: {
      executor: 'constant-arrival-rate',   // 固定速率发压
      rate: 5000,                          // 每秒 5000 请求
      timeUnit: '1s',
      preAllocatedVUs: 200,
      maxVUs: 1000,                        // 关键：给足 VU，系统卡顿时请求照样发
      duration: '60s',
    },
  },
  thresholds: {
    http_req_failed: ['rate<0.01'],
    // 开环下要盯"未完成的请求"，它们是协同遗漏的替代品
    vus_max: ['max<1000'],                 // VU 打满说明系统已经跟不上施压速率
  },
};

配套要报的指标：

  • offered load vs achieved load（想发多少 vs 实际发出去多少）——两者一旦背离，就是系统饱和的信号
  • 超时/未完成请求数 —— 开环下这些必须计入，否则又变成另一种遗漏
  • 完整延迟直方图（不是只报几个百分位点）—— Gil Tene 的 HdrHistogram 就是为此而生

六、顺带记住的三个关联陷阱

陷阱 一句话
对百分位取平均是错的 3 轮各得一个 p99，取平均 ≠ 整体 p99。要合并原始样本重算。（我用的"轮次结果取中位数"是安全的，别写成"平均 p99"）
平均值骗人 我实测过：APPEND 两种写法 avg 3.92ms vs 3.93ms 几乎相同，max 却是 39ms vs 287ms。avg/p50/p90/p99/p99.9/max 要一起报。
观察者效应 埋点本身有开销。加埋点后数字完全没变，反而要怀疑埋点没生效。

七、实践应用（这段是重点）

被问"你怎么做压测 / 怎么保证压测可信"时，加这一句：

"我用的 k6 是闭环模型，所以绝对延迟值会偏乐观——存在协同遗漏：系统变慢时施压速率会跟着下降，最慢的请求不会被完整计入。三种方案我用同一套施压模型做对比，相对结论是公平的；但如果要承诺 SLA，我会改用开环固定速率施压，并且报 offered load 和 achieved load 的背离情况。"

这句话的价值： 中文技术圈写压测文章会主动提"协同遗漏"的极少。它一次性证明三件事——① 你知道自己的工具在骗你 ② 你知道偏差影响哪个结论、不影响哪个结论 ③ 你有下一步的修正方案。这三样合起来就是"会做实验"和"会跑工具"的区别。
