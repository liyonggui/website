# Java 秒杀/库存场景压测脚本设计清单

本文用于设计 Java 秒杀、库存扣减、订单创建和异步消息链路的压测脚本。重点覆盖：

- 高热点请求模型
- 库存正确性
- 用户幂等
- 接口尾延迟
- MQ 异步链路
- 超载、故障和恢复

## 一、先定义被测链路

压测前明确本次只覆盖哪一段链路，避免把不同结论混在一起。

### 推荐拆分

1. **资格校验接口**
   - 活动时间
   - 用户是否登录
   - 商品是否存在
   - 是否重复参与
2. **库存预扣接口**
   - Redis 原子扣减
   - 分片库存
   - 本地预分配
   - 限流和快速失败
3. **订单创建链路**
   - 同步写库
   - MQ 异步创建
   - 幂等和重试
4. **订单查询接口**
   - 订单状态
   - 库存状态
   - 支付前资格确认
5. **支付或支付资格接口**
   - 只允许有效订单进入支付
   - 防止重复支付和失效订单支付

每次实验要注明：

- [ ] 被测接口
- [ ] 是否包含 Redis
- [ ] 是否包含 MySQL
- [ ] 是否包含 MQ
- [ ] 是否包含支付模拟
- [ ] 是否包含真实日志和监控

## 二、脚本必须具备的能力

- [ ] 支持固定并发
- [ ] 支持阶梯加压
- [ ] 支持固定 RPS
- [ ] 支持持续时间
- [ ] 支持预热
- [ ] 支持随机用户
- [ ] 支持固定用户
- [ ] 支持热点商品
- [ ] 支持多商品分布
- [ ] 支持唯一请求 ID
- [ ] 支持幂等键
- [ ] 支持请求签名或登录 Token
- [ ] 支持超时和重试配置
- [ ] 支持响应结果分类
- [ ] 支持错误样本保留
- [ ] 支持压测后数据核对

压测脚本不应无限重试。重试必须有上限，并记录：

- 原始请求 ID
- 重试次数
- 最终响应
- 最后一次失败原因

## 三、请求数据模型

### 1. 用户数据

准备多种用户集合：

- **唯一用户集**：每个请求使用不同用户，观察系统总体吞吐。
- **重复用户集**：少量用户高频请求，验证幂等和重复参与拦截。
- **热点用户集**：模拟异常流量或脚本攻击。
- **正常用户集**：按照业务比例分布。

字段建议：

```text
userId
token
deviceId
requestId
idempotencyKey
clientTimestamp
```

### 2. 商品数据

至少准备以下商品类型：

- 单一热点商品：大部分请求访问同一个商品。
- 多商品均匀分布：观察无热点时的基础能力。
- 长尾分布：少数商品承载大部分请求，更接近实际业务。
- 不存在商品：验证缓存穿透和参数校验。
- 已结束商品：验证活动状态校验。

字段建议：

```text
activityId
skuId
stock
shardCount
startTime
endTime
```

### 3. 请求比例

不要只压成功请求。建议显式配置：

```text
正常请求：70%
重复请求：10%
库存不足：8%
活动未开始/已结束：5%
非法参数：3%
网络重试或超时重放：4%
```

实际比例应根据业务模型调整，并在实验记录中固定。

## 四、核心压测场景

### 场景 1：正常流量基线

- [ ] 商品和用户均匀分布
- [ ] 库存充足
- [ ] 无故障、无重试
- [ ] 记录基础 QPS、p99、CPU、GC 和依赖耗时

目的：建立最小基线，确认脚本和链路没有明显问题。

### 场景 2：单商品热点

- [ ] 90%～100% 请求访问同一 SKU
- [ ] 用户尽量唯一
- [ ] 库存设置为可成功一段时间后耗尽
- [ ] 观察 Redis 热点、锁竞争、拒绝率和尾延迟

目的：验证真实热点下的系统边界。

### 场景 3：库存耗尽

- [ ] 将库存设置为远小于请求量
- [ ] 统计成功扣减数
- [ ] 统计失败数
- [ ] 校验最终库存不为负数
- [ ] 校验成功订单数不超过库存

目的：验证“高并发下正确拒绝”，而不是只追求吞吐。

### 场景 4：同一用户重复下单

- [ ] 同一用户并发发送多个请求
- [ ] 使用相同或不同幂等键分别测试
- [ ] 校验最多成功一次
- [ ] 校验重复请求的响应语义一致

目的：验证用户维度幂等和重复消费防护。

### 场景 5：网络重试和请求重放

- [ ] 首次请求在服务端已成功，但客户端模拟超时
- [ ] 客户端重试相同请求
- [ ] 校验不会重复扣库存或创建订单
- [ ] 记录幂等命中率和重复请求处理耗时

目的：模拟真实网络环境中的“客户端不知道服务端是否成功”。

### 场景 6：同步写库与异步下单

分别测试：

- [ ] Redis 扣减 + 同步创建订单
- [ ] Redis 扣减 + MQ 异步创建订单
- [ ] 异步创建 + 消费失败重试
- [ ] 异步创建 + 死信/补偿

重点观察：

- [ ] 接口 p99
- [ ] MQ 积压
- [ ] 订单落库延迟
- [ ] 重复消费
- [ ] 库存与订单数量是否一致
- [ ] 失败后是否可补偿

### 场景 7：分片库存对比

固定其他条件，只改变库存分片数：

- [ ] 1 个 Key
- [ ] 8 个 Key
- [ ] 16 个 Key
- [ ] 32 个 Key
- [ ] 64 个 Key

记录：

- [ ] 每个 Key 的命令量和延迟
- [ ] 分布是否均匀
- [ ] 应用侧聚合耗时
- [ ] Redis 连接和网络开销
- [ ] 最终库存准确性

注意：分片数增加不一定持续带来收益。需要记录收益拐点和管理成本。

### 场景 8：MQ 消费能力不足

- [ ] 生产速率逐步超过消费速率
- [ ] 固定消费者数量
- [ ] 记录 lag 和订单落库延迟
- [ ] 观察应用内存、队列和重试数量
- [ ] 恢复正常生产后，记录积压恢复时间

目的：确定消息链路的安全积压边界。

### 场景 9：依赖故障

分别注入：

- [ ] Redis 延迟 50ms、100ms、500ms
- [ ] Redis 短暂不可用
- [ ] MySQL 写入变慢
- [ ] MySQL 连接池耗尽
- [ ] MQ 停止消费
- [ ] 单个应用实例下线

验证：

- [ ] 是否快速失败
- [ ] 是否触发限流/熔断
- [ ] 是否发生库存重复扣减
- [ ] 是否出现消息丢失
- [ ] 是否产生可恢复的补偿记录

## 五、脚本执行阶段

### 阶段 1：预热

- [ ] 预热 JVM、连接池、缓存和 JIT
- [ ] 不把预热结果计入正式数据
- [ ] 确认活动数据和库存已初始化

### 阶段 2：阶梯加压

建议按以下步骤执行：

```text
10% 目标流量 → 25% → 50% → 75% → 100% → 125% → 150% → 200%
```

每一级至少观察：

- [ ] 吞吐是否继续增长
- [ ] p99 是否快速恶化
- [ ] 错误率是否超过阈值
- [ ] 线程池/连接池是否排队
- [ ] Redis、MySQL、MQ 是否出现积压

### 阶段 3：稳态运行

- [ ] 目标流量持续 10～30 分钟
- [ ] 记录每分钟吞吐和 p99
- [ ] 观察资源是否持续增长
- [ ] 观察 MQ 积压是否持续扩大

### 阶段 4：停止压测和恢复

- [ ] 停止新请求
- [ ] 记录 MQ 积压清空时间
- [ ] 记录订单最终落库完成时间
- [ ] 检查库存、订单和成功响应数量
- [ ] 检查失败消息、死信和补偿记录
- [ ] 检查应用和中间件资源是否恢复稳定

## 六、结果校验脚本清单

压测脚本之外，必须准备独立的校验脚本或 SQL。

### 1. 库存校验

- [ ] Redis 剩余库存
- [ ] 数据库库存
- [ ] 初始库存 - 成功扣减数
- [ ] 是否出现负库存
- [ ] 分片库存求和是否正确

### 2. 订单校验

- [ ] 成功响应数
- [ ] 唯一成功用户数
- [ ] 数据库订单数
- [ ] 重复订单数
- [ ] 未落库但已扣库存的数量
- [ ] 已落库但重复扣库存的数量

### 3. 消息校验

- [ ] 生产消息数
- [ ] 消费成功数
- [ ] 消费失败数
- [ ] 重试数
- [ ] 死信数
- [ ] 最终一致的消息数

### 4. 状态机校验

- [ ] 订单状态转换合法
- [ ] 已取消订单不能支付
- [ ] 未创建订单不能进入支付
- [ ] 已支付订单不能重复支付
- [ ] 超时未支付订单能释放或补偿库存

## 七、Java 压测脚本实现检查

- [ ] HTTP 客户端连接池已配置，避免每次请求新建连接。
- [ ] 连接、读取和整体请求超时已明确设置。
- [ ] 不在每个请求中同步打印完整响应。
- [ ] 使用高效统计方式记录延迟分布，避免压测客户端成为瓶颈。
- [ ] 请求体和 Token 可复用的部分提前准备。
- [ ] 随机数、JSON 序列化和日志不会成为主要额外开销。
- [ ] 压测客户端与被测服务尽量分离。
- [ ] 多压测实例时避免所有实例使用相同用户或相同 requestId。
- [ ] 记录服务端返回码、业务码和异常类型。
- [ ] 对超时请求单独统计，不要简单归类为普通失败。

## 十、秒杀场景的通过标准示例

具体阈值应根据业务目标制定，不能直接套用。可以先用以下维度定义：

- [ ] 成功订单数不超过可售库存
- [ ] 同一用户最多成功一次
- [ ] 重试不会产生重复订单
- [ ] 正常目标流量下错误率低于约定阈值
- [ ] p99 不超过业务可接受范围
- [ ] MQ 积压在约定时间内可恢复
- [ ] Redis、MySQL、MQ 故障时不会无限重试
- [ ] 压测结束后库存、订单、消息和状态机一致

> 秒杀压测最重要的结论不是“能承受多少 QPS”，而是“在什么流量、热点、库存和故障条件下，系统仍然正确、可控并且能够恢复”。
