写入链路降级设计：本地文件兜底 + 限速回放

2026-08-21bench 系列约 8 分钟阅读压测

性质：工程设计方案（内部沉淀，暂不作为文章内容发布） 适用：demo 高并发写入链路（HTTP → Disruptor → Kafka → 3 消费者 → MySQL/Redis/ES/Mongo） 前提数据：单机实测正常峰值 ~5,000~10,000 QPS，单条 payload ~200B

一、目标与非目标

目标

  1. 中间件不可用期间，写入接口保持可用（返回 200，不阻塞业务方）
  2. 降级期间产生的数据一条不丢，且可被完整回放
  3. 恢复后能在可控时间内完成回放，不把刚恢复的中间件二次打挂

非目标

  • 不追求降级期间的实时可查（读能力按第三节矩阵降级）
  • 不追求自动降级（切换由人决策，见第四节）
  • 不解决"MySQL 挂掉时的读"（无解，只能选陈旧快照或拒绝，见 3.2）

二、整体流程

正常态：HTTP → Disruptor → Kafka → 消费者 → 四库写入

降级态（开关 ON）：
  HTTP → Disruptor → 本地文件追加（长度前缀 + JSON + CRC32）→ 立即返回 200
                     （Kafka/四库写入路径全部旁路）

恢复态：限速回放器读取本地文件 → 幂等写回四库 → 对账 → 关闭降级开关

三、只读降级矩阵（关键：只读需要活着的读源）

不可用组件 只读是否成立 降级策略 风险
Redis ✅ 读穿透 MySQL 必须限流，否则缓存击穿打爆 DB；配单飞/互斥重建
ES ✅ 搜索降级为 DB like（仅小结果集）或列表页返回兜底数据 深分页/模糊查询会拖慢 DB
Kafka ⚠️ 读不受影响；写链路立即切本地文件 消费者积压不可见，需 lag 告警
Mongo ✅ 流水查询返回"暂不可用"，主链路不受影响 低
MySQL ❌ 无解：只能返回本地快照（标注过期时间）或直接拒绝 必须提前定策略，不能现场决定

结论：只有 MySQL 是唯一不可绕过的读源。 其余组件故障时，"降级为只读"都成立。

3.2 MySQL 故障时的三选一（需业务方预先签字）

  1. 返回本地缓存的最后快照 + 明确标注「数据截至 HH:MM」
  2. 读请求直接返回 503（保写不保读）
  3. 只读从库兜底（前提：从库独立故障域，否则同生共死）

四、切换机制：手动开关 + 自动告警

  • 配置中心一个布尔开关（Nacos/Apollo），秒级推送到全部实例，全集群状态一致
  • 自动探活只做告警和建议，不自动切换。理由：网络抖动会造成频繁来回切；部分实例降级部分不降级会导致数据分裂，回放时无法定序
  • 开关状态必须打进每条落盘记录（degraded=true + 开关版本），便于回放时按批次识别
  • 切换动作要写审计日志（谁、何时、原因）

五、落盘文件格式（能重放才算兜底）

[4B 长度 N][N 字节 payload JSON][4B CRC32]

payload 必含字段：

字段 作用
id 雪花 ID（本地可生成，天然幂等键）
ts 业务时间戳，回放时做 last-write-wins 定序
payload 原始数据
degraded 是否降级期写入 + 开关版本号
batch 批次号，用于回放进度与对账分组

硬性要求：

  1. 长度前缀 + CRC32：进程崩溃会留下半行，无校验就无法安全跳过
  2. 断点文件：单独记录已回放到哪个 offset（原子写：临时文件 + rename）
  3. 文件滚动：按大小或时间切分（如 256MB/个），回放完成即归档删除
  4. 刷盘策略：降级期数据不能只进 page cache——至少 FileChannel.force(false) 定时（如每 100ms）触发，否则机器宕机一样丢

六、磁盘水位线（不做就是反向故障）

按 5,000 QPS × 200B 估算落盘量：

降级时长 数据量
5 分钟 ~3 GB
30 分钟 ~18 GB
2 小时 ~72 GB

水位线策略（必须实现）：

磁盘使用率 动作
< 70% 正常降级落盘
70%~85% 只保核心业务写入，非核心接口返回 503 并告警
> 85% 拒绝全部写入（503），触发最高级告警

理由：磁盘写满会让服务从"降级可用"直接变成"彻底不可用"——这是比丢数据更糟的结局。宁可提前拒绝，不可最后崩盘。

七、回放状态机

IDLE → REPLAYING → VERIFYING → DONE
         ↓ (异常/需暂停)
       PAUSED → REPLAYING

回放规则：

  1. 限速：按正常峰值的 30% 灌入（可调），避免二次打挂刚恢复的中间件
  2. 幂等写入：MySQL INSERT IGNORE / upsert；ES 指定 id 的 index（天然幂等）；Redis set 覆盖；Mongo 按 _id upsert
  3. 乱序保护：同一 id 若新数据已走正常链路写入，回放时以 ts 做 last-write-wins，禁止旧值覆盖新值
  4. 可中断续传：断点 offset 落盘，重启后从断点继续
  5. 回放顺序：先 MySQL（主数据源）→ 再 Redis/ES/Mongo（可从 MySQL 重建的派生数据）
  6. 回放期间双写共存：新数据走正常链路，旧数据回放，两者互不阻塞

八、验收标准（对账，不是"看起来好了"）

1. 起压测（250 并发持续）
2. 中途 docker stop 全部中间件 → 打开降级开关
3. 持续写入 N 条，验证：接口全程 200、本地落盘 N 条、无半行/坏行
4. 等待 5 分钟 → docker start 中间件
5. 触发限速回放
6. 对账：MySQL 16 分表之和 == Redis == ES == Mongo == 注入总数 N
7. 全程记录：止血耗时、降级期错误率、回放总耗时、回放期间正常链路 P99

任何一步对不上，方案不成立。可复用 demo/verify.sh 的四库对账逻辑。

九、待决问题（后续演练时回答）

  • [ ] 多实例部署时，本地文件分散在各机器，回放由谁调度？（需中心化的任务分配或各实例自回放 + 全局对账）
  • [ ] 降级期间 Kafka 恢复但开关未关，新数据走文件还是走 Kafka？（需要"开关切换瞬间"的双写窗口设计）
  • [ ] 回放期间业务读请求命中不到未回放数据，是否需要"回放进度"对外暴露？
  • [ ] 磁盘 IO 本身成为降级期瓶颈时的表现（追加写吞吐上限、是否需要内存缓冲批量落盘）
