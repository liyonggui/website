# 高并发压测执行清单

本文用于 Java + Redis + MySQL + MQ 类系统的压测设计、执行、分析和复盘。目标不是只得到一个最高 QPS，而是建立一条可追溯的证据链：

> 实验目标 → 假设 → 控制变量 → 观测指标 → 结果 → 归因 → 结论 → 下一轮实验

## 一、压测前准备

### 1. 明确实验目标

- [ ] 明确本轮属于哪类测试：
  - [ ] 功能正确性
  - [ ] 性能基线
  - [ ] 稳定性
  - [ ] 极限容量
  - [ ] 故障恢复
- [ ] 写清楚需要回答的核心问题：
  - [ ] 在什么并发量下系统稳定？
  - [ ] 瓶颈位于业务代码、JVM、数据库、缓存、消息队列、网络还是内核？
  - [ ] 方案的吞吐、尾延迟和资源消耗是否满足要求？
  - [ ] 超过容量边界后，系统是否能限流、降级和恢复？

### 2. 写出实验假设

示例：

- 异步写库可以提升接口吞吐，但可能引入消息堆积和最终一致性延迟。
- Redis 将热点库存拆分为 32 个 Key 后，可以降低单 Key 竞争。
- 增大线程池只有在下游仍有处理能力时才会提升吞吐。

记录以下内容：

- [ ] 研究假设
- [ ] 预期收益
- [ ] 可能副作用
- [ ] 失败判定标准
- [ ] 需要验证的边界条件

### 3. 固定实验条件

- [ ] 代码版本和 Git 提交号
- [ ] 配置文件版本
- [ ] JVM 版本和启动参数
- [ ] 操作系统、CPU、内存、磁盘和网络
- [ ] 容器 CPU/内存限制及 cgroup 配置
- [ ] MySQL、Redis、MQ 版本及拓扑
- [ ] 测试数据规模、分布和热点比例
- [ ] 压测脚本版本
- [ ] 并发模型、请求比例和持续时间
- [ ] 日志级别、采样率和输出位置

### 4. 控制变量

- [ ] 每轮实验只改变一个主要变量。
- [ ] 保留基线组（Baseline）。
- [ ] 每个实验至少重复 3 次，避免偶然抖动。
- [ ] 每次实验前清理或记录缓存、队列、数据库和消费位点状态。
- [ ] 记录预热时间，不把 JVM 预热阶段作为正式结果。

## 二、环境和可观测性

### 1. 应用侧

- [ ] 请求总量、成功量、失败量
- [ ] QPS/TPS
- [ ] p50、p90、p95、p99、p999 和最大延迟
- [ ] 线程池活跃线程、队列长度、拒绝次数
- [ ] 数据库连接池活跃数、等待数、超时数
- [ ] Redis 连接池等待和命令耗时
- [ ] MQ 生产、消费、重试和死信数量
- [ ] 业务幂等命中数、重复请求数、补偿数

### 2. JVM 和操作系统

- [ ] CPU 使用率及 load average
- [ ] 堆使用率、老年代使用率、直接内存
- [ ] Young GC、Full GC 次数和停顿时间
- [ ] 线程数、上下文切换、阻塞和锁竞争
- [ ] 磁盘吞吐、IO wait、磁盘空间
- [ ] 网络连接数、重传、丢包和 socket 状态
- [ ] 文件描述符和端口使用情况
- [ ] 容器 CPU throttling、内存限制和 OOM 事件

### 3. MySQL

- [ ] QPS、TPS、活跃连接数
- [ ] 慢 SQL 和执行计划
- [ ] 行锁等待、死锁和锁冲突
- [ ] Buffer Pool 命中率
- [ ] redo/binlog 刷盘和写入压力
- [ ] 主从延迟及复制异常
- [ ] 磁盘空间和 I/O 等待

### 4. Redis

- [ ] 命令吞吐和命令延迟
- [ ] 命中率、miss、eviction
- [ ] 热 Key 和大 Key
- [ ] 内存碎片率
- [ ] 连接数、阻塞命令和超时
- [ ] 主从复制延迟或 Cluster 分片倾斜

### 5. MQ

- [ ] 生产速率和消费速率
- [ ] Topic/Queue 积压量
- [ ] Consumer lag
- [ ] 重试、重复消费和死信数量
- [ ] 分区/队列负载是否均衡
- [ ] Broker 磁盘、网络和请求延迟

## 三、标准执行流程

### 阶段 1：功能和数据正确性

- [ ] 低并发验证正常链路。
- [ ] 校验库存、订单、支付状态和消息状态。
- [ ] 验证重复请求、超时重试和重复消费。
- [ ] 压测前后核对数据库、缓存、队列和业务统计。

### 阶段 2：性能基线

- [ ] 关闭非必要的实验变量，建立最小链路基线。
- [ ] 逐步增加并发，观察吞吐和尾延迟曲线。
- [ ] 记录第一个明显瓶颈出现的并发点。
- [ ] 记录 CPU、GC、线程池和下游依赖状态。

### 阶段 3：单变量实验

- [ ] 每轮只调整一个参数。
- [ ] 例如：线程池大小、连接池大小、Redis Key 数量、批量大小或同步/异步模式。
- [ ] 保持请求比例、数据分布和测试时长一致。
- [ ] 对比收益、尾延迟、资源消耗和副作用。

### 阶段 4：稳定性测试

- [ ] 目标流量持续 10～30 分钟。
- [ ] 观察吞吐是否逐步下降。
- [ ] 观察堆、老年代、连接池和 MQ 积压是否持续增长。
- [ ] 检查是否出现周期性 GC、线程池抖动或慢请求堆积。

### 阶段 5：极限和过载测试

- [ ] 以目标流量的 1.2 倍、1.5 倍、2 倍逐级增加。
- [ ] 记录系统进入过载的边界。
- [ ] 验证限流、熔断、降级和快速失败是否生效。
- [ ] 停止压测后，检查积压、资源和错误率是否恢复。

### 阶段 6：故障注入和恢复

- [ ] Redis 延迟、超时或短暂不可用
- [ ] MySQL 连接耗尽、写入变慢或主库不可用
- [ ] MQ 停止消费、消费变慢或重复投递
- [ ] 单个应用实例下线
- [ ] 网络延迟、丢包或连接重置
- [ ] 线程池、连接池或磁盘空间达到上限
- [ ] 验证重试上限、死信、补偿和对账机制

## 四、核心实验清单

### 1. 同步与异步写入

- [ ] 同步写库
- [ ] 异步写库
- [ ] 异步写库 + 重试
- [ ] 异步写库 + 限流
- [ ] 异步写库 + 补偿/对账
- [ ] 对比接口响应、消息积压、数据一致性和恢复时间

### 2. Redis 单 Key 与分片 Key

- [ ] 单热点 Key
- [ ] 8 个分片 Key
- [ ] 32 个分片 Key
- [ ] 随机分布与用户/商品 Hash 分布
- [ ] 对比单 Key 延迟、热度分布、命令吞吐和管理复杂度

### 3. 线程池

- [ ] 20、50、100、200 线程逐级测试
- [ ] 记录队列等待、拒绝、上下文切换和 CPU
- [ ] 判断吞吐提升是否以 p99 恶化为代价
- [ ] 验证下游连接池是否成为新的瓶颈

### 4. 连接池

- [ ] 小连接池、基线连接池、大连接池
- [ ] 观察连接等待和数据库实际处理能力
- [ ] 验证连接池过大是否引起数据库线程、锁和 CPU 争用

### 5. 日志和输出

- [ ] 无日志
- [ ] 控制台同步输出
- [ ] 文件同步输出
- [ ] 异步日志
- [ ] 降低采样率
- [ ] 对比 CPU、磁盘 I/O、GC、吞吐和尾延迟

### 6. 数据库写入

- [ ] 单条写入
- [ ] 批量 10
- [ ] 批量 50
- [ ] 批量 200
- [ ] 高冲突更新
- [ ] 唯一索引冲突
- [ ] 大事务和小事务
- [ ] 对比锁等待、刷盘压力、吞吐和失败重试

### 7. MQ 积压

- [ ] 生产速率低于消费速率
- [ ] 生产速率接近消费速率
- [ ] 生产速率高于消费速率
- [ ] 消费者降速或暂停
- [ ] 重试消息增加
- [ ] 消费者扩容
- [ ] 验证积压告警、限流、扩容和恢复时间

## 五、结果判定标准

一次实验不能只写“QPS 提升”。至少回答：

- [ ] 是否支持原始假设？
- [ ] QPS/TPS 如何变化？
- [ ] p99/p999 如何变化？
- [ ] 成功率和业务正确性是否保持？
- [ ] CPU、内存、GC、I/O 是否出现新瓶颈？
- [ ] MQ、Redis、MySQL 是否出现积压或异常？
- [ ] 收益是否稳定且可复现？
- [ ] 是否引入一致性、恢复和运维成本？
- [ ] 是否值得进入下一轮或生产方案？

推荐结论格式：

> 在固定硬件、代码版本、数据分布和请求模型下，仅将 X 从 A 调整为 B。吞吐从 ___ 提升到 ___，p99 从 ___ 变化为 ___，CPU 从 ___ 变化为 ___。同时观察到 ___，说明主要瓶颈位于 ___。因此该方案在 ___ 条件下有效，但需要通过 ___ 控制副作用。

## 七、最终检查

- [ ] 结果可复现
- [ ] 控制变量清晰
- [ ] 业务正确性已校验
- [ ] 尾延迟而非只有平均值已记录
- [ ] 资源和中间件指标完整
- [ ] 过载边界已识别
- [ ] 故障后可以恢复
- [ ] 结论包含证据和适用条件

> 压测的最终目标不是找到最高吞吐，而是找到在正确性、延迟、稳定性、恢复能力和成本之间可接受的系统边界。
