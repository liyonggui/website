# 高并发写入测试总结

> 日期: 2026-06-17 ~ 06-18 | 硬件: 4C/8T 笔记本 (单台) | Docker 部署 MySQL/Redis/ES/Mongo/Kafka

---

## 〇、独立存储测试（四轮，模拟生产分机部署）

> **目的**: 生产环境各存储独立物理机，当前 4C/8T 挤在一起测的是 CPU 争抢下限。
> 分别测每个存储单独写入的极限，对应"某台机器上某个存储能接多少流量"。

### 测试方法

每轮注释掉其他三个存储的写入，只保留一个：

| 轮次 | 写入目标 | 模式 |
|:--:|--|--|
| 1 | **仅 MySQL** | sync（消费者线程直接 batchInsert） |
| 2 | **仅 Redis** | async（taskExecutor 异步 pipeline） |
| 3 | **仅 ES** | async（taskExecutor → bulk processor） |
| 4 | **仅 Mongo** | async（taskExecutor 批量写入） |

### 独立存储 QPS 数据

| 并发 | MySQL (sync) | Redis (async) | ES (async) | Mongo (async) |
|:--:|:--:|:--:|:--:|:--:|
| 100 | 3,169 | 3,347 | 4,210 | **5,110** |
| 150 | 6,057 | 4,856 | 6,110 | **6,789** |
| 200 | 6,216 | 5,294 | 6,522 | **7,135** |
| 250 | 7,623 | 5,688 | 6,582 | **7,627** |
| 300 | **8,437** | 5,967 | 6,678 | 7,845 |

### P95 延迟对比 @ 300 并发

| 存储 | 峰值 QPS | P95 延迟 | 平均延迟 |
|--|:--:|:--:|:--:|
| MySQL | **8,437** | ~47ms | ~11ms |
| Mongo | 7,845 | 49.8ms | 15.0ms |
| ES | 6,678 | 61.4ms | 18.3ms |
| Redis | 5,967 | ~68ms | ~22ms |

### 独立测试 vs 全量写入对比

```
全量写入 (版本 C, 四个存储一起): 峰值 6,826 QPS @ 250 并发
独立 MySQL 写入:                 峰值 8,437 QPS @ 300 并发  (+24%)
独立 Mongo 写入:                 峰值 7,845 QPS @ 300 并发  (+15%)
独立 ES 写入:                    峰值 6,678 QPS @ 300 并发  (接近全量)
独立 Redis 写入:                 峰值 5,967 QPS @ 300 并发  (-13% vs 全量!)
```

### 关键发现

1. **MySQL sync 才是真天花板**: 消费者线程直接 batchInsert，零调度开销，单存储撑到 **8,437 QPS**
2. **Mongo 异步最为均衡**: 7,845 QPS + P95 仅 49.8ms，稳定性和吞吐都是一流
3. **Redis "最快"的神话被打碎**: async 模式下 5,967 QPS 垫底，线程调度开销反超 I/O 收益
4. **ES 是全量写入的"锚点"**: 独立 6,678 接近全量 6,826，说明 ES 的 bulk processor 是整个链路的主要瓶颈
5. **分机部署预估**: 如果四个存储各独立部署 4C+，Java 应用 4C，预计可冲到 **10,000~12,000 QPS**

## 一、架构概览

```
HTTP → Controller → 拆分 user[] → RingBuffer → Producer → Kafka (4 partition)
                                                                    ↓
                                                    3 个 Kafka Consumer (并发消费)
                                                       ↓
                                                    写入 4 个存储
```

**关键组件:**
- `KafkaBatchConsumer`: 3 个消费者线程，批拉 + 分库写入
- `taskExecutor`: 线程池 core=16 / max=32 / 队列=1000 / **CallerRunsPolicy**

## 二、测试的三个版本

### 版本 A: ES 同步 + 3 异步 (Round 1)
```java
CasUtil.runSafe(() -> bulkProcessorESService.batchBulkWrite(list));  // ES 同步，阻塞消费者

CompletableFuture.allOf(
    Redis  → taskExecutor,   // 异步
    MySQL  → taskExecutor,   // 异步
    Mongo  → taskExecutor    // 异步
);
```
### 版本 B: 全部 4 异步 (Round 2)
```java
CompletableFuture.allOf(
    Redis  → taskExecutor,   // 异步
    MySQL  → taskExecutor,   // 异步
    ES     → taskExecutor,   // 异步
    Mongo  → taskExecutor    // 异步
);
```
### 版本 C: MySQL 同步 + 3 异步 (Round 3, 原始版, 最终最优)
```java

CompletableFuture.allOf(
    Redis  → taskExecutor,   // 异步
    ES     → taskExecutor,   // 异步
    Mongo  → taskExecutor    // 异步
);
```

## 四、拖慢因素分析

### 因素 1: `CasUtil.runSafe` 同步阻塞消费者线程

| | 机制 | 耗时 | 影响 |
|---|---|---|---|
| **ES sync** (版本 A) | Kafka 消费者线程调 `bulkAsync().get()`，等 HTTP 返回 | ~10-30ms/批 | 3 个消费者线程每批都要等，消费吞吐被压 ~40% |
| **MySQL sync** (版本 C) | Kafka 消费者线程调 `userMapper.batchInsert()`，等 DB 返回 | ~2-5ms/批 | 阻塞微小，不影响整体吞吐 |

```
版本 A 为什么差:
  3 个消费者线程 × 每批阻塞 10-30ms → 每个消费者每秒少处理 30-50 批
  → RingBuffer 释放变慢 → Producer 端反压 → 整体 QPS 跌 40%
```

### 因素 2: CallerRunsPolicy — 线程池退化为同步 (核心杀手)

```
taskExecutor 配置:
  core=16, max=32, queue=1000, CallerRunsPolicy

当 16 个核心线程全忙 + 队列 1000 满 → 新任务由调用者线程直接执行
```

| | taskExecutor 并发需求 | CallerRuns 触发频率 | 后果 |
|---|---|---|---|
| 版本 A (3 async) | 3 消费者 × 3 任务 = 9 | 低 | 偶尔退化 |
| 版本 B (4 async) | 3 消费者 × 4 任务 = 12 | **高** | 频繁退化 |
| 版本 C (3 async) | 3 消费者 × 3 任务 = 9 | 低 | 偶尔退化 |

```
版本 B 为什么会退化:
  4 个 async 任务 ÷ 16 core 线程 = 看似够用
  但 Redis/ES/Mongo/MySQL 都是 I/O 密集型，线程在等网络 I/O 时不释放 CPU
  → 16 个线程 × 60s keepAlive = 线程长期占用
  → 新批次到达 → queue(1000) 快速填满 → CallerRuns 触发
  → Kafka 消费者线程被迫同步执行 ES/Redis/Mongo 写入 ❌
  → 等于又在消费者线程上同步等 I/O，和版本 A 一样的悲剧
```

### 因素 3: 4C/8T 物理天花板

```
CPU 核心: 4 核 8 线程 (含超线程)
线程总数: Kafka 3 消费者 + taskExecutor 16 core + GC + 系统 ≈ 20+
CPU 绑定的极限: ~5,000-5,500 QPS (版本 A/B 反复撞)
版本 C 突破: ~6,800 QPS

版本 C 为什么能突破天花板?
  MySQL sync 在消费者线程做，不走 taskExecutor
  → 减少了 3 个 taskExecutor 争抢 (12 → 9)
  → CallerRuns 大幅减少
  → 消费者线程虽然同步等 MySQL，但 MySQL 是本地 Docker，延迟极低
  → 用 ~3ms 的"等"换来了 taskExecutor 的充分释放
```

### 因素 4: `batchInsert()` 是真实 DB 写，不是 `queue.offer()`

```java
// BatchInsertService.java line 67-71
@Transactional
public void batchInsert(List<User> userList) {
    userMapper.batchInsert(userList);  // ← 真正的 DB 批量 insert，不是入队！
}
```

```
这个发现很重要:
  - 版本 C 的 MySQL "同步" = 真的同步执行 DB insert，不是 queue.offer
  - 但它比"4 异步"版本反而更快
  - 说明: 在有限资源下，减少线程调度开销 > 消除 I/O 阻塞
  
  如果改成 queue.offer() 入队 + 定时刷盘，理论上还能更快，
  但版本 C 已经是实测最优。
```

## 五、设计原则总结

| 原则 | 说明 |
|---|---|
| **异步 ≠ 更快** | 当一个有限线程池被多个 I/O 任务打满，异步的线程切换开销 + CallerRuns 反噬会抵消异步收益 |
| **CallerRunsPolicy 是把双刃剑** | 防止 OOM (拒绝任务) 但会在高负载时把异步拉回同步，形成正反馈恶化 |
| **减少 taskExecutor 并发任务数是关键** | 从 4→3 个任务，QPS 提升了 +27% |
| **消费者线程做低成本同步操作是可接受的** | MySQL 本地批量 insert (~3ms) 在消费者线程做，比扔进过载线程池 + 上下文切换更高效 |
| **4C/8T 物理极限 ~6,800 QPS** | 当前架构在这个硬件上的天花板 |
| **独立存储测试验证了"同步不一定慢"** | MySQL sync 8,437 > Redis async 5,967，线程调度开销在 CPU 紧张时远大于 I/O 阻塞 |
| **生产环境预估 10,000+ QPS** | 四存储分离部署 + Java 独立，解除 CPU 争抢后预期可达 10,000~12,000 QPS |

## 六、如果要继续优化

| 方向 | 预期收益 | 依据 |
|---|---|---|
| **分离部署** (各存储独立物理机) | **10,000~12,000 QPS** | 独立测试 MySQL 8,437 + 释放 CPU 争抢 |
| **更多 CPU 核心** (8C/16T 以上) | 直接提高物理天花板 | 当前 4C/8T 是绝对瓶颈 |
| **Mongo/ES/Redis 都改成 sync** | +15~20% 吞吐 | sync 消除了 taskExecutor 线程调度开销 |
| **拆分线程池** (每个存储独立线程池) | 避免争抢，隔离故障 | 当前共享 taskExecutor 是一刀切 |
| **MySQL 改为 queue.offer 入队模式** | 彻底消除消费者线程阻塞 | 但版本 C 已经够快，增益有限 |
| **增加 Kafka 消费者线程数** (3→6) | 提速消费 | 需要更多 CPU 支撑 |
| **ES: 不用 bulk processor，改 sync** | 消除 BulkProcessor 内部调度开销 | 独立 ES 6,678 低于 Mongo 7,845 |
