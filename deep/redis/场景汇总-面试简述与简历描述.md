# 场景 1-10 汇总：面试简述 + 简历描述

---

## 一、面试简述精简版

> 下面按场景编号压缩到 **每场景 2~4 句话**，用 **问题 → 原因 → 结论** 三要素串联。

---

### 场景 1：Lettuce Pipeline 压测排查与优化

单机 Redis Pipeline 压测，从 **CPU 100%** 初期表象出发，逐步发现 **Pipeline 并发过载反噬**（8→16 并发吞吐反降 37%）、**Semaphore 令牌泄露**、**连接未释放**、**优雅关闭卡 15 秒**等 7 个问题。引入 **flush-Semaphore 反压** + `try/finally` 防泄漏 + **Lettuce 连接按 Worker 隔离** + **超时优化** 后，吞吐稳定在 ~350k cmd/s，P99 从 20ms 降至 5ms。

**面试一句话**：用 Semaphore 反压机制解决了多线程 Pipeline 并发过载导致的吞吐反噬，核心在于限制了"同时冲向 Redis 的 pipeline 数量"。

> 补充 **「混合命令类型 Pipeline」**（理论分析）：Pipeline 中混入 SET/HSET/ZADD/DEL 等多类型命令，导致主线程在不同命令分发路径间频繁切换，分支预测失败 + RESP 编码差异拖慢解析，slowlog 激增。生产建议按命令类型**分拆 Pipeline**，同类型一批，减少切换开销。

---

### 场景 2：大结构 Hash 批量写入 + RDB fork COW

50 万大 Hash（10 field × 256B）在 256MB 内存限制下持续写入，对比了 **无持久化 / RDB / AOF 三种持久化模式**。RDB 的 `BGSAVE` fork 在高写入 + 冷启动场景下产生 **~245MB COW（Copy-On-Write）**，几乎把物理内存翻倍，容易 OOM。**AOF rewrite percentage=100 时单次 COW 最小（~66MB）**。

**面试一句话**：测算出 RDB fork 的 COW 内存开销可达 `used_memory_rss × 1.5~2`，生产建议主节点**关持久化**、副本错峰做 BGSAVE。

> 补充 **「批量删除冷热混合 key」**（理论分析）：Pipeline 中 DEL（存量 key）与 SETEX（新增 key）交替执行 → alloc/free 高频交错 → jemalloc 碎片率飙升（`mem_fragmentation_ratio > 1.5`） + dict 反复缩容/扩容 → CPU 拉高。生产方案：`UNLINK` 异步删除替代 `DEL`，或 **RENAME 原子替换**消去显式删除。

---

### 场景 3：短期 TTL 海量过期 key 延迟抖动

50 万 key 同时 TTL=2s 过期，Redis 的 `activeExpireCycle` 在主线程做采样式过期扫描，导致 **P99 从 10ms 飙升到 159ms**。方案优先级：`lazyfree-lazy-expire yes`（异步释放内存）→ `hz=50 + effort=2` 切碎扫描波峰 → 应用层 TTL 随机偏移从源头打散。效果：P99 降至 34ms。

**面试一句话**：大量短 TTL key 同时到期让 Redis 主线程被过期扫描阻塞，用 lazyfree + 高 hz + TTL 随机打散三招从 159ms 降到 34ms。

---

### 场景 4：分布式信号量—12 个 Writer 竞争 Pipeline 槽位

单服务最优为 8 个 pipeline 并发槽位，但 12 个微服务同时写等于 96 个管道。用 Redis 全局计数器做**分布式 Semaphore**，遍历 2/4/8/12/16 个全局槽位，结论：**8 槽位性价比最优**（吞吐 320k cmd/s, P99 4.6ms, 无重试饥饿）。实现要点：① 仅成功持有时释放（Lua 原子性），② token + TTL 防泄漏，③ 随机退避防惊群。

**面试一句话**：用 Redis 实现分布式 Semaphore 限制 12 个微服务的全局并发 Pipeline 数，找到 8 槽位是吞吐与延迟的最优平衡点。

---

### 场景 5：HGETALL vs HSCAN—大 Hash 读写争抢

大 Hash（数千 field）调用 `HGETALL` 是 O(N) 阻塞操作，Redis 单线程被长时间占用，写请求 P99 从 <1ms 恶化到 >50ms。方案：实现 `RedisHashUtil`，依据 `HLEN` 三级阈值策略（<500 直下 HGETALL，500~5000 走 HSCAN 并 warn，≥5000 拒绝），**HSCAN count=200 为经验最优值**。核心结论：数据建模阶段就避免大 Hash（field ≤ 1000），是根本解。

**面试一句话**：封装了 HSCAN 安全工具类替代危险 HGETALL，用 field 数三级阈值策略避免大 Hash 阻塞 Redis 主线程。

---

### 场景 6：maxclients 连接数爆炸边界探测

微服务 12 实例 × 每实例多 Worker × 每 Worker 一条直连 → 连接数线性增长撞向 `maxclients` → 新连接被拒。对比了 **直连模式（连接数 = 并发数）** 与 **连接池模式（连接数有上限）**，结论：连接池 + Semaphore 排队，可以将连接数压缩到 `poolMaxTotal`（如 50），超出部分排队而非创建新连接，避免 `rejected_connections`。

**面试一句话**：将多微服务的 Pipeline 直连改为连接池模式，连接数从 ~200 降到 50，用排队替代拒绝。

---

### 场景 7：Cluster 跨槽 Pipeline CROSSSLOT 错误轰炸

单节点直连模式下，Pipeline 包含跨 slot 的 key → Redis 返回 `CROSSSLOT`，**整批 100 条全部失败**，高速写入下变成每秒几万条异常日志轰炸。两个解法：① 用 `{hashtag}` 把需同批的 key 强制路由到同一 slot；② 用 Cluster 客户端自动按 slot 分组、分别发送。推荐 hashtag，避免客户端开销。

**面试一句话**：Cluster 下 Pipeline 的所有 key 必须落同一 slot，否则整批作废。用 `{}` hashtag 强制同槽是最简解法。

---

### 场景 8：热点 Key Pipeline INCR 自增

#### 8-1：热点 Key 单节点瓶颈

高并发 INCR 同一 key → 全部打到唯一节点，单节点 CPU 100% + **主从复制管道积压**。结论：**Cluster 对热点 key 无效**（水平扩展不分散同 key 负载）。方案：**LOCAL_BUFFERED**——本地内存原子自增 + 定期 `INCRBY` 刷写给 Redis，本地吞吐 3000 万/秒（vs 直连 Redis 36 万/秒），RTT=10ms 跨地域场景效果放大 100 倍。

#### 8-2：Pipeline RTT 敏感度

论证了 **网络延迟对五种写入模式的不同冲击**：`SINGLE_KEY` / `DISTRIBUTED` / `SHARDED` 吞吐 ∝ 1/RTT（RTT 从 1ms 变 10ms → 吞吐掉 90%），而 `LOCAL_BUFFERED` / `COMPUTED` 因本地主循环，吞吐几乎与 RTT 无关。量化判据：**RTT > 2ms 就应切到 LOCAL_BUFFERED**。

**面试一句话**：热点 key 高并发自增用本地缓冲 + 定期 flush 方案，本地吞吐 3000 万/s 且不受 RTT 影响，比直连 Redis 提速 80 倍。

> 补充 **「Lua 嵌套 Pipeline」**（理论分析）：Pipeline 内循环调 EVAL 脚本 (`batchSize` 个 EVAL 命令串行执行)，主线程连续被占用 `batchSize × 单 EVAL 耗时`，全局命令延迟均匀飙升。最优方案：将分批逻辑**合并为 1 个 EVAL 脚本**（Lua 内做 for 循环），阻塞窗口从 N×T 压缩到 1×T。

---

### 场景 9：集合运算（SINTER/SUNION/SDIFF）高并发压测

Set 交集/并集/差集是 CPU 密集型，100 并发 × 10K 成员的 SINTER 让 P50 从 <1ms 恶化到 >30ms。核心优化：用 **SINTERSTORE/SUNIONSTORE 预计算结果写入新 key**（写时计算一次，读时直接 GET），将 CPU 压力从 N 次实时计算降低为 1 次。总结：Redis Set 集合运算只适合小集合（<1000 成员），大集合必须预计算+缓存。

**面试一句话**：大集合运算用 SINTERSTORE 预计算写 Redis 换取读时零成本，比实时运算性能高 10~50 倍。

---

### 场景 10：哨兵 vs 集群—写入阶段选型与故障全集

对 Sentinel（1 主 + 1 从 + 3 哨兵）和 Cluster（3 主分片 + 3 副分片）做了全面的 **稳态写入 / 故障 failover / 脑裂 / RPO** 对比压测。核心结论：① **稳态下单 hot key 写，集群无吞吐优势**（都是单节点瓶颈）；② **故障态 failRate 均可达 0%**（需应用层重试）；③ **脑裂两种模式都会发生**，根治方案都是 `min-replicas-to-write=1`；④ 整理了 **Sentinel 7 类 + Cluster 7 类共 14 种故障场景**的完整矩阵与解决方案。

**面试一句话**：完整对比了 Sentinel 和 Cluster 在写入阶段的稳态吞吐、故障 failover、脑裂和 RPO，整理出 14 种故障的完整 HA 矩阵。
