场景 9: 集合运算（合并/交集/差集）高并发压测

2026-07-10redis 系列约 87 分钟阅读Redis压测Java 并发

9.1 背景与问题

Redis Set 集合运算（SINTER/SUNION/SDIFF）复杂度：

  SINTER k1 k2 ... kk  →  Redis 会选择最小的输入集合作为遍历基准，
                          遍历其 S 个 member，对其它集合做 O(1) 哈希查找，
                          总体复杂度约 O(S * (k-1))，S = size(最小集合)，k = 输入集合数
  SUNION k1 k2 ... kk  →  将所有集合的 member 全部合并、去重后返回 → O(sum Ni)
  SDIFF k1 k2 ... kk   →  遍历第一个集合（同 SINTER 策略），排除其它集合中存在的 → O(N1 + sum(N2..Nk))

  注意：若客户端总是把大集合放在第一个参数，会放大成本；
        部分客户端/库可能自动重排以最小集合优先，但多数不保证此行为。

  当 ① 集合 size 大 且 ② 并发连接多 时：

  Worker-1 ── SINTER big:set:1 big:set:2 ─┐
  Worker-2 ── SUNION big:set:1 big:set:3 ─┤
  Worker-3 ── SDIFF big:set:2 big:set:4 ──┤ → 全部排队在 Redis 命令执行主线程
  Worker-4 ── SINTERSTORE dst big:set:1... ─┘

  → Redis 命令执行主线程 CPU 迅速饱和
  → 集合越大、并发越高，吞吐反降
  → 需要找到吞吐天花板 vs 集合大小的拐点

Redis 命令执行模型:
  - 命令逻辑在主线程串行执行（command execution 单线程）
  - Redis 6+ 可开启 I/O 线程并行化网络读写，但不并行执行命令逻辑
  - Redis Modules 和某些后台任务可能使用线程，但普通命令仍按主线程串行处理
  - 结论：CPU 密集型集合运算仍受主线程瓶颈限制

（以下为本次测试环境观测值，具体数值依赖 CPU 型号、Redis 版本、网络延迟、数据编码等）:
  - 10K 成员集合上的 SINTER 单次耗时约 ~0.3ms
  - 100 并发时全部排队 → P50 从 <1ms 恶化到 >30ms
  - 50 并发 × 10K 成员时吞吐仅 ~5K ops/sec

集合运算是 CPU 密集型命令中最危险的一类——小集合时毫秒级，大集合时秒级，极易触发 slowlog。

三个核心模式总结

SINTER  →  "同时满足 A 且 B 且 C"  →  共同好友、多标签筛选、多条件定向、权限校验
SDIFF   →  "有 A 但没有 B"         →  推荐新人、排除已转化、去重、缺货、黑名单过滤
SUNION  →  "A 加上 B 的合集"      →  全量覆盖池、多来源合并、多仓储汇总

这些场景的共同特征：需要快速判断某个 member 是否属于某个集合——这正是 Set 哈希结构 O(1) 查找的核心优势。

9.6 关键发现

9.6.1 吞吐天花板在 ~38K ops/sec（本次环境）

本次测试环境观测峰值: 38,031 ops/sec（1K members × 20 workers）。
该值随机器型号、Redis 版本、网络与数据编码显著波动，仅作容量估算参考。

超过此点 → 增加并发或扩大集合 → 吞吐反而下降：

  - 1K → 5K members: 吞吐降低 52%（38K → 18K）
  - 5K → 10K members: 吞吐再降 71%（18K → 5.2K）

原因：每轮 6 条集合运算命令中，每条 SINTER/SUNION/SDIFF 都需要遍历集合数据。10K 成员时单次 SINTER 就消耗 ~0.3ms Redis CPU（本次环境），50 个 worker 同时请求 → 排队延迟快速累积。

9.6.2 不同重叠度影响

压测中覆盖了四种重叠度：

  k1 与 k2 = 100%  → SINTER 遍历最小集合 → 结果集 = N（最大返回）
  k1 与 k3 = 30%   → SINTER 遍历最小集合 → 结果集 = 0.3N
  k2 与 k4 = 50%   → SINTER 遍历最小集合 → 结果集 = 0.5N
  k3 与 k5 ≈ 15%   → SINTER 遍历最小集合 → 结果集 = 0.15N（最小返回）

关键认知: Redis 会选择最小的输入集合作为遍历基准，
对它的每个 member 在其余集合中做 O(1) 哈希查找。
无论最终交集是多少，遍历开销是固定的（由最小集合的大小决定）。
结果集大小影响的是网络传输与结果处理，不影响 Redis 服务端遍历 CPU。
SDIFF/SUNION 类似——SUNION 合并所有集合 member 去重，复杂度 O(sum Ni)；
SDIFF 遍历第一个集合（或最小集合），排除其它集合存在的 member。

9.6.3 Store 变体的区别

命令 内存开销 CPU 开销 适用场景
SINTER 仅返回结果 O(N) 遍历 客户端直接使用结果
SINTERSTORE 写入新 key O(N) 遍历 + O(M) 写入 后续多用结果、缓存快照
SUNION 返回全部 O(N+M) 合并视图
SUNIONSTORE 写入新 key O(N+M) + 写入 持久化合并结果
SDIFF 返回差集 O(N) 增量/差异检测
SDIFFSTORE 写入新 key O(N) + 写入 快照差异 
性能结论: STORE 变体比只读变体多了写入和内存管理开销
（创建/覆盖目标 key、增删元素、内存分配与回收）。
在本环境观测中，high overlap (100%) 场景下 SINTERSTORE 比 SINTER 额外约 20% CPU，
但该比例会随结果集大小、写入策略（overwrite vs create）、Redis 内存碎片状态等波动。
在真实场景中，若结果需多次复用，STORE 变体以一次写入换多次读取，性价比高。
仅一次性使用时 SINTER 更优——省去写入开销且网络传输结果集即可。

9.7 SMOVE 原子性优势

SMOVE src dst member → 在一条 Redis 命令中完成:
  ① SREM src member
  ② SADD dst member

这是「先取再删再写」的原子替代方案，不需要 WATCH+MULTI/EXEC 事务：
  非原子做法: WATCH src → SMEMBERS src → SREM src m → SADD dst m → EXEC
  原子做法:  SMOVE src dst m  （一条命令，天然原子）
特性 WATCH+MULTI SMOVE
原子性 CAS 乐观锁，可能重试 命令级原子，无需重试
RTT 最少 4 次 1 次
错误处理 需处理 retry/abort 返回 0/1，语义清晰
与 Pipeline 配合 不支持事务内 pipeline 可放入 Pipeline 减少 RTT，但不保证多 SMOVE 整体原子性

注意: Pipeline 只是批量发送命令以减少 RTT，不保证多命令整体原子性。若需要多条 SMOVE 原子执行，需用 MULTI/EXEC 包裹。单条 SMOVE 可在 Pipeline 中安全使用——它本身是服务端原子命令。与 WATCH+MULTI 对比的核心优势是：单条命令直接完成 SREM+SADD，一劳永逸，无需重试循环。

9.8 ZUNIONSTORE / ZINTERSTORE 聚合策略选择

ZUNIONSTORE dst 2 z1 z2 AGGREGATE <SUM|MIN|MAX>

  SUM: score 相加         → 业务默认值（如积分汇总）
  MIN: 取最小 score       → 如「最低库存」
  MAX: 取最大 score       → 如「最高优先级」

ZINTERSTORE dst 2 z1 z2 AGGREGATE <SUM|MIN|MAX>

  SUM: 交集 score 相加    → 如「共同兴趣的加权总分」
  MIN: 取最小 score       → 如「最低活跃度」
  MAX: 取最大 score       → 如「最高消费额」

所有 6 种聚合组合均通过验证，选择建议：

场景 推荐聚合 理由
多维度总分排名 SUM 累加各项得分
取最低分安全排名 MIN 宁可低估不虚高
最高分特征提取 MAX 提取每个用户的最优表现
去重合并多集合 SUM with weight=1 等效于 Set 的 SUNION

9.9 SSCAN 遍历经验

SSCAN key cursor COUNT N

  - cursor 从 0 开始，返回 0 表示遍历结束
  - COUNT 是 hint，非精确值，单次可能返回少于或多于 COUNT 条
  - ⚠️ SSCAN 不是快照隔离：遍历期间若有并发 SADD/SREM，可能遗漏或重复返回元素
  - 大集合必须用 SSCAN，严禁 SMEMBERS

SSCAN 最佳实践:
  在本次测试环境下 COUNT=200 单次耗时 <1ms
  COUNT=1000 接近 SMEMBERS 行为，单次阻塞风险加剧
  客户端必须去重: 用 Set/HashSet 累积结果并消除重复
  设置 max rounds 与超时保护: 遍历超过 N 轮或 T 秒强制终止
  若需强一致性快照：在无写入的时间窗口遍历，或先 SINTERSTORE 导出到不可变 key 再遍历

// 推荐遍历模式
public Set<String> sScanAllSafe(String key, int count) {
    Set<String> result = new HashSet<>();
    String cursor = "0";
    int maxRounds = 1000;
    do {
        ScanArgs args = ScanArgs.Builder.limit(count);
        ScannedSet scan = commands.sscan(key, cursor, args);
        result.addAll(scan.getValues());
        cursor = scan.getCursor();
        if (--maxRounds <= 0) throw new TimeoutException("SSCAN too many rounds");
    } while (!"0".equals(cursor));
    return result;
}

9.14 架构策略：同 Slot + 分布式信号量管控

本节从架构层面总结集合运算的写入管控和查询优化策略，确保 Cluster 兼容性与性能天花板可控。

9.14.1 不同分片模式下集合运算的兼容性

架构模式 slot 概念 SINTER k1 k2 k3 是否报错
单体 Redis 无 ✅ 直接调用 不报错
Redis Cluster 16384 个，分布到多节点 ❌ key 不在同一 slot 时报 CROSSSLOT 会报错
代理分片（Twemproxy/Codis） 无（代理内部做） ❌ 代理层通常禁掉多 key 命令 会报错
手动取模分片（userId % N） 无（应用层路由） ⚠️ 跨分片时不报错，静默返回错误结果 不报错（最隐蔽）
单 Redis + 应用层拆小 key（防大 key） 无 ✅ 直接调用（同实例） 不报错

结论：只有 Cluster 和代理分片会显式报错，手动取模分片是最危险的——跨分片的 key 在各自 Redis 上执行，缺失的 key 被视为空集，静默返回错误结果。架构上必须通过 key 命名约束从根本上杜绝。

9.14.2 三层架构：写入管控 → 命名对齐 → 查询零判断

                      ┌─────────────────────────────────┐
                      │  层 1：写入管控（分布式信号量）         │
                      │  ├─ acquire slot (Lua 原子)          │
                      │  ├─ 按 userId 分片路由                 │
                      │  └─ release + token+TTL 防泄漏        │
                      │  作用：防止 N 个服务同时 SADD →        │
                      │        流量整形，避免并发写入失控         │
                      └──────────────┬──────────────────────┘
                                     │ 写入时 key 格式已定
                      ┌──────────────▼──────────────────────┐
                      │  层 2：Key 命名统一 (hashtag)         │
                      │  {userId}:friends                    │
                      │  {userId}:blocklist                  │
                      │  {userId}:tags                       │
                      │  只对 { } 内做 CRC16 → 必然同 slot     │
                      └──────────────┬──────────────────────┘
                                     │ 运行时零校验
                      ┌──────────────▼──────────────────────┐
                      │  层 3：业务层直接调                    │
                      │  SINTER / SUNION / SDIFF             │
                      │  零额外判断，无 hash tag 提取开销       │
                      └─────────────────────────────────────┘

为什么不需要运行时校验：写入时已通过信号量控制 + hashtag 约束保证了 key 命名，运行时直接调用即可。没必要每次 SINTER 前提取 {xxx} 比对——这是无效开销。

9.14.3 为何集合运算必须选同 slot

Redis Cluster 的 slot 规则：
  CRC16("{userId}:friends") % 16384 → 只计算 {userId} → slot X
  CRC16("{userId}:blocklist") % 16384 → 只计算 {userId} → slot X

  同 slot → 同节点 → SINTER 可直接在服务端完成。

vs 不同 slot（跨分片兜底方案）：
  SINTER k1 k2 → k1 在 Node A，k2 在 Node B → 无法执行原生命令
  → 需分别向 Node A、Node B 执行 SMEMBERS（或 SSCAN 分段）拉全量
  → 在集群中需多次 RTT（每个节点至少一次）
  → 在 10K member 场景下，单次网络传输可达数百 KB
  → 客户端内存需同时持有所有集合的完整数据
方案 网络传输 服务端 CPU 客户端内存 推荐
同 slot 直调 仅返回结果集 O(S*(k-1)) 服务端 结果集大小 ⭐
客户端拉全量求交集 k×N 条 member 无（客户端 CPU） k×N member 仅跨分片兜底
STORE 缓存结果 一次 RTT 一次 O(N) 结果集大小 适合高频复用

兜底方案代价量化：跨分片 SINTER k1 k2（各 10K member，50B per member）→ 网络传输约 2×10K×50B ≈ 1MB；若并发 50 请求 → 50MB/s 客户端入站带宽。仅在确实跨用户/跨分片时作为最后手段使用。

9.14.4 单 Redis + 应用层拆小 key 的陷阱

# 场景：为了防止大 key（如单 key 100 万 member DEL 会阻塞），
#       把一个大 Set 拆成 10 个小 Set，全部在同一台 Redis 上。

SADD user:123:followers:0 10万个member
SADD user:123:followers:1 10万个member
...
SADD user:123:followers:9 10万个member

# 做交集：
SINTER user:123:followers:0 user:123:followers:1 ... user:123:followers:9
# → 单机 Redis 无 slot 限制，语法完全正确 ✅
# → 但遍历量 = 10 × 10 万 = 100 万，和拆之前一样 O(N) ⚠️

核心认知：拆分不会降低 SINTER 的遍历总量。
  分片减少的是单 key 的 DEL/SADD/阻塞风险——这是拆分的目的。
  集合运算的 O(N) 支付在"遍历过程"，不因拆分而减少。

  拆分只在以下场景有意义：
    ✓ 避免单个 key 过大导致 DEL 阻塞主线程
    ✓ 避免 SMEMBERS 单次返回过多数据导致 OOM
    ✓ 多节点并行计算 + 合并（需要跨节点）
    ✗ 减少 SINTER/SUNION/SDIFF 的 CPU 遍历量

9.14.5 不同 sharding 模式下的集合运算快速决策表

分片模式 同分片运行 SINTER 跨分片 SINTER 正确性保证
单体 Redis ✅ 直接调 ✅ 直接调（所有 key 同实例） 天然正确
Cluster + hashtag ✅ 直接调 ❌ CROSSSLOT 报错 服务端报错
Cluster 无 hashtag ⚠️ 运气好如果 CRC16 同 slot ❌ CROSSSLOT 报错 不可靠

9.14.6 代码实现建议

// ==================== 推荐模式 ====================

// 写入：经信号量管控 + hashtag 统一命名
public void addToSet(long userId, String setName, String member) {
    // 层 1：分布式信号量 acquire（Lua 原子）
    String token = UUID.randomUUID().toString();
    boolean acquired = semaphore.acquire("set_write_slot:" + userId, token, 100);
    if (!acquired) throw new BusyException("Write slot busy");

    try {
        // 层 2：统一 hashtag 命名
        String key = "{" + userId + "}:" + setName;  // 所有同 userId 的 key 同 slot
        redis.sadd(key, member);
    } finally {
        // 层 1：release + token 防泄漏
        semaphore.release("set_write_slot:" + userId, token);
    }
}

// 查询：层 3 零判断
public Set<String> intersect(long userId, String setA, String setB) {
    // 直接调，不加任何校验——name 在写入层已保证为 {userId}:xxx 格式
    String keyA = "{" + userId + "}:" + setA;
    String keyB = "{" + userId + "}:" + setB;
    return redis.sinter(keyA, keyB);
}

// ==================== 兜底：跨分片交集（仅最后手段） ====================

// 仅用于跨 userId 查询（如"两个用户的共同好友"）——无法走同 slot 优化。
// 代价：需分别向多个节点 SMEMBERS（或 SSCAN 分段）拉全量。
//       网络传输 ×2 全量 member + 客户端内存 ×2 集合大小。
// 重度场景可替换为预计算/索引方案。
public Set<String> crossUserIntersect(long userA, long userB, String setName) {
    // ⚠️ 大集合时改 SSCAN 分段拉取，避免 SMEMBERS 单次 OOM
    Set<String> setA = redis.smembers("{" + userA + "}:" + setName);
    Set<String> setB = redis.smembers("{" + userB + "}:" + setName);
    setA.retainAll(setB);
    return setA;
}

9.15 替代方案与工程实践

9.15.1 预计算/缓存交集

对于热点集合对，使用 SINTERSTORE 定期或事件驱动生成缓存结果，设置合理 TTL，异步刷新。

⚠ 防缓存风暴（Cache Stampede）: 多个 worker/实例并发执行刷新会造成重复 CPU 花费，且直接写入目标 key 在高并发/大结果集时仍会在主线程上产生较长阻塞。推荐使用 "临时 key + RENAME 原子替换" 或 "分布式锁（SETNX）" 防止 stampede。

// 定时任务：每 30 秒刷新一次高频交集（带防 stampede 锁 + 临时 key）
@Scheduled(fixedDelay = 30_000)
public void refreshHotIntersection() {
    String lockKey = "lock:hot:intersection:" + userId;
    String cacheKey = "hot:intersection:" + userId;
    String tmpKey = cacheKey + ":tmp:" + UUID.randomUUID();

    // 尝试获取分布式锁（单机可用 SETNX，多实例用 Redis 锁）
    boolean locked = redis.setIfAbsent(lockKey, "1", Duration.ofSeconds(30));
    if (!locked) {
        // 其他实例正在刷新，读取旧缓存作为降级
        return;
    }

    try {
        // 写入临时 key，避免计算期间暴露不完整结果
        redis.sinterstore(tmpKey, "{userId}:setA", "{userId}:setB");
        redis.expire(tmpKey, 120);
        // RENAME 是原子操作，瞬间切换（无窗口期）
        redis.rename(tmpKey, cacheKey);
    } finally {
        // 释放锁（建议用 Lua 脚本校验 token 防误删）
        redis.delete(lockKey);
    }
}

适用于: 查询频率 >> 写入频率的集合对。

9.15.2 增量维护（反向索引）

写入时以 Lua 原子脚本维护热的交集/计数索引，牺牲写入复杂度换取读时低延迟。

⚠ 重要: Redis Lua 要求 key 必须通过 KEYS 数组传入（而非 ARGV），以便集群模式下正确路由。不遵循此约定会导致沙盒错误或集群兼容性问题。

-- 写入一个 member 时同步维护交集索引
-- KEYS[1] = srcSet, KEYS[2] = otherSet, KEYS[3] = targetIndex
-- ARGV[1] = member
redis.call('SADD', KEYS[1], ARGV[1])
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    redis.call('SADD', KEYS[3], ARGV[1])
end
return 1

适用于: 写入频率不高但查询频繁、且交叉维度固定的场景。

9.15.3 概率数据结构替代

⚠ 模块依赖: 以下 BF.* / CMS.* 命令来自 RedisBloom 模块（Redis Stack 自带，或单独安装）。标准 Redis 不带这些命令，需要先加载模块。误判率/内存由初始化参数决定，不是固定值。

场景 原生命令 概率替代 精度（可配置）
判断 member 是否存在 SISMEMBER Bloom Filter (BF.RESERVE key 0.01 1000000 → BF.EXISTS) 误判率可配置（如 0.01 = 1%）
计算唯一 member 数 SCARD HyperLogLog (PFCOUNT) 0.81% 标准误差
统计某 member 频率 需要额外计数 Count-Min Sketch (CMS.INITBYDIM → CMS.INCRBY) 可能高估，不低估 
# BloomFilt 示例（需要 RedisBloom 模块）
BF.RESERVE bf_key 0.01 1000000   # 1% 误判，容量 100 万
BF.ADD bf_key "user:123"
BF.EXISTS bf_key "user:123"      # → 1 (可能存在) / 0 (确定不存在)

适用于: 只需近似结果、集合规模极大的场景（几百万~几十亿级别）。

9.15.4 Lua 脚本合并多次 RTT

-- 原子执行：取最小集合的大小 + 做交集
-- KEYS[1..N] = 参与交集的 N 个集合
local sizes = {}
for i, key in ipairs(KEYS) do
    sizes[i] = redis.call('SCARD', key)
end
-- 选最小集合并返回交集
local minIdx = 1
for i = 2, #sizes do
    if sizes[i] < sizes[minIdx] then minIdx = i end
end
return redis.call('SINTER', unpack(KEYS))

⚠ 重要说明: - Lua 脚本把多次 RTT 合并为一次，能显著降低网络延迟开销，但不减轻主线程 CPU 负担——CPU 密集型逻辑仍在主线程串行执行。 - .call('SINTER', ...) 本身已是 Redis 原生实现且有内部优化（自动选最小集合遍历）；若要在 Lua 内自实现"最小集合优先遍历 + SISMEMBER"，Lua 循环的 CPU 开销可能高于原生 SINTER，不推荐。 - 要点: Lua 省的是 RTT，确保的是原子性，不是省 CPU。

9.15.5 外部并行计算

对于离线大规模集合运算（如日级别全量交集分析），考虑导出数据到 Spark/Flink 等外部引擎并行计算，Redis 仅做在线热数据服务。

redis-cli SLOWLOG GET 128 | while read line; do
    # 解析 slowlog id（每条约 4 行，id 在第 1 行）
    id=$(echo "$line" | awk '{print $1}')
    if [ "$id" -gt "$LAST_ID" ] 2>/dev/null; then
        echo "$line" >> /var/log/redis_slowlog.log
        NEW_LAST_ID=$id
    fi
done

echo "${NEW_LAST_ID:-$LAST_ID}" > "$LAST_ID_FILE"

# 返回: intset | listpack | hashtable

# 批量检查（安全方式：SCAN + pipeline，避免 KEYS）
redis-cli --scan --pattern "user:*:tags" | while read key; do
  enc=$(redis-cli OBJECT ENCODING "$key")
  size=$(redis-cli SCARD "$key")
  echo "$key | $enc | $size"
done

# 统计 intset/listpack 占比

9.17 写入策略：实时 SADD vs 定时任务同步

核心问题澄清：集合运算的 CPU 开销在读（SINTER/SUNION/SDIFF）而非写（SADD）。

9.17.1 写与读的 CPU 成本对比

操作 复杂度 10K 成员耗时 CPU 开销级别 需要异步吗
SADD 单条 member O(1) 哈希插入 < 1μs 几乎为零 ❌ 不需要
SREM 单条 member O(1) 哈希删除 < 1μs 几乎为零 ❌ 不需要
SINTER 两集合 O(S × (k-1)) ~0.3ms 这是 CPU 大户 ✅ 需缓存结果
SUNION 两集合 O(N1+N2) ~0.3ms 这是 CPU 大户 ✅ 需缓存结果
SDIFF 两集合 O(N1+N2) ~0.3ms 这是 CPU 大户 ✅ 需缓存结果 
┌─────────────────────────────────────────────────────────────┐
│  关键认知 (纠正误区):                                        │
│                                                             │
│  SADD 单条写入 CPU 开销 ≈ 1μs = 1/300 次 SINTER              │
│  → 同步 SADD 完全没有性能问题                                │
│  → 真正应该用定时任务预计算的是 SINTER/SUNION/SDIFF 的读结果  │
│                                                             │
│  不要为了省 O(1) 的写入，引入数据延迟这个更大的问题。          │
└─────────────────────────────────────────────────────────────┘

9.17.2 三种写入策略及适用场景

策略 A：实时增量 SADD（最常用）

// 用户加好友 → 立即 SADD，开销 O(1) < 1μs
public void addFriend(long userId, String friendId) {
    db.insert("friends", userId, friendId);                    // 持久化
    redis.sadd("user:" + userId + ":friends", friendId);      // < 1μs, 无需异步
}

适用: 单条增量变更（加好友、加标签、购买记录、用户行为） 理由: 用户加了好友，5 分钟后才在"共同好友"里看到？产品不可接受。

策略 B：定时全量覆盖（纯缓存场景）

// 人群包从大数据平台产出，每天更新一次 → 全量覆盖
@Scheduled(cron = "0 0 3 * * ?")  // 每天凌晨 3 点
public void syncAudienceTags() {
    List<UserTag> tags = db.query("select * from user_tags where ...");

    String tmpKey = "audience:target:tmp";         // 用临时 key 避免覆盖率窗口
    redis.del(tmpKey);
    for (UserTag t : tags) {
        redis.sadd(tmpKey, t.getUserId());
    }
    redis.rename(tmpKey, "audience:target");       // 原子替换
}

适用: 数据源是离线/批量计算的（人群包、日报、周期报表），实时同步没意义。 注意: 不要直接 DEL 原 key 再 SADD，用临时 key + RENAME 原子替换，避免查询窗口看到空集。

策略 C：实时 SADD + 定时对账（高可靠性）

// 实时变更 + 定时兜底，防止消息丢失 / Redis 重启数据丢失
public void addTag(String productId, String tag) {
    db.insert("product_tags", productId, tag);
    redis.sadd("tag:" + tag, productId);                   // 实时 (毫秒级)
    redis.sadd("tag:" + tag + ":version", productId);      // 版本标记
}

@Scheduled(fixedDelay = 300_000)  // 每 5 分钟对账
public void reconcile() {
    long lastVersion = redis.get("tag:version:last");
    long currentVersion = System.currentTimeMillis();

    List<ProductTag> changes = db.query(
        "select * from product_tags where updated_at > ?", lastVersion);

    for (ProductTag t : changes) {
        redis.sadd("tag:" + t.getTag(), t.getProductId());
    }
    redis.set("tag:version:last", currentVersion);
}

适用: 既需要毫秒级实时性，又需要防止消息队列丢消息、Redis 重启等异常。

9.17.3 三种策略决策树

需要实时性？
 ├─ 是 → 数据源是增量变更吗？
 │        ├─ 是 → 【策略 A】实时 SADD
 │        └─ 否 → 数据源是周期批量产出？
 │                └─ 是 → 【策略 C】实时 SADD + 定时全量对账
 └─ 否 → 数据每天才更新一次？
          └─ 是 → 【策略 B】定时全量覆盖

9.17.4 定时任务真正的价值：预计算 SINTER/SUNION 读结果

定时任务不应用来迁移 SADD 写操作（没必要），而应用来预计算 O(N) 读的结果：

// ❌ 错误理解：把 SADD 放到定时任务 → 牺牲实时性，换可忽略的 CPU
// ✅ 正确理解：把 SINTER 结果预计算 → 读操作由 O(N) 降为 O(1)

// 高频共同好友查询：每秒 1000 次请求 → 每次都 SINTER → CPU 炸
// 解法：定时预计算 + 缓存（加锁防 stampede + 临时 key 原子替换）

@Scheduled(fixedDelay = 60_000)  // 每分钟刷新一次
public void preCalculateCommonFriends() {
    List<Long> hotPairs = getHotUserPairs();  // 活跃用户对

    for (Pair p : hotPairs) {
        String cacheKey = "cache:common_friends:" + p.a + ":" + p.b;
        String tmpKey = cacheKey + ":tmp:" + UUID.randomUUID();
        String lockKey = "lock:" + cacheKey;

        // 用 SETNX 防 stampede：多个实例同时刷新只执行一次
        boolean locked = redis.setIfAbsent(lockKey, "1", Duration.ofSeconds(30));
        if (!locked) continue;  // 已有其他实例在刷新，跳过

        try {
            redis.sinterstore(tmpKey,
                "user:" + p.a + ":friends",
                "user:" + p.b + ":friends");
            redis.expire(tmpKey, 120);  // TTL 2 分钟
            redis.rename(tmpKey, cacheKey);  // 原子替换
        } finally {
            redis.delete(lockKey);
        }
    }
}

// 查询 → 直接读缓存 O(1)
public Set<String> commonFriends(long userA, long userB) {
    return redis.smembers("cache:common_friends:" + userA + ":" + userB);
    // 命中缓存 → 一次 RTT，零遍历
}

收益量化：1K members × 1000 QPS → 每 60s 一次预计算 vs 每次 0.15ms → CPU 节省 ~99%。

一句话定位

决策树
你的需求是啥？
│
├─ "统计有多少个不同的 X"
│   └─ HyperLogLog（12KB 固定，0.81% 误差）
│
├─ "判断 X 在不在集合里"
│   ├─ 必须 100% 准确      → Set（O(1) SISMEMBER）
│   └─ 1% 误判可以接受     → BloomFilter（内存省 18~100×）
│
├─ "统计每个 X 做了几次"
│   ├─ 必须精确            → ZSet / Hash
│   ├─ 允许略高估 + 内存紧 → CMS（~40KB 固定）
│   └─ 只要 Top-N          → CMS 初步计数 + ZSet 存 Top-N
│
├─ "需要列出集合里所有成员"
│   └─ Set / ZSet（概率结构做不到，它们不存具体 member）
│
└─ "百万级以下，内存还够"
    └─ 用 Set，不要过早优化。只有当内存账单来的时候再考虑概率结构。
三种结构组合使用
一个成熟系统的典型组合：

  用户统计
  ├─ 日活/月活           → HLL（去重计数，12KB 搞定）
  ├─ 今日登录用户 ID      → Set（热数据，百万级以下）
  └─ 历史登录用户去重     → BloomFilter（亿级，防缓存穿透）

  内容推荐
  ├─ 文章阅读量排行       → CMS 近似计数 + ZSet 精确 Top-100
  ├─ 已推荐去重          → BloomFilter（"这篇推过没？"）
  └─ 用户兴趣标签         → Set SINTER（精确交集，百万级）

  安全风控
  ├─ 黑名单手机号         → BloomFilter（亿级库，"0" 即放行）
  ├─ 登录失败频率         → CMS（防暴力破解）
  └─ 高风险用户精确名单   → Set（兜底 BloomFilter 的 1% 误判）

一句话总结：HLL 统计人、BF 判存在、CMS 量频率。 需求模糊用概率、查询列表用 Set、内存紧张选对路。Set 不丢精度；概率结构是主动取舍——用精度换 RAM，不是 bug 是设计。

9.18.10 正式环境迁移指南：从 Set/ZSet 平滑过渡到概率结构

要不要一开始就用？
起步阶段:   几千条数据，Set 内存几百 KB      → 完全不需要概率结构
增长阶段:   百万条数据，Set 内存几十 MB      → 可以开始考虑，但 Set 仍然扛得住
爆发阶段:   亿级数据，Set 内存几 GB~几十 GB  → 必须迁移，RAM 账单直接教你做人

原则：先跑起来，等内存告警了再迁。概率结构解决的是"规模问题"，不是"起步问题"。

迁移总策略：四步走，零停机
┌──────────────────────────────────────────────────────────────────┐
│             迁移总策略：双写 → 校验 → 切读 → 停写                   │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  阶段 1: 双写 (Double Write)                                      │
│    - 老逻辑 (Set) 和新逻辑 (HLL/BF/CMS) 同时写                     │
│    - 持续 1-7 天，累积新结构的历史数据                              │
│    - 此阶段读写仍以老逻辑为准                                      │
│                                                                  │
│  阶段 2: 校验 (Validate)                                          │
│    - 老结构和概率结构的返回值做交叉校验                             │
│    - 监控误差率、误判率在可接受范围内                               │
│    - 设好告警阈值，异常时立刻回滚                                   │
│                                                                  │
│  阶段 3: 切读 (Switch Read)                                       │
│    - 10% → 50% → 100% 灰度切换读取源                               │
│    - 每个灰度阶段至少观察 1-3 天                                    │
│    - 外部监控仪表盘对比前后数据波动                                  │
│                                                                  │
│  阶段 4: 停写 (Stop Old)                                          │
│    - 删除老结构写入代码                                             │
│    - 老 key 靠原有 TTL 自然过期，内存自动回收                        │
│    - 无需手动全量 DEL，零运维接触                                   │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
迁移方案 A：Set → HyperLogLog（UV/DAU 去重计数）
// ════════════ 阶段 1: 双写（持续 1 周）════════════
public void recordUV(long userId) {
    String dateKey  = "uv:" + LocalDate.now();       // 老：Set
    String hllKey   = "uv_hll:" + LocalDate.now();   // 新：HLL

    redis.sadd(dateKey, String.valueOf(userId));      // 老逻辑保留
    redis.pfadd(hllKey, String.valueOf(userId));      // 新逻辑并跑

    redis.expire(dateKey, 86400 * 30);
    redis.expire(hllKey, 86400 * 30);
}

// ════════════ 阶段 2: 离线校验（每天对账一次）════════════
@Scheduled(cron = "0 0 2 * * ?")  // 每天凌晨 2 点
public void validateHLL() {
    String today = LocalDate.now().toString();
    long setCount = redis.scard("uv:" + today);
    long hllCount = redis.pfcount("uv_hll:" + today);

    double error = Math.abs(setCount - hllCount) * 100.0 / setCount;
    if (error > 2.0) alert("HLL 误差超标: " + error + "%");
}

// ════════════ 阶段 3: 灰度切读 ════════════
public long getUV(String date) {
    int roll = ThreadLocalRandom.current().nextInt(100);
    if (roll < hllReadPercentage) return redis.pfcount("uv_hll:" + date);
    return redis.scard("uv:" + date);
}

// ════════════ 阶段 4: 停写 Set ════════════
public void recordUV(long userId) {
    redis.pfadd("uv_hll:" + LocalDate.now(), String.valueOf(userId));
    // redis.sadd 已删除
}

迁移方案 B：Set → BloomFilter（黑名单 / 去重）

⚠ BF 标准实现不支持删除。如果黑名单需要频繁移除成员，有两个选择： 1. 保留 Set 做精确删除（需接受 Set 的内存开销） 2. 使用 Counting BloomFilter（RedisBloom 模块支持 BF.INSERT ... NONSCALING，用计数器替代单 bit，可递减删除。注意：Counting BF 内存是标准 BF 的 3~4 倍，且误判率与实现复杂度更高）

// ════════════ 阶段 0: 全量初始化 BF ════════════
@PostConstruct
public void initBF() {
    redis.bfReserve("blacklist:bf", 0.01, 10_000_000);
    List<String> allPhones = db.query("SELECT phone FROM blacklist");
    for (String phone : allPhones) {
        redis.bfAdd("blacklist:bf", phone);
    }
}

// ════════════ 阶段 1: 双写 ════════════
public void addBlacklist(String phone) {
    db.insert("blacklist", phone);
    redis.sadd("blacklist:set", phone);    // 老
    redis.bfAdd("blacklist:bf", phone);    // 新
}

// ════════════ 阶段 2: 双读校验 ════════════
public boolean isBlacklisted(String phone) {
    if (!redis.bfExists("blacklist:bf", phone)) return false;
    boolean exact = redis.sismember("blacklist:set", phone);
    if (!exact) log.warn("BF false positive: phone={}", phone);
    return exact;
}

// ════════════ 阶段 3: 切读 ════════════
public boolean isBlacklisted(String phone) {
    return redis.bfExists("blacklist:bf", phone);
    // 1% 误判：偶尔冤枉一个正常用户 → 客服申诉解决，业务可接受
}

// 阶段 1: 双写
public void recordClick(long articleId) {
    redis.zincrby("clicks:zset", 1, "article:" + articleId);   // 老
    redis.cmsIncrBy("clicks:cms", "article:" + articleId, 1);  // 新
}

// 阶段 3: 组合方案 - CMS 计数 + ZSet 精确 Top-100
public void recordClick(long articleId) {
    redis.cmsIncrBy("clicks:cms", "article:" + articleId, 1);
    long approxCount = redis.cmsQuery("clicks:cms", "article:" + articleId);
    redis.zadd("clicks:top100", approxCount, "article:" + articleId);
    redis.zremrangeByRank("clicks:top100", 0, -101);
}

public List<String> getTop100() {
    return redis.zrevrange("clicks:top100", 0, 99);
}

核心结论
  不需要一开始就用。百万级以下 Set 完全够。
  迁移核心是"双写 → 校验 → 切读 → 停写"，四步走，零停机，随时可回滚。
  真正危险的是"到了 10 亿条还没迁"——那个时候再迁就是事故级别的项目了。
  老 key 靠 TTL 自然过期，无需手动全量 DEL，运维零接触。

  一句话: 早迁不急、晚迁不慌、不迁不行。
