# 场景 3 — 短期 TTL 海量过期 key 持续灌入

---

### TL;DR

**问题背景（一句话）：**
大量短 TTL（秒级）key 同时创建导致在到期时 Redis 的 active-expire 采样式扫描集中触发，从而在主线程上造成短时阻塞，导致 P99/max 大幅抖动，而 P50 保持较低。

**原因要点：**
1. `activeExpireCycle` 在主线程执行**采样式**过期扫描；`effort` 增加每次采样预算和扫描深度（提高单次 CPU/阻塞），`hz` 控制定时任务触发频率（提高扫描密度）。二者**不是精确线性关系**，实际删除量受过期 key 分布和 Redis 时间限制影响。
2. `lazyfree-lazy-expire` 将内存回收异步化（UNLINK → 后台 BIO 释放），显著减少主线程在释放内存上的阻塞，但**不消除扫描/定位过期 key 的主线程成本**。
3. 应用层 TTL 打散从源头减少同一时间到期 key 数量，根本弱化过期峰值；但打散会扩大 key 到期窗口（可能增加瞬时 key 数），需控制偏移幅度。
4. 过期压力来自"到期同步性"（同一时间大量 key 到期）与"key 空间大小"（同一窗口活跃 key 数）。

**解决策略（实操顺序）：**
1. **先启用 lazyfree（低风险兜底）** — 减少删除释放导致的主线程阻塞
2. 若短 TTL 且不能改应用 → 提高 hz（如 20~50）+ effort 降低到 1~3，把"单个波峰"切碎
3. 若能改应用 → TTL 加随机偏移（短 TTL 偏移控制在几秒级）
4. 长 TTL 周期批量写入 → 质数/互质 TTL 打破 LCM 汇集
5. 横向扩展 — 按 prefix/logic 拆分到多个 Redis 实例

**决策树：**
```
能改 Redis 配置？
├── 能 → ① 开 lazyfree（必须） → ② 短TTL? hz=50+effort=2 : 应用层打散为主
└── 否 → 能改应用？
          ├── 能 → TTL 随机打散（P99: 159ms→34ms）
          └── 否 → 横向拆分 key-space 或接受 P99 > 50ms
```

## 概述

Pipeline 持续写入短 TTL（2 秒）的 SETEX，模拟"缓存预热时大量短生命周期 key 同时创建、同时过期"的生产场景。观测 `activeExpireCycle` 抢占主线程导致延迟抖动。

## 压测架构

```
Worker-1 ── Redis 连接 1 ── [SETEX ttl:N 2 val] × batchSize ── flush ── awaitAll ── 循环
Worker-2 ── Redis 连接 2 ── [SETEX ttl:N 2 val] × batchSize ── flush ── awaitAll ── 循环
...
Worker-8 ── Redis 连接 8 ── [SETEX ttl:N 2 val] × batchSize ── flush ── awaitAll ── 循环
```

- key 空间 50 万，TTL 仅 2 秒
- value 16 字节（极小，焦点在过期行为）
- Redis `--active-expire-effort 10`（模拟生产激进过期扫描）
- 指标上报 5 秒一次，追踪 **P50/P99/max** 延迟 + expired_keys 增量

## 核心概念澄清：active-expire 与 lazyfree 的精确语义

### active-expire 不是线性 "hz × effort"

```
✗ 错误认知: 过期清理总量 = hz × effort（精确线性）
✗ 错误认知: 单次阻塞时间完全由 effort 决定

✓ 正确认知: active-expire 是"随机采样 + 时间受限"的自适应扫描
  - hz: 控制定时任务每秒触发次数（越高越频繁，但 CPU 开销也越大）
  - effort: 增加每次采样的预算和扫描深度，提高单次 CPU/阻塞时间
  - 实际删除量 → 受过期 key 分布 + Redis 时间限制 + key 大小 + 内存碎片共同影响
  - 单次阻塞长度 → effort 预算 + 待删除 key 的内存操作成本（大对象/复杂结构/碎片）
```

### lazyfree-lazy-expire 只异步化"内存回收"，不消除"扫描"开销

```
常规过期:
  主线程 [扫描定位过期key] → [DEL k1] → [DEL k2] → [处理命令]
               └── 扫描+内存释放期间所有命令排队 ──→

lazyfree:
  主线程 [扫描定位过期key] → [UNLINK k1,k2,k3] → [处理命令]
             ↑ 扫描仍占用主线程 ↑  UNLINK是常数级快操作
  后台 BIO 线程: [异步回收内存...]
```

**关键澄清：**
- lazyfree **不能消除**主线程在 active-expire 扫描/定位过期 key 上的 CPU 成本
- lazyfree 将 key 的**内存释放（free）** 交给后台 BIO 线程，主线程用 UNLINK 替代 DEL
- UNLINK 本身是常数级别快速操作，但如果要 UNLINK 的 key 极多，UNLINK 调用仍会花时间（但远小于同步 free）

**UNLINK 在复制/持久化上的影响：**
- UNLINK（或 lazyfree 删除动作）会在复制流/AOF 中以 `UNLINK`/`DEL` 形式传播到副本
- 副本端也会进行相应的删除处理（可能触发副本后台回收）
- 主从/持久化场景中需评估副本端/持久化端的删除负担，尤其是大量 key 同时被 UNLINK 时

### hz 提高的副作用

```
hz ↑:
  ✓ 定时任务更频繁触发 → 过期扫描更分散 → 单次阻塞更短（P99 ↓）
  ✗ 增加总 CPU 消耗 → 定时器中断/检查频率上升 → 低资源实例可能受影响
  ✗ 上下文切换开销增大
  → 最佳值需在吞吐、P99 与 CPU 之间折中：优先找最小能将 P99 压到可接受值的 hz
```

### TTL 打散的副作用

```
TTL=2s+rand(0,4s):
  ✓ 到期时间分散在 2~6s → 单窗口内到期 key 数大幅减少
  ✗ 窗口从 2s 拉宽到 2~6s → 瞬时 key 数可能增加（更多 key 同时存活）
  ✗ 短 TTL 场景偏移过大（如 10s+）会显著扩大 key-space → 增加扫描负担

建议:
  短 TTL（秒级）→ 偏移控制在几秒级（如 rand(0,4s)）
  长 TTL（时/天级）→ 使用质数 TTL 打破周期性 LCM 汇集
```

## 风险现象分析

### 1. 延迟抖动 — P99/max 远高于 P50

```
P50 延迟:  4-8ms      ← 正常水平（首轮尖刺行 29.7ms，不计入该区间）
P99 延迟: 51-159ms    ← 同一行 P50 的 5.4~14.8 倍（按行计算）
max 延迟: 82-262ms    ← 同一行 P50 的 8.8~26 倍（按行计算）
```

**根因**：`activeExpireCycle` 在 Redis 主线程中执行**采样式**过期扫描。当大量 key 同时过期，每次扫描命中大量过期 key，占用主线程数毫秒。在此期间，正常的 SETEX 命令被阻塞排队。

### 2. 过期速率的波动

5 秒窗口内过期量从 28k 飙升至 428k，表明大量 key 在第一波 TTL 到期后集中过期。`active-expire-effort 10` 的激进策略让 Redis 努力清理，但 CPU 消耗也从 0.8 增长到 3.2。

### 3. Key 数量剧烈波动

104k → 298k → 175k → 385k。过期和写入在持续拉锯——过期清理一批后 key 骤降，新写入又快速回拉。

### 4. 吞吐不稳定

567~1183 batches/s 波动。过期扫描高峰时（如 24s 处 P99=102ms），吞吐下降到 567；过期扫描收敛后（29s），吞吐反弹到 1183。

## 为什么 P50 很低但 P99 很高？

```
时间轴: ┌────┬────┬────┬────┬────┬────┬────┬────┬────┬────┐
请求:   │A   │B   │C   │D   │E   │F   │G   │H   │I   │J   │
延迟:   │5ms │6ms │6ms │150 │5ms │7ms │5ms │5ms │6ms │5ms │
                            ↑
                   activeExpireCycle 阻塞了主线程 144ms
                   期间所有请求 D/F/G/H 排队等待
```

- 大部分请求在两次过期扫描之间完成 → P50 = 5-6ms
- 恰好落在扫描窗口内的请求 → P99 = 100-160ms
- 最不幸的一个 → max = 262ms

**这解释了为什么只看平均延迟是致命的**：avg=12ms 看起来不错，但 P99 的实际用户体验已经突破了 100ms。

## 解决方案

| 优先级 | 方案 | 效果 | 副作用 |
|:--|:--|:--|:--|
| 1 | **启用 `lazyfree-lazy-expire yes`** | 主线程不阻塞于内存释放；低风险兜底 | 副本/AOF 端可能有压力 |
| 2 | **提高 `hz`** | 扫描更分散，单次阻塞更短 | CPU 开销增大 |
| 3 | **降低 `active-expire-effort`** | 单次扫描预算降低 → 单次阻塞缩短 | 清理不够快可能堆积 |
| 4 | **应用层打散 TTL** | 从源头减少同时到期 key 数 | 扩大到期窗口，瞬时 key 数增加 |
| 5 | **降低 key 空间** | 500k → 100k，减少轮替堆积量 | 业务约束 |
| 6 | **监控告警** | 多重指标交叉判断，快速发现问题 | — |

> **小步试验建议**：调整 hz/effort 或启用 lazyfree 时做 A/B 对比，记录 P99、CPU、expired_keys/s、replica lag、AOF/fsync 影响等，避免一次性大幅调整。

## 方案详解

### 1. `active-expire-effort` 和 `hz` 的含义

| 参数 | 含义 | 默认值 | 语义 |
|:--|:--|:--|:--|
| `hz` | 每秒执行定时任务的次数（越大越频繁） | 10 | 提高扫描密度，增加 CPU 定时开销 |
| `active-expire-effort` | 每次定时任务中过期扫描的采样预算与深度 | 1 | 越高越深入，单次阻塞越长 |

```
关键理解: hz 与 effort 并非精确线性关系

过期清理 ≈ 采样式自适应扫描：
  - hz 控制"检查频率"（更分散 → 单次负担小）
  - effort 控制"每次检查的采样深度"（更深 → 单次处理更多过期 key）
  - 实际清理量受过期 key 随机分布 + Redis 内置时间预算限制
  - 单次阻塞时间 ∝ effort ×（待删除 key 大小 + 内存碎片）
```

```
hz=10, effort=10（场景 3 原始配置）:
  0ms     100ms    200ms    300ms
  ┌─┐      ┌─┐      ┌─┐      ← 每次阻塞 ~15ms（effort=10 采样深度大）
  │████    │████    │████
  └──┘    └──┘    └──┘
   ↑ P99 尖刺

hz=50, effort=2（优化后）:
  0 20 40 60 80 100 120 140 160 180 200ms
  ▏▏▏▏▏▏▏▏▏▏                          ← 每次阻塞 ~1-2ms，基本无尖刺
```

### 2. `key 空间` 的含义

即 `app.ttl-bench.key-space` 配置。压测代码中每次写入随机选 key：

```java
String key = "ttl:" + ThreadLocalRandom.current().nextInt(keySpace);
```

`keySpace=500000` 意味着同一时刻最多有 50 万个不同 key 存活，TTL 到期时这些 key 都可能进入过期扫描范围。空间越大 → 采样命中过期 key 的概率/数量越高 → 扫描负担越重。

### 3. TTL 打散的局限性

不同级别的 TTL（1 天 / 1 小时 / 30 分钟）会在"最小公倍数"时间点自然汇集：

```
t=0  写入 10 万 key，TTL=1天 (86400s)
t=0  写入 10 万 key，TTL=1小时 (3600s)
t=0  写入 10 万 key，TTL=30分钟 (1800s)

t=3600  → 第 2 批 + 第 3 批 = 20 万汇集
t=7200  → 第 2 批 + 第 3 批 = 20 万汇集
t=86400 → 三批全部 = 30 万最大汇集
```

打散 TTL 只解决"同一批写入同时过期"，解决不了"不同批次在时间轴上自然交汇"。更根本的手段是：

| 层级 | 方案 | 效果 |
|:--|:--|:--|
| 写入层 | 分散写入时间，不要瞬间批量刷 | 到期时间自然错开 |
| TTL 层 | 使用质数/非整数 TTL（3553s 而非 3600s） | 打破最小公倍数汇集 |
| Redis 层 | `lazyfree-lazy-expire yes` | 汇集后的删除动作后台异步，不阻塞主线程 |

### 4. `lazyfree-lazy-expire yes` 原理

常规过期：主线程同步 `DEL key` → 大 key 或批量删除阻塞其他命令

```
常规删除: 主线程 [扫描] → [DEL k1] → [DEL k2] → [DEL k3] → [处理命令]
                     ←── 删除期间所有命令排队 ──→

lazyfree: 主线程 [扫描] → [UNLINK k1,k2,k3] → [处理命令]
             ↑ 扫描仍在主线程    ↑ UNLINK 常数级
            后台 BIO 线程: [异步回收内存...]
```

开启后主线程只标记删除，实际内存回收交给后台线程。**P99 尖刺的根源之一是"主线程被内存释放动作占用"**，lazyfree 把这部分移走。但扫描/定位过期 key 的开销仍在主线程。

> **注意**：UNLINK 会在复制流/AOF 中以 `UNLINK`/`DEL` 形式传播。如果大量 key 同时被 UNLINK，副本端也会经历相应的删除处理（可能触发后台回收）。主从场景中需监控 replica lag 和 replica CPU。

### 优化前 vs 优化后 对比

| 指标 | 优化前 (hz=10, effort=10) | 优化后 (hz=50, effort=2, lazyfree) | 改善 |
|:--|:--|:--|:--|
| **P50 延迟** | 4.6~29.7ms | **3.1~3.5ms** | ↓ 30%~90% |
| **P99 延迟** | 51~159ms | **5.65~16.96ms** | **↓ 9~10 倍** |

### 关键结论

```
P99 从 159ms → 16.96ms（下降 9.3 倍）
max 从 262ms → 41.41ms（下降 6.3 倍）
吞吐从 236k/s → 471k/s（提升 2 倍）
```

- **P99 尖刺被有效压制**：hz=50 让过期扫描更分散（扫描密度 ↑），effort=2 让单次扫描采样深度降低（单次阻塞 ↓），lazyfree 让内存释放不阻塞主线程
- **吞吐反而翻倍**：主线程不再被删除动作频繁阻塞，更多时间片用于处理命令
- **延迟曲线趋于平坦**：后续几秒 P99 逐渐收敛到 5-6ms，说明系统进入稳态后过期清理基本不影响正常请求

### 关键发现

**1. 应用层打散和 Redis 层优化效果接近**

> P99: 基线 159ms → Redis优化 17ms → 应用打散 34ms
> max: 基线 262ms → Redis优化 41ms → 应用打散 123ms

两者都把 P99 从 150ms+ 压到了 30ms 以内。Redis 层略优（P99 更低），但应用层打散完全不依赖运维改 Redis 参数。

**2. 应用层打散的 expired 增量远低**

```
基线:    28k~428k/5s  ← 大量集中过期
Redis:   113k~398k/5s  ← 过期清理更快，但仍在集中过期
打散:    1.5k~175k/5s  ← 到期时间分散后，每 5s 到期的量大幅下降
```

这说明 TTL 打散从**源头**减少了"同时过期 key 的数量"，不是硬扛，是压根不让它堆积。

**3. 第一窗口的尖刺是建连预热**

打散后 ~5s 处的 max=123ms 是因为刚开始写入，connections 尚未完全预热。10s 后就降到 34ms，和 Redis 优化持平。

**4. 最佳组合**

| 场景 | 推荐 |
|:--|:--|
| 不能改代码 | ② = hz=50 + effort=2 + lazyfree（纯 Redis 配置，P99 5.6~17ms） |
| 能改代码 | ③ 起步 = TTL 加随机偏移；再开 lazyfree 即 ⑤（综合最佳，P99 5.0~15ms） |
| 极致优化 | **⑤（打散 + lazyfree）** — P99 5.0~15ms、稳态吞吐 423k~481k，五轮综合最佳；**避免 ④**（打散 + hz=50 + effort=2 全叠）——④ 与 ⑤ 的差距在 hz/effort 而非打散本身 |

```
⑤ 统一打散: TTL=2+rand(0,4) → 所有 key 在 2~6s 内到期 → key 空间相对小

```

## 总结：三种武器的分工框架

### 各司其职

```
hz + effort  →  应对"同一秒内大量到期"   →  把波峰切碎（事后补救，提高扫描密度）
TTL 打散     →  应对"周期性 LCM 汇集"    →  不让波峰形成（源头消灭）
lazyfree     →  应对"无论如何都要删 key"  →  内存释放不阻塞主线程（最后兜底，低风险优先启用）
```

### 为什么这样分工

**短 TTL（秒级，固定到期）→ hz + effort 是主武器：**

```
40 万 key 同在第 2 秒到期 → 波峰又高又窄

hz=10: 第 2 秒只触发了 10 次采样扫描，每次采样可能命中更集中的过期 key → 每次都很重
hz=50: 第 2 秒触发 50 次采样扫描，单次需要处理的过期 key 更分散 → 切碎了 ✓
```

波峰本身避不开（TTL 固定），只能把扫描密度提高来分散单次负担。实测 ② 的 P99 从 159ms → 5.6ms 主要靠 hz 提高扫描密度。

**长 TTL（时/天级，周期性批量写入）→ TTL 打散是主武器：**

```
定时任务每小时写 10 万 key，TTL=3600s
→ 每到整点，10 万 key 同时到期 → 周期性超级波峰

hz=50 能切碎这个波峰吗？能，但：
  - hz 只能让每次扫描负担轻一点，不能消除"这一秒内要处理 10 万过期"的事实
  - 质数打散 (3593, 3607, 3613...) 直接让它们永不对齐 → 波峰消失 ✓
```

长 TTL 的波峰是"可避免的"——打散从源头消灭它，比事后切碎更优雅。

**所有场景 → lazyfree 是兜底（应优先启用）：**

```
无论波峰有没有被消灭/切碎，内存释放动作本身不应阻塞主线程。
lazyfree-lazy-expire yes 确保过期 key 删除走后台 BIO 线程 UNLINK。
这是低成本、低风险的操作，应在任何调优前先启用。
```

### 决策树

```
能改 Redis 配置？
  ├── 能 → ① 先开 lazyfree（必须，零成本兜底）
  │        │
  │        ├── 短 TTL（秒级）+ 固定到期 → 加 hz=50 + effort=2
  │        │     ②: P99 从 159ms → 5.6ms
  │        │
  │        ├── 短 TTL（秒级）+ 已打散 → 不需要 hz，lazyfree 就够
  │        │     ⑤: P99 从 159ms → 5ms（最佳）
  │        │
  │        └── 长 TTL（时/天级）+ 批量写 → 应用层质数打散 + hz=50 抹残余毛刺
  │
  └── 否 → 能改应用代码？
            ├── 能 → TTL 随机打散（③: P99 从 159ms → 34ms，能用）
            └── 否 → 横向拆分 key-space 或接受 P99 > 50ms
```

```yaml
# 实操顺序（推荐）
1. lazyfree-lazy-expire: yes       # 先兜底，最低风险
2. active-expire-effort: 1~3       # 降低单次采样深度
3. hz: 20~50                       # 提高扫描密度，视 CPU 可承受范围调整
4. 应用层 TTL 打散                   # 若可改代码
5. 横向拆分 key-space                # 若单实例不足以承载
```

### 一图总结

```
                    ┌─────────────────────────┐
                    │     key 会集中到期吗？    │
                    └───────────┬─────────────┘
                                │
              ┌─────────────────┼─────────────────┐
              ▼                 ▼                  ▼
         会，不可避免        会，但可避免          不会
      （固定短 TTL）    （长 TTL 周期批量）   （已打散稳态）
              │                 │                  │
              ▼                 ▼                  ▼
        hz + effort         质数打散          什么也不加
        切碎波峰            消灭波峰          lazyfree 兜底
              │                 │                  │
              └─────────────────┼──────────────────┘
                                ▼
                         lazyfree = yes
                    （所有场景的最后防线）
```

## 监控与告警建议

不仅要看 expired_keys 和延迟分位，还需同时监控以下指标以区分瓶颈来源（扫描 vs 删除 vs 复制）：

| 监控项 | 工具/命令 | 关注点 | 告警建议 |
|:--|:--|:--|:--|
| P50/P95/P99/max 延迟 | 客户端 HdrHistogram | 关注 P99 突刺 | P99 > 50ms 持续 1min → P1 |
| expired_keys/s | `INFO stats` | 过期速率突增 | > 100k/s 且 P99 > 50ms → P1 |
| `blocked_clients` | `INFO clients` | 被阻塞命令（BLPOP/XREAD 等）堆积 | > 0 持续 → P2 |
| `latency latest` | `LATENCY LATEST` | 直接观测 Redis 内部延迟事件 | 关注 expire 相关 events |
| `instantaneous_ops_per_sec` | `INFO stats` | 吞吐突降 | < baseline × 50% → P2 |
| `used_memory` / `used_memory_peak` | `INFO memory` | 内存峰值与波动 | 接近 maxmemory → P1 |
| CPU（主机 + Redis 进程） | `INFO cpu` + OS | CPU 突增 | > 80% 持续 1min → P1 |
| `replica lag` | `INFO replication` | UNLINK 传播导致 replica 延迟 | lag > 5s → P1 |
| `replica CPU` | replica 端监控 | replica 端删除负担 | > 80% → P2 |
| `rdb_last_save_time` / `aof_fsync` | `INFO persistence` | 持久化 I/O 影响 | fsync 延迟异常 → P2 |

> **注意**：hz 调高会增加 CPU 定时开销，需同时监控 Redis 进程 CPU。不要盲目把 hz 调太高（如 > 100）——会增加调度和统计开销，且在部分旧版或受限环境下效果递减。优先找最小能将 P99 压到目标值的 hz。

> **UNLINK 对副本的附加负担**：测试时关注副本端内存回收和持久化日志大小与速率，确保副本端不会因大量 UNLINK 传播导致回收延迟或内存峰值。

> **Pipeline/批量写入注意**：主线程阻塞会导致客户端写入延迟累积，可能造成网络层退避或连接阻塞。测试时同时观测客户端侧延迟。
