场景 10: 哨兵（Sentinel）vs 集群（Cluster）— 写入阶段选型压测

目标：为"写入阶段"做架构选型验证。聚焦两组对比： 1. 稳态写压测：哨兵 vs 集群 的纯写吞吐/延迟 2. 故障韧性压测：kill master → 观察写中断/恢复表现

基于场景 8.19 的结论（哨兵/单体稳态写 ≈ 单 master），本场景跳过单体，直接对比哨兵与集群。

10.1 背景与问题

为什么不做"单体 vs 哨兵"对比？

单体:  1 master → 所有写进这一个节点
哨兵:  1 master → 所有写也进这一个节点（replica 只读）

→ 两者的写路径都是「单 master 单线程事件循环」
→ 稳态写吞吐、延迟分布本质相同
→ 哨兵相比单体的区别仅在「故障时自动提升」，写性能无优势
→ 因此聚焦 哨兵 vs 集群

注意：哨兵与单体在写路径上相同，但在故障时写入的最终持久性依赖于副本与持久化策略（AOF/RDB）。哨兵可以自动提升 replica，但如果 replica 尚未落盘且主节点丢失，仍存在数据丢失的窗口（需用 WAIT/AOF/外部对账兜底）。

哨兵 vs 集群的核心差异（写入维度）：

维度 哨兵（主库/从库） 集群（主分片/副分片）
稳态写节点数 1（单主库） 3（多主分片，分片）
单热 key 写 单节点 单节点（路由到唯一主分片）
多 key 写 无跨 slot 限制 CROSSSLOT 限制 / hashtag
故障粒度 主库挂 → 全体写中断 单主分片挂 → 仅其 slot 写中断，其余照常
写中断恢复 Sentinel 提升从库 该主分片的副分片提升
配置复杂度 低 较高

10.4 稳态写压测

10.4.1 方法

  • 模式：Pipeline 100 条 SET 单 flush
  • 并发：16 线程 × 100 batch
  • 预热 3s + 采样 5s
  • 同一套参数在两套架构各跑一遍

10.4.2 实测数据（哨兵 vs 集群）

测试条件：Docker 6 节点（哨兵=1 主库+1 从库+3 sentinel；集群=3 主分片+3 副分片），appendonly no，batch=100，concurrency=16，预热 3s + 采样 5s。

指标 哨兵 (单 master) 集群 (多 master)
cmdPerSec ~369,300 354,900
p50Ms 4.650 4.360
p95Ms 8.002 12.598
p99Ms 15.970 18.233
avgLatencyMs 5.211 5.410
errors 12 7

实测结论：集群稳态吞吐（354,900）与哨兵（369,300）几乎相同（集群略低 ~4%）。

原因：本压测的 key 是 sc10:steady:c:{worker}:{i}，每个 worker 的所有 key 落在同一固定 slot（同一主分片），因此实际仍是单主分片在写，与哨兵的单主库无本质区别。这印证了关键结论：单热 key / 单 worker 分布写时，集群和哨兵都受单节点（单主分片单线程）限制，吞吐无优势。

p99 略高的原因可能是客户端/网络/路由处理引入的额外尾延迟：Cluster 客户端维护 slot 路由表并需要处理可能的重定向（MOVED/ASK），以及不同主分片的网络路径与负载不均都会影响尾延。因为本测试 key 固定在同一 slot，集群并未利用多主分片并行，所以吞吐接近哨兵。

若要体现集群多主分片优势：需把 key 设计成跨多个 slot 分布（不同 worker 写不同 slot），此时集群可并行摊分写入。这是后续可加测的点。

10.5 故障韧性压测

10.5.1 方法

  • 预热 6s 正常写 → 用 docker socket kill <master 容器> → 观察窗口（≥35s）
  • 指标：totalOps、failedOps、failRate、firstFailoverErrorMs、recoveredAfterMs

10.5.2 根本原因分析与修复（哨兵 failRate → 0）

问题：初版哨兵 failover 压测 failRate=0.105%（非零）。

根因（两层）：

根因 1: 观察窗口太短 (observeSec=15) < failover 完成时间
  Sentinel failover 时序受配置影响（down-after-milliseconds、failover-timeout、
  parallel-syncs）和网络/复制延迟影响。测试环境下 failover ≈18s，但实际环境可能更长
  ——因此把 observeSec 提高到 35s 作为安全余量更稳妥。

根因 2: 客户端无重试机制
  应用层应对短暂的写失败进行指数退避重试以吸收 failover 窗口内的错误，
  从而避免最终失败计数。

警告：failover 完成时间受多因素影响（down-after-milliseconds、sentinel quorum、网络延迟、replica 同步时长 parallel-syncs、复制滞后等），实际可高于/低于 18s。测试中将 observeSec 设为 35s 是对本环境的安全余量，生产应该用监测数据调整该窗口。

修复： 1. failover-observe-sec 15 → 35s：覆盖 failover 完成时间 + 余量，让重试有机会在 failover 后成功。 2. worker 应用层重试：batch 失败时指数退避（initial=100ms, ×2, cap=2s）重试，直到成功或窗口结束。吸收 failover 窗口内的暂时失败。

10.5.3 哨兵修复后实测（failRate = 0）

测试条件：kill redis-sentinel-master，预热 6s + 观察 35s + 应用层重试。

指标 修复前 (observe 15s, 无重试) 修复后 (observe 35s, 有重试)
totalOps 2,860,900 18,309,300
failedOps 3,000 0
failRate 0.105% 0.000% ✅
firstFailoverErrorMs 18,057 无错误
lastErr 18,080 无错误
recoveredAfterMs 0 0

验证结论： - failRate = 0.000%：整个 failover 期间没有任何 batch 最终失败 - totalOps 从 286 万增至 1,831 万：观察窗口延长 + 重试吸收了窗口期失败，吞吐大幅提升 - kill master 后，Sentinel 自动提升 replica 为新 master（get-master-addr-by-name mymaster 返回 172.19.0.4） - 应用层重试 + 哨兵自动跟随新 master = 写入最终全部成功

在本测试条件下（observeSec=35s + 应用层指数退避重试），所有最终返回成功的批次在新 master 上可见 → 从客户端可用性角度看 failRate=0（零丢失）。注意：这表示写已被复制到至少一个 replica 的内存中（由 WAIT 或复制语义保证），但不等同于写已持久化到磁盘；若需要持久化保证，还应配合 AOF/RDB 策略或更强同步策略。

Redis Cluster 的 failover 流程与 Sentinel/standalone 不同（依赖 cluster gossip、slot ownership 与投票），其 failover 时间与行为有差异。本测试在给定环境下两者都能通过应用层重试达到 failRate=0，但不应把二者的内部机制混为一谈：Cluster 的故障影响是按 slot 粒度（只有该主分片的 slot 受影响），而 Sentinel 是单个主库受影响。

10.6 关键结论（实测确认）

验证点 哨兵 集群
稳态写吞吐（单 worker 单 slot） ~36.9 万 cmd/s ~35.5 万 cmd/s（≈哨兵）

核心发现： 1. 稳态写入上，集群对单 worker/单热 key 无吞吐优势（354,900 vs 369,300，≈相同）。因为写路径都是单主分片单线程。 2. 集群的吞吐优势只在"多 key 均匀分布到多主分片"时体现（本压测未覆盖，可加测）。 3. 故障韧性上，哨兵在"应用层重试 + 足够观察窗口"后可做到 failRate=0（写入最终全部成功）。集群用同参数重跑后同样为 0。 4. 集群的粒度优势（仅 1/3 slot 中断）需在"整体吞吐凹陷"维度才能量化，本压测 key 分布未能体现。

选型建议（写入阶段）： - 数据量小、单机容量够、要求最简单高可用 → 哨兵（配置简单，故障自动转移，配合应用层重试实测 failRate 0%） - 数据量大、需水平扩展、多 key 高吞吐 → 集群（前提：key 能均匀分布到多主分片；单热 key 无优势） - 单热 key 极高吞吐 → 两者都受单节点限制，需本地方案（LOCAL_BUFFERED/COMPUTED）或写削峰

10.8 未同步数据丢失量化 (RPO V2)

10.8.1 问题背景

/sc10/failover 验证了 failRate=0（写入最终成功），但这只保证可用性。宕机瞬间，主节点上已确认但未复制到副本的写入可能丢失（一致性/RPO）。

RPO V2 的目标：量化 docker kill master 时「客户端已 ACK 但新 master 上不存在」的写入数。

10.8.2 设计要点

与 V1 (/sc10/rpo) 的关键区别：

维度 V1 V2
连接方式 Sentinel 客户端（故障后自动跟随新 master） 直连原 master IP
kill 后写入 自动跟随新 master 继续写 → ACK 被稀释 连接断开直接失败 → 不再记录 ACK
RPO 纯度 ACK 含新 master 的写入，丢失被稀释 ACK 严格只含 kill 前 WAIT 确认的写入

WAIT 命令保证的是写至少被复制到 N 个 replica 的内存并得到确认（返回值为实际确认数）；它不保证副本已经做了 fsync（已落盘）。因此在计算 RPO 时，WAIT 确认能保证"已 ACK 的写在新 master 可见"，但若要求 fsync 级别持久化，还需额外策略。

10.8.3 核心实现

每批 N 条 SET + 1 条 WAIT 1 1000 → flushCommands() → awaitAll()
                                                   ↓
                                WAIT 返回 replicas >= 1 → 记录 ACK
                                WAIT 返回 < 1 或不返回 → 异常，不记 ACK

// ★ 每批精确记录，避免并发 seq 交叉污染
long[] batchSeqs = new long[BATCH_SIZE];
for (int i = 0; i < BATCH_SIZE; i++) {
    long seq = globalSeq.incrementAndGet();
    batchSeqs[i] = seq;                     // 数组记录本批实际获取的 seq
    futures.add(sharedConn.async().set(key, "1"));
}
futures.add(sharedConn.async().waitForReplication(1, 1000));
sharedConn.flushCommands();
LettuceFutures.awaitAll(Duration.ofSeconds(10), futures);

Long replicas = waitFuture.get();
if (replicas == null || replicas < 1) throw new RuntimeException(...);
for (long s : batchSeqs) ackedKeys.add(s);  // 只加本批的

10.8.4 关键 Bug 修复

Bug 1：并发计数虚高

原代码用 for (s=firstSeq; s<=lastSeq; s++) 范围记录，16 线程共享 globalSeq 时，线程 A 获取到 [100, 102, 105] 但范围是 [100..105]，会把 B 的 101/103/104 也计为已 ACK → ackedKeys 虚高 → 宕机后扫描不到 → 误报为丢失。

修复：用 long[] batchSeqs 数组逐条记录本批实际写入的 seq。

实现要点：对 futures 的 await 应使用超时保护与重试策略（避免单个 waitFuture 永久阻塞）；当 WAIT 抛异常或超时时，需把该批标记为未 ACK，并按重试策略处理。batchSeqs 数组确保序列精确无交叉计入。

Bug 2：SCAN 轮次上限

原代码 while (scanRounds < 10000) 在写入 20 万+ key 时提前退出（COUNT 默认 10，最多扫 10 万 key），剩下 ~10 万 key 被误报为丢失 → RPO 虚高 ~60%。

修复：移除上限，改为 while (true) 靠 result.isFinished() 自然退出。

SCAN 默认 COUNT=10 是 hint，结果可能很慢。推荐在大数据量时使用 COUNT=2000~10000（根据网络延迟与服务器负载调优），并谨慎控制单次返回数量以防 OOM 或超时。

10.8.5 实测结果

指标 BATCH=10（修复后） BATCH=100（修复后）
ACK 确认写入 225,340 627,700
新 master 存量 225,340 627,800
丢失 key 0 0
RPO 0% 0%
吞吐（同窗口） 225k 627k (2.8x)

10.8.6 结论

  1. WAIT 1 + 严格返回值校验 在 Sentinel 模式下可做到 RPO=0%
  2. BATCH=100 吞吐是 BATCH=10 的 2.8 倍（WAIT 开销被摊销到更多 key 上）
  3. 宕机瞬间飞行中的批次（WAIT 尚未返回）不会被 ACK，不会计入丢失
  4. 写入路径：flushCommands → WAIT 确认 → ackedKeys.add() 保证了「已 ACK 必在副本上」

10.9 RPO V3: 本地文件持久化 vs 内存 TreeSet 对比

10.9.1 对比目的

V2 的 ackedKeys 存储在 JVM 堆内存（TreeSet），测试结束后丢弃。V3 改为写入本地文件，对比两种方案在 QPS、文件 I/O 开销上的差异。

10.9.2 方案对比

维度 V2 (内存 TreeSet) V3 (本地文件)
写入方式 TreeSet.add(seq) BufferedWriter.write(seq + "\n")
写入开销 O(log n) 排序 + 插入 O(1) 追加 + OS 缓冲
内存占用 ~28MB (60 万条) 极低（只含 writer buffer）
宕机后恢复 需重跑测试 从文件读取历史 ACK
I/O 无 磁盘写（OS 页缓存缓冲）
差集计算 TreeSet.removeAll O(n) 从文件读回 TreeSet 再差集

改进文件版实现：避免单个同步 BufferedWriter 竞争，可采用每线程本地 buffer + 后台合并写或无锁队列 + 单写线程批量刷盘，这能显著降低对吞吐的影响，同时保留进程重启恢复优势。

10.9.3 实测对比

测试条件：BATCH=100, concurrency=16, 预热 6s + 观察 35s, Sentinel 模式

指标 V2 (TreeSet 内存) V3 (BufferedWriter 文件)
ACK 确认写入 885,000 716,100
新 master 存量 885,100 716,200
丢失 key 0 0
RPO 0.000% 0.000%
吞吐 (keys/sec) ~21,600 ~17,500 (-19%)
存储模式 JVM 堆内存 (TreeSet) 本地文件 (BufferedWriter)
文件写入总耗时 N/A 1,433 ms（累计）
每批写入平均耗时 N/A 20 µs
文件大小 N/A 4.9 MB（62 万条）
文件回读耗时 N/A 297 ms
内存占用 ~28 MB (60 万 Long) ~0 (仅 writer buffer)
进程重启恢复 ❌ 丢数据，需重跑 ✅ 从文件读回历史 ACK

10.9.4 结论

  1. 两种方案 RPO 均为 0%：文件 I/O 不影响 WAIT 同步语义，宕机后哨兵选举 replica 为 master，数据已在副本上
  2. 文件版吞吐下降 19%：主要开销来自 synchronized 锁竞争（16 线程共享一个 BufferedWriter）
  3. 文件版的内存优势显著：62 万条 acked seq 只需 4.9MB 磁盘，而 TreeSet 需 ~28MB 堆内存
  4. 本压测场景推荐 V2（内存版）：压测进程不崩溃，内存可承受，差距计算更快
  5. 生产场景推荐 V3（文件版）：进程重启可恢复、内存无上限、支持长时间运行

10.10 数据恢复策略：各层级残余风险与最终兜底

10.10.1 问题：RPO=0 能证明零丢失吗？

10.8/10.9 实测 RPO=0%，但这只证明已 WAIT 确认的 key 在新 master 上全部存活。kill 瞬间还有两类数据未覆盖：

状态 说明 RPO 统计 真实状况
WAIT 已返回 客户端确认成功 已 ACK ✅ 在 replica 上，安全
WAIT 未返回 SET 已发到 master，WAIT 还在飞 未记录 ❓ 可能到 replica 了，也可能丢了

RPO=0 只能证明第一类零丢失。第二类数据量由 master_repl_offset - slave0:offset 决定，实测 ~5,374 字节 ≈ 119 个 key，但无法恢复其 value。

10.10.2 各层级保护方案的残余风险

保护层级                                残余窗口              能恢复 value？
────────────────────────────────────────────────────────────────────
WAIT 1 (同步复制)        ←──────── ~10ms RTT ─────────→ ✅ (WAIT 返回即安全)
AOF everysec (Redis)     ←──────── ~1s ───────────────→ ✅ (但不跨 failover)
AOF always (Redis)       ←──────── 0 (单机) ──────────→ ✅ (单机重启可恢复)
AOF always 双写 + WAIT   ←──────── 0 (跨 failover) ──→ ✅ (但 QPS 暴降)
本地文件快照 + offset    ←──────── 快照间隔 60s ──────→ ✅ (窗口内可恢复)
数据库定时对账 ── ★      ←──────── 对账间隔 30s ──────→ ✅ (最终一致性, 数学上不丢)

为什么 Redis 层无法做到真正的 100%？

  • AOF always 保证单机 fsync 后不丢，但 Sentinel failover 后新 master 是 replica，原 master 的 AOF 无人回放
  • AOF always 双写 + WAIT 理论上 100%，但每条写入触发两次 fsync，QPS 暴降 5-10 倍
  • 本地快照 缩小残余窗口到 60 秒，但更短间隔意味着更频繁的 fsync

核心矛盾：Redis 是数据副本，不是数据源头。故障是不可预测的，除非每条写入都同步等两块磁盘确认（2PC），否则总有窗口。

10.10.3 最终兜底方案：数据库水位线对账

原理：不在 Redis 层死磕 100%，而是用数据库作为 source of truth，定时对比补齐。

// 对账线程（每 30 秒执行）
void reconcile() {
    // ① 读水位线
    Instant lastReconciled = readWatermark("redis:cache");
    if (lastReconciled == null) lastReconciled = now().minusHours(1);

    // ② 查自上次对账以来数据库变更
    List<DataRow> changed = db.query(
        "SELECT * FROM t WHERE updated_at >= ?", lastReconciled);

    // ③ 缺了就补写 Redis
    for (DataRow row : changed) {
        if (!redis.exists("cache:" + row.id)) {
            redis.set("cache:" + row.id, toJson(row));
        }
    }

    // ④ 推进水位线
    writeWatermark("redis:cache", Instant.now());
}

关键设计： - 水位线存在 Redis 或 DB 中（reconcile:cursor），记录上次对账到的 DB 时间戳 - 对账时只查 updated_at >= lastReconciled 的增量数据，开销极低 - 水位线在对账结束后推进：中途崩溃只会重复对账（幂等安全） - 对账间隔 30 秒 → 最大丢失窗口 = 30 秒 + 对账耗时 ≈ 31 秒 - 对账时须保证 updated_at 的时钟一致性（最好用 DB 的事务时间或 monotonic cursor）；对账写 Redis 操作应为幂等（set NX/SET with version 或 overwrite），并在推进水位线时使用事务，防止推进后未完成的补写被跳过

10.10.4 为什么不建议本地快照方案

维度 本地文件快照 数据库水位线对账
写入时开销 每批写 value 缓存 → 热路径有开销 零（生产路径完全不碰对账逻辑）
磁盘 I/O 每 60s fsync 无额外 I/O
故障恢复 读快照 → offset 比较 → 只能恢复窗口内的 读 DB → 重写 Redis → 无窗口限制
依赖 本地磁盘（容器 crash 可能丢） 数据库（独立于 Redis / 独立于容器）
实现复杂度 需要 RingBuffer 改造 + 文件格式 + fsync 一个定时任务 + 一个时间戳字段

10.10.5 三层防护体系（推荐生产方案）

┌────────────────────────────────────────────────────┐
│           Redis 数据不丢的三层保障                  │
│                                                    │
│ ① WAIT 1 (同步复制)                                │
│    → 毫秒级, 99.9% 覆盖                            │
│    → 代价: 每个 batch 多一次 RTT (~8-10ms)          │
│                                                    │
│ ② AOF everysec (Redis 持久化)                      │
│    → 秒级, 单机 crash 重启可恢复                    │
│    → 代价: CPU/IO 开销 <5%                          │

10.11 脑裂防护：min-replicas-to-write 验证

10.11.1 脑裂 vs Crash——两种故障模型

前面 RPO 测试覆盖的是"主库进程崩溃"（docker kill），但生产环境中还存在更危险的场景——网络隔离导致的脑裂：

主库 Crash (已测)                        脑裂 (新测)
─────────────────────────────────────────────────────────────
docker kill master                   master 网络隔离（进程存活）
master 进程终止 → 不接受新写入         master 继续接受客户端写入！
Sentinel 选举 replica → 唯一 master    Sentinel 也选举 replica → 双主！
同一时刻只有一个节点写入              同一时刻两个节点都在写入
数据丢失：飞行中的 ~0-119 个 key       数据丢失：隔离期间 100% 写入被覆盖

脑裂的根本原因：旧主不依赖任何 replica 即可接受写入（min-replicas-to-write = 0），即使它的 replica 全部不可达。

10.11.2 脑裂复现（Docker 双网络隔离法）

由于 Redis 容器不带 iptables，通过 Docker 双网络 实现隔离：

正常状态（单网络 default）:
  client ─→ master ─→ replica
  sentinel ─→ master

脑裂状态（default + split-net）:
  default 网络:    client ─→ sentinel ─→ replica (新 master)
  split-net 网络:  client ─→ master (旧主, 仅 client 可达)
                    master  ─X─ sentinel  (default 网络已断开)
                    master  ─X─ replica   (default 网络已断开)

测试步骤（实测通过）：

# ① 创建私密网络，连接 master + client
docker network create split-net
docker network connect split-net redis-sentinel-master
docker network connect split-net lettuce-bench

# ② 将 master 从 sentinel 所在的 default 网络摘除
docker network disconnect redis-sentinel_redis-net redis-sentinel-master

# ③ 此时 master 仅通过 split-net 可达 client
#    sentinel 无法 PING master → +sdown → +odown → 选举 replica 为新 master

测试结果：

配置 min-replicas-to-write = 0 (默认):

  旧主 (split-net): SET brain_test "from_old_master"  → OK ✅
  新主 (default):   SET brain_test "from_new_master"  → OK ✅

  旧主 上: brain_test = "from_old_master"     ← 只有旧主的写入
  新主 上: brain_test = "from_new_master"     ← 只有新主的写入
  → 数据分裂确认 ❌

  恢复网络后:
  旧主被 Sentinel 降级为 replica → 全量同步新主
  旧主 DBSIZE: 556,201 → 被完全覆盖，脑裂期间的全部写入永久丢失 ❌

10.11.3 根治方案：min-replicas-to-write

# 在 master 上设置
CONFIG SET min-replicas-to-write 1    # 至少要有 1 个 replica 才接受写入
CONFIG SET min-replicas-max-lag 5     # replica 的复制延迟超过 5s 视为不可用

工作原理：Master 在每次接受写入前，检查是否有 ≥ min-replicas-to-write 个 replica 的复制延迟 ≤ min-replicas-max-lag。如果没有，直接返回错误。

// Redis 内部伪逻辑
if (activeReplicaCount < minReplicasToWrite) {
    return -ERR NOREPLICAS Not enough good replicas to write.
}

验证结果（实测通过）：

配置 min-replicas-to-write = 1:

  旧主 (split-net): SET test "should_fail"  
    → NOREPLICAS Not enough good replicas to write. ❌ 拒绝写入！

  新主 (default): SET test "from_new"  
    → OK ✅

  旧主 EXISTS test: 0     ← 无脏数据！脑裂完全预防
  新主 GET test: "from_new" ← 唯一合法写入

生产建议把 min-replicas-to-write 设置为 1，min-replicas-max-lag 设置为合适的秒数（如 5-10s），并配合监控（NOREPLICAS 错误率）、报警与人工/自动降级预案（CONFIG SET min-replicas-to-write 0）以应对 replica 全挂导致的可用性中断。

10.11.4 配置建议

参数 推荐值 说明
min-replicas-to-write 1 (至少) 1 主 1 从架构必须 ≥ 1，更多 replica 可设更高
min-replicas-max-lag 5-10 复制延迟容忍上限（秒），过度会影响跨园区部署
down-after-milliseconds 1000-5000 缩短主观下线判定时间，加速 failover

持久化：

# docker-compose.yml 中为 Redis 节点添加启动命令
command: >
  redis-server
  --min-replicas-to-write 1
  --min-replicas-max-lag 5

10.11.5 脑裂 vs Crash vs 防护后对比

故障模式 旧主行为 数据丢失量 Redis 原生防护
Crash (进程终止) 无写入 ~0-119 个飞行 key WAIT 1
脑裂 (默认配置) 持续接受写入 → 全被覆盖 隔离窗口内 100% 数据 无
脑裂 (min-replicas=1) 拒绝写入 → 零丢失 0 ✅ min-replicas-to-write

10.11.6 min-replicas-to-write 与 replica 数量的关系

核心结论：防脑裂只需要 = 1，与 replica 总数无关。

min-replicas-to-write 不是"需要多少个 replica 确认"
而是"至少需要多少个健康的 replica 才接受写入"

脑裂的唯一定义：master 被完全隔离 → 所有 replica 不可达 → 健康 replica 数为 0

不同 replica 数量下的行为：

架构 min-replicas replica 全挂 脑裂 (隔离)
1M + 1R 1 拒绝 ❌ 拒绝 ❌
1M + 2R 1 拒绝 ❌ 拒绝 ❌
1M + 5R 1 拒绝 ❌ 拒绝 ❌

= 1 时，三种架构对脑裂的防护完全相同——隔离后都是 0 个 replica → 拒绝写入。

多 replica 的唯一区别在中间态：

架构 min-replicas 1 个 replica 挂 4 个 replica 挂
1M + 2R 1 写入 ✅ —
1M + 5R 1 写入 ✅ 写入 ✅（还剩 1 个）

多 replica 的价值是调高 min-replicas 后仍保持可用性，而不是防脑裂：

1M + 5R, min-replicas-to-write = 2:
  0 个 replica → 拒绝（防脑裂 ✅）
  1 个 replica → 拒绝（防"1 个 replica + master 同时挂"的数据风险）
  2~5 个 replica → 写入 ✅

但这是冗余度的需求，不是脑裂防护的需求。
脑裂防护 = 1 即可。

运维建议：以业务可用性/一致性权衡决定 replica 数与 min-replicas。通常 2~3 个 replica（共 3~4 副本）+ min-replicas=1 能在低概率全挂事件下保证一致性并保有高可用性。

10.11.7 隔离后旧主仍是 ROLE=master，为什么不形成多主？

min-replicas-to-write 不能改变 Redis 节点的 ROLE，它只控制写入能力。

时间线（1M + 2R，min-replicas=1）:

t=0    正常: M(master) + R1 + R2（都健康）     → 写入 ✅
t=1    R1 挂: M + R2（健康）                  → 写入 ✅（满足 ≥1）
t=2    M 网络隔离: M(0 个 replica) + R1(挂了) + R2
        ├─ M: ROLE=master，但 0 个 replica → 拒绝写入 ❌
        └─ Sentinel 检测: +sdown → +odown → 选举 R2 为 master

t=6    两主并存:
        ┌─ M(旧主):  ROLE=master, 写入 ❌  ← "有主之名，无主之实"
        └─ R2(新主): ROLE=master, 写入 ✅

t=7    M 恢复网络 → Sentinel 发 SLAVEOF → M 降级为 slave
       → 全量同步 R2 → M 无脏数据 → 零丢失 ✅

隔离期间 ROLE=master 的节点有两个，但只有一个能写。旧主哑火。

10.11.8 为什么 Sentinel 不会产生 3 个 master？

Redis Sentinel 有两层机制保证同一时刻只执行一次 failover：

机制 作用
quorum 判定 Sentinel 会要求达到 quorum 才认为 master 确认下线并启动 failover，quorum 与 sentinel 数量的设置直接影响在网络分区下是否能触发 failover
epoch 递增 每次 failover 用严格递增的 epoch 号，后发生的 epoch 更高，无法并发
Sentinel leader 选举 3 个 Sentinel 中只有 1 个当选 leader，只有 leader 有权提升 replica
SLAVEOF 广播 leader 选完新 master 后，立即给其余所有 replica 发 SLAVEOF 指向新主 
假设最极端场景——连 Sentinel 也网络分裂:

分区 A: M + sentinel-1         → sentinel-1 只有 1 票, quorum=2 → 不能 failover
分区 B: R1~R5 + sentinel-2,3  → 2 票 ≥ quorum → 选举 R1 为新 master

结果: 1 个哑火的旧主 + 1 个正常的新主 = 仍只有 2 个 master

要出现 3 个 master，只能是人为操作失误（如手动 REPLICAOF NO ONE 绕过 Sentinel，或外部脚本并发操作时），不是 Sentinel 自身的行为。

10.11.9 总结

                    min-replicas = 0         min-replicas = 1
────────────────────────────────────────────────────────────────
脑裂时旧主角色        master                  master（不变）
脑裂时旧主写入        接受 ❌→ 数据分裂        拒绝 ✅→ 哑火
恢复后数据丢失        隔离窗口内 100%         0 ✅
最大 master 数        ？个（理论无上限）        2 个（1 个哑火 + 1 个活的）

公式:
  防脑裂的最小值 = 1（无论有多少个 replica）
  防 N-1 个 replica 同时挂的值 = N（冗余度的需求，不是脑裂防护的需求）

10.11.10 双刃剑：replica 全部宕机时的可用性

min-replicas-to-write 防得了脑裂，但防不了"replica 真的全挂了"。

场景

1M + 2R, min-replicas-to-write = 1

t=0    正常: M + R1(OK) + R2(OK)     → 写入 ✅

t=1    R1 机器故障（硬件损坏）
       R2 OOM 被 kill
       → 健康 replica 数 = 0
       → 写入: NOREPLICAS ❌  ← 全站写入停止！

t=2    Sentinel 还活着，但没 replica 可提升了
       → 无 failover 可执行
       → M 仍是唯一的节点，但拒绝一切写入

此时的状态：

维度 状态
Master 活着，但哑火
Replica 全挂，无备份
Sentinel 活着，但无 replica 可提升
写入 全部拒绝
风险 此时 master 再挂 → 数据全丢（无副本）

这是设计行为还是 Bug？

设计行为。 Redis 的 min-replicas-to-write 把"牺牲可用性换取一致性"做到了极致：

min-replicas-to-write = 0:
  replica 全挂 → 继续写 → 服务可用 ✅
  master 再挂 → 数据全丢 ❌   （无备份）

min-replicas-to-write = 1:
  replica 全挂 → 拒绝写 → 服务不可用 ❌
  master 再挂 → 数据已无法写入，无新增丢失 ✅

两者无法同时满足——这是 CAP 定理中 C（一致性）和 A（可用性）的经典取舍。

缓解方案

方案一：多 replica 降低全挂概率

1M + 5R, min-replicas-to-write = 1:
  需要 5 个 replica 全部挂才能触发 NOREPLICAS
  概率 = (单节点故障率)^5 → 极低

方案二：保留最后一个 replica 做安全网

# Sentinel 优先级：标记一个 replica 为高优先级，确保最少 1 个 replica 存活
redis-cli -p 26379 SENTINEL SET mymaster replica-priority 10   # 兜底 replica 优先不杀

方案三：降级开关

// 紧急情况下，动态关闭写保护
CONFIG SET min-replicas-to-write 0    // 宁可丢数据也要恢复服务

三层故障模式的完整对比

把"replica 全挂"加到对比矩阵中：

故障模式              旧主行为             数据风险          Redis 防护
──────────────────────────────────────────────────────────────────────
Crash（进程终止）     无写入                ~119 飞行 key    WAIT 1

脑裂（默认配置）       继续写入 ❌           100% 覆盖丢失    无

脑裂（min-replicas=1） 拒绝写入 ✅          0 ✅              min-replicas

Replica 全挂           拒绝写入 ⚠️          只是没新写入        min-replicas
（min-replicas=1）     ← 双刃剑            旧数据还在        但服务断了

结论

min-replicas-to-write = 1 的保护效果:

✅ 脑裂       → 旧主哑火，零丢失
⚠️ replica 全挂 → 全站拒绝写入（双刃剑，但无数据丢失）
❌ master 再挂 → 旧数据全丢（但不是 min-replicas 的问题——根本无副本了）

最优实践:
  1. 部署 3+ replica，min-replicas-to-write = 1
     → 需要 3 个 replica 同时挂才触发 NOREPLICAS（概率极低）
     → 脑裂被防住 ✅

  2. 紧急降级预案: CONFIG SET min-replicas-to-write 0
     → replica 真的全挂时，人工恢复写入能力

10.11.11 Sentinel vs Cluster：脑裂差异

3主分片3副分片 Cluster 架构下也会脑裂，且比 Sentinel 更复杂——每个主分片都可以独立分裂。

机制差异

Sentinel 脑裂（1M + NR）                     Cluster 脑裂（3M + 3R）
──────────────────────────────────────────────────────────────────────────
唯一的主库被隔离                              任意主分片被隔离
→ 最多 2 个 master                            → 该 slot 出现新主分片
                                               → 最多 6 个 master（3 旧 + 3 新）
影响全部数据                                  影响按 slot 粒度（仅隔离主分片负责的 slot）
无 epoch 保护                                有 epoch，但仅在恢复后生效——隔离期间旧主照写不误

Cluster 脑裂示意

关键约束：复制关系严格一一对应。 副分片 R1 通过 CLUSTER REPLICATE <M1-node-id> 只复制主分片 M1，failover 投票时也只能由 R1 接管 M1 的 slot。R2 不能抢 M1 的 slot，反之亦然。

正常:  M1(slot 0-5460)    M2(slot 5461-10922)   M3(slot 10923-16383)
         ↕                   ↕                      ↕
       R1(副分片)          R2(副分片)            R3(副分片)
       ↑ 只认 M1           ↑ 只认 M2              ↑ 只认 M3

M1 网络隔离后:
  旧 M1(隔离):    客户端-A 仍连着我 → slot 0-5460 照写 ✅
  集群其余节点:   发现 M1 失联 → gossip 投票 → 只有 R1 有资格接管 M1 的 slot
                  R1 升级为新主分片 M1'

  此时 4 个 master: M1(旧,哑火或正在写), M1'(新), M2, M3

M1 + M2 同时隔离:
  R1 → M1'，R2 → M2'（各管各的 slot，互不干涉）
  5 个 master: M1(旧), M1'(新), M2(旧), M2'(新), M3

3 个主分片全部隔离:
  R1 → M1'，R2 → M2'，R3 → M3'
  6 个 master (理论上限): 3 个旧主 + 3 个新主
  （因为只有 3 个副分片，不可能出现第 4 个新主）

Cluster 的 epoch 机制为什么不够？

Redis Cluster 的 failover 依赖严格递增的 configEpoch：新主获得更高 epoch，恢复后旧主发现自己 epoch 低 → 自动降级。但问题在于：

阶段 epoch 行为 写入状态
隔离中 旧主分片 epoch 未变，仍认为自己是 master 接受写入 ❌
恢复后 旧主分片发现更高 epoch → 降级为副分片 → 全量同步新主分片 隔离期写入全丢 ❌

epoch 只管事后清理，不管事前阻止。 就脑裂来说，Cluster 和 Sentinel 面临完全相同的问题：主分片不检查副分片健康状态就接受写入。

解决方案：完全相同

min-replicas-to-write 同样适用于 Cluster 的每个主分片，原理一模一样：

# 在 Cluster 每个主分片上执行（或写入 redis.conf）
CONFIG SET min-replicas-to-write 1

Cluster M1 隔离后（min-replicas-to-write = 1）:
  M1 发现自己 0 个副分片可达 → 返回 NOREPLICAS
  客户端-A 的所有写入被拒绝 ✅
  集群 M1' 正常接收写入 ✅

  恢复后: M1 降级为副分片 → 全量同步 M1' → 零分裂、零丢失 ✅

Sentinel vs Cluster 脑裂对比总表

维度 Sentinel（主库/从库） Cluster（主分片/副分片）
单次脑裂最大 master 数 2（1 旧主库 + 1 新主库） 2 × N（N = 隔离的主分片数，每对主副各出一个旧+新）
升级约束 任意从库可升主库 副分片只能升为自己所属主分片的主（CLUSTER REPLICATE 绑定）
影响范围 全量数据 按 slot 粒度
写入分裂风险 有（默认配置） 有（默认配置）
epoch 保护 无 有（恢复后生效，隔离期无效）
根治方案 min-replicas-to-write >= 1 同左，每个主分片独立配置
修复粒度 全局一个主库 每个主分片独立配置，可按 slot 重要程度差异化 
结论:
  Cluster 的 3 主分片架构让脑裂的影响范围更细粒度（按 slot），
  但也让脑裂最大 master 数翻了 N 倍。

  根因不变: 主分片默认不检查副分片健康就接受写入。
  解法不变: min-replicas-to-write >= 1，每个主分片都要配。

10.11.12 Sentinel 其他关键故障场景补充

脑裂（10.11.1~10.11.11）只是 Sentinel 高可用中的一类故障。以下三类同样关键，文档此前未覆盖。

场景 A：单个从库宕机

现象：

正常:  M(主库) ←→ R(从库)
       Sentinel × 3 监控 M

从库 R 宕机后:
  M 少了一个从库，但仍正常接受读写 ✅
  Sentinel 检测到 R 下线 → 尝试 failover 但发现 M 正常 → 不操作

  风险: 冗余度降为 0（没有可以升主的从库了）
  此时若 M 再宕机 → 无节点可以升主 → 写入彻底中断 ❌

影响分析：

维度 说明
写入可用性 不受影响（M 仍正常接受写入）
读负载 若有读分流到 R，则全部回落到 M
HA 冗余度 降为 0——M 一旦挂，全站不可写
持久化冗余 R 的 RDB/AOF 副本丢失，只剩 M 的持久化

解决方案：

层面 措施
多从库部署 至少 2 个从库，挂 1 个仍有冗余
自动告警 监控 connected_slaves 指标，发现 < 目标值立即告警
快速修复 从 RDB 备份快速重建新从库 SLAVEOF <master-ip> <port>
min-replicas-to-write 如果之前配的 min-replicas-to-write >= 2，从库挂到不足后 M 会拒写。建议用 min-replicas-to-write = max(N-1, 1)
持久化保障 M 的 appendonly yes + aof-rewrite-incremental-fsync yes 
# 监控从库数量
redis-cli -p 6379 INFO replication | grep connected_slaves

# 重建从库
redis-cli -p 6380 SLAVEOF <master-ip> 6379

场景 B：Sentinel 自身宕机（HA 降级）

现象：

Sentinel 集群: S1, S2, S3 (quorum=2)

S1 宕机:
  剩余 S2, S3 → 3 个中 2 个存活 → quorum 可达 ✅
  failover 能力正常 ✅

S1 + S2 同时宕机:
  剩余 S3 (1 个) → 单点 → quorum 不可达 ❌
  此时 M 宕机 → Sentinel 无法投票 → 无 failover ❌
  → 系统退化为"单机 Redis"（挂了就没了）

S1 + S2 + S3 全部宕机:
  M 宕机 → 无任何 Sentinel 存活 → 完全无 failover ❌
  → 只能人工介入

关键：Sentinel 不是一个、不是两个，而必须是奇数个（通常 3 或 5），且部署在不同机器上。quorum 通常设为 ceil(N/2)。

Sentinel 数量选择：

Sentinel 数 容忍宕机数 最低 quorum 适用场景
3 1 2 标准推荐（最常用）
5 2 3 中大型集群
1 0 1 ❌ 无意义（Sentinel 自己挂了 failover 也没了）

解决方案：

层面 措施
反亲和部署 3 个 Sentinel 部署在 3 台不同物理机/可用区
独立节点 Sentinel 不跟 Redis 同机部署（避免 Redis 挂了也打死 Sentinel）
监控告警 监控 sentinel_masters、sentinel_known_sentinels、sentinel_running_scripts
降级预案 Sentinel 全挂时，手动 CONFIG SET min-replicas-to-write 0 保证写入继续
哨兵恢复 丢失的 Sentinel 从幸存节点获取配置重新加入
关键配置 sentinel down-after-milliseconds、sentinel failover-timeout、sentinel parallel-syncs 
# 查看 Sentinel 状态
redis-cli -p 26379 SENTINEL MASTERS
redis-cli -p 26379 SENTINEL SENTINELS mymaster

# 查看当前 quorum 和存活 Sentinel 数
redis-cli -p 26379 SENTINEL MASTER mymaster

场景 C：主库 + 从库同时宕机（全量丢失）

现象：

正常:  M(主库) + R(从库)
       Sentinel × 3 监控

M 和 R 同时宕机（同宿主机、同机架停电、同 OOM 等）:
  → 全量数据丢失 ❌
  → Sentinel 检测到 M 和 R 都失联 → 无节点可升主
  → 所有读写全部失败 ❌
  → 只能从持久化备份恢复（RDB/AOF）

为什么最致命：

对比 脑裂（10.11.11） 主+从全挂（本场景）
数据是否还在 两边都有（但会冲突） 全丢（没有存活节点）
恢复手段 丢一边即可 只能从 RDB/AOF 文件备份恢复
RPO 0（舍弃旧主数据） ≥ RDB 保存间隔（上次持久化以来的写入全丢）
恢复时间 秒级（epoch 自动降级） 分钟到小时级（重建 + 全量加载）

这对应 Cluster 场景 2（主分片+副分片全挂），但 Sentinel 仅 1 主 + 1 从，挂了就是 100% 数据不可用。

解决方案：

层面 措施
反亲和部署 主库和从库部署在不同宿主机/机架/可用区（最重要！）
多从库 至少 2~3 个从库分散部署，同时挂的概率指数级下降
持久化冗余 M 开 AOF + RDB，R 开 RDB（或 AOF），且持久化文件定期异地备份
异地备份 RDB/AOF 文件定期异步复制到对象存储（S3/OSS/COS）或其他机器
快速恢复流程 预置恢复脚本：从最新备份复制 RDB → 启动 Redis → Sentinel 自动发现
监控 监控 M 和 R 是否在同一宿主机、同一电源、同一网络交换机 
# 快速恢复流程
# 1. 找一个新节点，复制最新 RDB 备份
scp backup/dump.rdb user@new-node:/data/

# 2. 启动 Redis（主库模式）
redis-server --port 6379 --dir /data --dbfilename dump.rdb

# 3. Sentinel 自动发现（或手动 SLAVEOF 加入）
# 从库同理，启动后 SLAVEOF <master-ip> 6379

# 数据丢失窗口 = 上次持久化 ~ 故障时刻
# RDB: 默认 save 900 1，最多丢 15 分钟数据
# AOF always: 最多丢最后 1 条
# AOF everysec: 最多丢最后 1 秒

总结—Sentinel 完整故障矩阵:
  - 主库 crash（10.5.3）           → 从库升主，failRate=0%  ✅ 已测
  - 主库脑裂（10.11.1~10.11.10）    → min-replicas-to-write 根治 ✅ 已测/分析
  - 单个从库宕机（本场景 A）        → 冗余降级，继续运行但有风险 ⚠️ 分析补充
  - Sentinel 自身宕机（本场景 B）   → HA 降级，需 quorum 保障  ⚠️ 分析补充
  - 主+从全挂（本场景 C）           → 全量丢失，最致命 🔴 分析补充

10.12 后续测试建议

  1. Key distribution 验证：做一组多 worker 且 key 跨 slot 的稳态写压测，验证集群并行写入扩容效果（期望看到集群吞吐随主分片数近线性增长）。
  2. Failover 延时分布：分别测量哨兵与集群在多次试验下的 failover latency 分布（p50/p95/p99），包含不同 down-after 值与网络延迟下的行为。
  3. WAIT 与持久化结合测试：对比 WAIT 1 + AOF everysec 与 WAIT 1 + AOF always 在故障与主从换主场景下的数据可恢复率与吞吐影响。
  4. 脑裂场景扩展：在不同 min-replicas-to-write 与 replica 数下做隔离测试，记录 NOREPLICAS 错误率、业务中断时间并模拟紧急降级流程（CONFIG SET）。
  5. 客户端行为测试：验证 Lettuce 在 failover 时的重连/路由切换时序、对 pipeline/transaction 的影响、以及是否会发生 MOVED/ASK 导致的重试成本。
  6. 文件版 ack 优化实验：实现 per-thread buffer + background flusher，评估吞吐恢复比与对重启恢复的影响。

10.13 集群四类故障场景对照与解决

本章归纳 Redis Cluster 3主分片3副分片架构下的四类典型故障，对照文档已有覆盖情况，并给出每种场景的根因与解决方案。

# 故障场景 文档覆盖 关键差异
1 某分片主节点宕机：副分片升级，短暂不可用 ✅ 10.5.4 已测 kill 1 个主分片 → failRate=0%
2 分片主+副全部宕机：slot 变孤儿，无节点接管 ❌ 未覆盖 比脑裂更极端——连升主的副分片都没了
3 集群网络分区：分片之间不通，全部读写阻塞 ⚠️ 部分 10.11.11 只测了单节点隔离（脑裂），未测集群整体分区
4 半数主节点故障：集群下线保护，停止接收写入 ❌ 未覆盖 Cluster 特有保护，文档只测过 kill 1 个主分片

场景 1：某分片主节点宕机

现象：

集群正常:
  M1(slot 0-5460)     M2(slot 5461-10922)    M3(slot 10923-16383)
    ↕                    ↕                       ↕
  R1(副)               R2(副)                  R3(副)

M1 宕机后:
  Cluster gossip 检测 M1 下线 → R1 发起 failover 投票
  R1 升为新 M1' → 接管 slot 0-5460

  宕机窗口 (~数秒): slot 0-5460 不可写
  恢复后: 3 主分片均正常，R1 变为新主 M1'

已测结论（10.5.4）：应用层指数退避重试 + observeSec=35s → failRate=0.000%。

生产方案：

层面 措施
客户端重试 指数退避（initial=100ms, cap=2s），吸收 failover 窗口内错误
集群配置 cluster-node-timeout 5000，缩短下线检测时间
副分片配置 确保每个主分片至少 1 个副分片，cluster-replica-no-failover no
监控告警 监控 cluster_state、cluster_slots_fail，告警 failover 事件

场景 2：分片主+副全部宕机（slot 孤儿）

现象：

M1 宕机 → R1 尝试 failover...
但 R1 也同时宕机（同宿主机、同机架、同时 OOM 等）
→ slot 0-5460 无任何节点接管

客户端操作 slot 0-5460 内的 key:
  → CLUSTERDOWN The cluster is down ❌
  → 即使 M2、M3 正常，集群也整体拒绝服务

根因：cluster-require-full-coverage yes（默认）要求 16384 个 slot 全部有健康节点。任一分片主副全挂 → slot 孤儿 → 集群全局拒写。

生产方案：

层面 措施
反亲和部署 同一分片的主副分片部署在不同宿主机/机架/可用区，避免单点故障波及主副
多副分片 每个主分片至少 2 个副分片，单副分片挂了还有第二个升主
快速恢复 从 RDB/AOF 备份恢复数据 → 新节点加入集群 → 手动 CLUSTER REPLICATE
临时降级 CLUSTER SETSLOT <slot> NODE <other-master-id> 把孤儿 slot 迁移到健康主分片（临时，会丢该 slot 数据）
降级配置 极端情况下 CONFIG SET cluster-require-full-coverage no（接受部分 slot 不可用，仅相关 key 报错，其余 slot 正常） 
# 紧急操作：把孤儿 slot 临时迁移到存活主分片（高风险，数据丢失）
redis-cli -p 7000 CLUSTER SETSLOT 0 NODE <M2-node-id>
redis-cli -p 7000 CLUSTER SETSLOT 1 NODE <M2-node-id>
# ... 迁移全部孤儿 slot

# 或接受部分不可用
redis-cli -p 7000 CONFIG SET cluster-require-full-coverage no

场景 3：集群网络分区（分片之间不通）

现象：

正常:  M1 ←→ M2 ←→ M3  (gossip 全网互通)

网络分区:
  分区 A: M1 + R1（与 M2/M3 不通）
  分区 B: M2 + R2, M3 + R3（与 M1 不通）

分区 A 的视角: M2/M3 失联 → slot 5461-16383 无节点 → CLUSTERDOWN
分区 B 的视角: M1 失联 → slot 0-5460 无节点 → CLUSTERDOWN

→ 两个分区都无法完成 16384 slot 覆盖 → 全员 CLUSTERDOWN ❌
  所有客户端的所有 key 都被拒绝

与已测脑裂的关键区别：

单节点隔离（10.11.11） 集群网络分区（本场景）
范围 1 个主分片 集群分裂为两个以上分区
隔离节点行为 仍接受写入（默认） 拒绝写入（cluster-require-full-coverage）
恢复结果 旧主数据被覆盖（无 min-replicas 时） 无数据分裂，但服务全停
危险程度 数据不一致 ❌ 服务不可用 ⚠️

生产方案：

层面 措施
网络冗余 多网卡 bond、冗余交换机、机架顶部交换机冗余
rack-aware 部署 同一分片主副跨机架/跨交换机，避免单链路故障同时断开主副
cluster-node-timeout 适当调大（如 15000ms）减少网络抖动导致的误判分区
降级配置 CONFIG SET cluster-require-full-coverage no（最后手段，接受部分不可用）
监控 监控 cluster 节点间 PING/PONG 延迟，提前发现网络劣化

场景 4：半数主节点故障，集群下线保护

现象：

3 主分片集群，M1、M2 同时故障:
  存活节点: M3 (仅 1 个主分片)
  M3 负责 slot 10923-16383，但 slot 0-10922 无节点接管

  cluster-require-full-coverage yes:
  → 16384 slot 不全覆盖 → CLUSTERDOWN ❌
  → M3 也拒绝写入，即使它的 slot 完全正常

3 主分片集群，M1 故障但 R1 成功升主:
  → 仍有 3 个主分片 → 集群正常 ✅

关键：触发条件不是"主分片宕机"本身，而是 slot 无法被覆盖 + cluster-require-full-coverage yes。副分片能快速升主就不会触发。

生产方案：

层面 措施
多副分片 每个主分片至少 2 个副分片 → 主+1副同时挂的概率大幅降低
快速 failover cluster-node-timeout 5000 + cluster-replica-validity-factor 5 → 副分片快速检测并升主
资源隔离 主分片部署在不同物理机上，副分片也分散，避免单宿主机故障同时打死多个主分片
人工恢复 从备份恢复故障主分片数据 → 新节点 CLUSTER MEET → 副分片模式加入
降级 CONFIG SET cluster-require-full-coverage no（接受剩余 slot 正常读写）

四类故障总结矩阵

故障场景              影响范围        已测？  核心解法
────────────────────────────────────────────────────────────
1. 单主分片宕机        该分片 slot      ✅     应用层重试 → failRate=0%
2. 主+副全挂(slot孤儿)  全局 CLUSTERDOWN  ❌    反亲和 + 多副分片 + 备份恢复
3. 集群网络分区         全局 CLUSTERDOWN  ⚠️    网络冗余 + rack-aware
4. 半数主分片故障       全局 CLUSTERDOWN  ❌    多副分片 + 快速 failover

共性:
  - 场景 2/3/4 都会触发 cluster-require-full-coverage → CLUSTERDOWN
  - 场景 2~4 比场景 1 严重一个量级（全局不可用 vs 局部不可用）
  - 多副分片是场景 2/4 的共同解药
  - 网络架构是场景 3 的根本解药

回归本质：四类故障就是高可用（HA）三要素

场景 1/4 → 节点冗余（replica 够不够，failover 快不快）
场景 2   → 部署冗余（主副有没有放在同一颗炸弹上）
场景 3   → 网络冗余（链路有没有单点）

统一公式:
  高可用 = 冗余 + 检测 + 切换 + 降级

           │         │         │         └─ cluster-require-full-coverage no（最后手段）
           │         │         └─ gossip 投票 + epoch failover
           │         └─ cluster-node-timeout / PING-PONG
           └─ 多副分片 + 反亲和 + 网络冗余

四类场景拆开是表象，合起来是同一个问题：集群能不能在部分组件故障后继续服务。答案取决于四要素各自做到了什么程度。

10.13.5 场景补充：单个副分片宕机

现象：

正常:  M1(slot 0-5460)    M2(slot 5461-10922)   M3(slot 10923-16383)
         ↕                   ↕                      ↕
       R1(副分片)          R2(副分片)            R3(副分片)

R1 宕机后:
  M1 少了一个副分片，但仍正常接受写入 ✅
  M1 的 slot 0-5460 读写正常 ✅

  Cluster 视角:
    gossip 检测到 R1 失联 → 标记为 FAIL
    M1 的 replicas 数从 1 降为 0
    cluster_state = ok（slot 仍被 M1 覆盖）

  → 集群整体正常，但 M1 分片的 HA 冗余度降为 0
  → 若此时 M1 再宕机 → slot 0-5460 变孤儿 → CLUSTERDOWN ❌

与 Sentinel 从库宕机的对称性：

Sentinel 单个从库宕机 Cluster 单个副分片宕机
写入是否受影响 不影响 不影响
影响范围 全局（仅 1 主库的 HA 降级） 局部分片（只 M1 的 HA 降级）
风险 M 再挂 → 全量不可用 M1 再挂 → slot 0-5460 孤儿 → 全局 CLUSTERDOWN

解决方案：

层面 措施
多副分片 每个主分片至少 2 个副分片，挂 1 个仍有冗余
反亲和部署 同一分片的主副部署在不同宿主机，避免单点故障同时打死

10.13.6 场景补充：Cluster 模式 RPO 量化

文档 10.8 节已完整测量了 Sentinel 模式下 WAIT 1 的 RPO（end-to-end 0 丢失）。但 Cluster 模式的 RPO 尚未量化。以下分析该缺口及理论预期。

WAIT 在 Cluster 下的行为：

客户端写 M1:
  SET key value
  WAIT 1 0  → 等待 1 个副分片确认
              → 此时 M1 有副分片 R1 → WAIT 返回 1 ✅
              → 同 Sentinel 的 WAIT 行为，原理完全相同

Cluster 特有影响:
  - WAIT 仅作用于当前连接的主分片，不跨分片
  - hash tag 写的 key 落在同一 slot → WAIT 同分片副本
  - 跨 slot 写 → 多个 WAIT，各自等各自分片的副分片

Cluster vs Sentinel WAIT 对比：

维度 Sentinel（10.8） Cluster（未测）
WAIT 作用域 全局主库 当前主分片
RPO 理论值 0（WAIT 1 + 副分片确认） 0（同原理）
唯一差异 不涉及 slot 路由 需要先分配到正确主分片，WAIT 才有意义
测量复杂度 低 中（需要确认 key 落在哪个 slot/分片）

Cluster 模式 RPO 测试设计（待实测）：

方案 1 - Hashtag 固定分片:
  key = {rpo}:seq   → 所有 key 落同一 slot → 同一主分片
  → 与 Sentinel 完全可比 → 预期 RPO = 0

方案 2 - 跨分片分布:
  key = rpo:{seq}   → 不同 seq 可能落不同 slot
  → 需要验证每个分片的 WAIT 都生效

测试流程:
  1. 3 主分片 + 3 副分片集群
  2. 持续写入，每条写完立即 WAIT 1
  3. kill 一个主分片（比如 M1）
  4. 记录最后一条收到 WAIT=1 响应的 seq
  5. 故障恢复后，check M1' 上的最大 seq
  6. RPO = 最后写入 seq - M1' 最大 seq

理论预期: RPO = 0（与 Sentinel 完全相同）

结论:
  理论上 WAIT 在 Cluster 和 Sentinel 下行为一致（都是同步复制到至少 1 个副本）。
  若实测不通过，可能与以下 Cluster 特有因素有关:
    1. gossip 延迟 vs WAIT 确认: WAIT 返回 ≠ gossip 已同步
    2. failover 过程中 slot 迁移: 旧主 WAIT 返回但 slot ownership 已在切换中
    3. cluster-require-full-coverage: 导致 CLIENTS 认为写入成功但集群整体拒收

  建议作为后续测试的优先项（10.12 节已列）。

关键实现点（踩坑记录）

  1. sentinel 启动时无法解析 master hostname：redis-sentinel 启动读取 monitor 配置时立即解析 hostname，若 docker DNS 时序不可靠会 FATAL。解决：entrypoint 用 getent hosts 解析出 master IP，sed 替换进 sentinel.conf 再启动。
  2. Lettuce sentinel master 名称：withSentinelMasterId() 必须用哨兵监控的 master 名（mymaster），不是容器名。
  3. 多 RedisClient bean 冲突：sentinel profile 下默认 RedisClient 与 sentinel RedisClient 并存 → NoUniqueBeanDefinitionException。解决：sentinel client 加 @Primary。
  4. SCAN 不设 COUNT 性能偏慢：默认 COUNT≈10，30 万 key 需 ~3 万次网络往返耗时 10-20 秒。加 COUNT 2000 可压缩到 <1 秒。
  5. Lettuce DNS 缓存与 IP 切换：Lettuce/客户端连接池的 DNS 解析与 cached address 在容器重启/重配置场景下会导致短时间内读写指向旧 IP，建议在容器中禁用长时间 DNS 缓存或显式让客户端定期刷新 sentinel 信息。
  6. docker network disconnect 隔离测试注意：用 docker network disconnect 做隔离时注意容器的 /etc/hosts 与 Docker DNS 缓存行为，最好在测试脚本中做 sleep/等待并验证 sentinel 状态再断网。
