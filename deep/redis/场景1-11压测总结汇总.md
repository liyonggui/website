# Redis 高并发压测全场景总结（场景 1-11）

> 本文件汇总 `docs/` 下 11 个压测场景的核心结论与简略压测过程，用于快速回顾。完整细节见各场景原始文档。

---

## 场景 1：Lettuce Pipeline 压测问题排查与优化

**压测过程**：Lettuce 异步 Pipeline 写入 Redis（单机），逐步排查 7 个问题；后追加 ZSet 排行榜专项（Rounds 6-9）。

**关键问题与修复**：

| # | 问题 | 结论 |
|:--:|------|------|
| 1 | Redis CPU 100% | 硬件天花板，单机吞吐有限 |
| 2 | Pipeline 并发过载反噬 | conc=16 时吞吐 -37%，需客户端反压（限并发 flush） |
| 3 | SecureRandom 并发争用 | 改 `ThreadLocalRandom`，消除全局同步锁 |
| 4 | Key 空间太小退化为覆盖写 | keySpace 不足 → 覆盖写掩盖真实写入成本，需足够大 key 空间 |
| 5 | AOF 刷盘影响 | 仅在开 AOF 时触发 |
| 6 | Pipeline 超时配置无效 | 配 1s 超时，真正生效 |
| 7 | 优雅关闭 | 两阶段关闭（优雅等待 + 超时强断），防令牌泄露 |

**核心数据**（SETEX 基线，batch=500, c=8, keySpace=5000 万）：优化前 435k（假数据）→ 优化后 **~287k cmd/s**（真实新写入成本），覆盖写占比 <1%。

**混合命令退化（c=8）**：

| 场景 | cmds/s | 退化% |
|------|--------|-------|
| 1 种（SET 基线）| 332,825 | — |
| 2 种（SETEX+HSET）| 257,856 | -22.5% |
| 3 种（+ZADD）| 240,706 | -27.7% |
| 5 种（大杂烩）| 268,057 | -19.5% |
| 3种+ZADD×10 | 81,678 | —（等效 +38% 但 P99×3）|

**ZSet 专项（c=64）**：

| 场景 | cmds/s | 退化% |
|------|--------|-------|
| 基线 SET | 193,795 | — |
| Raw ZADD 单key（500K→skiplist）| 168,851 | 12.9% |
| Raw ZADD 16分片 | 177,727 | 8.3% |
| Pipeline Top-100 | 104,405 | 46.1% |
| Pipeline Top-1000 | 138,225 | 28.7% |

**核心结论**：
1. Pipeline 并发并非越大越好，需反压。
2. key 空间大小决定"是否测到真实写入成本"。
3. 混合命令退化由"昂贵命令占比"（ZADD 跳表 O(logN)）决定，非种类数。
4. ZSet 分片在高吞吐写入下无效（0.16s 突破 listpack 阈值，路由开销成纯负担）。
5. 排行榜 Top-N 裁剪：Pipeline（ZADD+ZREMRANGEBYRANK）完胜 Lua EVAL（+12%~132%）。
6. 生产最优：Raw ZADD 实时写 + 异步定时 ZREMRANGEBYRANK 裁剪。

## 场景 2：大结构 Hash 批量写入

**压测过程**：多 worker 并发 HSET 大量大 Hash（每 key 10 field × ~256B，500K key，TTL=600s，maxmemory=256MB allkeys-lru）。对比无持久化 / RDB / AOF（percentage=100/500）的 COW、内存峰值与 OOM 风险。

**核心数据（COW 对比）**：

| 持久化模式 | 子进程存活 | COW 大小 |
|:--|:--|:--|
| RDB | ~2s | **~245MB** |
| AOF percentage=100 | ~2s | **~66MB**（最小）|
| AOF percentage=500 | ~3s | ~264MB |

**核心结论**：
1. **COW 大小 = 父进程在子进程存活期间写入触发的 copy-on-write 字节数**，与写入速率和 fork 持续时间强相关。
2. AOF percentage=100 高写入下单次 COW 最小，峰值内存压力最低（但 rewrite 频繁，累计 COW 大）。
3. **OOM 估算公式**：所需物理内存 ≈ `used_memory_rss` + 预计 `last_cow_size` + 10~20% 裕度；保守 `used_memory_rss × 1.5~2`。
4. **根除 COW 风险**：主节点关闭持久化 + 副本做持久化/备份 + 副本错峰 BGSAVE。
5. 生产必须关闭 THP（`transparent_hugepage=never`）。

**补充场景（冷热混合删除，已实测）**：

| 指标 | DEL+SETEX | UNLINK+SETEX | SETEX+RENAME |
|:--|:--:|:--:|:--:|
| cmds/s | 446,182 | **512,796** ✅ | 358,129 |
| P99 | 87.21ms | **47.62ms** ✅ | 99.29ms |
| slowlogΔ | 15 | **5** ✅ | 23 |

**结论**：UNLINK 全面领先 DEL（吞吐 +15%、P99 -45%、slowlog -67%）；RENAME 反而最差（内部隐式 DEL + 并发 tmp key 冲突）。生产一行改动 `del→unlink` 即可。

## 场景 3：短期 TTL 海量过期 key 持续灌入

**压测过程**：大量秒级 TTL key 持续写入，观察 active-expire 采样式扫描对主线程的阻塞与 P99 抖动。

**问题本质**：过期压力来自"到期同步性"（同一时间大量 key 到期）+ "key 空间大小"。

**五轮优化组合对比（场景3 优化验证 1-4，30s 稳态）**：

| 指标 | ① 基线（固定TTL,默认Redis）| ② Redis 层优化（hz=50,effort=2,lazyfree）| ③ 应用层打散（TTL+rand）| ④ 全量组合（打散+hz=50+effort=2+lazyfree）| ⑤ 打散+lazyfree |
|:--|:--|:--|:--|:--|:--|
| **P99** | **51~159ms** | **5.6~17ms** | 6.7~34ms | 6.0~16ms | **5.0~15ms** |
| **max** | **82~262ms** | **8~41ms** | 12~123ms | 13~85ms | **7~41ms** |
| 吞吐 | 37k~236k/s | 384k~471k/s | 187k~432k/s | 329k~466k/s | **423k~481k/s** |
| 综合评分 | ❌ | ⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐⭐（最佳） |

**核心结论**：
1. **P99 尖刺根因**：active-expire 在主线程采样式扫描 + 同步释放内存。
2. `hz` 控制扫描频率（密度），`effort` 控制单次扫描深度（阻塞），`lazyfree-lazy-expire` 只异步化内存回收，**不消除扫描开销**。
3. **决策树**：能改配置 → 开 lazyfree + 短 TTL 用 hz=50/effort=2（②）；能改应用 → TTL 随机打散（③: P99 159ms→34ms；再配合 lazyfree 即 ⑤: P99→5.0~15ms，五轮最佳）；都不能 → 横向拆分或接受 P99>50ms。
4. 实测最优组合：**⑤ = TTL 打散 + `lazyfree-lazy-expire=yes`**（P99 5.0~15ms、稳态吞吐 423k~481k）；不能改代码时最优为 ②（`hz=50 + effort=2 + lazyfree`，P99 5.6~17ms）。**避免 ④**（打散+hz=50+effort=2 全叠，P99 反升至 6.0~16ms）——④ 与 ⑤ 的差距在 hz/effort 而非打散本身。
5. 长 TTL 周期批量写入 → 质数/互质 TTL 打破 LCM 汇集。

## 场景 4：分布式信号量 — 多 Writer 竞争全局 Pipeline 槽位

**压测过程**：单服务最优 8 个 pipeline 槽位，生产 12 个 Java 服务同时写，用 Redis 全局信号量让 Writer 竞争有限槽位，遍历 slots 找全局最优。

**核心结论**：
1. **8 个全局槽位是性价比最优值**（cmd/s≈320k, P99≈4.6ms, retries=0）。
2. 实现要点：① 只在成功占有槽位时释放（不能无条件 DECR）；② 用 token+TTL 防泄漏；③ 用 Lua 保证原子性；④ 避免 tight spin-wait，用随机退避。
3. **retries=0 不等于无竞争**，吞吐才是真正的健康指标。
4. 风险评估三轴：吞吐 / 延迟 P99 / 公平性（retries/starvation）。

## 场景 5：读写争抢 — HGETALL vs HSCAN 全维度验证

**压测过程**：大 Hash（数千 field）上对比 HGETALL（O(N) 阻塞主线程）与 HSCAN（增量遍历）的读写争抢。

**核心结论**：
1. **HGETALL 在大 Hash 上 O(N) 阻塞主线程**，写请求排队、P99 激增/超时。
2. **HSCAN 增量不阻塞**，但返回不保证快照一致，`count` 只是 hint。
3. **数据建模优先**：单 key field 数 ≤ 1000（保守 500），从源头避免大 Hash。
4. 默认 reader-mode = HSCAN + count 可配置（经验值 200）；已知字段名用 HMGET 按需取。
5. `RedisHashUtil` 封装策略：HLEN < 500 直接 HGETALL；500~5000 warn 走 HSCAN；≥5000 拒绝。
6. 禁止在 Lua 中做大循环或 HGETALL/SMEMBERS 大 key 操作；Redis 7+ 可用 EVAL_RO 发只读副本。

## 场景 6：高并发多连接 Pipeline — maxclients 边界探测

**压测过程**：maxclients=500，Sweep 并发 10→360，对比 DIRECT 裸 / POOL / DIRECT+Semaphore 三种模式。

**实测数据（SETEX Pipeline, batch=20）**：

| 模式 | 吞吐 | 连接数 | 吞吐/连接 | Redis 压力 |
|:--|:--|:--|:--|:--|
| DIRECT 裸 | ~140k | =并发数（无上限）| 388 cmd/s/conn | ❌ 高 |
| POOL | ~58k | ≤poolMax | 4,143 | ✅ 低 |
| **DIRECT+Semaphore** | **~155k** | ≤semaphoreMax（实测 5-10）| **15,500** | ✅ 极低 |

**极限验证**：500 并发、Semaphore 仅 5 连接 → connectFail=231（客户端拦截），`redisRejectedConnections=0`（Redis 零拒绝），1,640 万命令零错误。

**核心结论**：
1. **DIRECT 模式 = 连接无上限，高并发必撞 maxclients**，连接被拒无优雅降级。
2. **POOL = 连接池硬上限，天然熔断器**，但吞吐被池机制限制。
3. **DIRECT+Semaphore = 裸 DIRECT 的吞吐 + POOL 的安全性**，只用 10 条连接打满 ~155k cmd/s，是最优方案。
4. poolMaxTotal 配置公式：`floor((maxclients - reserved) / instance_count / safetyFactor)`。
5. 监控 `rejected_connections` 的 δ（增长速率），delta>0 说明正在拒绝 → 紧急告警。

## 场景 7：Cluster 跨槽 Pipeline 错误轰炸

**压测过程**：3 主 3 从集群，对比集群客户端（自动按 slot 分组）与绕过客户端直连单节点两种方式。

**实测数据**：

| 方式 | CROSSSLOT | cmd/s |
|:--|:--|:--|
| 集群客户端 Pipeline SETEX（跨槽）| **0** | ~170k |
| 集群客户端 MSET（跨槽）| 0 | ~200k |
| 集群客户端 Pipeline HGET | 0 | ~390k |
| 绕过客户端直连单节点 | **~150 万/5s** | 0.4（几乎全失败）|

**核心结论**：
1. **CROSSSLOT 仅发生在"单通道"直连场景**——命令被发送到不拥有所有 key 的单个节点时触发。
2. **集群客户端（Lettuce Cluster）自动按 slot 分组发送，跨槽命令 CROSSSLOT=0**。
3. 绕过客户端直连单节点 → CROSSSLOT 100%，吞吐崩塌。
4. batchSize 越大 CROSSSLOT 线性增长（跨槽失败条数 ∝ batchSize）。
5. **CRC16 由客户端自动计算**，应用层无需关心。
6. 哈希标签（Hash Tag）是性能优化（强制同 slot）而非错误修复。

## 场景 8-1：热点 Key Pipeline INCR 自增

**压测过程**：16 并发 × 100 batch 全部 INCR 同一个 key，对比五种模式（SINGLE_KEY / DISTRIBUTED / SHARDED / LOCAL_BUFFERED / COMPUTED）。

**实测数据（16 并发, batch=100, 15s 采样）**：

| 模式 | 特点 | 本地吞吐 | Redis 写 |
|:--|:--|:--|:--|
| SINGLE_KEY | 直接 INCR | **359,610** cmd/s | 每次写，单节点瓶颈 |
| DISTRIBUTED | 随机 hashtag 后缀 | **293,819** | 分散多 slot，不可 MGET 聚合 |
| SHARDED | 固定 N 分片 | **254,313** | 分散 + 可 MGET 聚合 |
| LOCAL_BUFFERED | 本地 Atomic + 定期 INCRBY | ~35,000,000/s | 1 次/s |
| COMPUTED | 本地业务计算 + 批量写回 | ~95,000,000/s | 1 次/s |

> 口径：前三种模式为 Sweep Compare（5s 预热 + 15s 采样）正式数据；手动单次运行数值略低（~307K/~184K/~199K），以 sweep 为准（详见场景8-1 8.8 节口径说明）。

**核心结论**：
1. **热点 Key 是 Cluster 单点瓶颈**：`slot = CRC16(key) % 16384` 固定映射，高频 INCR 全部路由到同一 master。
2. 单点写入还会放大复制压力：replication backlog 被覆盖 → psync 失效 → 全量同步 → BGSAVE/COW 爆发。
3. **"计算在应用层，汇总写回 Redis"是优先策略**（LOCAL_BUFFERED/COMPUTED），本地吞吐达千万级/s，Redis 每秒仅 1 次写。
4. 需要强一致/实时去重 → 用 Lua/WAIT/单点原子操作（牺牲吞吐）。
5. 全量同步防护三层：基础设施（backlog、output-buffer-limit、diskless-sync、lazyfree）+ 应用层（自动降速）+ 运维层（错峰、告警）。

**场景 8.14（主从同步压测）**：高写入 + 从库全量重同步时，复制流占主节点输出带宽 72.6%，backlog 覆盖触发 psync 失效。根除方案三层防御 + 应用层自动降速兜底。

## 场景 8-2：Pipeline RTT 敏感度与 WAIT

**压测过程**：探索 Pipeline 在不同 batchSize 下对 RTT 的敏感度，以及 WAIT/同步对吞吐的影响；追加场景 8.21 EVAL 嵌套执行专项。

**场景 8.21（EVAL 嵌套执行，3×3 实测）**：

**三种模式定义**：
- **NESTED**：Pipeline 中 batchSize 个独立 EVAL（每个 1 次 INCRBY），Redis 排队执行小脚本，中间可穿插其他连接。
- **MERGED**：Pipeline 中 1 个 EVAL 脚本内 for 循环 batchSize 次，独占主线程直到全部完成。
- **RAW**：Pipeline 中 batchSize 个独立 INCRBY，零脚本开销（基线）。

**9 轮结果**：

| batchSize | 模式 | ops/s | sideP99 | slowlogΔ |
|:--:|:--|:--:|:--:|:--:|
| 100 | **NESTED** | 191,044 | 18.99ms | 6 |
| 100 | MERGED | 4,660 | 12.75ms | 20 |
| 100 | RAW | 455,483 | 14.95ms | 5 |
| 500 | NESTED | 207,264 | 45.80ms | 0 |
| 500 | MERGED | 1,281 | 28.28ms | 0 |
| 500 | RAW | 575,859 | 23.21ms | 0 |
| 1000 | NESTED | 196,931 | 49.73ms | 0 |
| 1000 | MERGED | 600 | **55.37ms** ※ | 0 |
| 1000 | RAW | 588,261 | 32.50ms | 0 |

※ B1000 时 MERGED 的 sideP99 反超 NESTED：单个大 EVAL 独占主线程 1000 次循环的伤害 > 1000 个小 EVAL 排队。

**核心结论**：
1. **RAW 原生命令最优**：吞吐 455-588K（NESTED 的 2.4-3.0 倍），sideP99 最低。
2. **NESTED EVAL 可行**：吞吐稳定 ~200K，sideP99 控制在 19-50ms，batchSize ≤ 100 时最稳。
3. **MERGED EVAL 危险**：sideP99 随 batchSize 超线性增长（13→28→55ms），batchSize > 100 后反超 NESTED，造成全局阻塞。
4. 分界点约在 batch=100，超过后 MERGED 的阻塞伤害 > NESTED 的脚本解析开销。
5. 生产优先级：能不用 EVAL 就不用 → 需要原子性时用 NESTED 且 batchSize≤100 → 避免 MERGED 大循环。

## 场景 9：集合运算（并/交/差）高并发压测

**压测过程**：先功能正确性验证（26/26 PASS），再做高并发梯度压测（Set 大小 500/1K/5K/10K × 并发）。

**实测数据（环境相关）**：

| 集合大小 N | 吞吐 |
|:--:|:--:|
| 500 | 30,499 |
| 1,000 ⭐ | **38,031**（甜蜜点）|
| 5,000 | 18,050（拐点，-52%）|
| 10,000 | 5,184（主线程 CPU 饱和）|

**核心结论**：
1. **SINTER 以最小输入集合为遍历基准**（O(S×(k-1))），SUNION 为 O(sum Ni)，SDIFF 遍历第一个集合并排除。
2. 参数顺序影响成本——把小集合放前面。
3. **SMOVE 是单命令原子方案**；Pipeline 减少 RTT 但不保证多命令原子性。
4. SSCAN 遍历必须去重 + max rounds/超时；非快照隔离。
5. **手动取模跨分片 SINTER 不报错但静默错误**（缺失 key 视为空集）——必须 hashtag 或校验。
6. 单 Redis 拆小 key 不减少 SINTER 遍历总量。
7. 概率数据结构（HyperLogLog/BloomFilter/CMS）vs 精确存储：内存与精度权衡，适合 UV、去重等场景。

## 场景 10：哨兵 vs 集群 — 写入阶段选型

**压测过程**：同参数（Pipeline 100 SET, 16 线程 × 100 batch, 预热 3s + 采样 5s）在哨兵（1 主+1 从+3 sentinel）和集群（3 主+3 从）各跑一遍稳态写 + kill master 故障韧性。

**稳态写吞吐（单 worker 单 slot）**：

| 指标 | 哨兵 | 集群 |
|:--|:--:|:--:|
| cmdPerSec | ~369,300 | ~354,900 |
| p50 | 4.650ms | 4.360ms |
| p99 | 15.970ms | 18.233ms |

> 集群与哨兵吞吐几乎相同（集群略低 ~4%）。因 key 落在同一固定 slot（单主分片），本质仍是单节点在写。**单热 key/单 worker 分布写时，集群和哨兵都受单节点限制，无吞吐优势。**

**故障韧性（kill master）**：

| 阶段 | 观察窗口 | 重试 | 哨兵 failRate | 集群 failRate |
|:--|:--:|:--:|:--:|:--:|
| 修复前 | 15s | 无 | 0.105% | 0.099% |
| **修复后** | **35s** | **指数退避重试** | **0.000%** | **0.000%** |

**核心结论**：
1. **稳态写入上集群对单 worker/单热 key 无吞吐优势**（≈相同），因为写路径都是单主分片单线程。
2. **集群的吞吐优势只在"多 key 均匀分布到多主分片"时体现**。
3. **故障韧性**：应用层重试 + 足够观察窗口（35s），哨兵和集群 kill master 都做到 failRate=0（零丢失）。
4. **选型建议**：数据量小/简单高可用 → 哨兵；数据量大/需水平扩展/多 key 高吞吐 → 集群（前提 key 能均匀分布）；单热 key 极高吞吐 → 两者都受限，需 LOCAL_BUFFERED/COMPUTED 本地方案。
5. RPO 兜底：数据库水位线对账是唯一数学上能保证最终一致性的手段。
6. **脑裂防护**：`min-replicas-to-write=1` 即可（与 replica 总数无关）。

## 场景 11：Redis 内部编码性能对比压测

**压测过程**：对 String（int/embstr/raw）、Hash（listpack/hashtable）、ZSet（listpack/skiplist）、Set（intset/listpack/hashtable）四类数据类型的内部编码做吞吐/延迟对比，每轮 5s 预热 + 10s 采样（c=16, batch=50），用 `OBJECT ENCODING` 验证编码，含公平对比（控制变量仅差 1 条触发转换）。

**前置认知（所有类型共性）**：**内部编码由数据自动决定，无法显式指定**——只能靠 member/value 的类型、数量、长度"凑"出目标编码，且转换均**单向不可逆**（删数据不会转回）。完整原理见 `docs/场景11` 文档。

### 11.1 String（int / embstr / raw）

| 编码 | 触发条件 | 内存布局 |
|:--:|------|------|
| **int** | value 是 64 位整数 | 8 字节 long 内联在 RedisObject |
| **embstr** | 字符串 ≤ 44B | 对象+sds 数据 1 次 malloc 连续分配 |
| **raw** | 字符串 > 44B | 对象+sds 2 次 malloc 分离 |

**核心数据**（12 轮，c=16）：

| 操作 | int | embstr | raw | 结论 |
|:--|:--:|:--:|:--:|:--|
| INCR | **532K** | — | — | 数值运算 int 碾压 |
| SET | 480K | 417K | 333K | embstr vs raw +25.3% |
| GET | 471K | 421K | 369K | embstr vs raw +14.2% |
| **APPEND** | — | 26.3K(max 287ms) | **33K(max 39ms)** | **raw 预分配反超** |

**核心结论**：
1. **数值运算用 int**：INCR/DECR 零分配，吞吐最高。
2. **短文本用 embstr**：连续内存 cache 友好，SET/GET 明显优于 raw。
3. **长文本/可变拼接用 raw**：raw 的 `sdsMakeRoomFor` 预分配使 APPEND 摊销 O(1)，max 延迟 39ms vs embstr 287ms（避免反复 realloc）。
4. 生产选型：计数器→int，短文本/缓存→embstr，长文/日志/拼接→raw。

### 11.2 Hash（listpack / hashtable）

| 编码 | 触发条件 | 内存布局 |
|:--:|------|------|
| **listpack** | field 数 ≤ 128 且 value ≤ 64B | 连续内存块 |
| **hashtable** | field 数 > 128 或 value > 64B | dict 哈希表 |

**核心数据**（14 轮，c=16）：

| 操作 | listpack(50f) | hashtable(1000f) | 结论 |
|:--|:--:|:--:|:--|
| HSET | 碾压 | 低 | listpack 紧凑 +2260% |
| HGET | 高 | 低 | listpack 占优（15.6×，规模不同仅示趋势） |
| **公平对比 HGET** | 127f **171,478** | 128f **207,092** | **hashtable +21% 反超** |

**核心结论**：
1. **小 Hash 用 listpack**：50 field 碾压 1000 field hashtable（HGET 15.6×；两者规模不同，仅示 O(N) vs O(1) 趋势）。
2. **临界点 hashtable 反超**：公平对比（127f vs 128f）下 hashtable +21%——listpack 是 O(N) 顺序扫描，临界时 N 大扫描成本反超 dict 的 O(1)。
3. **listpack 不必强制**：小数据自动生效；大数据保不住且 O(N) 反噬；分片/限容保 listpack 是纯负收益。
4. 生产选型：单 key field 数控制在 ≤100（保 listpack）或干脆用大 hashtable（O(1)）；**严禁**在大 hashtable 上 HGETALL（O(N) 阻塞，见场景 5）。

### 11.3 ZSet（listpack / skiplist）

| 编码 | 触发条件 | 内存布局 |
|:--:|------|------|
| **listpack** | member 数 ≤ 128 且 member ≤ 64B | 连续内存块 |
| **skiplist** | member 数 > 128 或 member > 64B | 跳表+dict，O(logN) |

**核心数据**（12 轮，c=16）：

| 操作 | listpack(50m) | skiplist(500m) | 结论 |
|:--|:--:|:--:|:--|
| ZADD | 126K | **139K** | **skiplist +11%** |
| ZSCORE | 300K | 299K | 接近 |
| ZRANGE | 188K | 188K | 接近 |
| ZINCRBY | 112K | **116K** | skiplist +4% |

**核心结论**：
1. **ZADD 上 skiplist 反而更快（+11%）**：ZADD 需按 score 定位插入点，skiplist 的 O(logN) 跳跃 < listpack 的 O(N) 线性扫描（尽管 skiplist member 更多）。
2. **ZSCORE/ZRANGE 两者接近**：都需按 member 名查找或顺序遍历，差异小。
3. **测试局限**：128 个短 member 未触发 skiplist（仍是 listpack），转换阈值需 >128——与 Hash 的 128 边界行为不同。
4. 生产选型：小排行榜用 listpack；**大排行榜/高并发 ZADD 用 skiplist**（排序定位优势）；不要刻意限容保 listpack。

### 11.4 Set（intset / listpack / hashtable）

| 编码 | 触发条件 | 内存布局 |
|:--:|------|------|
| **intset** | 全整数 且 数量 ≤ 512 | 有序紧凑整数数组 |
| **listpack** | 字符串 且 ≤ 128 且 ≤ 64B | 连续内存块 |
| **hashtable** | 整数 > 512，或字符串 > 128/>64B | dict 哈希表 |

**转换链**：intset→(加字符串)→listpack→(>128/>64B)→hashtable；intset→(整数>512)→hashtable。均单向不可逆。

**核心数据**（21 轮，c=16）：

| 操作 | intset(50整数) | listpack(50字符串) | hashtable(500长) | int vs ht |
|:--|:--:|:--:|:--:|:--:|
| SADD | 364K | 346K | 311K | +17% |
| SISMEMBER | 379K | 345K | 329K | +15% |
| SREM | 448K | 449K | 307K | +46% |
| SRANDMEMBER | 522K | 530K | 258K | +102% |
| **SMEMBERS** | 476K | 481K | **14K** | **+3136%** |

**公平对比**：intset 512整数 +22.1% 碾压 hashtable 513整数；但 128 短字符串未触发 hashtable（仍是 listpack）。

**核心结论**：
1. **intset 全面碾压**：纯整数集合二分查找，SADD/SISMEMBER/SREM/SRANDMEMBER 全面领先。
2. **SMEMBERS 是最大分水岭**：hashtable 全量读取慢 30 倍+（14K vs 476K，avg 54.7ms）——dict 遍历需逐个 dictEntry 分配返回对象。
3. **SRANDMEMBER 慢一半**：hashtable 需先计数再随机定位。
4. **测试局限**：128 短字符串未触发 hashtable（与 ZSet 一致），整数 513 则精确触发。
5. 生产选型：**整数别存成字符串**；避免在大 hashtable 上全量读取（用 SSCAN/分片）；"能否保小编码"意义不大，真正要防的是**大 hashtable 的全量读取**（数量级差距）。

### 11.5 四类型横向对比（共性总结）

| 维度 | String | Hash | ZSet | Set |
|:--|:--:|:--:|:--:|:--:|
| 编码 | int/embstr/raw | listpack/hashtable | listpack/skiplist | intset/listpack/hashtable |
| 能否显式指定 | ❌ | ❌ | ❌ | ❌ |
| 小数据最优 | embstr | listpack | listpack | intset/listpack |
| 大数据"全量读" | raw(拼接) | hashtable HGETALL 慢 | — | hashtable SMEMBERS 慢 30x |
| 临界反超现象 | — | 128f hashtable +21% | ZADD skiplist +11% | 512intset +22% |
| 结论 | 按 value 用途选编码 | 小用 listpack，大禁 HGETALL | 大排行榜用 skiplist | 整数用 intset，大禁 SMEMBERS |

**四类型通用生产原则**：
1. **编码不可强求**：小数据自动落入紧凑编码，无需干预。
2. **真正要防的是大结构的"全量读取"**（HGETALL/SMEMBERS/SRANDMEMBER/大 value 拼接）——这是数量级差距，改用分页（SSCAN/HSCAN）或分片。
3. **紧凑编码（listpack/intset/embstr）在临界点会因 O(N) 扫描反噬**，但大 hashtable/skiplist 的 O(1)/O(logN) 更稳——所以"刻意保小"不是银弹。
4. 分片同时规避：跨槽 CROSSSLOT（场景 7）、大 key 全量读阻塞（场景 5）、编码退化（本场景）。
