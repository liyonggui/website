AI Agent 项目集评估与改进建议

2026-10-09agent 系列约 29 分钟阅读AI AgentSpring AI

评估范围：Agent 教学项目、可观测性项目和 后端沙盒 业务后端沙盒。
评估时间：2026-09-20
评估方式：目录结构、README、Maven 配置、核心源码、测试目录、运行日志、Docker Compose 与 Git 忽略规则的静态检查。

1. 结论摘要

这是一个以“后端工程师转型 AI Agent”为主线的实验型项目集，技术路线比较完整：

最小 Agent
  -> RAG
  -> 真实业务工具
  -> Agent 工程化治理
  -> MCP Server / Client
  -> 自动评测
  -> OpenTelemetry / Langfuse 可观测

项目最大的价值不是单独实现了某个模型调用，而是展示了从“能调用模型”到“能接入真实业务、能治理、能评测、能观测”的完整思路。

综合评价如下：

维度 评价
学习路径设计 9/10
技术覆盖广度 8.5/10
Agent 工程化意识 8/10
评测意识 8.5/10
代码可维护性 6.5/10
测试与自动化 5/10
生产安全性 3/10
生产可部署性 5.5/10

当前最重要的改进方向不是继续增加框架，而是优先解决：

  1. 配置和密钥安全；
  2. phase5-mcp-client 工具轨迹记录的并发正确性；
  3. Agent 子项目自动化测试不足；
  4. 构建产物、日志和运行数据的仓库卫生；
  5. 实验代码与生产代码的边界。

3. 分项目评价

3.1 根目录和总览文档

主要入口：

  • README.md
  • 全链路.md
  • AI-Agent新手教学.md
  • RAG代码与原理详解.md

优点

  • 阶段划分清楚，能够展示 Agent 能力逐步演进。
  • README.md 同时包含端口、启动顺序、接口示例和实测基线，实用性较强。
  • 全链路.md 能够解释 Agent、MCP、业务后端、数据库之间的关系。
  • 文档记录了大量真实踩坑，包括 Spring AI 版本差异、MCP 配置、中文请求编码、RAG 指标和 Langfuse 接入问题。
  • 适合进一步整理为技术博客或学习材料。

问题

  • README.en.md 仍是模板内容，包含明显占位信息，影响项目专业度。
  • 文档大量依赖固定本机路径，换机器后复现成本较高。
  • “已实测”主要依赖人工 curl 和历史日志，缺少统一自动验证入口。
  • 各阶段 Spring Boot / Spring AI 版本存在差异，但没有集中维护兼容性说明。
  • 根目录同时存在源码、日志、数据库运行数据、构建产物和实验文件，项目边界不够干净。

建议

  1. 将根 README 改造成正式项目首页，包含项目定位、架构图、快速开始、安全说明、测试方式和已知限制。
  2. 完善英文 README，或者删除模板文件。
  3. 增加统一 scripts/ 目录，提供构建、启动、停止和端到端验证脚本。
  4. 将固定路径改为环境变量，例如 BACKEND_DIR、MCP_SERVER_URL 和 AGENT_URL。
  5. 增加版本兼容表，明确每个阶段的 JDK、Spring Boot、Spring AI 和 MCP 协议版本。

3.2 phase1-minimal-agent

项目路径：phase1-minimal-agent

优点

  • AgentConfig.java 结构简单，适合作为入门示例。
  • DemoTools.java 使用递归下降解析器计算表达式，没有直接执行脚本。
  • 工具描述较清晰，体现了工具描述对模型决策的重要性。
  • 同时提供同步接口和 SSE 流式接口，便于观察工具循环和首字延迟。

问题

  • 配置文件中曾出现直接写入的 DashScope API Key，必须立即撤销和轮换。
  • 没有输入长度限制、请求超时和统一错误响应。
  • 订单数据是静态内存 Map，只适合演示。
  • 没有该项目自己的自动化测试。
  • 计算器没有显式限制表达式长度和数值范围。

建议

  • 保留项目的最小性，不要在阶段 1 引入过多生产组件。
  • 为表达式解析器增加单元测试，覆盖优先级、括号、除零、非法字符和一元负号。
  • 在 Controller 层增加输入校验和长度限制。
  • 统一使用 ${DASHSCOPE_API_KEY}，不允许任何真实 Key 进入仓库。

3.3 phase2-rag

项目路径：phase2-rag

优点

  • KnowledgeIngestor.java 展示了 Markdown 切分、Embedding 和向量入库完整链路。
  • RagService.java 同时提供检索、带引用回答和确定性召回评测。
  • RagEvalService.java 已经实现 faithfulness、answer relevancy、context precision、context recall 和 rerank 对比。
  • 文档能够识别 precision@k 在小语料中的指标假象，并尝试使用 MRR、hit@1 和多轮中位数分析。
  • 已经具备“区分系统问题和量具问题”的评测意识。

问题

  • SimpleVectorStore 是进程内内存存储，重启后需要重新 Embedding。
  • 应用启动阶段直接调用外部 Embedding 服务，外部服务失败可能导致应用启动失败。
  • 按空行切分无法很好适应真实长文档。
  • 评测集硬编码在 Java 类中，不利于版本化和扩展。
  • LLM-as-judge 仍存在裁判偏差，当前主要靠提示词修正。
  • 该项目配置中存在硬编码 API Key 风险。

建议

  1. 将知识库导入从启动流程拆为独立命令或管理接口。
  2. 引入 documentId、chunkId、datasetVersion 和 updatedAt 等 metadata。
  3. 将评测集外置为 JSON/YAML 文件。
  4. 采用递归切分、语义切分和 overlap。
  5. 生产环境迁移到 Redis Vector Store、PgVector、Milvus 或云端向量库。
  6. 增加混合检索、检索缓存、Embedding 批处理和增量更新。
  7. 评测中增加 hit@1、MRR、nDCG、引用完整性和事实外推检测。

3.4 phase3-agent

项目路径：phase3-agent

优点

  • SchoolTools.java 将真实业务 HTTP 接口包装为模型工具。
  • 对返回结果进行字段裁剪和 Top-8 限制，具备 Token 控制意识。
  • AgentController.java 支持多轮会话、历史查看和 SSE 流式。
  • 默认业务地址指向本机后端，而不是生产地址，安全默认值正确。
  • 系统提示词要求事实性问题必须调用工具，方向正确。

问题

  • MessageWindowChatMemory 是本地内存实现，重启丢失，多实例不能共享。
  • 会话没有 TTL、用户隔离和容量治理。
  • 下游接口错误、超时和空响应的结构化处理不够完整。
  • 工具参数校验较弱。
  • 没有工具调用轨迹、请求 ID 和耗时信息。
  • 缺少 HTTP 合约测试。

建议

  • 将会话记忆迁移到 Redis，并增加 TTL、最大上下文长度和用户/租户隔离。
  • 复用 phase4 的 ToolGateway，统一处理超时、缓存、熔断和指标。
  • 用明确 DTO 替代大量 JsonNode 操作。
  • 为 /wxma 接口增加空数据、错误码、字段缺失和分页边界测试。

3.5 phase4-agent-ops

项目路径：phase4-agent-ops

优点

  • AgentService.java 实现了 LLM 并发舱壁。
  • ToolGateway.java 将缓存、熔断、降级和指标集中管理。
  • Breaker.java 清楚实现 CLOSED、OPEN、HALF_OPEN 状态。
  • AgentMetrics.java 已统计请求结果、工具成功率、Token、成本、缓存和熔断拒绝。
  • k6 使用 constant-arrival-rate 开环模型，压测设计比单纯固定 VU 更可靠。
  • 能区分“503 是准入护栏的正常行为”和“系统内部错误”。

问题

  • AgentService.java 使用宽泛的 catch (Exception)，错误分类和日志信息不足。
  • 自研熔断器适合教学，但生产环境建议使用 Resilience4j 或 Spring Cloud CircuitBreaker。
  • 缓存 Key 没有独立抽象，参数扩展时存在冲突风险。
  • 缓存缺少明确的数据新鲜度和主动失效策略。
  • 只限制了 LLM 并发，没有对不同下游工具分别限流。
  • 指标主要保存在 JVM 内存中，重启后丢失。

建议

  • 按参数错误、下游超时、下游 4xx、下游 5xx、MCP 错误、LLM 限流和供应商错误分类。
  • 使用统一错误码、trace ID 和结构化日志。
  • 增加工具级 timeout、retry、bulkhead、circuit breaker 和 rate limit。
  • 使用 Prometheus/Grafana 做长期观测。
  • 增加缓存和熔断状态机集成测试。
  • k6 指标中区分正常的护栏拒绝和真实错误。

3.6 phase5-mcp-server

项目路径：phase5-mcp-server

优点

  • 独立 MCP Server 避免了 后端框架 后端与 Spring AI 版本强耦合。
  • McpToolConfig.java 通过 MethodToolCallbackProvider 发布工具，边界清晰。
  • SchoolTools.java 的院校、专业和课程工具职责明确。
  • 已验证 initialize、tools/list 和 tools/call 的真实链路。
  • 下游 RestClient 配置了连接和读取超时。

问题

  • 没有看到认证、授权、租户隔离和调用方校验。
  • 缺少工具调用配额、审计和调用方身份。
  • 参数约束不够严格，分页上限和字符串长度需要显式限制。
  • 错误处理主要依赖下游异常，MCP 层错误协议仍可加强。
  • 仅限制返回 8 条，复杂查询缺少标准分页能力。

建议

  • 内网服务也增加认证和来源校验。
  • 为参数增加最小值、最大值、长度和枚举约束。
  • 使用统一结构化错误响应，并标记是否可重试。
  • 为每个 MCP 请求增加 request ID 和审计日志。
  • 增加 MCP initialize、tools/list、tools/call 集成测试。

3.7 phase5-mcp-client

项目路径：phase5-mcp-client

优点

  • AgentConfig.java 通过 ToolCallbackProvider 动态发现工具，体现了工具与 Agent 解耦。
  • 系统提示词比 phase3 更严格，强调事实题必须查工具。
  • RecordingToolCallback.java 记录工具名、参数、耗时和成功状态。
  • 已经具备 OpenTelemetry 和 Langfuse 接入基础。

关键问题：工具轨迹记录并发不安全

ToolCallRecorder.java 当前存在以下风险：

  1. byCid 中使用 ArrayList，并发写入不安全。
  2. 相同 cid 的并发请求会互相覆盖，begin(cid) 会重置已有轨迹。
  3. ThreadLocal 只适合当前调用线程，不能自然覆盖异步和流式边界。
  4. /stream 没有完整调用 begin 和 end，流式轨迹可能无法正确记录。
  5. 轨迹长期保存在内存中，没有 TTL 和容量上限。
  6. /trace 直接返回原始参数，可能暴露用户输入或敏感数据。

建议

  • 使用 requestId 标识一次请求，而不是只使用 cid。
  • 使用线程安全集合或并发事件队列。
  • 同步和流式请求统一建立、关闭轨迹上下文。
  • 增加 TTL、最大条数和参数脱敏。
  • 生产环境将轨迹写入 Redis、日志平台或 Langfuse。
  • /trace 增加权限控制，禁止任意查询其他会话。

3.8 phase6-eval

项目路径：phase6-eval

优点

  • EvalService.java 同时评测 keyword、trajectory 和 LLM judge。
  • 使用多轮评测和中位数，降低模型随机性影响。
  • 评测链路覆盖 Agent、MCP Client、MCP Server、业务后端和数据库。
  • gate.sh 能够将评测结果转为 CI 门禁。
  • 能识别“最终答案正确但没有查真实数据”的评测盲区。

问题

  • 场景集硬编码在 Java 类中，不便于版本化。
  • keyword 判断较粗糙，无法有效处理否定、实体混淆和数值错误。
  • trajectory 主要检查工具名和参数关键词，尚未充分检查顺序、次数和冗余调用。
  • LLM judge 仍然只有单一裁判模型。
  • gate.sh 使用 shell 文本解析 JSON，稳定性不如 JSON 解析工具。
  • 缺少评测结果持久化和历史趋势。

建议

  • 将场景集外置为 JSON/YAML，并增加场景 ID 和数据集版本。
  • 将评测拆成终答、工具选择、参数、顺序、调用次数、证据、延迟和成本等维度。
  • 使用 jq 或 Java JSON 解析替代 grep。
  • 增加人工校准集、多裁判或成对比较。
  • 接入 Langfuse Dataset/Evaluations，让线上样本进入回归集。

3.9 observability

项目路径：observability

优点

  • 能够观测 chat、tool call、memory 等 span。
  • 已经考虑 prompt、completion 和工具输入输出的追踪。
  • 能将 tracing 与 phase6 评测结合起来。
  • docker-compose.yml 记录了多个实际部署问题，经验价值较高。

风险

  • Compose 中包含开发环境默认密码、初始化账号和示例密钥。
  • prompt、completion 和工具参数可能包含个人信息或业务敏感数据。
  • 当前配置开启了完整内容采集，生产环境存在数据泄露风险。
  • 没有看到明确的数据保留周期、脱敏规则和容量策略。

建议

  • 分离 dev 和 prod Compose。
  • 生产环境禁止默认密码，所有凭据强制通过环境变量或 Secret Manager 注入。
  • 对手机号、Token、身份信息和业务敏感字段做脱敏。
  • 默认关闭完整 prompt/completion 采集，按环境显式开启。
  • 增加数据保留周期和存储容量限制。

3.10 后端沙盒

项目路径：后端沙盒仓库

这是一个规模较大的 后端框架 单体业务后端沙盒，包含系统管理、考试、院校、专业、课程、资源、工作流等模块。当前约有 615 个 Java 源文件，并包含一定数量的测试和 k6 压测脚本。

优点

  • 业务边界相对完整。
  • /wxma 公开查询接口作为 Agent/MCP 数据源，链路清晰。
  • 本地 MySQL、Redis、MongoDB 和 MinIO 都有 Compose 配置。
  • 有业务规则、安全和 HTTP 相关测试。
  • Agent 通过 HTTP 隔离接入，没有直接侵入核心后端实现。

主要问题

  • 多个配置文件包含开发密码、数据库密码、OSS 密钥、微信配置、JWT/SM4 配置等敏感信息。
  • pom.xml 中存在 Docker Registry 账号密码配置，这是严重的仓库卫生问题。
  • 数据库运行目录、日志和导入压缩包不应长期混在源码目录中。
  • 后端框架 商业授权边界需要在公开发布、博客和 GitHub 迁移时特别注意。
  • 单体规模较大，模块间耦合成本高。

建议

  1. 立即轮换已暴露的凭据。
  2. 从 Git 历史中清理敏感信息，而不只是修改当前文件。
  3. 使用 .env.example、本地未跟踪配置、CI Secret 或 Secret Manager。
  4. 对 Agent 只开放明确的只读业务接口。
  5. 给 /wxma 增加限流、审计、统一错误码、分页上限和脱敏。
  6. 暂时不建议为了微服务化而直接拆分部署，优先按业务域降低代码耦合。
  7. 公开发布前确认 后端框架 商业授权和业务数据授权边界。

4. 跨项目高优先级问题

P0：密钥和凭据泄露风险

目前发现的敏感信息类型包括：

  • DashScope API Key；
  • 数据库密码；
  • MongoDB 密码；
  • OSS Access Key/Secret Key；
  • 微信 App Secret；
  • JWT/SM4 密钥；
  • Docker Registry 用户名和密码；
  • Langfuse 初始化账号、密码和项目密钥。

重点检查文件包括：

  • phase1 application.yml
  • phase2 application.yml
  • 后端 dev 配置（仓库内 application-dev.yml）
  • 后端主配置（仓库内 application.yml）
  • 后端 pom（仓库内 pom.xml）
  • Langfuse docker-compose.yml

建议立即执行：

  1. 撤销并轮换所有真实 Key。
  2. 从当前文件删除明文值。
  3. 检查 Git 历史，而不是只修改最新版本。
  4. 增加 secret scanning。
  5. 将默认配置改为环境变量注入，并在缺失时明确失败。

P1：phase5 轨迹记录的并发正确性

这个问题会直接影响 trajectory 评测可信度，也可能造成会话数据串写。应优先修复 ToolCallRecorder 的 request ID、线程安全、流式上下文、TTL 和权限问题。

P1：Agent 子项目自动化测试不足

当前 phase1 到 phase6 基本没有独立 src/test 测试；业务后端虽然有一定测试，但不能覆盖 Agent、MCP 和评测链路。

建议最低测试矩阵：

项目 最低测试内容
phase1 表达式解析器、除零、非法输入
phase2 chunk、召回、引用、评测器
phase3 工具响应解析、空数据、错误响应
phase4 熔断状态机、缓存、超时、舱壁
phase5 MCP initialize、tools/list、tools/call
phase6 评测聚合、中位数、门禁判断

P1：构建产物和 IDE 文件被跟踪

当前 .gitignore 没有统一忽略所有模块的 target 和 .idea，部分 phase5/phase6 构建产物已被 Git 跟踪。

建议补充：

**/target/
**/.idea/
*.log

然后从 Git 索引中移除已经被跟踪的构建产物。

另外，工作区中存在较大的导入压缩文件：

  • 数据导入包（仓库内 doc/import_2026/zips/）

应确认该文件是否必须保留在项目目录中。

5. 推荐改进路线

第一阶段：安全与仓库卫生

  1. 轮换所有真实凭据。
  2. 清理 Git 历史中的敏感信息。
  3. 完善 .gitignore。
  4. 删除或迁移数据库运行数据、日志和构建产物。
  5. 增加 secret scanning。
  6. 用 .env.example 替代真实开发配置。

第二阶段：修复 Agent 运行正确性

  1. 修复 ToolCallRecorder 并发和流式问题。
  2. 增加 request ID、trace ID 和结构化日志。
  3. 给会话记忆、轨迹和缓存增加 TTL 与容量限制。
  4. 为工具调用设计结构化错误。
  5. 为 MCP Server 增加认证、限流和审计。
  6. 统一 phase3、phase4、phase5 的工具网关。

第三阶段：建立自动化质量门禁

  1. 为所有 Agent 子项目补充单元测试。
  2. 增加 MCP 协议集成测试。
  3. 将 phase6 场景集外置并版本化。
  4. 评测加入终答、工具选择、参数、顺序、调用次数、证据、延迟和成本。
  5. 将 run-e2e-gate.sh 接入 CI。

第四阶段：提高生产化程度

  1. 将内存 ChatMemory 迁移到 Redis。
  2. 将 SimpleVectorStore 迁移到持久化向量库。
  3. 使用 Resilience4j 替换自研熔断器。
  4. 对 Langfuse 做脱敏、采样和数据保留控制。
  5. 统一版本管理，减少 Spring Boot/Spring AI 版本漂移。
  6. 为每个服务提供健康检查、就绪检查和可重复部署脚本。

6. 推荐目标架构

建议最终形成以下边界：

用户/API Gateway
      |
      v
Agent API
  - 鉴权
  - 会话
  - 请求 ID / Trace ID
  - LLM 舱壁
      |
      v
Tool Gateway
  - 参数校验
  - 超时 / 重试
  - 缓存
  - 熔断 / 限流
  - 统一错误
      |
      +--> MCP Client --> MCP Server --> 只读业务接口
      |
      +--> RAG Retriever --> 持久化向量库
      |
      +--> Eval / Trace
               |
               +--> Prometheus / Grafana
               +--> Langfuse

7. 最终评价

这个目录已经不是几个互不相关的 Demo，而是一条比较完整的 Agent 工程学习路线：

  • phase1 解决“Agent 能不能工作”；
  • phase2 解决“Agent 能不能利用知识库”；
  • phase3 解决“Agent 能不能接入真实业务”；
  • phase4 解决“Agent 能不能稳定运行”；
  • phase5 解决“工具能不能解耦和复用”；
  • phase6 解决“效果能不能量化和回归”；
  • observability 解决“问题能不能被发现和定位”。

最值得保留和继续深化的特色是：

  1. 真实业务接口接入，而不是纯 Demo 工具；
  2. 对缓存、熔断、舱壁和压测的工程化思考；
  3. MCP 动态工具发现；
  4. trajectory 评测；
  5. 对评测指标和 LLM judge 偏差的反思。

如果按 P0/P1 问题完成治理，这个项目集可以从“很好的学习实验仓库”提升为：

面向后端工程师转 Agent 的完整作品集、技术文章素材和可演示的工程化样板。
